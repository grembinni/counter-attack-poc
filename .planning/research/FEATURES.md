# Feature Research — v1.6 Fouls, Cards & Restarts

**Domain:** Rule-fidelity expansion for an existing hex-grid football engine (server-authoritative state machine, Node/Socket.io + React/Zustand)
**Researched:** 2026-08-03
**Confidence:** HIGH (rulebook text was supplied verbatim by the user; codebase was inspected directly for every claim about existing mechanics/precedent). MEDIUM only where noted (general stoppage-flow sequencing patterns drawn from web research, not the project's own code).

This research does **not** re-derive the target rules — those are fixed in the milestone brief. It surfaces (1) concrete ambiguities in that rule text that need an explicit design decision before/during phase planning, (2) how to sequence these multi-step stoppage flows inside the existing turn-based state machine without deadlocking it, and (3) which rule clusters are safe to split across phases vs. which must ship together.

## Codebase Grounding (why this matters)

Before listing edge cases, five existing mechanisms materially de-risk this milestone and should anchor the design decisions below:

1. **`FREE_KICK_SETUP` is already a multi-stage stoppage flow** (`packages/server/src/gameEngine.ts`, ~L4074-4400): kicker-select sub-step → 3 alternating repositioning stages (`freeKickStageIndex` 0-3, `freeKickStageTeam()` resolves whose turn each stage is) → finalize-to-`PASS`. This is the direct template for Goal Kick, Corner Kick, and Throw-In — each should be modeled as its own staged sub-flow with the same shape (kicker/thrower placement → alternating team repositioning stages → accuracy/header resolution → hand back to `PASS`/`MOVE`), not as one generic "restart" phase.
2. **`computeCombinedScore(attribute, dice, penalties[])`** (`packages/shared/src/scoreUtils.ts`) already supports an arbitrary penalty-modifier array with a -2 floor (DICE-04). The Penalty Kick's "-2 GK dice" and the GK-Dive-at-Feet "3rd-hex -1 dice" both slot into this existing function with zero new dice-math — just new call sites passing `[-2]` / `[-1]`.
3. **Tie-on-duel → `LOOSE_BALL`** is an established, tested pattern (D-13, `computeLooseBall`) already used for shot/header ties. Penalty Kick's "tie = Loose Ball" is not a new mechanic, it's a new _trigger context_ for an existing one.
4. **`PlayerPiece.resilience` and `RefereeCard.leniency` already exist as typed fields** but are currently unused by any game logic (confirmed via repo-wide grep) — they were evidently reserved for this milestone. No data-model migration needed for Injury/Booking, only new logic that reads fields that already exist.
5. **The offside free-kick trigger is internally already generic** — the code that transitions into `FREE_KICK_SETUP` on an offside call uses a variable literally named `afterFoul` (L4001+). This confirms the milestone's own framing ("Foul-triggered free kick reuses the existing FREE_KICK_SETUP flow... with a new foul trigger") matches the code's actual design intent, not just a convenient description.

## Stoppage Flow Sequencing Patterns

**Core recommendation: use a fixed, deterministic resolution pipeline per stoppage type — not a generic interrupt stack.**

General turn-based/CCG engines (e.g., Magic: The Gathering's "stack," where triggered abilities are gathered in APNAP — Active-Player-Non-Active-Player — order and resolved LIFO) solve the problem of _player-chosen_ ordering among _multiple simultaneous, arbitrary_ triggers. That generality is unneeded complexity here: every stoppage in this milestone has a rulebook-specified, single, fixed order of sub-steps (e.g., "roll injury, roll booking, then the attacker chooses continue-or-restart" — always in that order, never player-reorderable). Building a generic priority/interrupt-stack system would be substantial unneeded machinery for a rule set that never actually needs arbitrary trigger ordering.

Instead, the codebase's own existing pattern — the `FREE_KICK_SETUP` staged sub-flow (`freeKickStageIndex` + `freeKickStageTeam()` + boundary `ActionEvent`s like `FK_KICKER_CHOSEN`/`FK_STAGE_ADVANCE` for Undo gating) — is already the right shape and should be replicated per new stoppage type:

1. **Each stoppage type gets its own `GamePhase` (or small family of phases)** — e.g., `GOAL_KICK_SETUP`, `CORNER_KICK_SETUP`, `THROW_IN_SETUP`, `PENALTY_KICK_SETUP` — mirroring `FREE_KICK_SETUP`/`KICK_OFF_SETUP`'s naming convention, not a single generic `RESTART` phase branching internally on a "restart type" field. The existing engine consistently prefers explicit phase enum members over internal type-branching (see the full `GamePhase` union already listing distinct phases for structurally similar things like `GK_KICK_TARGET`/`GK_KICK_MOVE` vs. a single generic GK-restart phase). Follow that precedent.
2. **Fixed-order sub-steps within each phase, tracked by an explicit stage index** (like `freeKickStageIndex`), not by ad-hoc boolean flags — Corner Kick in particular needs this given its two distinct repositioning windows plus alternating 2-at-a-time sub-batches (see Edge Cases above).
3. **Foul/injury/booking resolution belongs in the _duel-resolution_ code (inside `TACKLE_ATTEMPT`/`STEAL_ATTEMPT`/`GK_DIVE_AT_FEET` branches), not inside the restart-setup phases** — this is the most important sequencing rule in the whole milestone. It ensures injury/booking rolls fire on every foul (including ones the attacker "continues play" through, which never enter a restart-setup phase at all). Restart-setup phases (`FREE_KICK_SETUP`, `PENALTY_KICK_SETUP`) should only ever be _entered as a consequence of_ a foul already having been fully resolved (injury/booking already rolled), never used as the place where those rolls happen.
4. **Undo boundaries need the same treatment `FREE_KICK_SETUP` already established** (`FK_KICKER_CHOSEN`/`FK_STAGE_ADVANCE` as slot boundaries, `BUG-37`'s resolved-tackle-as-undo-floor pattern) — every new staged flow needs its own equivalent boundary events from day one, not retrofitted later. This is exactly the kind of thing that was flagged as tech debt for `FREE_KICK_SETUP` itself ("FREE_KICK_SETUP Undo not implemented" is still an open item per `.planning/todos/pending/free-kick-setup-undo-not-implemented.md`) — do not repeat that gap across four more new staged flows. Decide the Undo story for each new stoppage phase during its own phase design, not as a follow-up bug.
5. **Substitution windows should be a single shared "pre-stoppage" hook, not duplicated per restart type** (see Substitutions edge case table above) — implement once, have every staged-restart-setup phase's entry point route through it, rather than re-solving "pause here, offer a substitution" six separate times.
6. **The GK-Dive-at-Feet attacking variant should reuse the existing `GK_DIVE`/`SNAPSHOT_DEFLECT` "declare → reactive interrupt phase → resolve" shape** already established for shots — do not invent a new interaction model for what's structurally the same "attacker acts, defending team reacts before resolution" pattern already proven in the codebase.

    ├──required by──> Throw-In (sideline exit)

    ├──requires──> existing computeCombinedScore -2 GK penalty mechanic (already exists, DICE-04)
    └──requires──> existing tie→LOOSE_BALL mechanic (already exists, D-13) — new trigger context only

    ├──gates──> Fouls, Injury, GK-Dive-at-Feet, Penalty Kick, Foul-triggered Free Kick (all under "Fouls")
    ├──gates──> Booking (additionally requires Fouls enabled to ever fire — see Settings edge case)
    ├──gates──> Goal Kick, Corner Kick, Throw-In, Out-of-Bounds Detection (all under "Out-of-Bounds/Restarts")
    └──does NOT gate──> Substitutions (always-on, no toggle)

### Dependency Notes

- **Out-of-Bounds Detection is the one true prerequisite of this milestone** — Goal Kick, Corner Kick, and Throw-In are all unreachable without it, and it requires a new `lastTouchedByPieceId`-style tracking field that doesn't exist in the current data model. Anything phased before Out-of-Bounds Detection in this cluster is phasing the _effect_ before the _cause_.
- **Fouls → Injury/Booking is a hard bundle**, not because of code reuse but because the rulebook itself states both rolls "always happen regardless of [attacker] choice" on every foul — there's no meaningful way to ship "Fouls" without also shipping Injury and Booking's roll mechanics (even if the Booking _toggle_ can independently suppress the booking half — see Settings notes).
- **GK-Dive-at-Feet is a foul/Penalty-Kick dependency, not an Out-of-Bounds/Restarts dependency** — despite "penalty kick" sounding restart-adjacent, it's entirely gated by the Fouls cluster in this rule set (see Settings edge case above).
- **Substitutions is the most independent of all ten rule areas** — it only _hard_-requires Injury (for the forced-2nd-injury-substitution trigger) but is otherwise a self-contained, always-on manual action that can be exercised at any existing stoppage (including pre-existing ones like `HALF_TIME`/`KICK_OFF_SETUP`) without needing any of the other nine new mechanics to exist first.

## Phase Splitting Recommendation

Mapping the above dependency graph onto safely-separable vs. must-ship-together clusters, for the roadmapper's phase-sequencing decision:

### Must Ship Together (cannot be meaningfully split)

**Cluster 1 — Fouls / Injury / Booking / GK-Dive-at-Feet / Penalty Kick / Foul-triggered Free Kick.**
These six are one rule area, not six. Injury and Booking rolls are a mandatory, un-skippable side effect of every foul — there is no partial/incremental version of "Fouls" that doesn't also include them. GK-Dive-at-Feet exists specifically to create a new foul source that feeds Penalty Kick, and Penalty Kick has no other trigger in this milestone — building GK-Dive-at-Feet without Penalty Kick (or vice versa) leaves a dead-end mechanic. Foul-triggered Free Kick is the cheapest item in this cluster (pure reuse of existing `FREE_KICK_SETUP` with a new trigger) and should not be pulled out on its own, since it's meaningless without Fouls existing to trigger it. **Recommend one phase** (possibly split into 2 plans within that phase — e.g., "foul detection + injury/booking rolls" then "GK-dive-at-feet + penalty kick" — but not split across phase boundaries, since the second half is untestable without the first).

### Independently Shippable (safe to split into its own phase)

**Cluster 2 — Out-of-Bounds Detection + Goal Kick + Corner Kick + Throw-In.**
This cluster is fully self-contained from Cluster 1 — none of these four rule areas depend on Fouls, Injury, Booking, GK-Dive-at-Feet, or Penalty Kick in any way (per the dependency graph above), and it maps directly onto its own dedicated Settings toggle ("Out-of-Bounds/Restarts"), independently enableable per the brief. It has its own strong internal ordering requirement, though (Out-of-Bounds Detection must land before or alongside the first of the three restart types — see Sequencing section), and Corner Kick is meaningfully more state-machine-complex than Goal Kick or Throw-In (two sequential repositioning windows, finer alternation granularity) — so if this cluster itself needs splitting across 2 phases for size reasons, split it as **(Out-of-Bounds Detection + Throw-In + Goal Kick)** in one phase and **(Corner Kick)** alone in a following phase, not by pulling Out-of-Bounds Detection out on its own with no restart type to pair it with (that would ship undetectable/unobservable logic with nothing to verify it end-to-end).

**Cluster 3 — Substitutions.**
Genuinely independent, per the dependency notes above — it only soft-depends on Injury for one of its _trigger sources_ (forced substitution), but the manual/voluntary substitution flow itself (jersey-number/lineup-slot inheritance, 3-per-match cap, +1-minute added-time contribution, the shared "substitution window" hook at any stoppage) can be built and fully tested using only pre-existing stoppages (`KICK_OFF_SETUP`, `HALF_TIME`) with zero dependency on any other v1.6 mechanic. **Could ship in its own phase before, after, or interleaved with either of the two clusters above** — the only ordering constraint is that if it ships _before_ Cluster 1, the "2nd injury forces a substitution" and "red-carded player cannot be replaced" trigger wiring must be added retroactively when Cluster 1 lands (a small, well-contained follow-up, not a rebuild).

**Settings screen toggle wiring** should track alongside its corresponding cluster (Fouls + Booking toggles land with Cluster 1; Out-of-Bounds/Restarts toggle lands with Cluster 2) rather than as a separate phase — each toggle is meaningless without its cluster's logic to gate, and each cluster is meaningless (untoggleable, always-on in dev/test only) without its toggle.

### Recommended Phase Order

1. **Out-of-Bounds Detection + Throw-In + Goal Kick** (establishes the new `lastTouchedByPieceId` tracking and exit-classification foundation; two of the three simpler new restart flows; wires the Out-of-Bounds/Restarts toggle)
2. **Corner Kick** (the most state-machine-complex of the three restart types; builds on the classification foundation from phase 1 rather than duplicating it)
3. **Fouls + Injury + Booking + GK-Dive-at-Feet + Penalty Kick + Foul-triggered Free Kick** (the one true must-ship-together cluster; wires the Fouls + Booking toggles)
4. **Substitutions** (fully independent; placed last only because it's lowest-risk and benefits from Cluster 1's injury/red-card trigger wiring already existing, avoiding a retroactive follow-up — but could be moved earlier if the roadmapper prefers to de-risk it first)

This order front-loads the cluster with the more novel state-machine work (staged multi-window repositioning, new ball-touch tracking) while it's freshest, and defers the highest-_rules_-ambiguity cluster (Fouls/Booking, with its several must-confirm-against-the-rulebook-text items) to give more lead time for those ambiguities to be resolved via REQUIREMENTS.md before implementation starts.
