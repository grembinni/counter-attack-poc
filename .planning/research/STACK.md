# Stack Research

**Domain:** Real-time hex-grid board game — foul/card/injury/substitution/restart mechanics (v1.6 milestone)
**Researched:** 2026-08-03
**Confidence:** HIGH

## Headline Recommendation

**Add zero new runtime dependencies.** Every v1.6 target feature (fouls, GK-dive-at-feet duel, bookings, injuries, substitutions, penalty kicks, goal kick/corner kick/throw-in restarts, out-of-bounds detection) is expressible as an extension of three patterns that already exist and are validated across five prior milestones:

1. **The `GamePhase` FSM** (`packages/shared/src/types.ts` union type + phase handler functions in `packages/server/src/gameEngine.ts`, 4,747 lines) — new phases are added as new union members with a corresponding `apply*` handler, exactly as `FREE_KICK_SETUP` was added in Phase 17/25 for offside.
2. **The pure dice-duel pattern** (`crypto.randomInt`-backed `rollDice()` in `packages/server/src/diceUtils.ts`, called only from the socket layer in `gameHandlers.ts`, then passed as data into pure `apply*` functions in `gameEngine.ts` — see the `ARCH-01` comments on `applyRoll`/`applyGKRestart`: _"does NOT call rollDice() itself... all dice must [be pre-rolled and injected]"_). Every new roll-of-1 foul check, booking check, injury check, and the -2 GK penalty-kick dice modifier fit this exact shape: roll happens in the handler, comparison/branching happens in a pure, unit-testable function.
3. **The pure hex-math module** (`packages/shared/src/hex.ts` + `packages/shared/src/pitch.ts`) — `toCube`/`fromCube`, `hexDistance`, `hexNeighbors`, `isPitchHex`, and the cube-coordinate-vector approach already used by `computeLooseBall` (Key Decision, v1.2) are sufficient to build out-of-bounds classification with zero new geometry code.

This is consistent with the project's established stack philosophy (`CLAUDE.md`): Colyseus and boardgame.io were explicitly rejected in v1.0 because "the EVENT-driven model of Counter Attack... doesn't need [a framework's] continuous sync" — the same reasoning applies here. A foul/card/injury/substitution system is state transitions triggered by discrete player/server actions, which is exactly what the hand-rolled FSM was built for.

## Codebase Facts That Drove These Recommendations

Verified directly in the repo before writing this file (not assumed):

- `packages/server/src/gameEngine.ts` (4,747 lines) already contains 27 `GamePhase` union members (`LOBBY`, `KICK_OFF`, `KICK_OFF_SETUP`, `MOVE`, `PASS`, `SNAPSHOT_TARGET`, `GK_DIVE`, `SNAPSHOT_DEFLECT`, `SHOT`, `HEADER`, `SNAPSHOT`, `LOOSE_BALL`, `HIGH_PASS_MOVE`, `GK_RESTART`, `GK_QUICK_THROW`, `GK_KICK_TARGET`, `GK_KICK_MOVE`, `FREE_MOVE_ATTACK`, `FREE_MOVE_DEFENSE`, `FIRST_TIME_PASS_MOVE`, `FREE_KICK_SETUP`, `HALF_TIME`, `FULL_TIME`, `REPLAY`, plus `LOBBY`/`KICK_OFF`), each with a handler function following the same shape. `FREE_KICK_SETUP` (added Phase 17/25 for OFFSIDE-02) is the direct precedent for every new v1.6 restart phase.
- `rollDice()` (`packages/server/src/diceUtils.ts`) wraps `crypto.randomInt(1, 7)` and is called from exactly 24 sites, all inside `packages/server/src/gameHandlers.ts` — confirmed by grep. `gameEngine.ts` never calls it directly; its `apply*` functions accept already-rolled dice as parameters (explicit `ARCH-01` comments on `applyRoll`/`applyGKRestart`). This handler-rolls / engine-applies split is the exact seam v1.6's new roll types (foul check, booking check, injury check, GK-dive-at-feet, penalty duel) plug into.
- `PlayerAttributes` (`packages/shared/src/types.ts` lines 18-23) currently has `pace`, `shooting`, `tackling`, `heading`, `handling` (and presumably `passing`) — no `resilience` or discipline/`leniency` attribute exists yet. These are new **data** fields on an existing type, not new infrastructure; roster CSV/seed data (`packages/shared/scripts/seed-rosters.ts`, `packages/shared/src/data`) will need the new columns.
- `hex.ts` already exports `toCube`/`fromCube`/`hexDistance`/`hexNeighbors`/`hexesInRange`/`isUnderZoI`/`hexLine`/`getZoIDefenders` — a complete cube-coordinate toolkit. `pitch.ts` already exports `isPitchHex`/`isInRegion`/`PITCH_HEXES`/`PITCH_REGIONS` over a fixed 37×26 rectangular grid (`q∈[0,36]`, `r∈[0,25]`). Today the ball is _clamped_ to stay inside this grid (per `isPitchHex`'s docstring: "Used by Loose Ball boundary enforcement to keep the ball in play"); v1.6 needs to detect _which_ boundary a scatter-walk crosses and classify it (sideline vs. attacking byline vs. defending byline) rather than clamp silently. That's a new pure function in `pitch.ts` built entirely on data already there.
- `GameState` (`packages/shared/src/types.ts`) already carries an added-time accumulator used by the existing `MATCH-02` mechanic and multi-stage free-kick fields (`freeKickHex`, stage counters around lines 970-990) — both are direct reuse targets for substitutions' "+1 added time" rule and the new restart types' staged-repositioning flow, respectively.
- No new package is referenced anywhere in the v1.6 milestone scope in `.planning/PROJECT.md`; the "Explicitly deferred" list (RESP-01..09, game-stats overlay, reconnection grace period, rematch, chat, draft history) confirms the project's own roadmap treats v1.6 as pure game-logic/data extension, not new subsystem introduction.

### Development Tools — no changes

The existing toolchain (vitest 2.1.9, ESLint 9.39.4 + typescript-eslint 8.60.0, knip 6.29.0, Prettier 3.8.3) is sufficient. The project's existing regression-test style — hand-written unit tests per duel/branch (e.g. the 72-case `computeLooseBall` regression suite cited in the v1.2 Key Decision) — is the right pattern to extend for foul/card/injury/restart branches. There is no need for a property-based testing library (e.g. `fast-check`) given the project has sustained 1,738 tests with this approach through five milestones without one.

## Stack Patterns by Variant

**If a feature is a new duel type** (GK-dive-at-feet, penalty kick):

- Model it directly on `computeHeaderDuelDetail` — attacker roll + attribute vs. defender roll + attribute (+ any flat modifier, e.g. the penalty kick's `-2` on the GK side), returning a `*DuelDetail` object consumed by a phase-transition function.
- Because every existing shot/header/tackle duel in the codebase already follows this exact shape; a sixth duel type is a template fill-in, not new design.

**If a feature is a new restart type** (goal kick, corner kick, throw-in):

- Model it directly on `FREE_KICK_SETUP`'s staged-repositioning sequence (taker select → staged reposition stages → delivery), reusing the existing stage-counter field shape already in `GameState`.
- Because the rulebook's repositioning/accuracy/header rules for these restarts are structurally the same "select a taker, both teams reposition, resolve delivery" shape v1.3 already built and shipped once for offside free kicks.

**If a feature is a persistent status effect** (booking count, injury/attribute reduction, cards-per-player, subs-used-per-team):

- Add fields directly to the existing `PlayerPiece`/roster and per-team `GameState` structures (mirroring how `paceUsedByPieceId`, `highPassCarrierId`, and `firstTimePassCarrierId` were added in prior milestones) — not a separate "status effects" subsystem.
- Because the project's established pattern for new persistent per-piece/per-team state is a typed field on the existing state object, broadcast via the existing full-snapshot mechanism (`ARCH-04`) — a parallel status-effect registry would be a second, inconsistent state-management approach.

**If a feature is a boolean toggle at game creation** (Fouls / Booking / Out-of-Bounds-Restarts):

- Extend `GameSettingsScreen.tsx`'s existing toggle-checkbox pattern (built v1.4 for Draft Mode) with three more independent checkboxes, threading the resulting flags through the same settings-payload path already wired from client → room-create/game-start → server `GameState`.
- Because this is explicitly called out in the milestone context as reusing an existing screen/pattern, not building new settings infrastructure.
