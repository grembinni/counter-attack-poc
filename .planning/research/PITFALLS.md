# Pitfalls Research

**Domain:** Project-specific pitfalls for v1.8 (Roster Interaction Overhaul & Rules Audit) — adding select-based roster interaction, GK response-move resequencing, permanent jersey numbers, foul-banner-sequencing bug resolution, final-third confirm fix, and a rulebook gap analysis to an existing, mature real-time hex-football engine.
**Researched:** 2026-08-30
**Confidence:** HIGH (all findings grounded in direct inspection of this codebase's current source — `LineupAssignmentScreen.tsx`, `gameEngine.ts`, `roomStore.ts`, `EventBanner.tsx`, `.planning/debug/foul-banner-sequence-not-pausing.md` — not generic industry advice)

## Critical Pitfalls

### Pitfall 1: Select-to-swap built as a third mode instead of replacing the two drag modes' shared risk surface

**What goes wrong:**
`LineupAssignmentScreen.tsx` already has a documented, hard-won convention (see the file's own `MidmatchSubMode` comment, added specifically because of this milestone's own research): the default positioning mode (`handleMidmatchRepositionDrop`) and the stage-and-confirm substitution mode (`handleMidmatchSubstituteDrop`) are two **structurally separate functions that share no guard body** — a "Pitfall 5 HARD CONSTRAINT" the Phase 42 code comments call out explicitly. If select-based interaction is implemented as a single unified `handleClick(pieceId)` that branches internally on `subMode` to decide eligibility/swap-vs-substitute rules, it silently reintroduces the exact shared-guard-body risk Phase 42 deliberately avoided — a positioning-swap-only guard (e.g. "not GK, not slot 0") could leak into the substitution path, or a substitution-only guard (e.g. "must come from bench") could leak into repositioning, each in the direction that lets an illegal move through client-side (server remains authoritative, but the UX and rejection-message mapping — see the `gameError` string-matching `useEffect` at the top of the component — will silently stop firing for the newly-merged path).

**Why it happens:** Click-to-select naturally invites "one selection state, one handler" thinking (`selectedPieceId`, click again to confirm) because that is how the rest of the game's action model already works (`GameBoard.tsx`'s piece selection). But roster reposition and substitution have genuinely different eligibility rules (reposition: on-pitch non-GK, non-slot-0, own team, no pending action; substitution: bench-sourced, capped at `MAX_SUBS_PER_TEAM`, gated by `pendingSub === null`, stages via popup rather than firing synchronously) baked into two different server messages (`GAME_ROSTER_REPOSITION` vs `GAME_SUBSTITUTION`). Converging the client interaction model tempts converging the eligibility logic too.

**How to avoid:** Keep two selection-state variables (or a tagged union mirroring the existing `MidmatchDragState`/`DragState` conventions already used in this file), and two eligible-target computations, one per mode — never one `computeEligibleTargets(subMode, selection)` that branches internally in a way that shares occupancy/ZoI logic across both rulesets. Reuse `isActivePiece` (the BUG-38 shared predicate) for the underlying occupancy check in both, but keep the mode-specific caps/gates (`pendingSub === null`, `slotIndexNum !== 0`, `piece.role !== 'GK'`, `readOnly`, `actionPending`) as two separate guard clauses, matching the existing drag-and-drop split exactly. Also verify: does a selection made in one mode survive a mode toggle (Reposition ↔ Substitute)? The existing drag implementation resets `midmatchDrag`/`pendingSub` are NOT both cleared on mode toggle today (only entering substitution mode clears the positioning-mode drag per the SUB-11/12 comment) — select-based interaction must explicitly clear ITS OWN selected-piece state on every mode toggle, or a green "selected" highlight will visually survive into the wrong mode and let a stale selection be used as the first half of an illegal cross-mode swap.

**Warning signs:** A single handler function that takes `subMode` as a parameter and has an `if (subMode === 'reposition') { ... } else { ... }` branch inside it (rather than two top-level functions); a single `eligibleTargets` array/Set that isn't recomputed distinctly per mode; a selection surviving across the Reposition/Substitute toggle button click in manual testing.

**How to avoid:** [see above]

**Phase to address:** The phase implementing SELECT-01..0N (select-based swap/substitution). Should explicitly re-derive both eligible-target sets as pure functions with unit tests proving mode-crossing selections are impossible.

### Pitfall 2: Box-entry resequencing collides with the phase's own documented "whitelist, not blacklist" design decision

**What goes wrong:**
`computeBoxEntryOffer` is invoked from exactly one place — the centralized `broadcastState` hook in `roomStore.ts` — and is deliberately gated by `GK_BOX_ENTRY_PHASES = new Set(['MOVE', 'PASS', 'LOOSE_BALL'])`, an **inclusion whitelist chosen specifically over an exclusion blacklist** (see the large code comment above that constant) because "the ball landing inside a penalty area as the direct, already-established consequence of an in-progress shot/header/corner/penalty/GK-catch sequence... is NOT a restart-setup phase... yet offering a second, unrelated GK interrupt on top of a duel/catch/reposition window that's already resolving the exact same 'ball entered the box' situation is nonsensical and hijacks the existing, correct flow." `GK_DIVE` (the shot-blocking dive phase) is explicitly and intentionally **excluded** from this whitelist today. Resequencing the box-entry offer to fire "before the shot-blocking dive on an outside-the-box shot" requires either (a) adding a shot-declaration-adjacent phase to the whitelist — which the existing comment already argues against for other GK-interaction phases and 8 named regression suites depend on the current exclusivity — or (b) inserting a brand-new pre-`GK_DIVE` interrupt point that isn't routed through the single `broadcastState` hook at all, which would fork the "one offer hook, one place" architecture this feature was deliberately built around (the doc comment: "mirroring `applyFreeMoveZoneCheck` as the single ARCH-04 entry point so both goalkeeper interrupts fire after literally any action with zero per-handler wiring elsewhere"). Either path risks the box-entry offer firing a SECOND, redundant GK interrupt on top of the shot duel it's supposed to precede, or firing on a shot that's about to be saved/missed anyway — making the offer meaningless in exactly the case the milestone context calls out.

**Why it happens:** "Fire before X instead of after X" reads as a simple reordering, but here X (`GK_DIVE`) isn't a step in a linear pipeline — it's a phase transition computed by `applyDeclareShot`, itself called from a handler, with box-entry checked in a completely separate, later, centralized broadcast-time hook. The two mechanisms were built with an explicit non-interaction contract (box-entry NEVER fires around a shot phase); resequencing has to change that contract, not just move a call.

**How to avoid:** Before implementing, re-read `roomStore.ts`'s `GK_BOX_ENTRY_PHASES` comment and the `computeGkDiveAtFeetOffer` sibling ("unlike `computeBoxEntryOffer`, `computeGkDiveAtFeetOffer` is LEVEL-triggered, not edge-triggered") in full — both explain WHY the current phases were chosen, not just WHAT they are. Decide explicitly (and document in the plan) which of the two paths above is intended: is the box-entry offer now supposed to intercept `applyDeclareShot`'s transition into `GK_DIVE` itself (i.e., "shot declared outside the box, ball crosses into the box as part of that declaration, offer reposition, THEN allow GK_DIVE to proceed") — if so this is new logic inside/around `applyDeclareShot`, not a `GK_BOX_ENTRY_PHASES` whitelist change. Add a regression test that asserts box-entry does NOT fire a second time once `GK_DIVE` is entered (the existing "at most one offer per broadcast" referential-equality guard in `broadcastState` should still hold). Cross-check the `gkBoxEntryUsedByTeam`/`gkDiveAtFeetUsedByTeam` cap independence explicitly documented as D-11 ("this cap is INDEPENDENT of `gkDiveAtFeetUsedByTeam`") — confirm the new ordering doesn't accidentally make consuming one cap block the other, or double-consume the box-entry cap for a single shot.

**Warning signs:** A shot from outside the box where GK_DIVE is entered with no box-entry prompt ever shown (contract untouched — feature not actually delivered); a shot where the box-entry prompt appears AND THEN the GK also gets a `GK_DIVE` dive choice on the same shot (double-interrupt, exactly what the whitelist comment warns against); existing shot/header/corner/penalty/GK-catch regression suites (8 named in the comment) failing after the change.

**Phase to address:** The GK-response-resequencing phase. Should start by writing the "does box-entry now fire on a `GK_DIVE`-bound shot, and does `GK_DIVE` still fire exactly once after" test BEFORE touching `roomStore.ts` or `gameEngine.ts`, to pin the intended contract before implementation.

### Pitfall 3: "Permanent" jersey numbers regress at one of the ≥7 known reset/continuity sites

**What goes wrong:**
Jersey numbers currently flow from at least three structurally different sources depending on context: `buildSquadPieces` assigns `number: homeSlots[i].jerseyNumber`/`awaySlots[i].jerseyNumber` from the **formation slot**, not the player; `applySubstitution` has the incoming player **inherit** the departing piece's `jerseyNumber` (SUB-03); and `applyRosterReposition`'s swap helper explicitly **carries the piece's existing `number` forward unchanged** (`number: pieceA.number` / `number: pieceB.number`) when two on-pitch players swap positions. Layered on top, `applyRosterContinuity` is called at a minimum of these confirmed sites: the unsaveable-shot GOAL branch (`applyDeclareShot`), the penalty-kick GOAL branch, `applyHalfTimeStart`, and the generic goal-reset helper (grep shows 4+ call sites of `applyRosterContinuity(buildKickOffPieces(...), state.pieces, ...)` across `gameEngine.ts`) — each one rebuilds a **fresh** `pieces` array from `buildKickOffPieces` (which re-derives `number` from the formation slot again) and then overlays only identity/status fields from the live roster. If "permanent number, assigned once at kickoff" is implemented as a change to `buildSquadPieces`/`buildKickOffPieces` alone, every one of those `applyRosterContinuity` call sites will silently **regenerate** numbers from formation-slot order on the next goal or half-time reset, undoing the permanence for any player who has since moved position (via reposition) or been substituted in — exactly the historical pattern already called out for `applyRosterContinuity`'s own header comment: "keeping identity from the live roster... so a swap... survives every goal and half-time reset."

**Why it happens:** "Permanent" values in this codebase are made permanent by being pulled INTO the continuity overlay's preserved-field list, not by changing the value's origin function — `applyRosterContinuity`'s docstring already establishes the pattern ("takes ONLY `position` from the reset array, keeping identity from the live roster") for exactly this class of problem (SUB-03 number inheritance surviving goal/half-time resets). A jersey-number fix that changes only where numbers are assigned at kickoff, without also auditing and updating `applyRosterContinuity`'s field-preservation list, will work in the pregame lineup screen and immediately after kickoff, then regress on the very first goal — a delay that makes the bug easy to miss in a quick manual test.

**How to avoid:** Grep for every `applyRosterContinuity(` call site (currently 4 in `gameEngine.ts`, confirmed at the unsaveable-shot GOAL branch, the penalty-kick GOAL branch, `applyHalfTimeStart`, and one further site) plus every direct `buildKickOffPieces`/`buildSquadPieces` call, and confirm `number` is explicitly added to the "preserved from live roster" field set in `applyRosterContinuity`, not left to fall through to the freshly-rebuilt reset array. Also check the reposition-swap helper (`applyRosterReposition`'s pieceA/pieceB reassignment) and `applySubstitution`'s inheritance branch — both must continue to read the CURRENT permanent number (whichever field ends up authoritative) rather than any positional derivation. Write one regression test per reset site (goal, half-time, penalty-goal) that substitutes a player, gives them a non-default number, triggers the reset, and asserts the number is unchanged — mirroring the existing "4 in-engine reset sites + 3 handler-side goal resets covered" test pattern documented in v1.6's Key Decisions for `applyRosterContinuity`.

**Warning signs:** A jersey number that displays correctly on the lineup/roster screen and immediately after kickoff, but reverts to a different number after the first goal or at half-time; any test that substitutes-then-resets but never asserts on `number` specifically (only on `redCarded`/`onPitch`/identity fields, which is what the existing `applyRosterContinuity` tests were written to prove).

**Phase to address:** The permanent-jersey-numbers phase. Should explicitly extend (not bypass) `applyRosterContinuity`, and its plan's task list should name every current call site by line/function rather than "wherever pieces get reset."

### Pitfall 4: Re-attempting the banner-sequencing fix by patching the same reachable-but-wrong hypothesis instead of following the debug log's own next steps

**What goes wrong:**
`.planning/debug/foul-banner-sequence-not-pausing.md` documents a full investigation that already: (1) found and shipped a REAL bug (the same-commit `active`-state-closure race between `EventBanner.tsx`'s qualifying-event queue effect and its `RESTART_BANNERS` phase-entry effect, fixed via `activeRef` in commit `0664573`), (2) explicitly proved that fix is **not reachable from any current foul call site** (every `resolveFoulChain` call site transitions to `FOUL_CHOICE`, which is NOT in `RESTART_BANNERS`), and (3) the user retested live after the fix shipped and confirmed the reported symptom ("shows foul and disappears with nothing else") was UNCHANGED. The investigation's own `next_action` field names a specific, untested lead: the FoulChoicePanel visibly appearing at the EXACT moment the Foul banner disappears — worth checking whether this is a genuine React-state loss vs. a CSS/DOM stacking issue where the banner is still technically `active` in state but visually covered/hidden by the panel. If this milestone's fix re-runs a tail-only-diffing-style symptom patch (re-verifying `EventBanner.tsx`'s queue logic in isolation again, as the ORIGINAL Phase 39-04 fix reportedly did per the debug log's `started` field) rather than picking up the CSS/DOM-stacking lead or getting a live two-browser repro with React DevTools open, it will very likely reproduce the exact same "eliminated, doesn't fix it" outcome a second time.

**Why it happens:** The banner subsystem's own unit/integration tests (30+ tests, including a dedicated same-commit race regression test) all pass, and multiple synthetic reproductions using the REAL `setGameState` store action (not just the raw-Zustand-setState test harness) also pass cleanly — meaning the failure is proven to NOT be reproducible in any isolated component or store test. This strongly suggests the bug lives in something the synthetic tests structurally cannot capture: real socket-broadcast timing, real DOM layout/stacking between `EventBanner` and `FoulChoicePanel`, or a genuine live two-browser race that a single-process test harness never exercises. A team picking this back up without reading the "Eliminated" and "blind_spots" sections closely risks re-deriving the same activeRef-style fix (already shipped, already proven insufficient) or writing more synthetic single-broadcast tests (already proven passing, therefore uninformative).

**How to avoid:** Read the entire debug log first — particularly the `Eliminated` section (2 hypotheses already ruled out with evidence) and the final `next_action` field, which specifies exactly what to do next: get a live two-browser repro with React DevTools open and check whether `active` state in `EventBanner` is null or non-null at the moment "nothing else appears" (state-loss vs. visual-covering). If a live repro isn't feasible, the CSS/DOM-stacking hypothesis can be tested more cheaply first: render `EventBanner` and `FoulChoicePanel` together in a jsdom/RTL test and assert on computed z-index/stacking-context and visibility, or grep `GameBoard.tsx`'s conditional action-panel swap for anything that could reposition/hide the banner's DOM node (not its React state) when `FoulChoicePanel` mounts. Also worth re-testing the alternate, DEFERRED-not-fixed lead the log surfaced: the actual banner ORDER mismatch (code shows Injury before Booking; user's stated expectation was Booking before Injury) — this was explicitly left unfixed as "not the root cause of the doesn't-advance complaint" but should be closed as a real, if secondary, defect while this area is being reopened.

**Warning signs:** A new fix attempt that only touches `EventBanner.tsx`'s effect/queue logic again without touching `FoulChoicePanel.tsx` or `GameBoard.tsx`'s layout; a fix "verified" only via unit/component tests with no live two-browser or DOM-stacking check, given that exact verification gap is what let the 0664573 fix ship as "safe" while still not resolving the symptom; declaring the bug closed based on synthetic-test pass rate alone (the log shows this already happened once).

**Phase to address:** The banner-sequencing-bug phase. Its plan should open by re-stating (not re-deriving) the debug log's confirmed root-cause status ("real race found and fixed, but proven unreachable from any foul path; true trigger still unconfirmed") and its first task should be the live-repro-with-devtools or DOM-stacking check the log names, not another EventBanner.tsx code read-through.

### Pitfall 5: Rules-gap audit scope-creeps into fixing, or misclassifies intentional simplifications as gaps

**What goes wrong:**
This codebase has an extensive, explicitly documented history of INTENTIONAL rule simplifications and deferrals that are easy to mistake for implementation gaps if the audit works only from the rulebook forward rather than cross-checking `.planning/PROJECT.md`'s "Out of Scope" / "Deferred" sections first: `FTP_MOVE_ENABLED=false` (First-Time-Pass sub-phase deliberately disabled, code kept for a future toggle); NUTMEG-01+ (nutmeg confirmed by the user to be a distinct mechanic from steal, deliberately excluded from FOUL-01's foul triggers pending its own design); "Substitution roster limit beyond 3" (explicitly out of scope because no Extra Time period exists for the rulebook's +1-sub allowance to attach to); RESP-01..09 (response-move single-selection activation model, deferred across FIVE consecutive milestones — the single largest, most consequential deferred item in the project, and NOT what this milestone's gap analysis is meant to fix, only document). A gap analysis that (a) flags `FTP_MOVE_ENABLED=false` as a "missing feature" without noting it's a documented, intentional flag, or (b) starts fixing small rule mismatches it finds along the way (the milestone's own stated goal is "an audit deliverable... not fixes in this milestone"), or (c) fails to log something that WAS silently descoped in an earlier milestone (e.g., the Phase 30 draft-tier recalibration explicitly marked "superseded design, not silently overwritten" in the requirements archive — a good example of the RIGHT way to document a descope, worth using as the audit's own template) will produce a findings doc the next milestone's scoping can't trust.

**Why it happens:** A large, multi-milestone rule-engine codebase accumulates deliberate, well-reasoned simplifications for good reasons (playtesting feedback, missing prerequisite mechanics like Extra Time, explicit user rulings like the nutmeg/steal distinction) — but those reasons live scattered across `PROJECT.md` Key Decisions, milestone REQUIREMENTS.md archives, and code comments, not in one place the rulebook itself can be diffed against. An auditor working rulebook-section-by-rulebook-section without first building a cross-reference to `PROJECT.md`'s Deferred/Out-of-Scope/Key-Decisions sections will re-discover already-known, already-decided gaps and present them as new findings — or worse, silently "fix" one because the fix looks small in isolation, expanding this milestone's actual scope contrary to its explicit audit-only goal.

**How to avoid:** Before reading the rulebook, build a checklist FROM `.planning/PROJECT.md`'s "Deferred," "Out of Scope," and "Key Decisions" tables (the ones marked "superseded design" or with an explicit rationale column) — every rulebook gap the audit finds should first be checked against this list. If it's already there, the audit's job is to CONFIRM the existing description is still accurate (has anything shipped since that closes it?), not re-document it as new. For genuinely new findings, follow the existing project convention exactly: cite the rulebook section/page, the current code behavior with a file:line reference, and explicitly classify each finding as (i) a genuine gap worth scheduling, (ii) an intentional simplification that should be added to Out of Scope/Deferred with a rationale (following the Phase 30 "superseded design, not silently overwritten" precedent), or (iii) a false positive (code that looks incomplete but is intentionally simplified — e.g., a toggle defaulting to a simpler behavior). Do not touch implementation code in this phase — the milestone context is explicit that this is a findings doc, not fixes; any "just this one small fix" urge should become a line item in the findings doc's "candidate next-milestone phase" section instead.

**Warning signs:** A findings doc with no cross-references to existing `PROJECT.md` Deferred/Out-of-Scope entries; a git diff touching `gameEngine.ts`/`gameHandlers.ts` game-logic files during what should be a pure-documentation phase; a "gap" that turns out to match `FTP_MOVE_ENABLED`, NUTMEG-01+, RESP-01..09, or the Extra-Time-substitution-cap item verbatim.

**Phase to address:** The rulebook-gap-analysis phase itself. Its plan's first task should be "build the known-deferred/out-of-scope cross-reference list from PROJECT.md" before any rulebook reading begins, and its success criteria should explicitly exclude any source-file diffs outside `.planning/`.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|-----------------|------------------|
| Branching a single click-handler on `subMode` instead of keeping two structurally separate handlers (mirrors current drag-and-drop split) | Less code to write initially | Reintroduces the exact shared-guard-body regression risk Phase 42's own retrospective flagged as this milestone's highest-risk area | Never — the existing file's own code comments treat this as a hard constraint, not a style preference |
| Whitelisting a new phase into `GK_BOX_ENTRY_PHASES` to make box-entry "fire before" `GK_DIVE` without re-deriving the intended contract | Fast, small diff | Risks double-interrupting a shot duel or making offers meaningless on shots that are about to resolve anyway — silently breaks the documented "at most one GK interrupt per broadcast" invariant | Never without an explicit new regression test proving no double-interrupt |
| Assigning permanent jersey numbers only at `buildSquadPieces`/kickoff without touching `applyRosterContinuity`'s preserved-field set | Looks correct in a quick pregame + first-half smoke test | Silently regresses on the first goal or half-time reset for any player who moved/subbed since kickoff | Never — must be paired with an `applyRosterContinuity` field-preservation update in the same change |
| Declaring the banner-sequencing bug "fixed" based on unit/component test pass rate alone | Fast to close out the todo | Repeats the exact outcome already observed once (0664573 shipped clean, symptom persisted) | Never for this specific bug — live/DOM-stacking verification is required given the documented history |
| Fixing a rulebook gap inline while writing the audit findings doc | Feels efficient — "already found it, might as well fix it" | Violates the milestone's explicit audit-only scope, and an unreviewed inline fix in a rules-critical engine risks a regression with no dedicated test-plan/phase around it | Never in this milestone; log it as a candidate phase instead |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Trusting client-computed eligible-target sets for select-based swap/substitution as authoritative | A crafted `GAME_ROSTER_REPOSITION`/`GAME_SUBSTITUTION` payload could attempt an illegal swap if the server-side guard list drifts from the new client selection logic | Server-side guards (`applyRosterReposition`, `applySubstitution`) remain the sole source of truth exactly as today — the select-based UI only mirrors them for UX; add/extend server-side tests for the same eligibility rules independently of the client rewrite |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|------------------|
| Select-based swap with no clear "deselect" affordance when clicking a non-eligible hex/card | Player gets stuck with a stale green selection and can't tell how to cancel it | Explicit rule (per milestone context): click again on the same card = deselect; clicking any other non-eligible target should also cleanly no-op/deselect, not silently ignore the click |
| GK box-entry offer appearing on a shot that's already effectively decided (post-resequencing) | Makes the new offer feel meaningless/annoying rather than a real tactical choice, exactly the failure mode called out in the milestone context | Confirm the offer is computed and shown BEFORE the shot's dice/duel resolves, not merely before the GK_DIVE phase label is set — order relative to the actual outcome-determining roll matters, not just the phase name |
| Final-third confirm button staying grey / warning still showing when only the GK hasn't moved | Player thinks the turn is stuck, may hunt for a phantom unmoved outfield player | GK-exclusion should be a single shared predicate (mirroring `isActivePiece`'s "one predicate, every consumer" pattern) used both for the button-enable check and the warning-text check, not two independently-written conditions that can drift apart |

## "Looks Done But Isn't" Checklist

- [ ] **Select-based roster swap:** Often missing a mode-toggle-clears-selection reset — verify clicking Reposition→Substitute (and back) with an active green selection does not leave that selection usable in the new mode.
- [ ] **GK box-entry resequencing:** Often missing the "does GK_DIVE still fire exactly once, and does box-entry never double-fire on the same shot" regression — verify against the 8 existing shot/header/corner/penalty/GK-catch suites named in `roomStore.ts`'s comment, not just new tests for the new behavior.
- [ ] **Permanent jersey numbers:** Often missing at least one of the ≥4 `applyRosterContinuity` call sites (goal via unsaveable shot, goal via penalty, half-time, and any other goal-reset path) — verify with a substitute-then-score-again test per site, not just one happy-path test.
- [ ] **Banner-sequencing fix:** Often "fixed" by unit/component tests alone — verify via a live two-browser session or a DOM-stacking-aware test, per the debug log's own stated remaining verification gap.
- [ ] **Rulebook gap analysis:** Often missing a cross-check against `PROJECT.md`'s existing Deferred/Out-of-Scope/Key-Decisions entries — verify every "gap" found is checked against that list before being logged as new.

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|-----------------|
| Select-based swap ships with a shared-guard-body regression | MEDIUM | Split back into two functions per the existing `MidmatchSubMode` doc-comment convention; add the mode-crossing-selection regression test that should have existed from the start |
| Box-entry resequencing breaks one of the 8 named existing shot/header/corner/penalty/GK-catch suites | MEDIUM | Revert to the whitelist-only mechanism, re-scope the resequencing as new logic inside `applyDeclareShot`'s pre-`GK_DIVE` transition instead of a `GK_BOX_ENTRY_PHASES` change |

| Rules-gap audit accidentally includes an inline code fix | LOW | Revert the inline fix, convert it to a findings-doc line item with a proposed future phase, keep the audit deliverable doc-only |
