# Pitfalls Research

**Domain:** Adding features to an existing, mature, server-authoritative real-time game engine with a full-state-snapshot broadcast model (Counter Attack POC, v1.7 milestone)
**Researched:** 2026-08-21
**Confidence:** HIGH — every pitfall below is grounded in direct reads of the current codebase (file:line citations included), not generic advice. Two pitfalls (#7, #8) are _confirmed, currently-live bugs_ discovered during this research, not hypothetical risks.

This file assumes the reader has read `.planning/PROJECT.md` (Context/Key Decisions/Key Pitfalls) and `.planning/STATE.md` (Key Pitfalls to Avoid). It does not repeat those documented bug classes verbatim — it applies them concretely to the 6 v1.7 features.

## Critical Pitfalls

### Pitfall 1: Referee Leniency is a dual-consumer field — overriding it changes booking AND added time together

**What goes wrong:**
`refereeCard.leniency` is read in two unrelated formulas: `rollsBooking(die, leniency)` = `die >= leniency` in `packages/shared/src/fouls.ts:102-103` (booking threshold — LOWER leniency = MORE bookings), and `newAddedTime = roll + state.refereeCard.leniency + (state.addedTimeBonus ?? 0)` in `packages/server/src/gameEngine.ts:2537` (added-time bonus — HIGHER leniency = MORE added time). A manager who overrides leniency to 2 ("strict ref, more cards") to see more bookings will, as an unannounced side effect, also reduce added time every half. If the v1.7 UI presents the override purely as "referee strictness," managers will be surprised by an added-time change they never asked for.

**Why it happens:**
The two consumers were built in different phases (added-time in Phase 8, booking in Phase 39) against the same field, and nothing documents the coupling except a comment buried in `types.ts:1735-1744`. A developer implementing the override toggle in isolation (only touching `fouls.ts`/booking code) will not naturally discover the added-time consumer.

**How to avoid:**
Before implementing, grep `refereeCard.leniency` across the whole repo (not just `fouls.ts`) and enumerate every consumer. Either (a) document in the settings UI that leniency also affects added time, or (b) split the field if the requirement truly means "booking strictness only" — but confirm with the user first since splitting changes the added-time formula's existing behavior for the _random_ (non-overridden) case too, which is out of scope. Add a regression test asserting both formulas read the overridden value identically to the random-roll case (no special-cased override path in either consumer).

**Warning signs:** A plan that touches only `fouls.ts`/`resolveBooking` without also touching or at least referencing `gameEngine.ts:2537`'s added-time roll.

**Phase to address:** The phase implementing the Referee Leniency toggle (Feature 1). Needs its own regression test asserting `newAddedTime` uses the overridden leniency identically to a random one.

### Pitfall 2: Leniency override needs server-side range re-validation and grows an already-fragile positional-parameter function

**What goes wrong:**
`buildInitialGameState` (`packages/server/src/gameEngine.ts:351-400`) is already an 11-parameter positional function that has grown by 2-6 optional booleans/arrays in each of the last three milestones (v1.6 alone added `outOfBoundsEnabled`, `foulsEnabled`, `bookingEnabled`, `injuryEnabled`, `homeBench`, `awayBench`). Adding a `leniencyOverride?: number` parameter continues this pattern and risks a parameter-order mistake at any of the multiple call sites (initial game start, and any future re-init path). Separately, the manual leniency value (2-5 per the requirement) is chosen client-side on the settings screen — exactly like `goalHex` in `applyDeclareShot` (which the codebase explicitly re-validates server-side, "never trust client coordinates," `gameEngine.ts:8488`), a malicious or buggy client could submit 1 or 6 (or a non-integer) and the server must not trust it blindly.

**Why it happens:**
Optional trailing parameters are the path of least resistance for extending an existing well-tested function signature; a range check feels like "just a UI constraint" once the toggle already exists in the settings form.

**How to avoid:** Add explicit server-side clamping/validation of the override value (2-5 inclusive integer) in the room-settings-confirm handler, mirroring the `INVALID_TARGET` pattern already used for shot/header/free-kick targets. Consider whether this is the parameter that finally justifies converting `buildInitialGameState` to an options-object — at minimum, add the new parameter with an explicit inline doc comment (matching the existing style) and update every call site in the same commit, not just the default path.

**Warning signs:** Any test that calls `buildInitialGameState` positionally without the new parameter and doesn't fail loudly if that silently shifts a later argument.

**Phase to address:** Same phase as Pitfall 1 (Referee Leniency toggle). Verify via a server-side rejection test for leniency values outside 2-5 when override is enabled.

### Pitfall 3: Card/injury iconography is already triplicated inline — a 4th silently-different copy is the likely outcome, not a shared component

**What goes wrong:**
The exact same inline ternary — `piece.redCarded === true ? 'red' : (piece.yellowCards ?? 0) > 0 ? 'yellow' : null` — is already duplicated verbatim in three files: `PieceOverlay.tsx:238`, `PlayerStatsPanel.tsx:151`, and `LineupAssignmentScreen.tsx:455`. The 4th surface, the bench card (`BenchCarousel.tsx` / `DraftPackCarousel.tsx`), currently renders `redCarded` as a distinct "RED CARD" badge (`DraftPackCarousel.tsx:113-115`) with **no yellow-card or injury iconography at all** — `injuryCount` is not referenced anywhere in `BenchCarousel.tsx`. "Unify iconography across 4 surfaces" is therefore not a refactor of one existing pattern into a shared component — it requires _adding_ net-new yellow/injury display to the bench surface while _replacing_ three already-working, independently-tested inline copies, each with its own snapshot/DOM-attribute tests (`PieceOverlay.test.tsx:286-294`, `PlayerStatsPanel.test.tsx:150`, `LineupAssignmentScreen.test.tsx`).

**Why it happens:** Each card surface was built in a different phase (PieceOverlay in early phases, PlayerStatsPanel alongside it, LineupAssignmentScreen in Phase 29, BenchCarousel/DraftPackCarousel in Phase 40) by different plans that each solved "show this player's card status" locally rather than reaching for a shared component that didn't exist yet.

**How to avoid:** Before writing the shared icon component, grep for `redCarded === true ?` and `yellowCards` and `injuryCount` across ALL of `packages/client/src/components` (not just the 3 known sites) to catch any other copy. Build the shared component to accept `{ redCarded, yellowCards, injuryCount }` and use it to _replace_ all 4 sites in the same plan, not just wire it into new bench markup. Keep each surface's existing DOM test assertions (`data-card="red"` etc.) passing unchanged if the shared component preserves the same output contract — that lets prior tests double as regression coverage for the refactor.

**Warning signs:** A plan/PR that adds the shared component but only imports it in 1-2 of the 4 surfaces; `knip` or a grep audit still finding the old inline ternary after the plan closes.

**Phase to address:** The phase implementing UI iconography/layout consistency (Feature 2). Verify by grepping for the old inline ternary pattern post-implementation (should return zero matches) and confirming BenchCarousel now renders yellow/injury status it never did before.

### Pitfall 4: The Fouls-dependency grey-out logic is enforced in two disconnected places — moving toggles into a drawer risks breaking one without noticing

**What goes wrong:**
`GameSettingsScreen.tsx` enforces "Booking/Injury require Fouls" via **two independent mechanisms** that must both stay correct: (1) a render-time `disabled={!fouls}` + `toggleBooking`/`toggleInjury` early-return guard (lines 176-184, 90-99), and (2) a confirm-time normalization `booking: fouls && booking, injury: fouls && injury` (lines 112-115) that is the actual source of truth sent to the server. These are not derived from one shared computation — they are two copies of the same rule, already flagged by their own comments as intentionally mirroring each other ("same guard as Booking"). Restructuring toggles into a collapsible/two-column Advanced drawer is exactly the kind of change (new component boundary, toggles possibly rendered by a shared `<ToggleRow>` component) that tends to carry over the visual guard but drop the confirm-time normalization (or vice versa), producing a toggle that _looks_ correctly greyed out but still sends a stale `true` to the server, or a toggle whose state is normalized correctly but shows the wrong checked/unchecked visual state before confirm.

**Why it happens:** The two guards exist because "cannot be toggled" (UX) and "has no effect even if somehow toggled" (data integrity/defense-in-depth) are different concerns that were solved independently rather than through one derived-state helper.

**How to avoid:** When refactoring into the drawer, extract a single derived-state function (e.g., `deriveEffectiveSettings(fouls, booking, injury, ...)`) used by BOTH the render-time disabled/grey styling AND the confirm-time payload, so there is exactly one place to get this rule right. Apply the same pattern proactively to the two _new_ v1.7 toggles that will need similar dependent-disable behavior: Referee Leniency's numeric input (should be inert/hidden unless the leniency toggle itself is on) and the Tackle/Steal decline toggle if it ever gains sub-options.

**Warning signs:** A drawer redesign PR that only touches JSX/CSS and doesn't touch `handleConfirm`'s normalization logic at all — a sign the two guards were not unified.

**Phase to address:** The phase implementing the Advanced settings drawer/two-column layout (Feature 3). Regression test: toggle Fouls off with Booking/Injury previously checked, open/close the drawer, confirm — assert the emitted payload still has `booking: false, injury: false` regardless of drawer collapsed/expanded state.

### Pitfall 5: The new positioning-mode substitution UX is a coexisting mode bolted onto the SAME tested component, not a new screen — highest regression risk of the milestone

**What goes wrong:**
`LineupAssignmentScreen.tsx` already contains tested, shipped drag-and-drop substitution logic from Phase 40 (SUB-02..07: 3-sub cap, jersey/slot inheritance, `redCarded`/`subbedOut` permanent unavailability, `applyRosterContinuity` overlay) with its own extensive test file (`LineupAssignmentScreen.test.tsx`, including `SUB-02`/`SUB-06`/D-12/D-13 assertions at lines 671-756). v1.7 requires this same screen to grow a **second, coexisting interaction mode** (default player-positioning/drag-and-drop-swap, distinct from substitution) that must be mutually exclusive with substitution mode (disabled when an action is selected; bench players not selectable in positioning mode) and share the same drag-and-drop event handlers and the same on-pitch piece cards. Because both modes render through the same component and likely the same drag handlers, an implementation that adds a `mode` branch without carefully re-threading every existing guard (3-sub cap check, red-card/subbed-out exclusion, `applyRosterContinuity` overlay behavior) risks silently changing behavior for the OTHER mode — e.g., a positioning-mode drag handler that reuses the substitution drop handler's occupancy check could accidentally allow a positioning-mode swap onto a red-carded bench marker's vacated slot, or a substitution-mode guard that was previously unconditional could become conditionally skipped if a shared "isDraggable" helper is refactored to be mode-aware and someone flips a boolean.

**Why it happens:** The path of least resistance for "add a new interaction mode to an existing screen" is to add an `if (mode === 'position') {...} else {...}` branch inside the existing drag/drop callbacks rather than fully separating the two modes' logic — this is efficient for shared visual chrome but dangerous for shared _guard_ logic, since a bug in the shared branch affects both modes simultaneously.

**How to avoid:** Before writing the positioning mode, enumerate every existing guard in `LineupAssignmentScreen.tsx`'s drag/drop path (3-sub cap, `redCarded === true → isBlocked` at line 456, bench-card non-draggability checks in `BenchCarousel.tsx:111`, `applyRosterContinuity`-driven state) and write a test matrix that exercises each guard under BOTH modes before implementation starts (test-first for the coexistence boundary specifically, not just the new feature). Keep substitution-mode's drop handler and positioning-mode's drop handler as two separate functions that happen to share a lower-level "can this piece be dragged at all" predicate (redCarded/subbedOut exclusion), rather than one handler with mode-conditionals threaded through the cap/guard checks themselves.

**Warning signs:** A single "onDrop" handler gains a `mode` parameter and its existing SUB-02..07 guard conditions get wrapped in `if (mode === 'substitute')` — that is the exact refactor shape most likely to silently narrow an existing guard's applicability.

**Phase to address:** The phase implementing the Substitution UX overhaul (Feature 4) — this is the single highest-regression-risk item in the milestone and should get its own full re-run of the existing `LineupAssignmentScreen.test.tsx` SUB-0X assertions as an explicit gate before any new positioning-mode tests are considered sufficient, not merely "tests still pass" but a deliberate side-by-side check that each SUB-0X assertion still exercises the code path it originally covered.

### Pitfall 6: CONFIRMED LIVE BUG — DEFLECT_ATTEMPT's defender list never excludes red-carded/off-pitch pieces

**What goes wrong:**
Both places that build the deflecting-defender list — `gameHandlers.ts:1285-1287` (SNAPSHOT_DEFLECT) and `gameHandlers.ts:2288-2290` (regular SHOT) — filter defenders with exactly `(p) => p.teamId === defendingTeam && p.role !== 'GK'`. Neither filter excludes `p.redCarded === true` or `p.onPitch === false`. Every other consumer that was audited during the resolved `red-card-bench-removal-scope` debug session (`.planning/debug/resolved/red-card-bench-removal-scope.md`) — `computeGoalKickEligibleIds`, `computeCornerKickEligibleIds`, `applyFreeMoveZoneCheck`, `computePenaltyKickEligibleIds`, `isProfessionalFoul`, the GK dive-at-feet/box-entry offer functions, and `applyMove` itself — was patched to exclude red-carded pieces. The two `DEFLECT_ATTEMPT` builder sites were never touched by that fix, because deflection wasn't in scope for that debug session. This is the exact "downstream consumer doesn't check it" bug class the project has already shipped multiple times, and it directly explains the currently-open user-reported bug ("red-carded players remain on the field and can still trigger game interactions, e.g. deflection"): a sent-off defender, still present in `state.pieces` at a live on-pitch position (by design — see the `onPitch` field doc comment, `types.ts:64-76`), is still eligible to roll a deflection die and can still deflect a shot.

**Why it happens:** The `redCarded`/`onPitch` exclusion pattern is not centralized — it is a `.filter((p) => p.redCarded !== true)` clause that must be independently remembered at every site that builds a list of "opposing team's outfield pieces," and `gameHandlers.ts`'s deflection-input builders predate the red-card feature entirely (they use the pre-existing `p.role !== 'GK'` shape), so they were never in the mental model of "sites that need the new exclusion" when Phase 39/the debug session ran.

**How to avoid:** Add `p.redCarded !== true` (or `p.onPitch !== false`, whichever the team standardizes on — see recommendation below) to both `gameHandlers.ts` deflection-input filters in the same commit. Given how many independent sites already implement this exclusion ad hoc, strongly consider extracting a single shared helper (e.g., `isActivePiece(p)` or `filterActivePieces(pieces)`) used everywhere a "list of eligible/opposing pieces" is built, rather than continuing to hand-write the same filter clause. This is the single highest-value structural fix available in this milestone for preventing pitfall #6 and #7's bug class from recurring a third time.

**Warning signs:** Any `.filter((p) => p.teamId === ...)` or `.filter((p) => p.role !== 'GK')` clause anywhere in `gameEngine.ts`/`gameHandlers.ts` that does NOT also check `redCarded`/`onPitch` — grep for this pattern as a dedicated audit task.

**Phase to address:** Should be fixed as part of the phase implementing the Substitution UX overhaul (Feature 4) bug-fix scope ("plus a bug fix ensuring red-carded players are fully removed from play in every phase, not just visually hidden" — this is precisely that bug). Needs its own regression test: a red-carded defender positioned on a shot's path must never appear in the `DEFLECT_ATTEMPT` defender-input list, mirroring the existing `computeGoalKickEligibleIds`/`computeCornerKickEligibleIds` exclusion tests added during the debug session.

### Pitfall 7: CONFIRMED LIVE BUG — moveValidator's ZoI opponent list has zero red-card/off-pitch awareness

**What goes wrong:**
`packages/shared/src/moveValidator.ts:95` computes ZoI steal-trigger opponents as `state.pieces.filter((p) => p.teamId !== piece.teamId)` — no `redCarded`/`onPitch` exclusion anywhere in the file (confirmed by a full-file grep returning zero matches for either field name). This means a red-carded opponent, despite being visually hidden from the pitch (`HexGrid.tsx:761`'s `onPitch === false` render-skip) and unable to move itself, can still register as a `getZoIDefenders` threat and trigger a `STEAL_ATTEMPT`/`TACKLE_ATTEMPT` against the ball carrier purely by virtue of still occupying a live `position` in `state.pieces`. This is the same root cause and same bug class as Pitfall #6, in a different file the debug session's grep-based audit did not cover (that session's evidence log explicitly says it grepped `gameEngine.ts` and `fouls.ts` only — `moveValidator.ts` in `packages/shared` was never checked).

**Why it happens:** `packages/shared` is a separate package from `packages/server`, so a grep audit scoped to "everywhere in the server" (as the resolved debug session's evidence log describes) structurally misses shared-package validators that also build eligibility lists from `state.pieces`.

**How to avoid:** Re-run the red-card exclusion audit across `packages/shared` as well as `packages/server` — specifically `moveValidator.ts` and `passValidator.ts` (also returned zero matches for `redCarded`/`onPitch`/`interceptors` in this research and should be independently verified for a ZoI-interceptor-list gap on the pass side, mirroring the movement-side gap found here). Apply the same shared `isActivePiece`/`filterActivePieces` helper recommended in Pitfall #6, imported into `packages/shared` where these lists are built, so server and client-shared logic use one definition instead of two independently-audited ones.

**Warning signs:** Any opponent/interceptor/defender list built from `state.pieces` inside `packages/shared` (not just `packages/server`) without a redCarded/onPitch filter.

**Phase to address:** Same phase as Pitfall #6 (Substitution UX overhaul bug-fix scope). This is the other concrete "downstream consumer" gap the milestone context asked about — ship both fixes together since they share root cause and remediation shape.

### Pitfall 8: A new "declined" tackle/steal state risks conflating with the existing "attempted" exclusion sets across ~30 reset call sites

**What goes wrong:**
`state.stealAttemptedByIds`/`state.tackleAttemptedByIds` currently mean "already attempted (rolled), now excluded from re-triggering the same duel type this sequence" (`moveValidator.ts:97-99, 116-120`). These arrays are reset to `[]` at more than 30 independent call sites throughout `gameEngine.ts` (every PASS transition, every restart-setup phase entry, half-time, kick-off, etc. — confirmed by direct grep). The new v1.7 "prompt-and-decline" mechanic needs the OPPOSITE semantic for a declined (not attempted) tackle/steal: "still eligible, keep the risk ring active, prompt again on a later move step." If this new state is implemented as a third value inside the _same_ tracking array/field (e.g., overloading `stealAttemptedByIds` to also carry "declined" ids), any of the ~30 reset sites that clears the array for a legitimate reason (e.g., a new PASS phase, where "attempted" should reset) would also incorrectly clear "declined" state that conceptually should persist differently (e.g., persisting across move steps within the SAME movement phase, not just within a duel sequence) — or vice versa, a site that correctly should NOT touch "attempted" tracking might get missed for the new "declined" set entirely, since it wasn't in the original 30-site enumeration.

**Why it happens:** The path of least resistance is extending an existing, well-understood array rather than introducing a cleanly separate field, because the existing array is already threaded through the exact ZoI ring/exclusion logic the new feature needs to hook into.

**How to avoid:** Introduce a genuinely separate field (e.g., `stealDeclinedByIds`/`tackleDeclinedByIds`) with its own explicit reset semantics documented from day one — do NOT overload the existing arrays' values. Before writing the reset logic, grep every one of the ~30 `stealAttemptedByIds: []` / `tackleAttemptedByIds: []` reset sites and decide, site-by-site, whether the new declined-set should reset there too (it likely should reset at the same PASS-transition/duel-sequence boundaries as the attempted set, since "declined, re-prompt-eligible" is presumably also sequence-scoped) — write this as an explicit table in the plan, not an assumption. Add a shared reset helper if the two arrays should always reset together, to avoid a 31st future call site missing one but not the other.

**Warning signs:** A diff that touches `stealAttemptedByIds`'s existing value shape (e.g., changing it from `string[]` to a richer type) instead of adding a sibling field. A diff that resets the new declined-set at fewer sites than the existing attempted-set's ~30.

**Phase to address:** The phase implementing the Tackle/Steal prompt-and-decline toggle (Feature 5). Needs a dedicated regression test enumerating every phase-transition reset site and asserting the new declined-set's reset behavior at each one — mirroring the rigor already applied to `subsUsed` vs `addedTimeBonus` (`types.ts:1729-1744`, "must never be reset together").

### Pitfall 9: A new tackle/steal-decline interaction needs its own ActionEventType, registered everywhere Undo/Replay expects a full checklist

**What goes wrong:** This project has shipped the "new dice-roll/ActionEventType members are invisible to Undo/Replay unless registered in every relevant list" bug class twice already (BUG-30/31, BUG-37 — documented in `STATE.md`'s Key Pitfalls). A "decline" action is a genuinely new player choice (distinct from the existing `TACKLE_ATTEMPT`/`STEAL_ATTEMPT` dice-roll events), and if it's implemented as a new `ActionEventType` (e.g., `TACKLE_DECLINED`), it needs registration in: the `isBoundary` disjunction inside `applyUndo` (`gameEngine.ts:3247` onward — is a decline a slot boundary or not? Almost certainly NOT, since the whole point is the player remains eligible to be prompted again, unlike a resolved attempt which IS a hard boundary per BUG-37/D-13), `REPLAY_ELIGIBLE_TYPES` (or the exclusion list alongside `DEFLECT_ATTEMPT`/`SLOT_ADVANCE` at `gameEngine.ts:9714-9723`, if a decline "produces no standalone board change"), and possibly `ELIGIBLE_NEXT_ACTIONS` if declining should be followed by specific next-action eligibility.

**Why it happens:** The checklist is not enforced by the type system — `ActionEventType` is a string-literal union, and each consuming list independently opts a new member in or out; nothing fails to compile if a new member is added to the union but omitted from `REPLAY_ELIGIBLE_TYPES` or the `isBoundary` disjunction.

**How to avoid:** Before writing the decline event, explicitly decide and document: (1) should Undo be able to cross back over a decline (very likely YES, since declining shouldn't lock in anything the way a resolved dice roll does per the BUG-37 precedent) — if so, deliberately do NOT add it to the `isBoundary` disjunction, and add a regression test proving Undo still works across a decline; (2) does replay need to visually show a decline happened, or is it a no-op like `DEFLECT_ATTEMPT`/`SLOT_ADVANCE` — decide and add it to the correct list explicitly, not by omission.

**Warning signs:** A new `ActionEventType` union member added to `types.ts` without a corresponding new test in `gameEngine.undoReplay*.test.ts`-style files, mirroring the existing pattern for TACKLE_ATTEMPT/GK_DIVE_AT_FEET/SUBSTITUTION boundary tests.

**Phase to address:** Same phase as Pitfall #8 (Tackle/Steal decline). Needs its own regression test mirroring `gameEngine.undoReplay39.test.ts`'s pattern (Undo/Replay coverage added alongside Phase 39's new event types).

### Pitfall 10: Match-stat counters risk the same "must never be reset together" trap as `subsUsed`/`addedTimeBonus` — but in the opposite direction

**What goes wrong:** The project has one documented precedent for exactly this shape of bug: `subsUsed` (whole-match, never reset at half-time) vs `addedTimeBonus` (per-half, reset at the half boundary) — two counters that look similar but must never be reset by the same code path (`types.ts:1729-1744`). The v1.7 match-stat counters (possession%, pass count, tackle/steal success%, shot count, xG, fouls/cards) are described as running MATCH totals, reachable via the Game Summary popup "at any time" including at half-time and full-time. Verified by reading the goal-reset return object (`gameEngine.ts:4330-4360`): it spreads `...state` first, so any _new_ field not explicitly listed in that return object survives a goal reset by default — this is the SAFE direction for match-wide counters. The risk is the opposite: a developer implementing half-time/full-time transition code might reflexively copy the `addedTimeBonus`-style "reset per half" pattern for a stat counter that should actually persist across halves (all 6 requested stats are match-wide, not per-half, per the requirement text), silently zeroing possession/passes/shots/xG/fouls at the 45-minute mark.

**Why it happens:** The `addedTimeBonus` per-half-reset pattern is the most recently-written, most visible precedent in the codebase for "a counter that resets at half-time" — it is the example a developer is most likely to pattern-match against, even though it's the wrong pattern for match-wide stats.

**How to avoid:** Before implementing, write an explicit one-line reset-policy comment for each new stat field, following `subsUsed`'s exact comment style ("NEVER reset at half-time — independent of X"), and add it at the point of definition in `types.ts`. Add one regression test per stat counter asserting it survives a half-time transition unchanged, mirroring `gameEngine.secondHalf.test.ts`'s existing half-time assertions.

**Warning signs:** Any half-time or full-time reset code path (`applyHalfTimeStart`, the FULL_TIME transition) that touches a newly-added stat field at all — the correct diff for these 6 stat fields should show ZERO changes to `applyHalfTimeStart`.

**Phase to address:** The phase implementing the Game Summary popup / match-stat tracking (Feature 6).

### Pitfall 11: xG-per-shot capture point is genuinely ambiguous across 4+ separate, independently-coded resolution branches

**What goes wrong:** Confirmed by direct code read: `computeShotPathDeflection` (the shared pure helper) is invoked from two structurally separate handler blocks — the SNAPSHOT_DEFLECT branch (`gameHandlers.ts:1328`) and the regular SHOT branch (`gameHandlers.ts:2331`) — each with its own independently-written defender-input-building loop (duplicated, not shared, per Pitfall #6/#7's evidence). The GK-dive-at-feet duel and headed-shot-at-goal paths are separate resolution branches entirely (per `.planning/PROJECT.md`'s own framing: "SHOT vs GK_DIVING vs SNAPSHOT_DEFLECT all resolve differently"). An xG implementation that captures "defenders in the box at time of shot" by instrumenting only the most obvious/main SHOT branch will silently produce no xG value (or a wrong one) for snapshot shots, headed shots, and GK-dive-at-feet-triggered penalties — each of which is a distinct shot-like scoring opportunity a user would expect to see in the xG-per-shot popup.

**Why it happens:** The engine's shot-resolution logic grew branch-by-branch across multiple milestones (regular shots in early phases, SNAPSHOT in a later phase, headers with their own goal-line routing, GK-dive-at-feet fouling into penalties in Phase 39) without a single unifying "a shot is being attempted" event/hook that all branches funnel through — each branch independently builds its own dice/defender inputs and its own event-log entries.

**How to avoid:** Before implementing xG, enumerate every distinct branch that can result in a `SHOT_ATTEMPT`-family or goal-scoring event by grepping `ActionEventType` members related to shooting/heading/penalties and tracing each to its resolution code, not just the two `computeShotPathDeflection` call sites found in this research. Consider adding a single shared "capture shot context" helper (defender-in-box count, distance, angle) called at the START of each branch, immediately after the shot/header/penalty target is declared but before any dice are rolled — this both centralizes the xG input-gathering logic and creates one place to audit for completeness (mirroring the `applyRosterContinuity` pattern of "one function called at every reset site" rather than duplicating logic per-branch).

**Warning signs:** An xG implementation that only has test coverage for the standard `applyDeclareShot`/regular-SHOT path, with no test asserting a snapshot deflection, headed shot, or GK-dive-at-feet-triggered penalty also produces a Game Summary xG entry.

**Phase to address:** The phase implementing the Game Summary popup / xG tracking (Feature 6). Needs its own regression test matrix: one xG-capture assertion per distinct shot-resolution branch (SHOT, SNAPSHOT_DEFLECT/SNAPSHOT_TARGET, headed shot, penalty kick, GK-dive-at-feet-triggered penalty) — do not consider this complete with only the main-branch test passing.

### Pitfall 12: Possession/pass-count tracking needs an explicit "single source of truth" decision — live counter vs. eventLog scan — before implementation, or it will drift

**What goes wrong:** The project already made and documented this exact architectural decision once, for a different feature: out-of-bounds classification uses `ball.lastTouchedBy` as "the single source of truth... not derived retroactively from eventLog scans" specifically because "one authoritative field is simpler to reason about and test than re-deriving possession history on every exit" (`STATE.md` Decisions Locked, v1.6). Match-stat counters (especially possession%, which requires tracking cumulative time/actions per team) face the identical choice: a live running counter (updated incrementally at every relevant action, requiring registration at every possession-changing call site — passes, tackles, steals, interceptions, GK possession) vs. a derive-on-demand scan of `state.eventLog` when the Game Summary popup opens. Given the popup is explicitly "reachable at any time," a live-counter approach inherits the full "must register at every relevant list" bug class this project has shipped multiple times (new event types invisible to X unless registered everywhere); an eventLog-scan approach avoids that class entirely at the cost of being computed lazily.

**Why it happens:** A live running counter feels more "real-time" and is often the first instinct for a server-authoritative game that already broadcasts full state on every action — but this project's own precedent (the `lastTouchedBy` decision) explicitly favored a single authoritative field over incremental tracking specifically to avoid this bug class.

**How to avoid:** Default to computing match stats by scanning `state.eventLog` at the moment the Game Summary popup is requested (a pure function taking `eventLog` + `pieces` and returning the stats object), not by threading incremental counters through every action handler. This mirrors the existing `lastTouchedBy`-over-eventLog-scan precedent in the opposite direction (deliberately choosing the scan here, since a running counter would require exactly the kind of "registered everywhere" incremental bookkeeping the project has repeatedly gotten wrong) and is well-suited to an on-demand popup rather than something needing to be efficient on every broadcast. If a live counter is chosen anyway for performance reasons, explicitly document why and add the same "registered everywhere" checklist rigor used for `ActionEventType` additions.

**Warning signs:** A plan that adds new fields to `GameState` for running possession/pass/tackle counters, threaded through many individual action handlers, without a stated reason a pure eventLog-derived computation was rejected.

**Phase to address:** The phase implementing the Game Summary popup / match-stat tracking (Feature 6) — this decision should be made explicitly during that phase's planning (mirroring how `RESEARCH.md`'s architecture questions were resolved for v1.6), not discovered mid-implementation.

## Technical Debt Patterns

| Shortcut                                                                                                                             | Immediate Benefit                                     | Long-term Cost                                                                                                                                             | When Acceptable                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Overloading `stealAttemptedByIds`/`tackleAttemptedByIds` to also encode "declined" state instead of adding sibling fields            | Reuses existing ZoI ring-rendering wiring immediately | Conflates two semantically different lifecycles across ~30 reset sites (Pitfall #8)                                                                        | Never — the project has an explicit written precedent (`subsUsed`/`addedTimeBonus`) against conflating similar-looking counters                                                             |
| Adding `leniencyOverride` as another optional trailing positional parameter to `buildInitialGameState`                               | Zero call-site churn beyond the new parameter         | Continues an already-fragile 11+-parameter positional function; each future addition raises the parameter-order-mistake risk                               | Acceptable for this one addition IF paired with an explicit inline doc comment matching existing style; flag for a future options-object refactor rather than doing it ad hoc mid-milestone |
| Hand-writing a `redCarded !== true` filter clause at each new eligibility site instead of extracting a shared `isActivePiece` helper | Fast, matches existing (inconsistent) codebase style  | Directly caused Pitfalls #6 and #7 — this exact shortcut has now caused the same class of bug at least 3 times (DEFLECT_ATTEMPT x2, ZoI opponents)         | Never going forward — extract the shared helper now while fixing #6/#7, since the cost of NOT doing so has already materialized twice                                                       |
| Computing xG only for the main SHOT branch and deferring snapshot/header/penalty coverage to "later"                                 | Ships a visible xG number in the popup quickly        | Produces a popup that silently underreports or omits xG for a meaningful fraction of real shot attempts, undermining user trust in the whole stats feature | Only acceptable if explicitly scoped and disclosed as a known gap in the phase's requirements — not as a silent omission                                                                    |

## Integration Gotchas

Not applicable in the traditional "external service" sense — Counter Attack POC has no third-party integrations in these 6 features. The equivalent internal-integration gotchas are covered under Critical Pitfalls above (cross-module consumer gaps between `packages/shared` and `packages/server`, and cross-surface UI duplication).

| Integration                                                                                            | Common Mistake                                                                                                                                         | Correct Approach                                                                                                                                                                                   |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/shared` validators (moveValidator, passValidator) vs `packages/server` eligibility functions | Auditing/fixing a cross-cutting concern (e.g., red-card exclusion) only in `packages/server` because that's where most of the game logic visibly lives | Any audit for a state-flag exclusion (redCarded, onPitch, future declined-state) must explicitly include `packages/shared`'s validators, which build their own independent opponent/defender lists |
| Client settings form (`GameSettingsScreen.tsx`) vs server-side `buildInitialGameState` defaults        | Trusting the client-side default/range constraint (e.g., leniency 2-5) as sufficient validation                                                        | Server must independently re-validate any client-supplied numeric/range value the same way it already does for shot/header/free-kick target hexes                                                  |

## Performance Traps

At this project's scale (2 concurrent players, single-room, full-state-snapshot broadcast after every action — `ARCH-01..07`), none of the 6 v1.7 features introduce a meaningful performance risk. The one item worth flagging:

| Trap                                                                                                                                                              | Symptoms                                                                                                       | Prevention                                                                                                                                                       | When It Breaks                                                                                                                                                 |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Computing match stats (possession%, pass count, etc.) via a full `eventLog` scan on every state broadcast (instead of only when the Game Summary popup is opened) | Slightly larger CPU cost per broadcast as `eventLog` grows across a full match (up to ~90 "minutes" of events) | Scan `eventLog` lazily only when the popup is requested (client-triggered or a dedicated server query), not as part of the routine post-action broadcast payload | Irrelevant at 2-player POC scale either way — flagged only because "compute on every broadcast" is the more obvious-looking but wasteful implementation choice |

## Security Mistakes

| Mistake                                                                                                                                                          | Risk                                                                                                                                                        | Prevention                                                                                                                                                                                                  |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Trusting the client-supplied Referee Leniency override value (2-5) without server-side re-validation                                                             | A modified/buggy client could submit an out-of-range value (e.g., 1 or 6, or non-integer), silently unbalancing booking/added-time math for the whole match | Re-validate range and integer-ness server-side in the room-settings-confirm handler, exactly like `applyDeclareShot`'s existing `INVALID_TARGET` server-side re-check pattern (`gameEngine.ts:8512-8523`)   |
| Trusting client-reported match-stat values (if any client-side computation feeds the summary popup) rather than deriving stats server-side from `state.eventLog` | A modified client could display fabricated stats to its own player, or (if stats were ever sent server-ward and trusted) corrupt shared state               | Compute match stats server-side (or as a pure function over server-broadcast `eventLog`/`GameState` that both clients compute identically from trusted data) — never accept a stats payload FROM the client |

## "Looks Done But Isn't" Checklist

- [ ] **Red-carded player removal:** Often "looks done" once `HexGrid.tsx`'s `onPitch === false` guard hides the piece visually — verify by attempting to trigger `DEFLECT_ATTEMPT` and a ZoI steal/tackle prompt against a red-carded piece specifically (Pitfalls #6/#7), not just re-checking movement/goal-kick/corner-kick/free-move (already fixed).
- [ ] **Card/injury icon unification:** Often "looks done" once the shared component renders correctly on 2-3 of the 4 surfaces — verify BenchCarousel specifically now shows yellow-card AND injury iconography, since it previously showed neither (Pitfall #3).
- [ ] **Fouls-dependency grey-out after drawer restructure:** Often "looks done" once the visual disabled state renders correctly in the collapsed/expanded drawer — verify the actual confirm-time payload sent to the server still normalizes `booking`/`injury` to `false` when `fouls` is off, independent of drawer open/closed state at confirm time (Pitfall #4).
- [ ] **Tackle/steal decline reset behavior:** Often "looks done" once the happy-path decline-then-re-prompt flow works in a single movement phase — verify the new declined-state resets (or doesn't) correctly across a PASS transition, a half-time boundary, and an Undo, not just within one uninterrupted movement sequence (Pitfall #8).
- [ ] **Match-stat half-time persistence:** Often "looks done" in a single-half playtest — verify every stat counter explicitly survives (unchanged) a half-time transition, since that boundary is never exercised in a short manual test (Pitfall #10).
- [ ] **xG coverage breadth:** Often "looks done" once a regular open-play shot produces a plausible xG number — verify snapshot shots, headed shots, and penalty kicks (including GK-dive-at-feet-triggered ones) also produce an xG entry in the popup (Pitfall #11).
