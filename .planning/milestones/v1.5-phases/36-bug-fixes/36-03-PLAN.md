<objective>
Restrict and restructure draft-pack supply fallback (BUG-35 / D-08, D-09, D-11, D-12):

1. **D-08** — when a pack slot's exact tier is short, cascade DOWN through tiers within the
   already-selected pool(s) first (`chase → rare → uncommon → common`), never substituting a
   HIGHER tier than the slot called for.
2. **D-09** — only after the same-pool cascade is exhausted may the existing cross-pool
   `FALLBACK_POOL_ORDER` chain be reached, and it may contribute `common`-tier cards ONLY.
   This is a behaviour change: today's fallback backfills at whatever tier is short.
3. **D-11** — a shortfall surviving both still throws the existing loud "insufficient supply"
   error. Never silently reuse a card or deal a short pack.
4. **D-12** — audit + regression tests proving (a) same-pool cascade is tried before any
   cross-pool reach and (b) cross-pool never yields a non-common card.

Purpose: Plan 36-02's match-wide dedup (D-06) materially increases how often a round runs short,
and today's unrestricted cross-pool backfill would quietly hand a `['original']` host rare and
chase cards from MLS. D-08/D-09 keep the host inside their chosen pool for everything except
plain commons.

Output: a cascade-aware tier-supply model in `draftEngine.ts`, a common-only cross-pool filter,
unit + integration regression coverage, and a crash guard on the one call site where a D-11 throw
would otherwise take the Node process down.
</objective>

## Existing shape (as of Plan 36-02)

`generateDraftPacks`' tiered branch calls, in order:
`resolveTieredCandidates(...)` → `tierSupplyMeetsNeed(classified, round)` guard (throws if false)
→ `buildTierPoolsForRound(round, classified, rng)` → `sortSlotsRarestFirst(round.slots)` →
`drawFromPool(tierPool, slot.count, bucketCounts)` per slot per pack.

`resolveTieredCandidates` itself loops the cross-pool `fallbackChain`, breaking as soon as
`tierSupplyMeetsNeed(classified, round)` returns true.

## New cascade table (module-level const in draftEngine.ts)

```typescript
/**
 * D-08 (Phase 36, BUG-35): the strictly-LOWER tiers a short slot may cascade into, in order.
 * A slot is never upgraded — no entry here is rarer than its key.
 */
const TIER_CASCADE_BELOW: Readonly<Record<PackSlot['tier'], readonly DraftTier[]>> = {
  chase: ['rare', 'uncommon', 'common'],
  chaseOrRare: ['uncommon', 'common'],
  rare: ['uncommon', 'common'],
  uncommon: ['common'],
  common: [],
};

/** The slot's own tier(s) first, then its D-08 cascade — full draw priority order. */
function tierDrawOrder(tier: PackSlot['tier']): readonly DraftTier[] {
  const primary: readonly DraftTier[] =
    tier === 'chaseOrRare' ? ['chase', 'rare'] : [tier as DraftTier];
  return [...primary, ...TIER_CASCADE_BELOW[tier]];
}
```

## Cascade-aware `tierSupplyMeetsNeed` (replaces the current per-slot independent check)

A pure greedy counting simulation that mirrors the pool builder's priority. No RNG — it is called
from inside `resolveTieredCandidates`' loop, where no `rng` is in scope.

1. Build `remaining: Record<DraftTier, number>` by counting `classified` per `p.tier`.
2. Build `needByTier: Map<PackSlot['tier'], number>` by summing `slot.count * PACKS_PER_ROUND`
   across `round.slots`, aggregating slots that share a tier.
3. Iterate the distinct tiers rarest-first, sorted by the existing `SLOT_RARITY_ORDER`.
4. For each tier, walk `tierDrawOrder(tier)`; take `Math.min(need, remaining[source])` from each
   source, decrementing both; stop when `need` hits 0.
5. If any tier still has `need > 0` after exhausting its draw order, return `false`. Otherwise `true`.

Rarest-first ordering is what makes "cascade competes fairly" true: a chaseOrRare slot that has to
borrow uncommons takes them before the uncommon slot claims its own population.

`tierSupplyCount` becomes unreferenced once this lands — delete it (CLEANUP-01 precedent).

## Cascade-aware `buildTierPoolsForRound`

Same rarest-first iteration over distinct slot tiers, with a `claimed: Set<string>` shared across
the whole round so a card can only land in one tier's pool:

1. Compute the same `needByTier` map.
2. For each distinct tier rarest-first:
   - `pool` = shuffle(all unclaimed `classified` whose `p.tier` is in the slot's PRIMARY tiers).
     Primary for `chaseOrRare` is `chase` + `rare` merged into one shuffled pool (Phase 30 D-25 —
     an unbiased mix, never "prefer chase"); primary for any other slot tier is that tier alone.
     Taking the FULL primary population (not just `need`) preserves today's behaviour and keeps
     `drawFromPool`'s DEF/MID/FWD_ST bucket-cap scan its existing slack.
   - Then, for each tier in `TIER_CASCADE_BELOW[tier]` in order, while `pool.length < need`: shuffle
     the unclaimed candidates of that lower tier and append only `need - pool.length` of them.
     Cascade takes the exact shortfall and no more, so a lower slot is never starved beyond what the
     rarer slot genuinely needed.
   - Mark every card now in `pool` as `claimed`, and `pools.set(tier, pool)`.

The counting simulation in `tierSupplyMeetsNeed` and this builder stay consistent because a rarer
slot claiming its entire primary population can never starve a lower slot (cascade only ever goes
down), and cascade top-up takes exactly the shortfall in both models.

## D-09 cross-pool restriction (inside `resolveTieredCandidates`)

The existing loop already only runs when `tierSupplyMeetsNeed` is false; because that check is now
cascade-aware, the loop is unreachable while the same-pool cascade can still cover the round —
that IS D-12(a), no extra ordering code is needed. The one change is the `fallbackPlayers` filter,
which must additionally require the candidate be common-tier.

**CRITICAL correction to 36-PATTERNS.md's sketch:** `resolvePoolPlayers` returns `PoolPlayer[]`,
which has NO `tier` field — `p.tier === 'common'` does not compile and would be wrong even if it
did. The tier must be computed with the module's own helpers:
`classifyTier(computeTotalStat(p)) === 'common'`.
