<objective>
Clamp Undo at a resolved dice-roll action (BUG-37 / D-13). Today a defender can move adjacent to
the carrier, trigger a `TACKLE_ATTEMPT` (or a `STEAL_ATTEMPT`) that resolves as FAIL, and then Undo
straight back past that resolved roll into the pre-contest move history — effectively re-rolling a
committed dice outcome.

Purpose: this is the defect folded in from
`.planning/todos/pending/undo-boundary-should-stop-at-dice-roll-trigger.md`.

D-13 is explicit that Undo is **boundary-clamped, not disabled**: after the attempt resolves, Undo
must keep working normally for any steps taken AFTER it, and only refuse to cross back over it.

**The correct edit site is the boundary-detection reducer, NOT the lockout check.** `applyUndo`
contains two distinct checks. The `isBoundary` disjunction (~lines 1399-1408) computes the floor
below which Undo may not reach — that is the one to extend. The separate
`currentSlotEvents.some((e) => e.type === 'SLOT_ADVANCE' || e.type === 'DICE_ROLL')` check
(~line 1413) is a full per-slot LOCKOUT that returns `UNDO_LOCKED`; adding these event types there
would make Undo permanently unavailable for the rest of the slot, directly contradicting D-13.

Output: a two-term extension to the boundary disjunction on both the server (authoritative) and the
client (UX mirror), with regression tests proving clamp-not-lockout on both sides.
</objective>

- `applyUndo(state: GameState): ApplyUndoResult` — `packages/server/src/gameEngine.ts:1393`.
  Authoritative. `ApplyUndoResult` is unchanged:
  `{ ok: false; reason: 'UNDO_LOCKED' | 'NOTHING_TO_UNDO' } | { ok: true; state: GameState }`.
- `canUndo` — the IIFE-computed boolean inside `ActionPanel` (`ActionPanel.tsx:251-287`). UX only;
  it gates the Undo button's `disabled` attribute and never mutates game state.

Relevant existing behaviour verified against source:

- On a FAILED tackle, `applyMove` appends a `TACKLE_ATTEMPT` event and returns with `phase` still
  `MOVE` and NO `DICE_ROLL` event — which is exactly why the existing line-1413 lockout does not
  catch this case and why the bug exists.
- On a SUCCESSFUL tackle or steal, the phase leaves `MOVE` entirely and `applyStartMovement` later
  emits the `KICK_OFF` boundary marker, so possession-change flows are already protected.
- The triggering `MOVE` event is appended BEFORE the `TACKLE_ATTEMPT` event, so the defender's own
  contest-triggering move correctly falls below the new floor and becomes un-undoable.
- `reduce` takes the LAST matching index, so a later `SLOT_ADVANCE` or `KICK_OFF` still wins over a
  stale earlier `TACKLE_ATTEMPT` — the new terms need no phase guard.
