<objective>
Close the folded header-winner-eligibility gap (VERIFICATION.md truth 4, status: failed). Plan 31-04 correctly appended the header-duel winner's id to `movedPieceIds` inside `applyResolveHeaderTarget`'s two non-goal branches while `state.phase === 'PASS'`. But `applyStartMovement` (gameEngine.ts:435-478) — the ONLY function that transitions PASS/KICK_OFF/LOOSE_BALL into MOVE — unconditionally resets `movedPieceIds: []` at line 463, discarding the append before the Movement Phase it targets ever begins. The verifier empirically confirmed the winner id is present after `applyResolveHeaderTarget` and gone after `applyStartMovement`. This plan adds a dedicated OPTIONAL carry field to `GameState` (mirroring `contestedPieceIds`), populated by `applyResolveHeaderTarget` and merged into `movedPieceIds` by `applyStartMovement` (then cleared), so the winner stays spent for exactly one Movement Phase.

Purpose: A header winner has already acted this turn; the todo requires it be "ineligible... in the next movement phase". The current fix is defeated in the real game flow — the piece is fully selectable again once the Movement Phase begins.
Output: `carriedMovedPieceIds` field on `GameState`; population in `applyResolveHeaderTarget` (both non-goal branches); merge-then-clear in `applyStartMovement`; a chained regression test in `gameEngine.rule11.test.ts`.

Note: the review (CR-01) observed that the adjacent `contestedPieceIds` field suffers the identical unconditional-reset defeat. That is a pre-existing, out-of-scope defect — do NOT fix it and do NOT reuse its broken carry pattern.
