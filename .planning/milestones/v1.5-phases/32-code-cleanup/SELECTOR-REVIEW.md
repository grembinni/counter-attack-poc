**Phase:** 32-code-cleanup (CLEANUP-03, D-05/D-06)

## Scope and Methodology

This store has **zero whole-store component subscriptions** (confirmed by grepping `packages/client/src` for `useGameStore((s) => ({` and any bare `useGameStore()` call with no selector — no matches). Every component call site already selects a single narrow field (e.g. `useGameStore((s) => s.playerSlot)`), consistent with the locked per-slice-selector convention (STATE.md, "Zustand per-slice selectors in HexGrid (Pitfall 6)"). **No component-level selector fixes are warranted or included in this review.**

The store's real "selector" surface — the thing that actually behaves like a memoized/derived value and can go stale — is entirely internal to the store module itself:

1. Four **derived-and-stored** fields that are computed by explicit helper/inline logic and written via `set()` at multiple mutation sites, rather than derived on read: `validMoveHexes`, `tackleRiskHexes`, `validPassTargetHexes`, `interceptionRiskHexes`.
2. The `setGameState` action's hand-rolled multi-boolean **dependency gate** (`responseMoveStateChanged`, `responseMovePaceExhausted`, `phaseChanged`, `pieceStillExists`, `activationComplete`) that decides whether to clear or retain the current UI selection on every server broadcast — functionally a manually-reimplemented `useEffect`/`useMemo` dependency array.

This review catalogs both, using the `Field/Selector | Derives | Recomputed at | Stale-risk? | Verdict` table shape from `32-RESEARCH.md` § Architecture Patterns Pattern 3.

### `validMoveHexes` stale-risk detail (the three problems driving the `fix` verdict)

1. **Real bug — KICK_OFF_SETUP / FREE_KICK_SETUP silently lose their highlight on any same-phase broadcast.** `setGameState`'s sticky-selection logic (L747-895) has dedicated branches for HIGH*PASS_MOVE/GK_KICK_MOVE/FIRST_TIME_PASS_MOVE, SNAPSHOT_DEFLECT, and FREE_MOVE_ATTACK/DEFENSE, but **no branch for KICK_OFF_SETUP or FREE_KICK_SETUP**. Both phases fall through to the generic branch at L886-895, which calls `computeMovementValidHexes` → `validateMove(gameState, piece, hex)` for every candidate. `validateMove`'s first guard (`packages/shared/src/moveValidator.ts` L60) is `if (state.movementSlot === null) return { ok: false, reason: 'WRONG_SLOT' }` — and `movementSlot` is `null` throughout both KICK_OFF_SETUP and FREE_KICK_SETUP (it is a MOVEMENT-phase-only field). So every candidate hex is rejected and `validMoveHexes` collapses to `[]`. Concretely: if Player A selects a piece during KICK_OFF_SETUP and Player B then repositions \_any* piece (a normal, expected concurrent action during this phase), the server broadcast reaches Player A's client, `phaseChanged`/`responseMoveStateChanged`/`activationComplete` are all `false` (none of them look at KICK_OFF_SETUP/FREE_KICK_SETUP-specific fields), so the sticky path runs and silently wipes Player A's zone highlight even though nothing Player A did changed their own valid destinations. This is exactly the "Nth mutation path that forgets to recompute silently shows stale highlights" pattern RESEARCH.md Pattern 3 predicted. This is a genuine, currently-shipping defect in this store's derived-state bookkeeping (not a hypothetical), and it lives squarely inside the reviewed surface (`setGameState`'s dependency-gate/recompute bookkeeping for `validMoveHexes`) — so it is fixed in this phase (Task 2) via the same established precedent as commit `7950a18` ("add SNAPSHOT_DEFLECT recompute path to setGameState sticky-selection").
2. **Redundant duplication — HIGH_PASS_MOVE/GK_KICK_MOVE/FIRST_TIME_PASS_MOVE sticky block reimplements `computeResponseMoveValidHexes` inline instead of calling it.** `selectPiece`'s three branches for these phases (L538, L624, L653) call the shared `computeResponseMoveValidHexes` helper. `setGameState`'s sticky block for the _same three phases_ (L784-824) does **not** call that helper — it reimplements the `strict-1`-mode subset of its logic by hand (`hexesInRange(piece.position, 1).filter(...)` with the same three checks), via a 3-way nested ternary for `paceRemaining`/`lockedId`. This is the "hand-rolled dependency array" pattern D-06 explicitly calls out: two implementations of the same rule that can silently drift if one is changed without the other. `SNAPSHOT_DEFLECT`'s sticky block (L826-853) already demonstrates the correct pattern (calls `computeResponseMoveValidHexes` with the lock check done by the caller) — the HIGH_PASS_MOVE/GK_KICK_MOVE/FIRST_TIME_PASS_MOVE sticky block should follow the same shape.
3. **Minor duplication — FREE_MOVE_ATTACK/DEFENSE's valid-hex filter is copy-pasted between `selectPiece` (L577-586) and `setGameState`'s sticky block (L865-874).** Byte-for-byte identical filter logic (`hexesInRange(piece.position, 1)` + `PITCH_HEXES` membership + occupancy + `hexDistance === 1`), differing only in the pace-budget lookup expression. Same class of risk as #2 — a future change to one copy that misses the other silently desyncs FREE_MOVE_ATTACK behavior from FREE_MOVE_DEFENSE/re-selection behavior.

Additionally, the KICK_OFF_SETUP (L412-433) and FREE_KICK_SETUP (L475-504) valid-hex computations in `selectPiece` are themselves large inline blocks with no reusable helper — extracting them is a **prerequisite** for fixing problem #1 above (the fix needs the exact same logic available to both `selectPiece` and `setGameState`'s new sticky branches), so this extraction is bundled into the same fix, not a separate line item.

## Catalog: `setGameState`'s Hand-Rolled Dependency Gate

The gate (L722-745, feeding the OR'd clear-condition at L747-754) has five boolean/condition terms deciding whether the previous selection survives a broadcast:

| Gate term                   | Guards                                                                                                                                           | Distinct from the others?                                                                                                                                                                                | Verdict                |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- |
| `responseMoveStateChanged`  | ATTACKER→DEFENDER (or KICKER→OPP) slot hand-off across `movementSlot`/`firstTimePassMovementSlot`/`highPassMovementSlot`/`gkKickMovementSlot`    | Yes — a slot can hand off with pace still at 0 (immediate skip), which `responseMovePaceExhausted` alone would not catch. Verified live by BUG-09 regression tests 1-3 (`useGameStore.test.ts` L397-443) | **keep — irreducible** |
| `responseMovePaceExhausted` | Same-slot pace-cap-reached (no slot field change yet, e.g. the piece that just moved is still locked into the current slot but has no pace left) | Yes — distinct trigger from a slot change; verified live by BUG-09 tests 4/6 (clears) and the paired regression guards tests 5/7 (retains when NOT exhausted) — both directions are exercised            | **keep — irreducible** |
| `phaseChanged`              | Genuine `GamePhase` transitions (also independently gates `headerContestantIds` retention at L771, per UX-15)                                    | Yes — the only term that looks at `newState.phase !== prevState.phase` directly; phase can change without any of the other four terms being true (e.g. HEADER→PASS)                                      | **keep — irreducible** |
| `!pieceStillExists`         | Defensive: the previously-selected piece no longer exists in `newState.pieces` (rare — e.g. end-of-match/replay reset)                           | Yes — no other term inspects piece existence                                                                                                                                                             | **keep — irreducible** |
| `activationComplete`        | Multi-hex MOVEMENT-phase activation finished (`prevSelectedId` appears in `movedPieceIds`)                                                       | Yes — MOVEMENT-phase-specific completion signal with no slot/pace-field equivalent (plain MOVEMENT has no `*MovementSlot`/`*PaceUsed` fields)                                                            | **keep — irreducible** |

`prevSelectedId === null` (also OR'd into the clear condition, L752) is not a computed gate — it is the direct "nothing was selected" base case and does not warrant its own review row.

**Finding: no redundant or removable gate terms.** Each of the five terms guards a genuinely distinct trigger with existing regression-test coverage (BUG-09 test suite, `useGameStore.test.ts` L328-512) confirming both the "fires" and "doesn't fire" side for the two most complex terms (`responseMoveStateChanged`/`responseMovePaceExhausted`). Collapsing any of them would reintroduce the exact bug each was added to fix (see inline comments at L718-729, L744, referencing BUG-09 and the specific slot/pace/activation scenarios). This part of the review confirms the gate is **not** a source of staleness — it is the correctly-scoped fix surface; the staleness lives downstream in the _recompute_ logic the gate feeds into (see `validMoveHexes` findings above), not in the gate's own conditions.

## Resolution (Task 2) — Applied Fixes

All three `validMoveHexes` problems identified above were fixed via one consolidated refactor to `packages/client/src/store/useGameStore.ts`:

1. **KICK_OFF_SETUP / FREE_KICK_SETUP sticky-highlight bug (problem #1) — APPLIED.** Extracted the KICK_OFF_SETUP zone rule into a new pure helper `computeKickOffSetupValidHexes(id, gameState, myTeam)` and the FREE_KICK_SETUP stage/team-gated rule into `computeFreeKickSetupValidHexes(id, piece, gameState, myTeam)` (the latter returns `null` when the current player's turn/selection is no longer valid — e.g. the active stage advanced to the other team — so the caller can clear selection exactly as `selectPiece`'s original guard cascade would). `selectPiece`'s KICK_OFF_SETUP and FREE_KICK_SETUP branches now call these helpers (behavior-identical refactor — same guard order, same outputs, proven by the existing FREE_KICK_SETUP test suite staying green). `setGameState` gained two new dedicated sticky branches (mirroring the SNAPSHOT_DEFLECT branch's existing shape) that call the same helpers on every same-phase broadcast, so the highlight now survives concurrent opponent actions during KICK_OFF_SETUP/FREE_KICK_SETUP instead of silently collapsing to `[]`. New regression tests added in `useGameStore.test.ts`: two for KICK_OFF_SETUP ("stays highlighted across a same-phase broadcast" + a defense-in-depth piece-removed-clears-selection case) and two for FREE_KICK_SETUP ("stays highlighted across a same-stage broadcast" + "clears when the active stage hands off to the other team").
2. **HIGH_PASS_MOVE/GK_KICK_MOVE/FIRST_TIME_PASS_MOVE sticky duplication (problem #2) — APPLIED.** Introduced four named `ResponseMoveValidHexConfig` constants (`HIGH_PASS_MOVE_CONFIG`, `GK_KICK_MOVE_CONFIG`, `FIRST_TIME_PASS_MOVE_CONFIG`, `SNAPSHOT_DEFLECT_CONFIG`) at module scope, replacing the inline config object literals previously repeated at each `selectPiece` branch and (for SNAPSHOT_DEFLECT) its sticky block. `setGameState`'s sticky block for HIGH_PASS_MOVE/GK_KICK_MOVE/FIRST_TIME_PASS_MOVE now derives `paceRemaining`/`lockedId` from the matching config and calls `computeResponseMoveValidHexes` directly (deleting the hand-rolled 3-way ternary + inline filter), exactly mirroring the pattern the SNAPSHOT_DEFLECT sticky block already used. Zero behavior change for these three phases — `useGameStore.test.ts` BUG-09 tests 1-5 (slot hand-off / pace-exhaustion clearing + regression guard) pass unmodified.
3. **FREE_MOVE_ATTACK/DEFENSE duplicated filter (problem #3) — APPLIED.** Extracted the shared filter into a new pure helper `computeFreeMoveValidHexes(id, piece, gameState)`; both `selectPiece`'s FREE_MOVE_ATTACK/DEFENSE branch and `setGameState`'s sticky block now call it. Zero behavior change — the FREE_MOVE_ATTACK/DEFENSE sticky-selection test suite (`useGameStore.test.ts` L271-326) passes unmodified.

No `fix`-verdict row was downgraded to `keep — irreducible` — all three were implementable as behavior-preserving-or-bug-fixing refactors backed by either existing test coverage (problems #2/#3) or new regression coverage added alongside the fix (problem #1).
