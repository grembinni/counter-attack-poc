**Note on the away/home team-identity literals still asserted-absent by `PieceOverlay.test.tsx`** (`#1a56b0`, `#c0392b`, `#9b59b6`, `#db2777`): these were already migrated to `TEAM_CONFIGS` lookups in an earlier phase (Phase 15/32) — do not reintroduce them as tokens; the tests validating their absence stay unchanged.

**Runtime `--team-accent` derivation (THEME-03, Pattern 4 — single source, not per-component lookups):**

```tsx
// Applied once, at each screen's outermost wrapper element:
<div className={styles.gameBoard} style={{ '--team-accent': teamColor } as React.CSSProperties}>
```

- `teamColor` = `TEAM_CONFIGS[activeTeamId].palette.uiColor` (existing single source of truth, unchanged — Phase 15/18/32 decision).
- Applies to every screen root that currently threads `useTeamAccentColor(teamId)` through multiple individual `style={{color}}` props: `GameBoard.tsx`, `TeamSelectionScreen.tsx`, `UniformSelectionScreen.tsx`, `LineupAssignmentScreen.tsx`.
- Descendant CSS Modules read it via `color: var(--team-accent);` / `border-color: var(--team-accent);` — no per-component prop threading.
- Screens with no active team yet (lobby, pre-selection) do not set the variable; consumers fall back to `--color-accent-gold` (`#f5c518`) or the static `#1a56b0` default listed above, whichever the existing call site already used as its fallback — do not invent a new fallback value.

**Scope boundary (Pitfall 5):** Token migration covers both `*.module.css` literals AND inline `style={{ color: '#hex' }}` literals in `.tsx` files (e.g. `KickOffSetupPanel.tsx:97/105`, `FreeKickSetupPanel.tsx:187/193`, `GameBoard.tsx:211/283`). Inline styles read `var()` directly as a string — no cast needed: `style={{ color: 'var(--color-danger)' }}`.

**Out of scope for this token file:** `PitchMarkings.tsx` and `GoalNets.tsx` static pitch-line/net color literals (cosmetic field decor, not chrome) and the `UNIFORM_STYLES` jersey-pattern renderer (a separate, already-reviewed system). Do not migrate these in Phase 33.

### B. Highlight / Ring Color Table (HILITE-01..05)

Per 33-RESEARCH.md Pattern 3, this is not one flat table — it is three category tables. `docs/HIGHLIGHT-REFERENCE.md` (new file, sibling to `docs/ARCHITECTURE.md`) must contain all three, matching these exact values. This resolves 33-RESEARCH.md's Open Questions 1–3 with final decisions (no further discretion needed at implementation time).

**Traffic-light semantic legend (D-01):**

- 🟢 Green = safe / valid action target
- 🟡 Amber/orange = caution / risk
- 🔴 Red = danger / rule-violation — reserved EXCLUSIVELY for the offside ring (HILITE-02). No other element in the app may use red for any other meaning.
- 🔵 Blue = neutral info (zone/placement guidance, ball-related neutral state)
- 🟣 Purple = shot-opportunity / goal-target (the "distinct non-red" color required by D-02)
- ⚪ White = informational trajectory/path preview (existing established use, outside the 5-color traffic-light system by design — do not force these into a traffic-light color)
- 🟨 Gold = confirmation/required-action ring accent (existing established use, also outside the 5-color system — same swatch as `--color-accent-gold` in the chrome token table; this is an intentional, documented value reuse per Pitfall 4, not a duplicate/competing gold)
