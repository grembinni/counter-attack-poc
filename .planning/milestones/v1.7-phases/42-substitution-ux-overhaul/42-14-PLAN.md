<objective>
Close gap item 6 from `42-10-SUMMARY.md`: swapping a player into a slot occupied by a red-carded player's active neighbour can stack two active players in one slot instead of cleanly swapping.

Purpose — the mechanism, traced through the current tree:

1. `applyRosterReposition` (`gameEngine.ts:3263`) swaps the OCCUPANT between two slots: `id`, `position` and `number` stay bound to the slot, everything else travels with the person. So the person arriving in slot B takes slot B's `position`.
2. D-05 deliberately allows a sent-off player's slot to be a reposition participant — guard 6 in that function (`:3322`) explicitly documents that no `isActivePiece` rejection belongs there.
3. BUG-38's fix (this phase) made a sent-off piece's frozen hex stop reporting as occupied (`moveValidator.ts:71`, `gameEngine.ts:638`/`:2450`, `outOfBounds.ts:199`, etc.). Human verification step 21 confirmed this works: "hex no longer blocked" — CONFIRMED PASS.
4. Therefore an active piece can now legitimately walk onto the sent-off piece's frozen hex during play. When the manager later repositions another active player INTO the sent-off slot, that player is assigned the sent-off piece's frozen `position` — the hex the first active piece is already standing on. Two active pieces, one hex. Exactly the reported stacking.

This is a genuine interaction between BUG-38's fix and D-05's droppable vacated slot, reachable only through the combination this phase shipped. The fix must preserve D-05 (the slot stays droppable when its hex is free) while making the stacking outcome impossible, per the verifier's own wording: "the swap should be blocked (or correctly resolved) whenever the destination already holds an active player who was not properly displaced."

Output: a destination-occupancy guard in the engine, a matching roster-panel message, and a client-side pre-gate so the SENT OFF slot stops advertising a drop that will be refused.
</objective>

## Design decision recorded (D-05 preserved, not weakened)

D-05 says a sent-off player's vacated formation slot "remains a real, empty slot ... it does not stay permanently locked". This plan keeps that: the slot is rejected ONLY when its frozen hex is currently occupied by a different active piece. When the hex is free — the ordinary case — the reposition still succeeds exactly as 42-06 shipped it. The engine's existing guard-6 comment ("Do NOT 'fix' this by adding `isActivePiece`") stays true and must be kept verbatim: this plan does not add an `isActivePiece` rejection on the participants, it adds an occupancy check on the two destination hexes.
