<objective>
Accumulate the six non-shot whole-match statistics — possession (STATS-04), completed passes (STATS-05), tackle/steal attempts and successes (STATS-06), and fouls, yellow cards and red cards (STATS-09) — at the single `broadcastState` choke point, by diffing the newly appended `eventLog` slice and the `actionCount` delta against the previous broadcast.

This deliberately diverges from the `subsUsed` precedent of incrementing inline at the call site. `subsUsed` has one call site; these six statistics are produced across the pass resolution branches, both duel-resolution paths, and the shared foul chain, while `actionCount` alone is advanced inline at fifteen-plus independent return sites (45-RESEARCH.md Pitfall 4). A per-site instrumentation pass would touch more code than the entire rest of this phase and would have no single place to test. `broadcastState` already runs after every state-mutating handler and already maintains one pre/post diff baseline (`lastBroadcastBallPosition`), so extending that same edge-trigger pattern gives one well-tested choke point instead.

Purpose: one reducer, one call site, six statistics.
Output: a new pure `foldMatchStats` reducer, three new `Room` baselines, and a single fold call inside `broadcastState`.
</objective>

<planner_decisions>
- **PD-08 — "completed pass" definition (STATS-05), resolving 45-RESEARCH.md Open Question 2 / Assumption A1.** Counted: `STANDARD_PASS`, `FIRST_TIME_PASS`, and `LONG_BALL` with `accurate === true`; `HP_ACCURACY` with `accurate === true`; and `HEADED_PASS` whose `ballAfter.carrierId` resolves to a piece on the passer's own team. Not counted: `HIGH_PASS` (a declare-time log entry, always `accurate: null` — counting it would double-count every high pass alongside its `HP_ACCURACY` completion), `GK_KICK`, `GK_PUNT`, `THROW_IN_PLACE`, `GOAL_KICK`, and `CORNER_KICK_ACCURACY` (goalkeeper distribution and dead-ball restarts are not open-play passes in the sense every soccer stats UI means, and Counter Attack's own rules treat them as distinct restart mechanics). This filter list is a single array constant in the reducer so it can be adjusted later without touching branch logic.
- **PD-09 — pass team attribution.** Resolve in order: the event's declared `passerId` looked up in `state.pieces`; for `LONG_BALL`, whose declared variant carries no `passerId`, use `ballAfter.carrierId` instead; if neither resolves to a known piece, skip the event and credit nobody. The skip is deliberately silent rather than throwing — this is a display-only statistic and a hard failure here would take down a live match. (Runtime note for the implementer: `applyRoll`'s PASS case builds `LONG_BALL` through a computed `type: deliveredPassType` literal that does set a runtime `passerId`, but the declared type does not include it, so narrowing on `LONG_BALL` and reading `passerId` is a type error. Use `ballAfter.carrierId`; do not widen the shared type to work around it.)
- **PD-10 — card counting (STATS-09).** `BOOKING_CHECK` increments `yellowCards` when `card === 'yellow'` OR `secondYellow === true`, and increments `redCards` when `card === 'red'`. `resolveBooking` (`packages/shared/src/fouls.ts:138-140`) returns `{ card: 'red', secondYellow: true }` for a second bookable offence, so without the `secondYellow` clause a second yellow would register as a red only and the yellow count would understate. A second yellow is both a yellow and a red in real football statistics, so it increments both.
- **PD-11 — the fold is the last state mutation before the offer hooks read state.** `foldMatchStats` is invoked immediately after `applyFreeMoveZoneCheck` and BEFORE `const state = room.gameState;`, so that every downstream spread inside `broadcastState` (the `GK_BOX_ENTRY_PROMPT` and `GK_DIVE_AT_FEET_PROMPT` phase substitutions) carries the folded `matchStats` forward automatically. Inserting it after those hooks would require each hook's spread to be audited for field preservation.
- **PD-12 — the three new baselines advance unconditionally.** `lastBroadcastBallPosition` is deliberately NOT advanced during `TACKLE_STEAL_PROMPT` (a Phase 43 decision protecting a goalkeeper edge-trigger). The three new baselines added here must advance on EVERY broadcast without that guard: skipping the advance would re-fold the same event slice on the following resume broadcast and double-count every statistic produced during a tackle/steal prompt. Place the new assignments outside the existing `if (room.gameState.phase !== 'TACKLE_STEAL_PROMPT')` block, and comment why they differ.
- **PD-13 — undo safety, verified not assumed.** `applyUndo` (`gameEngine.ts` ~4000-4270) removes exactly one event from `eventLog`, shrinking it by one, and never touches `actionCount` (grep-verified: zero occurrences of `actionCount` in the whole function). The removed event is always a movement event (`MOVE`/`HP_MOVE`/`FTP_MOVE`/`GK_KICK_MOVE`/`SNAP_DEFLECT_MOVE`/`FK_SETUP_MOVE`/`GOAL_KICK_MOVE`/`CORNER_KICK_MOVE`), and undo is hard-locked the moment any `DICE_ROLL` or `SLOT_ADVANCE` appears in the current slot — so it can never remove a pass, duel, foul or booking event. No decrement logic is therefore required. The only defect the shrink can cause is an out-of-range slice baseline, which is handled by clamping the previous length to the current length before slicing.
</planner_decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client action → handler → engine → `eventLog` | Client-emitted actions append events that this reducer then counts. The reducer reads only server-produced events, never client payloads. |
| `room.gameState` → `GAME_STATE` broadcast → both browsers | The folded counters leave the server for two untrusted clients on every broadcast. |
| `Room` in-memory baselines → fold correctness | Room-level mutable baselines determine what gets counted; corrupting them corrupts every statistic. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-45-08 | Tampering | A client inflating its own possession, pass or tackle numbers | mitigate | No new client→server event, handler, or handler parameter is introduced. The reducer's only inputs are `room.gameState.eventLog`, `room.gameState.pieces`, `room.gameState.actionCount`, and the server-held previous baselines. ASVS V5 is not engaged because there is no new input surface. |
| T-45-09 | Tampering | Double-counting via repeated broadcasts of the same state | mitigate | The fold is driven by a monotonically advancing event-log length baseline, so a repeat broadcast produces an empty slice and a zero delta. Pinned by an explicit idempotency test and by the PD-12 unconditional-advance rule, whose failure mode (a `TACKLE_STEAL_PROMPT` re-fold) has its own named test. |
| T-45-10 | Tampering | Wrong possession attribution around every turnover (Pitfall 5) | mitigate | The pre-action attacking team is captured in a dedicated `Room` baseline and passed explicitly into the reducer, which is contractually forbidden from reading the team from any event or from post-action state. A named test reproduces the steal-flips-possession-and-advances-clock combination. |
| T-45-11 | Denial of service | An out-of-range slice or a throw inside the reducer taking down every live broadcast | mitigate | The reducer has no throw paths (structural guards only, matching `broadcastState`'s existing no-try/catch style), unresolvable piece lookups are skipped silently per PD-09, and the previous-length baseline is clamped to the current length before slicing per PD-13. |
| T-45-12 | Information disclosure | Both players seeing identical statistics | accept | Intended and required by STATS-01/STATS-02. ASVS V4 applies only narrowly: match statistics are not secret, so no per-team filtering is needed, unlike the `DraftClientView` privacy split. The existing full-snapshot broadcast already delivers identical bytes to both sockets. |
| T-45-SC | Tampering | npm/pip/cargo installs | mitigate | Not applicable — this plan installs zero packages, consistent with 45-RESEARCH.md's Package Legitimacy Audit finding that the phase adds no dependency to any workspace package. No install task exists, so no legitimacy checkpoint is required. |
