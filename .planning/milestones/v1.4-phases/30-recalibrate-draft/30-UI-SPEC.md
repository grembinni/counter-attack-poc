## Design System

| Property          | Value                                                                                          |
| ----------------- | ---------------------------------------------------------------------------------------------- |
| Tool              | none                                                                                           |
| Preset            | not applicable                                                                                 |
| Component library | none — plain React + CSS Modules                                                               |
| Icon library      | none (text/emoji glyphs only, e.g. arrow chars for carousel nav)                               |
| Font              | system default (no `font-family` declared anywhere in the codebase; inherits OS UI font stack) |

**No design-system gate triggered.** `components.json`/`tailwind.config.*`/`postcss.config.*` were not found anywhere in the repo (confirmed via `ls` scan at repo root). This is a deliberate, established convention: all 29 prior phases (dating to Phase 12's "Visual Token & Hex Layer") use plain CSS Modules with a single hand-maintained dark-theme token set, documented verbatim at the top of `LineupAssignmentScreen.module.css`:

```
--bg-page: #1a1a2e; --bg-surface: #16213e; --border: #0f3460;
--text: #e0e0e0; --text-dim: #a0a0a0; --accent: #f5c518;
```

(These are documentation comments only — not actual CSS custom properties; values are hardcoded as hex literals throughout every `.module.css` file.) Phase 30 is a narrow rules/data/visual-token recalibration of the existing draft feature (CONTEXT.md frames it as "not a bug-fix or additive feature" but explicitly _not_ a redesign either). Introducing shadcn/Tailwind now would contradict that scope and create a two-system codebase. **Decision: continue the established plain-CSS-Modules convention. Do not initialize shadcn for this phase.**

## Spacing Scale

Declared values (must be multiples of 4), confirmed against existing `LineupAssignmentScreen.module.css` usage — no changes needed, this phase reuses the scale as-is:

| Token | Value | Usage                                                                           |
| ----- | ----- | ------------------------------------------------------------------------------- |
| xs    | 4px   | `.cardMeta`/`.cardHeader` inline gaps, chip row gaps                            |
| sm    | 8px   | `.column`/`.formationColumns`/`.carouselViewport` gaps, `.statCardBase` padding |
| md    | 16px  | `.screen` padding, `.formationColumns` gap, section `gap`                       |
| lg    | 24px  | `.screen` outer padding                                                         |
| xl    | 32px  | not directly used pre-existing; reserved if a new section wrapper is needed     |
| 2xl   | 48px  | `.confirmButtonGreen` horizontal padding                                        |
| 3xl   | 64px  | not used                                                                        |

**Exceptions:**

- `.carouselNav` is 32×32px — a touch-target-floor exception, not on the 8pt scale by design (documented in the existing CSS comment above the rule; unchanged by this phase).
- Card border widths (1px base, 3px tier variants) are stroke widths, not spacing, and are exempt from the 4px scale by convention (unchanged).

No new spacing tokens are introduced by this phase's rounds/pack UI — round labels, pick-counters, and the 4-card GK-only pack row reuse `.draftPackRow`/`.carouselViewport`/`.carouselTrack`/`.cyclePickCounter` spacing exactly as they exist today.

## Typography

Existing scale (unchanged by this phase — confirmed present in `LineupAssignmentScreen.module.css`, `GameSettingsScreen.module.css`, `DraftPackCarousel` via shared styles):

| Role            | Size | Weight          | Line Height                                                                               |
| --------------- | ---- | --------------- | ----------------------------------------------------------------------------------------- |
| Body/label      | 12px | 700 (bold)      | 1.3 (browser default; not explicitly set — do not add `line-height` overrides this phase) |
| Status/CTA text | 14px | 700 (bold)      | 1.3                                                                                       |
| Section heading | 22px | 800 (extrabold) | 1.2 (explicit, `.matchSetupHeading`)                                                      |

Only 2 weights are used across the whole screen family: **700 (bold)** for nearly everything, and **800 (extrabold)** reserved for the single top-level `.matchSetupHeading`. This phase must not introduce a third weight.

Only 3 sizes are in active use (12px / 14px / 22px). This phase's new UI (round labels, per-round pick-count text, GK-pack indicator) must reuse one of these three — do not introduce a 4th size. Recommendation: round/pick-count labels use the existing `.cyclePickCounter` treatment (12px/700/`#a0a0a0`) verbatim.

### Tier border colors (D-22 — this phase's actual color change)

This is the one color contract this phase modifies. Tier borders are a **4-value semantic accent system** layered on top of the 60/30/10 palette above — they exist only as a 3px card-border stroke, never as a fill/background, so they do not compete with the accent-10% budget.

| Tier       | Old value (being replaced)                                   | New value (D-22)                                                                                       | CSS class           |
| ---------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ | ------------------- |
| Chase      | `#a855f7` (purple)                                           | `#a855f7` (purple) — **unchanged, already correct**                                                    | `.cardTierChase`    |
| Rare       | `#ef4444` (red)                                              | `#ef4444` (red) — **unchanged, already correct**                                                       | `.cardTierRare`     |
| Uncommon   | `#eab308` (yellow, committed) / green (uncommitted WIP edit) | `#22c55e` (green)                                                                                      | `.cardTierUncommon` |
| Common     | `#22c55e` (green, committed) / yellow (uncommitted WIP edit) | `#ffffff` (white)                                                                                      | `.cardTierCommon`   |
| ~~Keeper~~ | `#ffffff` (white)                                            | **DELETED** — `.cardTierKeeper` class and the `'keeper'` `DraftTier` value are removed entirely (D-05) | n/a                 |

Note: `#ef4444` (rare) is the same hex already reserved for destructive/error text elsewhere on the screen (`.statusWaiting`, `.swapRejection`). This is a pre-existing coincidental collision (not introduced by this phase) — rare-tier card borders and error text never appear in the same visual context (borders are on cards; error text is standalone), so no contract violation, but flagged for awareness.

**Important:** `#22c55e` is _also_ currently used for `.confirmButtonGreen` and `.statusActive` (both mean "success/ready" states). Reassigning `#22c55e` to the uncommon-tier border creates the same kind of coincidental collision as rare/red above — acceptable for the same reason (cards vs. buttons/status text are visually distinct contexts), but do not let this phase's implementation accidentally reuse `.statusActive`'s green for anything tier-adjacent expecting them to mean the same thing.

## Additional Contract Notes (phase-specific, beyond template defaults)

These capture UI-surface decisions from `30-CONTEXT.md` that the planner/executor need but don't map cleanly onto the template's generic fields above:

1. **D-23 — extend tier border to starting-11 lineup slots.** Currently only `DraftPackCarousel.tsx` (draft-stage carousel) applies `TIER_CARD_CLASS`-style tier borders. `LineupAssignmentScreen.tsx`'s starting-11 formation-column cards use state-based classes only (`.statCard` / `.statCardLocked` / `.statCardConfirmed` / drag variants) with **no tier border at all**. This phase must compose the tier border into those same cards (e.g. combine `.statCardLocked`/`.statCardConfirmed`/etc. with the appropriate `.cardTier*` class, or add a tier-aware variant of each state class) so tier color is visible on every card surface: draft carousel, bench carousel, **and** starting-11 slots. Do not change the existing `min-width: 320px` tier-card sizing rule to also apply to the 260px-wide starting-11 grid (that grid is fixed at 1260px/4-column per the existing `.statCardBase` comment) — border color/width only, not card dimensions, on the starting-11 surface.
2. **`resolveTieredCard`'s `'keeper'` fallback (LineupAssignmentScreen.tsx ~line 270-275) must be updated** in the same pass that removes the `'keeper'` `DraftTier` value (D-05): its current `player.role === 'GK' ? 'keeper' : 'common'` heuristic needs a new fallback tier for GK cards now that `'keeper'` no longer exists as a valid `DraftTier`. Recommendation: fall back to `'common'` for both branches (since GKs use the identical common/uncommon/rare/chase cutoffs per D-04) — this is a functional/data decision, not purely visual, so confirm with planner/executor rather than treating as settled here.
3. **`.cardTierKeeper` CSS class deletion (D-05)** must happen alongside the `TIER_CARD_CLASS` map update in `DraftPackCarousel.tsx` (currently has a `keeper: styles.cardTierKeeper!` entry that will no longer type-check once `'keeper'` is removed from `DraftTier`).
4. **Legends/Icons unlock (D-08) is a pure state change, not a new visual pattern** — the existing enabled-checkbox styling (used today by Original/MLS/International) already defines exactly what an enabled Legends/Icons checkbox should look like. No new CSS is needed; only the `disabled` boolean and `SELECTABLE_DRAFT_POOLS` array change (client `GameSettingsScreen.tsx` line ~41, server allow-list). Do not restyle the already-correct enabled-checkbox appearance.
5. **Round-count/pick-count display is the only genuinely new UI surface this phase adds.** Everything else (tier colors, pool checkboxes) is a value swap on existing components. Keep the round/pick-count display visually subordinate to the existing carousel — same treatment as `.cyclePickCounter` (12px/700/muted gray), not a new prominent heading. It sits in addition to (not replacing) the existing waiting-indicator/keeper-banner slot in the layout — except the keeper-banner slot itself is now dead code per Copywriting Contract row 3 above and should be removed, not repurposed.
