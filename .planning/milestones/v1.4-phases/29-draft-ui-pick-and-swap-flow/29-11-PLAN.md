<objective>
Close the single remaining CRITICAL gap on Phase 29: the draft→game lifecycle handlers do not consistently enforce draft-completion invariants (29-VERIFICATION.md "Critical Gaps" #1, sourced from 29-REVIEW.md CR-01/CR-02/CR-03). Three independently-confirmed defects — all missing server-side authorization/lifecycle guards — let a client desynchronize authoritative game state:

- **CR-01** (`roomHandlers.ts` LINEUP_CONFIRM draft branch): never checks `draftSession.draftComplete`, so a full-but-mechanically-incomplete draft can start a match a full cycle early (all 11 slots fill by cycle 3 / 12 cards; `draftComplete` only flips at cycle 4 / 16 cards).
- **CR-02** (`roomHandlers.ts` DRAFT_PICK): missing the `requesterConfirmed || room.gameState !== null` guard that DRAFT_REARRANGE already has — composes with CR-01 to let post-kickoff DRAFT_PICKs mutate `draftSession` and yank both clients back to the draft screen.
- **CR-03** (`createServer.ts` reconnect): the `!draftComplete` restriction excludes the post-complete/pre-confirm window, stranding a reconnecting socket with no re-sync event (a plain network-hiccup scenario, contradicting the CLAUDE.md Socket.io reconnection-with-state-recovery design value).

Purpose: satisfy the derived truth behind ROADMAP Phase 29 Success Criteria #2 ("via real-time WebSocket coordination") and #5 ("after the draft completes…"). Phase 29 is the last phase in the v1.4 roadmap — there is no later phase to defer these to.

Output: three minimal, guard-only source edits plus negative-path regression tests that actually reach each previously-unguarded window (WR-02).

**Why one plan, three tasks:** the three fixes are one concern (draft lifecycle authorization) and compose into a single exploit chain (CR-01 enables CR-02). They are independent guard additions with zero ordering dependency between tasks, so they share Wave 1. CR-01 and CR-02 are kept as separate tasks (distinct handlers, distinct error codes, distinct test windows) per the gap-closure requirement to not bundle; they are not merged because they guard different lifecycle points with different error semantics (`DRAFT_NOT_COMPLETE` vs `LINEUP_ALREADY_CONFIRMED`).
