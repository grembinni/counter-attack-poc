<objective>
Build the client surface for the whole Goal Kick flow: a `GoalKickSetupPanel` covering all five goal-kick phases, the store emitters and piece-selection logic behind them, and the pitch wiring that makes the two reposition windows, the teammate-head target selection and the 3-hex travel window clickable (GOALKICK-04, GOALKICK-05, D-01, D-07, D-08).

Purpose: Plans 37-08 and 37-09 built the entire server-side goal-kick chain, and Plan 37-02 registered every new phase in `PHASE_LABEL` while deliberately leaving the `GameBoard` dispatch ternary alone with a comment naming this plan. Without this plan the chain is unreachable — a manager whose team is awarded a goal kick sees a generic `ActionPanel` with no way to act. Per D-07 the panel follows Phase 35's locked conventions (`"Confirm"` verb, no container border, two-line title plus detail helper text, `"{Team} is repositioning…"` waiting phrasing). Per D-08 every highlight maps onto an existing `HexHighlightType` member — no new tint types and no edit to `docs/HIGHLIGHT-REFERENCE.md`.

Output: `GoalKickSetupPanel` (plus CSS module and tests), the `emitGoalKickChoice` / `emitGoalKickTarget` store actions with their selection branches, the `GameBoard` dispatch branch, and the `HexGrid` wiring for all three interaction modes.
</objective>

## Decisions locked by this plan (D-07 / D-08 discretion resolved)

- **One panel, five phases.** `GoalKickSetupPanel` branches internally on `GOAL_KICK_SETUP_GK`, `GOAL_KICK_SETUP_OPPONENT`, `GOAL_KICK_CHOICE`, `GOAL_KICK_TARGET` and `GOAL_KICK_MOVE`, matching the single component name the phase inventory and the UI-SPEC both use. Splitting it into five components would fragment the shared waiting-state, heading and error rows for no benefit.
- **D-07 resolution:** the panel adopts Phase 35's conventions in full — a `.panel` with no `border` rule, a 12px/700 `.panelHeading` reading `Goal Kick`, 11px/400 `.constraintRow` rows, the `"Confirm"` verb on both end-window CTAs, and the verbatim `"{Attacking|Defending} team is repositioning…"` waiting string on the three repositioning-shaped phases. The two adaptations, both grounded in existing analogs: `GOAL_KICK_CHOICE` uses a keeper-choice waiting string rather than a repositioning one (matching the existing `GK_RESTART` panel's `"Keeper is choosing how to restart play…"`), and `GOAL_KICK_TARGET` renders no CTA at all because the target is a pitch click (matching the existing `GK_KICK_TARGET` panel).
- **UI-SPEC copy locks honoured verbatim:** the choice buttons read exactly `Kick` and `Standard Pass`; the soft end-turn guard reads `"{N} players left to reposition, are you sure you want to end your turn?"` with `Cancel` / `Yes, end turn`.
- **D-08 resolution:** reposition-window and travel-window destination hexes reuse the existing `safe` tint automatically, because `HexGrid`'s `isHighlighted` derivation already routes any populated `validMoveHexes` through it for phases outside the `GK_DIVE` / `SNAPSHOT_DEFLECT` / header-target exclusion list. Target-selection hexes reuse the existing `'gk-kick-target'` `HexHighlightType` — the exact existing semantic ("hexes this keeper may kick to"). No new `HexHighlightType` member, no `HexCell.tsx` edit, no `docs/HIGHLIGHT-REFERENCE.md` edit.
- **No `ActionPanel` change.** After the `standard` choice the state is `phase: 'PASS'` with `lastActionType: 'GOAL_KICK_RESTART'`, whose `ELIGIBLE_NEXT_ACTIONS` row (Plan 37-02) already contains only `STANDARD_PASS` — so the existing `ActionPanel` renders exactly one correct button with zero edits. Adding goal-kick-specific copy there would create a second source of truth for which actions are legal; do not add one.
- **Spacing (UI-SPEC):** `gap: 4px` and `padding: 4px 8px`. The legacy 3px / `4px 6px` values in `FreeKickSetupPanel.module.css` are explicitly forbidden in new components.
