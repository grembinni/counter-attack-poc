<objective>
Close the one BLOCKER gap in `37-VERIFICATION.md` (= CR-01 in `37-REVIEW.md`): stale throw-in tracking state (`throwInHex` / `throwInTeam` / `throwInPhasesTaken`) survives a tackle or steal that ends a throw-in Movement Phase early, and can then resurrect on a later, unrelated Movement Phase — corrupting that team's `ELIGIBLE_NEXT_ACTIONS` (silently dropping `SNAPSHOT` / `SHOT` / `LONG_BALL`, and after a second phase locking `MOVEMENT` out entirely) and surfacing a stale "Throw-In!" prompt in `ActionPanel.tsx`.

Output: a single shared `THROW_IN_TEARDOWN` literal applied at every break-in-play early return in `applyMove`, a narrowed `throwInStillValid` guard in `applyEndTurn` that no longer depends on enumerating turnover call sites, new unit coverage for all three early returns, an end-to-end regression test for the exact reachable sequence documented in `37-REVIEW.md`, and a REQUIREMENTS.md traceability sync.

## Decisions locked by this plan

- **D-11-01 — Both halves of the CR-01 fix are applied, not one or the other.** `37-REVIEW.md` offers a minimum fix (clear the fields on the two early returns) and a more robust alternative (stop inferring "throw-in in progress" from `carrier.teamId === state.throwInTeam`). Both are implemented here. The teardown alone leaves the unsound inference in place for any future early return; the narrowed guard alone leaves genuinely stale fields on the state where a later reader could trip over them. Together the invariant holds even if a future edit adds a fourth early return.
- **D-11-02 — No new `GameState` field.** An explicit `throwInInProgress` boolean would need clearing at exactly the same call sites the bug is about, so it would not be more robust. Instead the guard is narrowed against `state.lastActionType`, which every turnover path already overwrites unconditionally (`'SUCCESSFUL_TACKLE'` on tackle/steal success, `'DEFLECTION'` on a defending-team pickup) and which `applyStartMovement` deliberately preserves across a Movement-Phase start (verified: `applyStartMovement`'s returned literal does not set `lastActionType`, so `...state` carries it).
- **D-11-03 — The narrowing clause is NOT paired to `throwInPhasesTaken`.** The clause accepts `lastActionType === null` (set by `applyThrowInPlace` when Movement Phase 1 starts) **or** `lastActionType === 'THROW_IN_MOVEMENT_1'` (preserved by `applyStartMovement` when Movement Phase 2 starts), without requiring `null` to pair with `0` and `'THROW_IN_MOVEMENT_1'` to pair with `1`. A strict pairwise rule would invalidate the pre-existing, legitimately-passing unit test at `gameEngine.outOfBounds.test.ts:582` (`{ ...throwInMoveEndState, throwInPhasesTaken: 1 }` leaves `lastActionType` at `null`). The non-pairwise form still blocks every turnover marker, which is the whole failure mode.
- **D-11-04 — The third early return is included.** `applyMove`'s defending-team loose-ball-pickup return (`phase: 'PASS'`, `lastActionType: 'DEFLECTION'`) is the same class of break-in-play early return and is also missing the teardown. It is currently unreachable during a throw-in Movement Phase (the thrower holds the ball, so `ball.carrierId` is never `null` there), so it is defensive — but it costs one line and removes the need to reason about reachability again later.

## Deliberately NOT done in this plan

- **IN-01 (`resolveThrowInHex`'s last-resort fallback can return an occupied hex)** is deferred, not forgotten. `37-REVIEW.md` rates it Info and states "No action required for v1 given the practical unreachability" — exhausting a radius-6 disk (~127 candidate hexes) on a 37x26 pitch holding 22 pieces cannot happen in the current 1v1 game. Widening the radius or changing the return type would alter working fallback logic with no reachable defect to fix. Revisit only if piece count or pitch size changes; the review records the concrete follow-up options.
