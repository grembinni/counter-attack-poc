<objective>
Close the single remaining open gap in `37-UAT.md` (test 6, severity minor): _"partial pass. It does highlight the target hex but it should display the same white radius hexes as a header for the response move."_

Plan 37-18 shipped `HeaderTargetRing`, the gold bullseye at `goalKickTargetHex` — the tester confirms that part works. What is still missing is the white, selection-independent radius of hexes around it. That radius already exists in this codebase: `highPassContestZoneSet` in `HexGrid.tsx` (lines 234-245) highlights the landing hex plus every pitch hex within 2 of it, feeding `isShotPathActionTint` (line 489) and `isShotPathTint` (line 502). It is gated exclusively on `phase === 'HIGH_PASS_MOVE'`.

`GOAL_KICK_MOVE` is the structural twin of `HIGH_PASS_MOVE`: both are single-piece-per-team response-move windows that resolve directly into a `HEADER` contest, and `applyGoalKickMoveEnd`'s doc comment says so verbatim — _"with an eligible header contest enters HEADER (copying the HIGH_PASS -> HEADER eligibility check verbatim)"_ (`gameEngine.ts:3910`). It never got the equivalent branch.

Plan 37-18 explicitly deferred this work under "Deliberately NOT done", reasoning that _"adding a second range overlay is unrequested scope and would collide with those tints."_ Both halves of that reasoning turned out to be wrong, and the debug session (`.planning/debug/goal-kick-header-response-move-radius-missing.md`) records why: it is not a second overlay (the first one already exists and simply needs its phase condition widened), and it does not collide (the tint precedence between the contest zone and the green `safe` valid-move tint is already defined and shipped — see D-19-04).

The green per-piece `safe` highlight the 37-18 author was thinking of is a different, already-working mechanism: it appears only after a piece is clicked and shows one adjacent hex at a time (`GOAL_KICK_MOVE_CONFIG`, `clickDistanceMode: 'strict-1'`). It is not what the tester is asking for and is not touched by this plan.

Purpose: this is the last unclosed item in Phase 37. Phase 38's corner kick has the same "both teams move one player into a contest" window and will inherit the generalised set for free rather than adding a third copy.

Output: `highPassContestZoneSet` generalised into a phase-driven `headerContestZoneSet`, tests covering both phases and the negative cases, and a `HIGHLIGHT-REFERENCE.md` note recording the gate.
</objective>

## Decisions locked by this plan

- **D-19-01 — Generalise the existing set; do not add a parallel one.** Rename `highPassContestZoneSet` to `headerContestZoneSet` and derive its centre from the phase. A parallel `goalKickContestZoneSet` would need its own arm in both `isShotPathActionTint` and `isShotPathTint`, doubling the surface where the two phases could drift apart. One set, one centre variable, two unchanged consumption sites. The name change is safe: `grep -rn 'highPassContestZoneSet' packages/*/src docs` returns hits in `HexGrid.tsx` only — no test, no doc and no other module references it.

- **D-19-02 — The radius stays 2, and 2 is not negotiable.** It is the server's header-eligibility predicate, not a pace budget. `applyGoalKickMoveEnd` computes `homeEligible`/`awayEligible` as `hexDistance(p.position, targetHex) <= 2` (`gameEngine.ts:3997-4002`), copied verbatim from the HIGH_PASS branch. Do not "improve" this to 3 to match `GOAL_KICK_MOVE_CONFIG`'s `paceCap: 3` — a 3-hex preview would advertise a contest the server refuses to award, which is a worse bug than the one being fixed. (`HIGH_PASS_MOVE_CONFIG` also carries `paceCap: 3` against a radius of 2, confirming the two numbers are unrelated.)

- **D-19-03 — Centre the GOAL_KICK_MOVE radius on `goalKickTargetHex`, not on `ball.position`.** The two are equal today — `applyGoalKickTarget` sets `ball.position` and `goalKickTargetHex` to the same hex on entry (`gameEngine.ts:3866-3872`) — but the server's eligibility check reads `state.goalKickTargetHex`, so that is the field the preview must mirror. It also degrades safely: a null target yields an empty set rather than a radius drawn around a stale ball. The selector already exists at `HexGrid.tsx:142` (added by 37-18) — no new selector, no new Zustand subscription. HIGH_PASS_MOVE keeps `ball.position` unchanged.

- **D-19-04 — Accept that an in-zone valid-move destination renders white (`shot-path-action`) rather than green (`safe`).** `isShotPathActionTint` sits above `isSafeTint` in `HexGrid`'s single tint ternary (lines 537-561), so a hex that is both inside the radius and a valid destination for the selected piece takes the brighter white. This is not a collision and not a regression — it is precisely what `HIGH_PASS_MOVE` has done since the Bug 1 fix, and it is the intended affordance: brighter white means "step here and you are in the contest". Reproducing HIGH_PASS_MOVE's behaviour exactly is the whole point of the gap.

- **D-19-05 — Both teams, no `isActivePlayer` gate.** The existing HIGH_PASS_MOVE branch has no `isActivePlayer` condition, GOALKICK-05 gives each team its own response move, and `HeaderTargetRing` is already ungated per D-18-03. A preview only the kicking side could see would leave the defending manager aiming blind — the exact complaint that opened this gap.

- **D-19-06 — Exactly two phases qualify: HIGH_PASS_MOVE and GOAL_KICK_MOVE.** The gate is "response-move windows that resolve into a HEADER contest", not "response-move windows". `GK_KICK_MOVE` looks like a twin (same `paceCap: 3`, same `clickDistanceMode: 'strict-1'`, same KICKER/OPP slot shape) but its accurate branch transitions to `PASS` with the receiver catching the ball (`gameHandlers.ts:993-1005`) — there is no header, so no contest zone. `FIRST_TIME_PASS_MOVE` likewise delivers. Both must stay untinted, and a test pins each.

## Deliberately NOT done in this plan

- **Any change to the green per-piece `safe` valid-move highlight.** `canSelectGoalKickMove` (`HexGrid.tsx:746-753`), `selectPiece`'s `GOAL_KICK_MOVE` branch and `GOAL_KICK_MOVE_CONFIG` are all correct and covered by passing tests (`useGameStore.test.ts:613-621`). The debug session eliminated this mechanism as the cause. Do not touch it.
- **Any change to `HeaderTargetRing`.** The gold bullseye passed UAT. The white radius renders underneath it as a hex tint; the bullseye is an always-on-top overlay. They compose without either being modified.
- **Extracting the radius `2` into a shared constant across `packages/shared`.** It is currently written three times (twice in `gameEngine.ts`, once in `HexGrid.tsx`). Consolidating it is a genuine improvement but touches the server and shared packages for a client-only minor UAT gap; log it as a follow-up rather than growing this plan.
- **Any server-side change whatsoever.** This gap is entirely a client render gate. `packages/server` and `packages/shared` are untouched and are run only as regression checks.
