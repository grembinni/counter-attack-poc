### Gaps Summary

Both items flagged by the prior verification round are now closed and independently re-confirmed: CR-01 (the stale throw-in-tracking blocker, closed by plan 37-11 with 11 new regression tests and a full 772/772 server-suite pass) and the WR-01/WR-02 warnings (closed by plan 37-12). Three of the four roadmap success criteria — continuous last-toucher tracking (#1), the throw-in flow including its interrupt-safety (#2), and the disabled-toggle preservation guarantee (#4) — are fully verified with solid, tested implementations.

However, a fresh code review performed after gap closure (`37-REVIEW.md`, dated after 37-11/37-12) surfaced a new, previously-unreported BLOCKER inside the goal-kick reposition mechanism (success criterion #3 / requirement GOALKICK-02): `applyGoalKickReposition` and its `GAME_MOVE` handler branch validate adjacency, occupancy, and payload shape, but never validate that the destination hex is actually on the pitch — a check every sibling repositioning path in this same feature family (`applyGoalKickTarget`, `validateResponseMoveStep`, the client's own `PITCH_HEXES` filter) does enforce. This verification independently confirmed the finding by direct code read of both files (no `isPitchHex` call anywhere in `applyGoalKickReposition`'s body or its handler branch, despite `isPitchHex` being imported and used elsewhere in both files), confirmed the goal kick's own eligibility rule (`homeThird`/`awayThird`, i.e. `q<=10` or `q>=26`) places boundary-column pieces — a normal goalkeeper/defender position, not a contrived edge case — one adjacent-hex click from an off-grid coordinate, and confirmed no existing test exercises this path (the suite's one `OFF_PITCH` rejection test targets a different function, `GAME_GOAL_KICK_TARGET`).

This is not a hypothetical or purely defensive-coding concern: a piece placed off-grid this way has no recovery path (every subsequent click is still "adjacent to current position," so the piece can be walked arbitrarily far off-grid within its own 6-hex budget), stays there for the rest of the match, silently corrupts offside/ZoI/every geometry-based rule, and disappears from the rendered pitch. Because this is a hole in the exact reposition mechanism GOALKICK-02 requires ("both final-thirds reposition up to 6 hexes each... goalkeeper's team first"), and is reachable by any non-compliant client (the server has zero independent defense — the compliant client's own hex-filtering is the only thing currently preventing this in normal play), it blocks a clean pass for success criterion #3 under the same standard the prior verification round applied to CR-01.

**Recommended next step:** add the `isPitchHex(to)` guard to both `applyGoalKickReposition` (gameEngine.ts) and its `GAME_MOVE` handler branch (gameHandlers.ts) — both files already import `isPitchHex`, and the fix mirrors the existing `applyGoalKickTarget` pattern exactly — plus a regression test mirroring the existing `GAME_GOAL_KICK_TARGET` off-pitch test, scoped to the reposition branch. This is a small, well-scoped, single-root-cause fix (same shape as CR-01's gap closure), not a design change.
