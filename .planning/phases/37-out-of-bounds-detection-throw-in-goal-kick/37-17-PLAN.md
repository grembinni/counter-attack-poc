Close a confirmed client-flow regression from `37-UAT.md`.

Test 10 (MINOR, but a confirmed regression unique to this phase) — "selecting standard pass takes to new prompt to select standard pass, should not have to select twice before taking the action." `ELIGIBLE_NEXT_ACTIONS.GOAL_KICK_RESTART` is the singleton set `{ STANDARD_PASS }` (`packages/shared/src/actionSequence.ts:114`). Note: an earlier draft of this plan also bundled a rewording of the throw-in step-choice screen's "Movement Phase" copy, sourced from a UAT gap (Test 4) whose attribution to the user turned out to be uncertain on review. That copy change has been dropped from this plan at the user's request — this plan now closes only the confirmed Test 10 regression, plus the Back-button cleanup that Test 10's own fix requires (see below).

Purpose: `ELIGIBLE_NEXT_ACTIONS.GOAL_KICK_RESTART`'s singleton set makes the goal-kick Standard Pass path feel broken today. Fixing the singleton case generically also pre-empts the same complaint for Phase 38's corner kick, which will add another narrow restart row to `ELIGIBLE_NEXT_ACTIONS`.

Output: a generic singleton auto-selection in the store gated to the acting client, and a Back button suppressed where there is nothing to go back to.

## Decisions locked by this plan

- **D-17-01 — The auto-selection is generic over singleton pass-type sets, not special-cased to `GOAL_KICK_RESTART`.** `ELIGIBLE_NEXT_ACTIONS` already encodes "how many choices does the player actually have"; a hardcoded `lastActionType === 'GOAL_KICK_RESTART'` check would duplicate that knowledge in a second place and would have to be edited again for Phase 38's corner-kick row. The rule is: exactly one eligible member, and that member is a pass type the Step-1 chooser would have rendered as a button.
- **D-17-02 — It lives in `useGameStore.setGameState`, not in an `ActionPanel` effect.** The Step-1 chooser sits behind several early `return`s inside `ActionPanel`'s render, so a hook there would have to be hoisted to the component top and re-derive state the store already owns. Doing it in the store also means any future panel that reads `selectedPassType` benefits automatically.
- **D-17-03 — It must call `setSelectedPassType`, never `set({ selectedPassType })` directly.** `setSelectedPassType` (`useGameStore.ts:~460-534`) does substantially more than assign the field: it computes `validPassTargetHexes` and `interceptionRiskHexes` and clears `passTargetHex`. Assigning the field directly would advance the UI to Step 2 with no clickable targets at all — a worse bug than the one being fixed.
- **D-17-04 — Gated to the acting client.** `setSelectedPassType` populates `validPassTargetHexes`, and `HexGrid`'s `isPassTargetTint` is not gated on `isActivePlayer` — so auto-selecting on both clients would paint the goalkeeper's pass options onto the defending player's board. The auto-selection must run only when `deriveMyTeam(playerSlot)` equals the incoming `activeTeam`, using the same null-safe helper every other branch in this store uses (D-04/Pitfall 4).
- **D-17-05 — Suppress the Step-2 Back button when the eligible set is a singleton.** Step 2's Back button calls `setSelectedPassType(null)`, which would drop the player straight back into the one-button Step 1 the fix exists to remove. With one option there is nothing to go back _to_, so the button is not rendered in that case. Where two or more options exist it is unchanged.

## Deliberately NOT done in this plan

- **Any rewording of the throw-in step-choice screen's "Movement Phase" copy.** This was in an earlier draft of this plan, sourced from `37-UAT.md`'s Test 4 gap. On review, the user was not confident they had actually reported that gap — its text appeared in the session transcript in a way that was not clearly attributable to a genuine user message. Rather than ship a copy change built on an uncertain report, it is dropped entirely. If the user does want the throw-in step-choice copy changed, that should come in as a fresh, explicitly-confirmed request.
- **Auto-advancing non-pass singleton actions** (e.g. a future row eligible only for `MOVEMENT` or only for `SHOT`). Those route through `emitStartMovement` / `setShootingMode`, which have side effects beyond selection state; auto-firing them would take an irreversible action without a click. Only pass-type selection — which is purely local UI state and reversible until a target is confirmed — is auto-advanced.
- **The header-target ring for `GOAL_KICK_MOVE`** (`37-UAT.md` Test 11) — owned by `37-18-PLAN.md`, which runs in the same wave against a disjoint file set.
