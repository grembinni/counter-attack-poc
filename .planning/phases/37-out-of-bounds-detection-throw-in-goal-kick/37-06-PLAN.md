<objective>
Deliver the throw itself: cap it at 6 hexes, keep Low and High on the existing unmodified Standard-Pass and High-Pass-to-Header mechanics, clear the throw-in context on delivery, and prove via socket-level integration tests that an overthrown throw is reclassified by the same detection system (THROWIN-01, THROWIN-04, THROWIN-05, D-04).

THROWIN-05/D-04 needs no branch at all: an inaccurate throw already routes through the `LOOSE_BALL` site that Plan 37-04 made out-of-bounds-aware, which is exactly what "the same detection system" means.

Output: the 6-hex cap and context clearing in the `GAME_ROLL` pass branch, plus `throwIn.integration.test.ts` (a Wave-0 gap from `37-VALIDATION.md`).

## Decisions locked by this plan

- **Context clears at throw commit, not at delivery.** `throwInHex` / `throwInTeam` / `throwInPhasesTaken` are nulled the moment the throw passes validation and `lastActionType` is committed — before the HIGH_PASS repositioning detour and before the accuracy roll. Rationale: the throw has been taken, so the throw-in is over; and an inaccurate throw must be able to establish a _fresh_ throw-in context via the out-of-bounds hook without colliding with the old one (D-04).
- **No `isPitchHex` widening of `validatePass`.** Per RESEARCH.md Assumption A4, the shared validator stays unchanged; the throw target gets its pitch-boundary guard in the handler layer only.
