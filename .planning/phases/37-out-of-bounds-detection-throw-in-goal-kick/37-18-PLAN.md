<objective>
Close the Test 11 gap in `37-UAT.md` — "after select player to target with kick, header ring should be visible to guide single player response move from each team."

No header-target highlight was ever designed for the `GOAL_KICK_MOVE` travel window. `applyGoalKickTarget` correctly sets both `ball.position` and `goalKickTargetHex` when entering the phase, and `goalKickTargetHex` is a live `GameState` field — but no client component reads it. The only thing rendering at that hex today is `BallLocationRing`, the generic white ball marker shared across seventeen response phases; `37-10-PLAN.md` scoped its `HexGrid` highlight work to target _selection_ (`GOAL_KICK_TARGET`) and the acting piece's own destination tint, and never added anything anchored at `goalKickTargetHex` once the travel window opens.

GOALKICK-05 requires that "both teams may each move one player up to 3 hexes" while the kicked ball travels, and that "the receiver must attempt a header". Without a visible contest point, neither manager can aim that one move — which is precisely what the tester reported.

The same gap entry also records `docs/HIGHLIGHT-REFERENCE.md` as stale: it documents `BALL_MARKER_PHASES` as an "exact 11-phase list" and enumerates eleven phases, but the code has carried seventeen since Plan 37-02 added the six Phase-37 restart phases. The document declares itself the single source of truth for every highlight colour (HILITE-05), so leaving it wrong makes the next highlight change start from a false premise.

Purpose: this is the last unclosed rendering gap in the goal-kick flow, and Phase 38's corner kick will need the same "here is where the contest happens" affordance — building it as a standalone overlay component now means Phase 38 reuses it rather than reinventing it.

Output: a `HeaderTargetRing` component with tests, wired as a topmost SVG sibling in `HexGrid`, plus a corrected and extended `HIGHLIGHT-REFERENCE.md`.
</objective>

## Decisions locked by this plan

- **D-18-01 — A standalone always-on-top overlay, not a new `HexHighlightType`.** `HIGHLIGHT-REFERENCE.md` section 1 states at most one `highlightType` renders per hex, and that hex will frequently also be a valid response-move destination or a `gk-kick-target`. A tint would therefore be silently out-prioritised by `HexGrid`'s single tint ternary exactly when it matters most. `BallLocationRing` is the established precedent for "must never be hidden or out-prioritised" (section 3), and the new marker follows it verbatim in structure and placement.
- **D-18-02 — Gold, and shaped as a bullseye.** The marker shares its hex with `BallLocationRing`'s white outline during this phase (the ball sits at `goalKickTargetHex`), so it must be distinguishable at a glance from that white edge, from the green `header-target`/`safe`/`pass-target` family, from the blue `gk-kick-target`, and from the red offside ring which the document reserves exclusively for offside. Gold (`#f5c518`) is the documented "confirmation / required-action ring accent" and is the correct semantic: the target is the confirmed kick destination and the required contest point. To keep it distinct from `RING_STYLES.confirmed`'s single solid gold hex edge, the marker draws two concentric gold hex outlines — an outer one slightly larger than the hex and an inner one at roughly half scale — reading unmistakably as a target rather than a selection ring.
- **D-18-03 — Both teams see it, ungated by `isActivePlayer`.** GOALKICK-05 gives each team one response move; a marker only the kicking side could see would leave the defending manager guessing. This also matches `BallLocationRing`, which is ungated.
- **D-18-04 — `pointerEvents="none"`, exactly as `BallLocationRing` does it.** The marker is drawn on top of `HexCell` polygons and `PieceOverlay`; without this, it would swallow clicks on the very hex a manager is trying to move toward.
- **D-18-05 — Phase gating lives inside the component, not at the call site.** `BallLocationRing` owns its own `BALL_MARKER_PHASES` gate and returns `null` when it does not apply. `HeaderTargetRing` mirrors that: it takes `phase` and a nullable `targetHex` and returns `null` unless the phase is `GOAL_KICK_MOVE` and the target is non-null. This keeps `HexGrid`'s already-dense render free of one more conditional and keeps the gate testable in isolation.
- **D-18-06 — The doc fix corrects the existing `BALL_MARKER_PHASES` list rather than adding a note beside it.** The stale text names an "exact 11-phase list" and enumerates eleven phases while the code carries seventeen. A document that claims to be the single source of truth must be corrected in place, with the count and the enumeration both matched to `BallLocationRing.tsx`'s actual `BALL_MARKER_PHASES` at the time of the edit.

## Deliberately NOT done in this plan

- **A 3-hex reachability highlight for the travel window.** The gap asks for a marker at the contest point; `HexGrid` already tints the acting piece's own valid destinations once it is selected. Adding a second range overlay is unrequested scope and would collide with those tints.
- **Any change to `BallLocationRing.tsx` itself.** `GOAL_KICK_MOVE` is already in `BALL_MARKER_PHASES` and the white marker is correct there — the gap is the absence of a _purpose-built_ marker alongside it, not a defect in the generic one. Only that component's test file is touched, to pin the phase-list count the doc now asserts.
- **The `GOAL_KICK_TARGET` selection step.** It already highlights eligible teammates via the `gk-kick-target` tint (`HexGrid.tsx:523`), which `37-10` verified. This plan covers only the window _after_ the target is chosen.
- **Auditing the other sixteen `BALL_MARKER_PHASES` entries against the doc's prose claims.** The correction is scoped to making the count and enumeration match the code; the per-phase rationale prose stays as written.
