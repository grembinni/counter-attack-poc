Close three UAT gaps that share one root cause: `HexGrid.tsx`'s `pitch-clip` clipPath geometry does not match `axialToPixel`'s ODD-Q stagger, so whole rows of in-bounds hexes are removed from the rendered (and hit-tested) pitch.

The three symptoms, all from `37-UAT.md`:

1. Test 2 (BLOCKER) — "the throw in player disapears when selected and is never returned to the game." The thrower is placed correctly server-side; it lands on a boundary-row hex that the clip erases.
2. Test 3 (MAJOR) — "20,0 is not being treated as out of bounds, (even, 0) is out of bounds." Every even-q `r=0` hex renders at 0% visibility, so the tester's on-screen model of the pitch edge disagrees with the rules engine.
3. Test 7 (MAJOR) — "(even, 26) should be out of bounds." `r=26` does not exist (`MAX_R=25`); the perceived inconsistency is the odd-q `r=25` row rendering at ~50% visibility along the bottom edge.

It also removes the largest contributor to the Test 8 BLOCKER ("several coordinates give errors when clicked"): a clipped hex is an unclickable hex, because SVG `clip-path` clips pointer hit-testing exactly as it clips painting.

Until the rendered boundary and the rules boundary agree, no throw-in, goal-kick or corner-kick (Phase 38) restart at a pitch edge can be trusted or UAT-verified.

## The geometry, worked out

All values below use `HEX_SIZE = 20` and `SQRT3 = Math.sqrt(3)`, so one row pitch is `HEX_SIZE * SQRT3 = 34.6410161514` and one flat-top hex's half-height is `HEX_SIZE * SQRT3 / 2 = 17.3205080757` (the 60°/120° corners sit at `cy ± HEX_SIZE * sin(60°)`, and `sin(60°) = SQRT3/2`).

`axialToPixel` (`hexToPixel.ts:24-25`) gives `cy = HEX_SIZE * SQRT3 * (r + 0.5 * (q % 2))`. So:

| Row            | centre `cy` | hex spans `cy ± 17.3205` | visible under today's clip |
| -------------- | ----------- | ------------------------ | -------------------------- |
| even-q, `r=0`  | 0           | −17.3205 … 17.3205       | **0%** (entirely above)    |
| odd-q, `r=0`   | 17.3205     | 0 … 34.6410              | ~50% (top half cut)        |
| even-q, `r=25` | 866.0254    | 848.7049 … 883.3459      | 100%                       |
| odd-q, `r=25`  | 883.3459    | 866.0254 … 900.6664      | ~50% (bottom half cut)     |

Today's clip rect is `y = CLIP_Y = 17.3205080757`, `height = CLIP_H = HEX_SIZE * SQRT3 * 25 = 866.0254`, i.e. the band `[17.3205, 883.3459]`. The comment above those constants (`HexGrid.tsx:32-33`) asserts "odd-q r=0 top-flat at line → full" and "odd-q r=24 bot-flat at line → full" — both claims are wrong; the code has never matched its own stated intent.

The clipPath is referenced by a `<g>` nested inside `<g transform="translate(20, 17.3205)">`, so its coordinates are LOCAL post-translate values (this is a locked project decision in `STATE.md`; do not re-add the translate offset). `PitchMarkings.tsx` shares that same local space and hardcodes the same `17.3`/`883.3` literals for its outline — which is why the outline currently looks like a correct straight-edged pitch while silently sitting half a row inside the true hex extent.

## Decisions locked by this plan

- **D-14-01 — The clip rectangle and the pitch outline must be driven by one exported constant.** Today the same two magic numbers are duplicated across `HexGrid.tsx` (2 constants) and `PitchMarkings.tsx` (11 separate `y` literals across endlines, touchlines, halfway line, final-third ticks and corner arcs). Any fix that edits one and not the other produces an outline that cuts through in-bounds hexes. `PITCH_CLIP` lives in `hexToPixel.ts` because that module already owns `axialToPixel`, `hexPolygonPoints` and `computeViewBox` — the entire pixel-space contract — and is already imported by both consumers.
- **D-14-02 — The horizontal clip is NOT changed.** `CLIP_X = −10` / `CLIP_RIGHT = 1090` trim only the 180°/0° vertex tips of the `q=0` and `q=36` columns (the hex centres are at local `x = 0` and `x = 1080`, and the tips extend to `−20` and `1100`). No hex is removed and no hex centre is unreachable, so the goal-net framing this produces is preserved verbatim. The defect is purely vertical.
- **D-14-03 — `PITCH_CLIP` is computed from `HEX_SIZE`/`SQRT3` expressions, never from decimal literals.** The current bug is a hand-computed literal that drifted from the formula it was supposed to encode. Every field of `PITCH_CLIP` must be an arithmetic expression in `HEX_SIZE` so a future `HEX_SIZE` change cannot reintroduce the mismatch.
- **D-14-04 — The boundary model itself (Option A vs Option B) is the user's decision, not the planner's.** Both options fully close all three symptoms. They differ in what the pitch _is_, which is a game-rule question the source artifacts do not answer: `.planning/STATE.md` still lists "Board layout … Difficult-angle hexes approximated; TODO: verify against `docs/board-photo.jpg` when available (D-06)" as an open blocking dependency, and the UAT reporter asserted twice that the staggered half-row hexes should be out of bounds. Task 1 puts the decision to the user.
- **D-14-05 — No `PieceOverlay` / `BallMarker` / `BallLocationRing` change.** All three render inside the clipped `<g>`, so they inherit the fix automatically. The "disappearing thrower" needs no component-level change once the clip is correct.
