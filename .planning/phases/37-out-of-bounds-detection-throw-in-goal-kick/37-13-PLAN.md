## Decisions locked by this plan

- **D-13-01 — Both layers get the guard, not one.** `37-VERIFICATION.md` lists two artifacts with the same root cause. The engine guard is the authoritative one (`applyGoalKickReposition` is called from exactly one handler today, but it is exported and reachable from tests and any future caller). The handler guard is what produces the correct `OFF_PITCH` wire code and stops the coordinate one layer earlier. Neither alone is sufficient: engine-only leaves the wire code as the vague `MOVE_INVALID`; handler-only leaves the exported engine function unguarded for its next caller.
- **D-13-02 — Engine returns `MOVE_INVALID` + `detail: 'OFF_PITCH'`; the handler emits the bare string `OFF_PITCH`.** `ApplyMoveResult`'s failure branch (`gameEngine.ts:653-657`) types `reason` as `'WRONG_SLOT' | 'WRONG_TEAM' | 'PIECE_NOT_FOUND' | 'MOVE_INVALID' | 'WRONG_PHASE'` with a free-form `detail?: string`. Widening that union to add `'OFF_PITCH'` would ripple through every `applyMove` consumer for no benefit, so the engine follows the established `MOVE_INVALID` + `detail` idiom used by all six of its sibling rejections. Because the handler emits `result.reason` and never `result.detail` (documented in the pre-existing comment at `goalKick.integration.test.ts:615-618`), the handler must own the `OFF_PITCH` wire code itself — exactly as the THROWIN-04 off-pitch guard already does at `gameHandlers.ts:1546-1552`.
- **D-13-03 — Guard placement: after adjacency, before occupancy.** Adjacency stays first so a far-away off-pitch coordinate still returns the pre-existing `OUT_OF_RANGE` (no existing unit test changes meaning). `OFF_PITCH` precedes `OCCUPIED` because no piece can ever stand on an off-pitch hex, so the two can never both apply — the ordering is observationally unambiguous and every pre-existing rejection keeps its exact precedence.
- **D-13-04 — Handler ordering: payload-shape check strictly first.** `isPitchHex` dereferences `hex.q` / `hex.r` (`pitch.ts:195-197`), so calling it on the `null`/non-object payloads the existing shape check rejects would throw inside the handler rather than emit a clean `GAME_ERROR`. The new guard goes immediately after the existing `typeof to.q === 'number'` block (`gameHandlers.ts:665-674`) and immediately before the `applyGoalKickReposition` call at line 675.
- **D-13-05 — No client change.** `37-VERIFICATION.md`'s claim that the compliant client already filters through `PITCH_HEXES` was independently re-confirmed during planning: `computeFreeMoveValidHexes` (`packages/client/src/store/useGameStore.ts:406-419`) filters on `PITCH_HEXES.some(...)` at line 412, and both the `selectPiece` goal-kick branch (~line 696) and the sticky-selection branch (~line 1065) route through it. There is nothing to fix client-side.
- **D-13-06 — No `.planning/REQUIREMENTS.md` edit.** `GOALKICK-02` already reads `[x]` at line 61 and `| GOALKICK-02 | Phase 37 | Complete |` at line 142. `37-VERIFICATION.md` correctly calls that checkbox stale _today_; this plan lands the fix that makes it accurate.
