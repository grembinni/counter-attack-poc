The goal-kick defect is a design error, not a coding slip. `triggerOutOfBoundsRestart`'s `GOAL_KICK` branch (`packages/server/src/gameEngine.ts:3265-3304`) sets `ball.position` and the `OUT_OF_BOUNDS` event's `ballAfter` to `gk.position` — the goalkeeper's _live_ position — exactly as `37-04-PLAN.md:109` instructed. ## The restart-hex coordinate, and why it needs confirming

The UAT report asks for "34,13 or 4, 13". Those two are not mirrors of each other: the board's away mirror is `q_away = 36 - q_home` (`packages/shared/src/formations.ts:23,38`), so `34` mirrors `2`, and `4` mirrors `32`. One of the two numbers is a slip.

`34` matches the away mirror of the goalkeeper's formation-default slot exactly: every one of the four formations places `GK` at `{ q: 2, r: 13 }` (`formations.ts:46, 62, 78, 94`), mirroring to `{ q: 34, r: 13 }`. `r: 13` is the byline centre in both cases (`homeGoal` is `q=0, r∈[10,16]`, so `r=13` is its midpoint — `packages/shared/src/pitch.ts:51-52,68-69`).

This plan therefore implements `{ q: 2, r: 13 }` / `{ q: 34, r: 13 }` — mirror-symmetric, byline-centred, and already the canonical goalkeeper hex in the codebase — and puts the value behind a single exported constant so changing it is a one-line edit. Task 4's checkpoint asks the user to confirm the exact hex before the plan is considered closed.

## Decisions locked by this plan

- **D-15-01 — The restart hex is a named exported constant, not an inline literal.** It is a game rule value the user may want to tune (see above), it is needed in two places (ball position and GK position) and will be needed again by Phase 38's corner kick for its own fixed restart coordinates. A single `GOAL_KICK_RESTART_HEX` record keyed by `'home' | 'away'` makes both the tuning edit and the mirror-symmetry check one-line operations.
- **D-15-02 — It lives in `packages/shared/src/outOfBounds.ts`, not `pitch.ts`.** `outOfBounds.ts` is already the restart-classification module (`classifyExit`, `bylineOwner`, `classifyOutOfBounds`, `resolveThrowInHex`) and already imports `isPitchHex` and the hex helpers this needs. `pitch.ts` owns board _geometry_, not restart _rules_, and is additionally owned by `37-14-PLAN.md` under its Option B branch.
- **D-15-03 — Occupancy is resolved with the existing `resolveThrowInHex`, not a new helper.** That function (`outOfBounds.ts:106-134`) is already the project's tested "nearest free on-pitch hex, deterministic tie-break by ascending q then r" primitive, and the throw-in restart already depends on it. Call it with the piece list _excluding the goalkeeper being placed_, so the keeper's own current position never counts as blocking its own destination. Do not add a second nearest-free-hex implementation.
- **D-15-04 — Both the ball and the goalkeeper piece move.** Today only `ball.position` is written. Leaving the keeper behind would make `ball.carrierId = gk.id` point at a piece standing somewhere else, which every downstream `hexDistance` rule (pass range, ZoI, the kick accuracy check) would read as a carrier separated from its own ball. The `OUT_OF_BOUNDS` event's `ballAfter.position` must be updated to match.
- **D-15-05 — `computeGoalKickEligibleIds` is called with the post-placement piece list.** It is invoked in the same return object that repositions the keeper (`gameEngine.ts:3288`). It currently receives `state.pieces` — the pre-move list. Once the keeper actually moves, the eligible-list computation must see the moved keeper, or the two states disagree from the first frame of the reposition window.
- **D-15-06 — `T-37-66` gets the same two-layer treatment `37-13` gave the goal-kick branch.** Engine guard returns `MOVE_INVALID` + `detail: 'OFF_PITCH'` (the `ApplyMoveResult.reason` union stays unwidened); handler guard emits the precise `OFF_PITCH` wire code. The handler additionally gains the payload-shape check the goal-kick branch has and the free-move branch lacks, placed strictly before `isPitchHex`, because `isPitchHex` dereferences `.q`/`.r` and is not null-safe.

## Deliberately NOT done in this plan

- **Auto-clearing defenders out of the penalty box during the goal-kick reposition windows** (`37-UAT.md`, Test 8, MAJOR). Its own diagnosis concludes it is "not a bug — a missing/never-specified feature": GOALKICK-02 says final-thirds players _may_ reposition, and no decision anywhere in Phase 37 mentions forced relocation. Implementing it would require inventing the target hex, the tie-breaking, and its interaction with the 6-hex budget. It needs a new requirement (GOALKICK-02a) first and is flagged back to the user rather than guessed at here.
- **Any change to `GK_RESTART`/`GK_KICK_TARGET`/`GK_KICK_MOVE`.** Those are the catch/save restart chain; GOALKICK-01 deliberately keeps the goal kick separate from them.
- **Undo/replay handling for the new keeper reposition.** The `OUT_OF_BOUNDS` event already exists and already carries `ballAfter`; this plan corrects its payload but adds no new `ActionEventType`, so the `isBoundary` / `REPLAY_ELIGIBLE_TYPES` / `ELIGIBLE_NEXT_ACTIONS` checklist that `STATE.md` warns about is not triggered. Task 2 must confirm that in the SUMMARY rather than assume it.
