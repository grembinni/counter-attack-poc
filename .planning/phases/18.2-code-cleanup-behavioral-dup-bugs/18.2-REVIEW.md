## Summary

This is a fresh, full-scope re-review of phase 18.2's final state, now including gap-closure plan 18.2-06 (the `useGameStore.test.ts` fixture-discrimination fix for "Test 7"). I verified the plan 06 fix directly: `snapshotDeflectState()` (lines 385-395) now sets `movementSlot: null`, which forces the pre-fix fallthrough path (`computeMovementValidHexes` → `validateMove`'s `WRONG_SLOT` guard) to genuinely fail, making Test 6/Test 7 actually discriminating between the fixed and unfixed `setGameState` SNAPSHOT_DEFLECT sticky-selection branch (lines 758-777 of `useGameStore.ts`). All 80 client tests and 24 server tests (gameEngine.phase10 + gameHandlers.phase18-02) pass; both packages typecheck and lint cleanly.

No new Critical/BLOCKER-tier defects were found. All Warning/Info findings from the prior review round (after gap-closure plan 05) were re-verified line-by-line against the current code and remain accurate; they are restated below since this is a full re-review rather than a delta. One new Info-tier finding is added: three of the four response-move test fixtures in `useGameStore.test.ts` (`highPassMoveState`, `firstTimePassMoveState`, `gkKickMoveState`) still inherit a stale, production-impossible `movementSlot: 'ATTACKER_4'` from `mockMovementState` — the exact same fixture-hygiene defect class that gap-closure plan 06 just fixed for `snapshotDeflectState`. I traced this carefully: it is currently inert (not a live test-discrimination gap) because `setGameState`'s sticky block for these three phases (lines 707-748) branches purely on `newState.phase`, never reading `movementSlot` — unlike the `SNAPSHOT_DEFLECT` fallthrough that plan 06 fixed, which _did_ depend on it transitively through `validateMove`. But the latent risk is real: if a future refactor folds one of these three phases' sticky-selection logic through any `movementSlot`-sensitive path (as already happened once, for SNAPSHOT_DEFLECT), the stale fixtures would silently stop discriminating, exactly as Test 7 did pre-plan-06.

No injection, XSS, hardcoded-secret, or other security-classed issues were found in any of the 9 files. This remains server-authoritative game logic plus a presentational React component; every client-side guard mirrored in `useGameStore.ts`/`HexGrid.tsx` is consistently re-validated server-side in `gameHandlers.ts`/`gameEngine.ts` (e.g. `validateResponseMoveStep`'s carrier-exclusion, lock, pace-cap, distance, pitch-boundary, and occupancy guards all re-run server-side regardless of what the client claims, confirmed by `gameHandlers.phase18-02.test.ts`'s BUG-11 WRONG_PIECE rejection test).

## Warnings

### WR-01: `validateHeading`'s rejection reasons (`OUT_OF_RANGE`, `CONSECUTIVE_HEADER`) are silently discarded by both `gameEngine.ts` call sites, and no caller enforces the >2-hex header range rule

**File:** `packages/server/src/gameEngine.ts:2148-2152, 2852-2856`; `packages/server/src/gameHandlers.ts:2444-2451`; `packages/shared/src/headingValidator.ts:61-86`
**Issue:**
`validateHeading` documents (headingValidator.ts:5-6) that a challenger more than 2 hexes from the ball is `OUT_OF_RANGE` and should be rejected, and that two consecutive headed passes are disallowed (`CONSECUTIVE_HEADER`). Both production call sites in `gameEngine.ts` use the result only to compute a dice penalty:

```ts
const headResult = validateHeading(state, attackerPiece, state.ball.position, {
  previousActionWasHeadedPass: false,
  otherChallengerIds: [defenderPiece.id],
});
const penaltyMod = headResult.ok && headResult.contested ? headResult.penaltyModifier : 0;
```

When `headResult.ok` is `false` (i.e. the challenger is `OUT_OF_RANGE`), this expression evaluates to `penaltyMod = 0` — the same value as a fully-valid, in-range, uncontested header. The rejection is never surfaced; the contest proceeds as if nothing were wrong. `previousActionWasHeadedPass` is hardcoded to `false` at both call sites, so `CONSECUTIVE_HEADER` (HEAD-04) can never fire through this path either, making that branch of the validator permanently dead code from the engine's perspective.

This would be a self-correcting non-issue if a distance check happened upstream (at contestant nomination time), but `GAME_HEADER_CONTESTANT` (`gameHandlers.ts:2424-2451`, re-verified this round) only validates piece ownership (`piece.teamId !== teamSlot`) — there is no `hexDistance(piece.position, ball.position) <= 2` check anywhere in the nomination path. A player can nominate any of their own pieces, anywhere on the pitch, as a header contestant, and it will roll a full, unpenalized header duel.

**Fix:** Either (a) reject `OUT_OF_RANGE` contestants at `GAME_HEADER_CONTESTANT` time (filter `ids` through `hexDistance(piece.position, state.ball.position) <= 2` before accepting the nomination, emitting `INVALID_CONTESTANT` for any that fail), or (b) if out-of-range nomination is intentionally permissive in this ruleset, remove the now-misleading `OUT_OF_RANGE` reason from `validateHeading` and the dead `previousActionWasHeadedPass` plumbing, and document explicitly that range is UX-only.

### WR-02: `ResponseMoveValidHexConfig.lockedPieceIdField` (client) is declared but never read by `computeResponseMoveValidHexes`

**File:** `packages/client/src/store/useGameStore.ts:196-216, 224-244`
**Issue:** The `ResponseMoveValidHexConfig` type declares `lockedPieceIdField`, and every call site (lines 493-498, 565-570, 587-592, 615-620, and the `setGameState` sticky-block call at 763-768) populates it, but `computeResponseMoveValidHexes`'s body (lines 224-244) never reads `config.lockedPieceIdField` — every caller independently re-implements the lock check (`lockedId !== null && lockedId !== id`) before invoking the helper. The field is dead configuration: it documents intent but has no runtime effect inside the function it's passed to. Contrast with the server-side equivalent (`gameHandlers.ts`'s `ResponseMoveConfig.lockedPieceIdKey`, line 156), which IS read inside `validateResponseMoveStep` (line 228) — confirming this is a real client/server asymmetry, not a stylistic choice. A future maintainer could reasonably assume the client helper enforces the lock and skip the caller-side check, silently reintroducing a bypass — the same class of mistake that produced the SNAPSHOT_DEFLECT sticky-selection gap fixed in gap-closure plans 05/06, where one of several near-identical call sites was missed.
**Fix:** Either have `computeResponseMoveValidHexes` enforce the lock itself (returning `[]` early when `gameState[config.lockedPieceIdField]` is set to something other than `id`), removing the now-duplicated caller-side guard at all 5 call sites, or remove the unused field from the type and tighten the doc comment to state explicitly that lock-checking is the caller's responsibility.

### WR-03: `FREE_MOVE_ATTACK`/`FREE_MOVE_DEFENSE` sticky-selection geometry is duplicated a third time instead of sharing a helper

**File:** `packages/client/src/store/useGameStore.ts:525-534, 789-799`
**Issue:** `selectPiece`'s `FREE_MOVE_ATTACK`/`FREE_MOVE_DEFENSE` branch (lines 506-537) and `setGameState`'s parallel sticky block for the same phases (lines 784-808) both inline the identical adjacency/occupancy/pitch-boundary filter (`hexesInRange(...).filter(...)` with three checks: pitch membership, occupancy excluding self, `hexDistance === 1`), byte-for-byte, rather than sharing a helper analogous to `computeMovementValidHexes`. Both copies are currently behaviorally consistent (both use `hexDistance === 1`, matching `applyFreeMove`'s server-side single-step enforcement), so this is not a live bug today — but it is the exact "behavioral dup" pattern this phase's title calls out, and duplicated-but-currently-consistent logic in this codebase has already produced one real, shipped bug (the SNAPSHOT_DEFLECT gap, fixed across plans 05/06) when one of N copies was missed during a refactor.
**Fix:** Extract a `computeFreeMoveValidHexes(id, piece, gameState)` helper analogous to `computeMovementValidHexes`, used by both `selectPiece` and `setGameState`.

### WR-04: `validateResponseMoveStep`'s `NOT_ADJACENT` error reason is misleading for `'range'`-mode phases

**File:** `packages/server/src/gameHandlers.ts:237-246`
**Issue:** The shared guard sequence uses the single error reason `'NOT_ADJACENT'` for two structurally different failures:

```ts
const clickDistance = hexDistance(piece.position, to);
if (config.clickDistanceMode === 'strict-1') {
  if (clickDistance !== 1) {
    return fail('NOT_ADJACENT');
  }
} else {
  if (clickDistance < 1 || clickDistance > paceRemaining) {
    return fail('NOT_ADJACENT');
  }
}
```

For `'strict-1'` phases (`HIGH_PASS_MOVE`, `GK_KICK_MOVE`, `FIRST_TIME_PASS_MOVE`) "not adjacent" is an accurate description. For `'range'`-mode `SNAPSHOT_DEFLECT`, a click 3 hexes away when only 2 hexes of pace remain is rejected with the same `'NOT_ADJACENT'` reason, which is inaccurate — the destination may well be adjacent-or-closer in the geometric sense but still exceed the remaining pace budget. No client code currently branches on the literal string (verified again this round — no match in `packages/client`), so this is not a live bug, but it will confuse anyone debugging a `GAME_ERROR` log or adding client-side error-specific UX later.
**Fix:** Split into two reasons (e.g. keep `'NOT_ADJACENT'` for `'strict-1'`, add a `'PACE_EXCEEDED'`-style or new `'OUT_OF_RANGE'` reason for `'range'` mode), or rename the single shared reason to something mode-agnostic like `'INVALID_DISTANCE'`.

## Info

### IN-01: Shot-path deflection threshold formula is hand-duplicated in 4 places with no shared constant

**File:** `packages/server/src/gameEngine.ts:3098-3115` (`computeShotPathDeflection`); `packages/server/src/gameHandlers.ts:910-913` (SNAPSHOT_DEFLECT end-turn inline loop) and `:1525-1528` (GAME_SHOT inline loop); `packages/client/src/components/ActionLog.tsx:295` (`hasBonus`, Set A only, used for display text)
**Issue:** The same deflection-threshold predicate (`die === 5 || die === 6 || die + tackling >= 10` for Set A; `die === 6 || die + tackling >= 10` for Set B) is implemented four separate times across three files. `gameHandlers.ts`'s two inline loops re-derive `didDeflect` per defender using the exact formula immediately before calling `computeShotPathDeflection(...)` — the canonical helper that already encodes this formula and is imported into the same file — solely to build per-defender `DEFLECT_ATTEMPT` log events (one event per defender, with an early `break` after the first deflection), since `computeShotPathDeflection` only returns the single winning result. `ActionLog.tsx`'s `hasBonus` independently re-derives the Set A half of the same formula for display purposes. All four copies currently agree (re-verified this round), but nothing prevents future drift — a rules tweak to one copy requires remembering all four call sites.
**Fix:** Export a small `isDeflected(band: 'A' | 'B', die: number, tackling: number): boolean` helper from `gameEngine.ts` (or `packages/shared/src`, if it needs to be usable from `ActionLog.tsx` directly) and have all four sites call it instead of re-deriving the boolean inline.

### IN-02: `validateHeading`'s `excludedPieceIds` (HEAD-05) is computed but never consumed by either production caller, and a structurally near-identical "goal-line redirect" is implemented twice

**File:** `packages/shared/src/headingValidator.ts:84`; `packages/server/src/gameEngine.ts:2148-2156, 2161, 2852-2864, 2960-3061`
**Issue:** `validateHeading`'s contested-result branch builds `excludedPieceIds: string[] = [challenger.id, ...otherIds]` specifically so "the Phase 4 FSM can enforce the 'player who headed cannot head again this sequence' rule" (per the function's own doc comment, HEAD-05). Both production call sites in `gameEngine.ts` destructure only `headResult.penaltyModifier` from the result and never read `headResult.excludedPieceIds`. The actual HEAD-05-equivalent exclusion in the engine is implemented via a separately-derived `contestedIds = [...attackerContestantIds, ...defenderContestantIds]` (gameEngine.ts:2161, written to `state.contestedPieceIds` and checked by `applyMove`'s `CONTESTED_PIECE` guard) — a parallel mechanism that happens to achieve a similar effect through different code, rather than consuming the validator's own purpose-built output.

Relatedly, the same "goal-line header → GK_DIVE" redirect logic (HEAD-03) exists in two places: inline inside `applyRoll`'s legacy contested-HEADER branch (gameEngine.ts:2144-2244, only reachable when `headerDuelWinner` is `undefined`) and in `applyResolveHeaderTarget` (gameEngine.ts:2960-3061, the live production path reached via `GAME_HEADER_TARGET` after `GAME_HEADER_CONTESTANT` sets `headerDuelWinner`). I traced the handler guard at `gameHandlers.ts:1368-1372` (`DUEL_ALREADY_RESOLVED` rejection once `headerDuelWinner !== undefined`) and confirmed the `applyRoll` inline branch is in practice unreachable from the live `GAME_ROLL` socket path once a duel has been contested via the two-step contestant/target flow — it survives only as a direct-unit-test-callable code path (exercised by `gameEngine.phase10.test.ts`'s D-21/D-23/HEAD-03 describe blocks), per the engine's own comment at gameEngine.ts:2215-2219. This is the same "two independent implementations of the same rule" pattern the phase exists to clean up, just with more surface area (full phase-transition logic, not just a penalty calculation) than the originally-flagged `excludedPieceIds` gap.
**Fix:** Either wire `headResult.excludedPieceIds` into the `contestedPieceIds` assignment (replacing the separately-derived `contestedIds`), or remove `excludedPieceIds` from `HeadingResult`'s contested variant and update the doc comment. Separately, consider whether the `applyRoll` legacy contested-HEADER branch can be deleted now that the two-step `GAME_HEADER_CONTESTANT`/`GAME_HEADER_TARGET` flow is the only live path, with its test coverage migrated to exercise `applyResolveHeaderTarget` directly instead.

### IN-03: `pieceColorOf`/`pieceName`/`slotTeamColor` read `useGameStore.getState()` directly inside render-path helper functions

**File:** `packages/client/src/components/ActionLog.tsx:9-38`
**Issue:** These module-level helpers call `useGameStore.getState()` synchronously rather than receiving `selectedTeams`/`pieces`/`attackingTeam` as parameters. This is a one-time read, not a subscription, and `ActionLog`'s component body separately subscribes to `gameState.eventLog` and `gameState.selectedTeams` (lines 738-740) to force a re-render when either changes — currently consistent, not a bug. It is a fragile pattern, though: any new field these helpers start depending on must be manually added to the component's subscription list, or the log will silently render stale data on a state change that doesn't touch `eventLog`/`selectedTeams`.
**Fix:** No functional change required; add a comment near line 738 enumerating exactly which module-level helpers' inputs are covered by these two subscriptions, so future additions to `pieceColorOf`/`pieceName`/`slotTeamColor` are reminded to update the subscription list too.

### IN-04: Pace-cap magic numbers (`1`, `2`, `3`, `6`) are duplicated across client and server with no shared constant

**File:** `packages/client/src/store/useGameStore.ts:496, 568, 590, 618, 520, 766, 798` (FREE*MOVE: 525, 533, 785, 798); `packages/server/src/gameHandlers.ts:403, 443, 474, 514`
**Issue:** The pace caps for each response-move phase (`HIGH_PASS_MOVE`=3, `FIRST_TIME_PASS_MOVE`=1, `GK_KICK_MOVE`=3, `SNAPSHOT_DEFLECT`=2, `FREE_MOVE*\*`=6) are repeated as literal numbers in both `useGameStore.ts`'s `ResponseMoveValidHexConfig`/inline-filter call sites and `gameHandlers.ts`'s `ResponseMoveConfig`call sites, with no shared constant tying them together. They currently agree, but nothing enforces that — a rules change to one of these caps requires remembering to update both files (plus`useGameStore.test.ts`'s and `HexGrid.test.tsx`'s hardcoded expectations), and a mismatch would silently let the client display the wrong valid-move set without any compile-time or runtime signal.
**Fix:** Define the per-phase pace caps once in `packages/shared/src`(e.g.`RESPONSE_MOVE_PACE_CAPS`) and import on both sides.

### IN-05: Three of four response-move test fixtures in `useGameStore.test.ts` still carry the stale `movementSlot: 'ATTACKER_4'` that gap-closure plan 06 just removed from the fourth

**File:** `packages/client/src/store/useGameStore.test.ts:341-355` (`highPassMoveState`), `:357-371` (`firstTimePassMoveState`), `:373-383` (`gkKickMoveState`)
**Issue:** Gap-closure plan 18.2-06 fixed `snapshotDeflectState()` (line 391) to explicitly set `movementSlot: null`, because the inherited `movementSlot: 'ATTACKER_4'` from `...mockMovementState` made "Test 7" (the SNAPSHOT_DEFLECT non-exhausted sticky-recompute regression guard) pass identically whether or not the production fix existed — the stale field caused the OLD buggy fallthrough path to accidentally produce the same result as the NEW fixed path. The three sibling factory functions for the other response-move phases — `highPassMoveState`, `firstTimePassMoveState`, and `gkKickMoveState` — were not touched by plan 06 and still inherit the same stale, production-impossible `movementSlot: 'ATTACKER_4'` (these phases are only ever entered from `phase === 'PASS'`, where `movementSlot` is always `null` in real play — confirmed by tracing `gameEngine.ts`'s `FIRST_TIME_PASS_MOVE`/`GK_KICK_MOVE` transition sites and `gameHandlers.ts`'s `HIGH_PASS_MOVE` transition site, none of which override `movementSlot` away from the `null` value already in effect during `PASS`).

I verified this is currently inert, not a live bug: `setGameState`'s sticky-selection block for `HIGH_PASS_MOVE`/`GK_KICK_MOVE`/`FIRST_TIME_PASS_MOVE` (useGameStore.ts:707-748) branches purely on `newState.phase`, never reads `movementSlot`, so the stale value has no effect on Test 1-5's outcomes. But this is exactly the same fixture-hygiene class of defect that just shipped one real bug (the SNAPSHOT_DEFLECT case, where the equivalent stale field DID matter because that phase's fallthrough routed through `movementSlot`-sensitive `validateMove`). If a future refactor moves any of these three phases' sticky-selection logic onto a shared `movementSlot`-sensitive path, these three fixtures would silently stop discriminating between fixed and broken behavior, the same way Test 7 did before plan 06.
**Fix:** Add `movementSlot: null` to `highPassMoveState`, `firstTimePassMoveState`, and `gkKickMoveState` (and audit the equivalent fixtures in `HexGrid.test.tsx` and `gameEngine.phase10.test.ts` for the same pattern, though `gameEngine.phase10.test.ts`'s `makeShotState`/`makeActionState`/`makeHeaderState` were already verified this round to correctly set `movementSlot: null`) so every response-move fixture matches the production-only-reachable state shape, removing the latent risk before any future refactor reintroduces a movementSlot-sensitive dependency.
