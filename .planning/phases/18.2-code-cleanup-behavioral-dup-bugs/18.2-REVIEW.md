# Phase 18.2: Code Review Report

**Reviewed:** 2026-06-22T11:09:38Z
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

This phase's stated goal is consolidating duplicated behavioral logic and fixing the bugs that duplication produced. The largest finding (CR-01) is exactly that class of defect surviving the consolidation: commit `fd98056` ("extract computeResponseMoveValidHexes + computeMovementValidHexes") built a shared, parameterized helper that every `selectPiece` response-move branch (including `SNAPSHOT_DEFLECT`) now calls, but the parallel `setGameState` sticky-selection block was deliberately left as the old hand-duplicated code ("per plan scope discipline," per the commit message) — and that old code has never supported `SNAPSHOT_DEFLECT` at all. The result: a defender who clicks a piece during `SNAPSHOT_DEFLECT` and moves it less than the full 2-hex budget loses their selection/highlight on the very next server broadcast, even though they still have pace remaining and the documented UX (a `computeResponseMoveValidHexes`-shared, single-click-any-distance "range" mode) says they should be able to continue moving the same piece. This is a live, reachable regression in the only game phase that still hand-duplicates this logic, and it was not caught by any test in this phase ("Test 5" in the BUG-09 suite covers the non-exhausted sticky case for `HIGH_PASS_MOVE` but the equivalent case for `SNAPSHOT_DEFLECT` is missing).

The remaining findings are smaller: an unreachable/dead `lockedPieceIdField` config field in the client helper, a subtle UI-text inconsistency in `ActionLog.tsx`'s deflection-bonus wording, and a few maintainability nits (duplicated sticky-block geometry for `FREE_MOVE_*`, an unused exported type field, and a magic-number duplication between client and server pace caps). No injection, XSS, or hardcoded-secret issues were found — this is server-authoritative game logic and a presentational React component; the attack surface here is narrow and the server-side `validateResponseMoveStep`/`applyFreeKickMove`/etc. guards consistently re-validate everything the client claims (good defense-in-depth pattern, consistently applied).

## Critical Issues

### CR-01: `setGameState` sticky-selection never recomputes valid hexes for `SNAPSHOT_DEFLECT`, clearing a live selection mid-budget

**File:** `packages/client/src/store/useGameStore.ts:637-790` (gap is the absence of a `SNAPSHOT_DEFLECT` branch between lines 707-748 and the fallthrough at 781-789)
**Issue:**
`selectPiece`'s `SNAPSHOT_DEFLECT` branch (lines 598-623) correctly calls the shared `computeResponseMoveValidHexes` helper with `clickDistanceMode: 'range'` and `paceCap: 2`, allowing a single click to consume 1 or 2 hexes of the defender's repositioning budget — mirroring the server's `validateResponseMoveStep` (`gameHandlers.ts:200-256`) which uses the identical `'range'` semantics for this phase.

However, `setGameState`'s sticky-selection block — which re-derives `validMoveHexes` for the still-selected piece after every server broadcast — only special-cases `HIGH_PASS_MOVE`, `GK_KICK_MOVE`, and `FIRST_TIME_PASS_MOVE` (the `if` at line 708-712), then has a separate parallel block for `FREE_MOVE_ATTACK`/`FREE_MOVE_DEFENSE` (line 755), and finally falls through to `computeMovementValidHexes(piece, newState)` (line 781) for everything else — including `SNAPSHOT_DEFLECT`.

`computeMovementValidHexes` (lines 173-189) calls `validateMove(gameState, piece, hex)` from `@counter-attack/shared`. `validateMove`'s very first guard (`moveValidator.ts:60`) is:

```ts
if (state.movementSlot === null) return { ok: false, reason: 'WRONG_SLOT' };
```

`SNAPSHOT_DEFLECT` is not part of the 4-5-2 movement sequence and never sets `movementSlot` (it stays `null` throughout), so every candidate hex is rejected with `WRONG_SLOT`, and `computeMovementValidHexes` always returns an empty `validMoveHexes` array for this phase.

Concrete reproduction: defender has 2 hexes of pace, clicks 1 hex away (using `'range'` mode to move 1 of 2 available hexes in one click). The server accepts the move and broadcasts the new state. `setGameState` runs: `responseMoveStateChanged` is `false` (no slot field for `SNAPSHOT_DEFLECT` exists to change), `responseMovePaceExhausted` is `false` (only 1 of 2 hexes used), `phaseChanged` is `false`, the piece still exists and is not in `movedPieceIds` — so the function reaches the sticky-recompute path, falls through every specific branch, and ends up calling `computeMovementValidHexes`, which silently returns `[]`. The piece stays "selected" (`selectedPieceId` is preserved) but renders with zero clickable destinations, even though 1 hex of budget remains and the UX contract (the `'range'` mode comment at line 610-614 of `useGameStore.ts`) explicitly says a single click should be able to use any remaining distance.

This was not introduced by this phase's consolidation commit (the gap pre-dates it — confirmed via `git show fd98056^`), but this phase's own commit message explicitly chose to leave it ("HP/GK_KICK/FTP sticky-selection block left untouched per plan scope discipline") while simultaneously building the exact shared helper (`computeResponseMoveValidHexes`) that would trivially fix it. Given the phase's mandate is "code cleanup, behavioral dup bugs," and the duplicate/divergent code remains live and reachable, this is in scope and should be fixed now rather than deferred again.

No test in this PR's test files (`useGameStore.test.ts`'s BUG-09 describe block, `HexGrid.test.tsx`) exercises the non-exhausted `SNAPSHOT_DEFLECT` sticky case — Test 6 only covers pace-exhaustion (which correctly clears via `responseMovePaceExhausted`), not the partial-budget case that this bug affects.

**Fix:** Add `SNAPSHOT_DEFLECT` to the response-move sticky block and route it through `computeResponseMoveValidHexes` (the same helper `selectPiece` already uses), e.g.:

```ts
// HIGH_PASS_MOVE / GK_KICK_MOVE / FIRST_TIME_PASS_MOVE / SNAPSHOT_DEFLECT: re-run
// phase-specific valid move logic via the shared helper.
if (
  newState.phase === 'HIGH_PASS_MOVE' ||
  newState.phase === 'GK_KICK_MOVE' ||
  newState.phase === 'FIRST_TIME_PASS_MOVE' ||
  newState.phase === 'SNAPSHOT_DEFLECT'
) {
  const config: ResponseMoveValidHexConfig =
    newState.phase === 'GK_KICK_MOVE'
      ? {
          lockedPieceIdField: 'gkKickMovedPieceId',
          paceUsedField: 'gkKickPaceUsed',
          paceCap: 3,
          clickDistanceMode: 'strict-1',
        }
      : newState.phase === 'FIRST_TIME_PASS_MOVE'
        ? {
            lockedPieceIdField: 'firstTimePassMovedPieceId',
            paceUsedField: 'firstTimePassPaceUsed',
            paceCap: 1,
            clickDistanceMode: 'strict-1',
          }
        : newState.phase === 'SNAPSHOT_DEFLECT'
          ? {
              lockedPieceIdField: 'snapDeflectMovedPieceId',
              paceUsedField: 'snapDeflectPaceUsed',
              paceCap: 2,
              clickDistanceMode: 'range',
            }
          : {
              lockedPieceIdField: 'highPassMovedPieceId',
              paceUsedField: 'highPassPaceUsed',
              paceCap: 3,
              clickDistanceMode: 'strict-1',
            };
  const stickyValid = computeResponseMoveValidHexes(prevSelectedId, piece, newState, config);
  set({
    gameState: newState,
    selectedPieceId: prevSelectedId,
    validMoveHexes: stickyValid,
    tackleRiskHexes: [],
    lastMovedPieceId: null,
  });
  return;
}
```

This both fixes the bug and removes the hand-duplicated inline filter logic (lines 713-739), which was the actual goal of this phase's consolidation work. Add a regression test mirroring `useGameStore.test.ts`'s existing "Test 5" pattern but for `SNAPSHOT_DEFLECT` with `snapDeflectPaceUsed: 1` (not yet exhausted) to lock this in.

## Warnings

### WR-01: `ResponseMoveValidHexConfig.lockedPieceIdField` is declared but never read by `computeResponseMoveValidHexes`

**File:** `packages/client/src/store/useGameStore.ts:196-216, 224-244`
**Issue:** The `ResponseMoveValidHexConfig` type declares `lockedPieceIdField` (lines 198-202) and every one of the 4 call sites (lines 493-498, 565-570, 587-592, 615-620) populates it. However, `computeResponseMoveValidHexes`'s body (lines 224-244) never reads `config.lockedPieceIdField` — the lock check is done by the caller before invoking the helper (e.g. lines 488-492 for `HIGH_PASS_MOVE`). The field is dead configuration: it documents intent but has no runtime effect inside the function it's passed to, which is misleading — a future maintainer could reasonably assume the helper enforces the lock and skip the caller-side check, silently reintroducing a bypass.
**Fix:** Either have `computeResponseMoveValidHexes` actually enforce the lock (returning `[]` early when `gameState[config.lockedPieceIdField]` is set to something other than `id`), removing the need for callers to duplicate that guard, or remove the unused field from the type and tighten the doc comment to state explicitly that lock-checking is the caller's responsibility.

### WR-02: `ActionLog.tsx`'s `[DEFLECT]` Tackling-bonus wording can render a self-contradicting line

**File:** `packages/client/src/components/ActionLog.tsx:290-312`
**Issue:** `hasBonus` is computed independently of `deflected`:

```ts
const hasBonus = event.band === 'A' && event.die < 5;
const rollStr = hasBonus
  ? `die ${event.die} + Tackling ${event.tackling} = ${event.die + event.tackling}`
  : `die ${event.die}`;
```

Per the server logic this mirrors (`gameHandlers.ts:910-913`, `gameEngine.ts:3111-3115`), Set A deflects when `die === 5 || die === 6 || die + tackling >= 10`. When `die < 5` and `deflected === true`, the deflection can ONLY have happened because `die + tackling >= 10` — so showing the `+ Tackling` term is correct and necessary there. But when `die < 5` and `deflected === false` (failed deflection, the common case), the line still renders `die X + Tackling Y = Z` even though the bare-die path (`die === 5/6`) was never relevant and the combined total didn't reach 10 — this is fine and not misleading on its own. The actual gap: when `event.band === 'A'` and `die >= 5` and the defender FAILS to deflect, this is impossible per the server's own deflection formula (die 5 or 6 always deflects on Set A), so `hasBonus` being `false` in that case is unreachable — not a bug, just dead branch coverage. Reclassifying: this is benign on inspection; no actual self-contradiction was found, only an asymmetry that's worth a comment for future maintainers since the formula is split across 3 files (`gameHandlers.ts`, `gameEngine.ts`, `ActionLog.tsx`) with no single shared constant.
**Fix:** Extract the Set A/B deflection-threshold predicate into a single shared helper in `packages/shared/src` (e.g. `computeDeflectionThreshold(band, die, tackling)`) and import it in all three places, so the three independent reimplementations (gameHandlers.ts, gameEngine.ts's `computeShotPathDeflection`, and ActionLog.tsx's `hasBonus`) cannot silently drift from each other in a future change.

### WR-03: `FREE_MOVE_ATTACK`/`FREE_MOVE_DEFENSE` sticky-selection geometry is duplicated a third time instead of using `computeResponseMoveValidHexes`

**File:** `packages/client/src/store/useGameStore.ts:525-534, 755-770`
**Issue:** `selectPiece`'s `FREE_MOVE_ATTACK`/`FREE_MOVE_DEFENSE` branch (lines 525-534) and `setGameState`'s parallel sticky block for the same phases (lines 755-770) both inline the identical adjacency/occupancy/pitch-boundary filter (`hexesInRange(...).filter(...)` with the same three checks), rather than sharing a helper. This is the same duplication pattern that `computeResponseMoveValidHexes`/`computeMovementValidHexes` were created to eliminate elsewhere in this same commit, but FREE_MOVE was explicitly left out ("Cluster 4... left untouched per plan scope discipline"). Unlike the `SNAPSHOT_DEFLECT` gap (CR-01), this duplication is currently behaviorally consistent in both copies (both use `hexDistance === 1`, matching `applyFreeMove`'s server-side single-step enforcement), so it's not a live bug — but it is the exact code smell this phase's title calls out, and the lack of a shared helper here means a future edit to one copy (e.g. extending FREE_MOVE to multi-hex single clicks) is likely to repeat the SNAPSHOT_DEFLECT mistake by only updating one of the two copies.
**Fix:** Extract a `computeFreeMoveValidHexes(id, piece, gameState)` helper analogous to `computeMovementValidHexes`, used by both `selectPiece` and `setGameState`.

## Info

### IN-01: `pieceColorOf`/`pieceName`/`slotTeamColor` read `useGameStore.getState()` directly inside render-path helper functions

**File:** `packages/client/src/components/ActionLog.tsx:9-38`
**Issue:** These module-level helpers call `useGameStore.getState()` synchronously rather than receiving `selectedTeams`/`pieces`/`attackingTeam` as parameters. The file's own comment (line 8) correctly notes this is "safe in module-level helpers" because it's a one-time read, not a subscription — and `ActionLog`'s component body does separately subscribe to `gameState.eventLog` and `gameState.selectedTeams` (lines 738-740) to force a re-render when either changes. This is consistent and not a bug, but it is a fragile pattern: any new field these helpers start depending on (e.g. if `pieceName` started reading something beyond `gameState.pieces`) must be manually added to the component's subscription list at lines 738-740, or the log will silently render stale data on the next state change that doesn't touch `eventLog`/`selectedTeams`. Worth a one-line comment at the helper definitions cross-referencing the subscription list, or consolidating to pass state down explicitly.
**Fix:** No functional change required; add a comment near line 738 enumerating exactly which module-level helpers' inputs are covered by these two subscriptions, so future additions to `pieceColorOf`/`pieceName`/`slotTeamColor` are reminded to update the subscription list too.

### IN-02: Pace-cap magic numbers (`1`, `2`, `3`, `6`) are duplicated across client and server with no shared constant

**File:** `packages/client/src/store/useGameStore.ts:496, 568, 590, 618, 520, 756`; `packages/server/src/gameHandlers.ts:403, 443, 474, 514`
**Issue:** The pace caps for each response-move phase (`HIGH_PASS_MOVE`=3, `FIRST_TIME_PASS_MOVE`=1, `GK_KICK_MOVE`=3, `SNAPSHOT_DEFLECT`=2, `FREE_MOVE_*`=6) are repeated as literal numbers in both `useGameStore.ts`'s `ResponseMoveValidHexConfig` call sites and `gameHandlers.ts`'s `ResponseMoveConfig` call sites, with no shared constant tying them together. They currently agree, but nothing enforces that — a rules change to one of these caps requires remembering to update both files (plus `useGameStore.test.ts`'s and `HexGrid.test.tsx`'s hardcoded expectations), and a mismatch would silently let the client display the wrong valid-move set without any compile-time or runtime signal.
**Fix:** Define the per-phase pace caps once in `packages/shared/src` (e.g. `RESPONSE_MOVE_PACE_CAPS`) and import on both sides.
