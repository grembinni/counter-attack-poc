# Phase 18.2: Code Review Report

**Reviewed:** 2026-06-22T00:00:00Z
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

This is a fresh, full-scope review of phase 18.2's final state, including gap-closure plan 18.2-05. The prior review's sole BLOCKER (CR-01: `setGameState`'s sticky-selection block never recomputed valid hexes for `SNAPSHOT_DEFLECT`, silently emptying `validMoveHexes` for a piece with pace remaining) has been verified fixed: `useGameStore.ts` now has a dedicated `SNAPSHOT_DEFLECT` branch (lines 758–777) that routes through `computeResponseMoveValidHexes` with `clickDistanceMode: 'range'`, mirroring `selectPiece`'s own `SNAPSHOT_DEFLECT` branch, and `useGameStore.test.ts`'s BUG-09 describe block now has a "Test 7" regression guard (lines 494–510) that would fail if this regressed. No remaining BLOCKER/Critical issues were found in this pass.

This review surfaces one new finding not previously flagged: `validateHeading` (the shared HEAD-01/HEAD-04/HEAD-05 validator in `headingValidator.ts`) is invoked twice in `gameEngine.ts` purely to extract `penaltyModifier` — both call sites discard the `ok: false` rejection reasons (`OUT_OF_RANGE`, `CONSECUTIVE_HEADER`) entirely, treating any non-`ok` or non-`contested` result identically to "no penalty, contest proceeds." Combined with the fact that the `GAME_HEADER_CONTESTANT` handler validates contestant ownership but never checks `hexDistance(piece.position, ball.position) <= 2`, a contestant nominated from anywhere on the pitch gets a full, unpenalized header roll — HEAD-01's distance-based range/penalty rule is only partially enforced (the -1 penalty at distance 2 fires correctly when reached, but the >2 rejection never does). This is flagged as a Warning rather than a Critical because it's a rules-fidelity gap in a v1 POC, not a crash, security issue, or data-loss risk, and no test in the reviewed files exercises an out-of-range header nomination either way.

The remaining findings carried forward from the prior review (WR-01 lock-field dead config, WR-02/now-IN dup'd deflection-threshold formula, WR-03 duplicated FREE_MOVE sticky-selection geometry, IN-01 module-level store reads, IN-02 magic-number pace caps) are all still present in the current code and are restated below for completeness, since this is a full re-review rather than a delta. No injection, XSS, hardcoded-secret, or other security-classed issues were found — this remains server-authoritative game logic plus a presentational React component, and every client-side guard mirrored in `useGameStore.ts`/`HexGrid.tsx` is consistently re-validated server-side in `gameHandlers.ts`/`gameEngine.ts` (e.g. `validateResponseMoveStep`'s carrier-exclusion, lock, pace-cap, distance, pitch-boundary, and occupancy guards all re-run regardless of what the client claims).

## Warnings

### WR-01: `validateHeading`'s rejection reasons (`OUT_OF_RANGE`, `CONSECUTIVE_HEADER`) are silently discarded by both `gameEngine.ts` call sites, and no caller enforces the >2-hex header range rule

**File:** `packages/server/src/gameEngine.ts:2148-2152, 2852-2856`; `packages/server/src/gameHandlers.ts:2444-2451`; `packages/shared/src/headingValidator.ts:61-86`
**Issue:**
`validateHeading` documents (headingValidator.ts:5-6) that a challenger more than 2 hexes from the ball is `OUT_OF_RANGE` and should be rejected, and that two consecutive headed passes are disallowed (`CONSECUTIVE_HEADER`). Both production call sites in `gameEngine.ts` use the result only to compute a dice penalty:

```ts
const headResult = validateHeading(state, attackerPiece, state.ball.position, {
  previousActionWasHeadedPass: false,
  otherChallengerIds: [defenderPiece.id],
});
const penaltyMod = headResult.ok && headResult.contested ? headResult.penaltyModifier : 0;
```

When `headResult.ok` is `false` (i.e. the challenger is `OUT_OF_RANGE`), this expression evaluates to `penaltyMod = 0` — the same value as a fully-valid, in-range, uncontested header. The rejection is never surfaced; the contest proceeds as if nothing were wrong. `previousActionWasHeadedPass` is hardcoded to `false` at both call sites, so `CONSECUTIVE_HEADER` (HEAD-04) can never fire through this path either, making that branch of the validator permanently dead code from the engine's perspective.

This would be a self-correcting non-issue if a distance check happened upstream (at contestant nomination time), but `GAME_HEADER_CONTESTANT` (`gameHandlers.ts:2424-2451`) only validates piece ownership (`piece.teamId !== teamSlot`) — there is no `hexDistance(piece.position, ball.position) <= 2` check anywhere in the nomination path. A player can nominate any of their own pieces, anywhere on the pitch, as a header contestant, and it will roll a full, unpenalized header duel.

**Fix:** Either (a) reject `OUT_OF_RANGE` contestants at `GAME_HEADER_CONTESTANT` time (filter `ids` through `hexDistance(piece.position, state.ball.position) <= 2` before accepting the nomination, emitting `INVALID_CONTESTANT` for any that fail), or (b) if out-of-range nomination is intentionally permissive in this ruleset, remove the now-misleading `OUT_OF_RANGE` reason from `validateHeading` and the dead `previousActionWasHeadedPass` plumbing, and document explicitly that range is UX-only (client should already filter `headerContestantIds` candidates by distance, but the server should not silently accept a result it never validates).

### WR-02: `ResponseMoveValidHexConfig.lockedPieceIdField` (client) is declared but never read by `computeResponseMoveValidHexes`

**File:** `packages/client/src/store/useGameStore.ts:196-216, 224-244`
**Issue:** The `ResponseMoveValidHexConfig` type declares `lockedPieceIdField` and every call site (lines 493-498, 565-570, 587-592, 615-620, and the new sticky-block call at 763-768) populates it, but `computeResponseMoveValidHexes`'s body never reads `config.lockedPieceIdField` — every caller independently re-implements the lock check (`lockedId !== null && lockedId !== id`) before invoking the helper. The field is dead configuration: it documents intent but has no runtime effect inside the function it's passed to. A future maintainer could reasonably assume the helper enforces the lock and skip the caller-side check, silently reintroducing a bypass — this is exactly the class of mistake the SNAPSHOT_DEFLECT sticky-selection gap (the prior review's CR-01, now fixed) fell into, where one of several near-identical call sites was missed.
**Fix:** Either have `computeResponseMoveValidHexes` enforce the lock itself (returning `[]` early when `gameState[config.lockedPieceIdField]` is set to something other than `id`), removing the now-duplicated caller-side guard at all 5 call sites, or remove the unused field from the type and tighten the doc comment to state explicitly that lock-checking is the caller's responsibility.

### WR-03: `FREE_MOVE_ATTACK`/`FREE_MOVE_DEFENSE` sticky-selection geometry is duplicated a third time instead of sharing a helper

**File:** `packages/client/src/store/useGameStore.ts:525-534, 784-799`
**Issue:** `selectPiece`'s `FREE_MOVE_ATTACK`/`FREE_MOVE_DEFENSE` branch and `setGameState`'s parallel sticky block for the same phases both inline the identical adjacency/occupancy/pitch-boundary filter (`hexesInRange(...).filter(...)` with three checks: pitch membership, occupancy excluding self, `hexDistance === 1`), rather than sharing a helper analogous to `computeMovementValidHexes`. Both copies are currently behaviorally consistent (both use `hexDistance === 1`, matching `applyFreeMove`'s server-side single-step enforcement), so this is not a live bug today — but it is the exact "behavioral dup" pattern this phase's title calls out, and per WR-02 above, duplicated-but-currently-consistent logic in this codebase has already produced one real, shipped bug (CR-01 in the prior review) when one of N copies was missed during a refactor.
**Fix:** Extract a `computeFreeMoveValidHexes(id, piece, gameState)` helper analogous to `computeMovementValidHexes`, used by both `selectPiece` and `setGameState`.

### WR-04: `validateResponseMoveStep`'s `NOT_ADJACENT` error reason is misleading for `'range'`-mode phases

**File:** `packages/server/src/gameHandlers.ts:237-246`
**Issue:** The shared guard sequence uses the single error reason `'NOT_ADJACENT'` for two structurally different failures:

```ts
const clickDistance = hexDistance(piece.position, to);
if (config.clickDistanceMode === 'strict-1') {
  if (clickDistance !== 1) {
    return fail('NOT_ADJACENT');
  }
} else {
  if (clickDistance < 1 || clickDistance > paceRemaining) {
    return fail('NOT_ADJACENT');
  }
}
```

For `'strict-1'` phases (`HIGH_PASS_MOVE`, `GK_KICK_MOVE`, `FIRST_TIME_PASS_MOVE`) "not adjacent" is an accurate description. For `'range'`-mode `SNAPSHOT_DEFLECT`, a click 3 hexes away when only 2 hexes of pace remain is rejected with the same `'NOT_ADJACENT'` reason, which is inaccurate — the destination may well be adjacent-or-closer in the geometric sense but still exceed the remaining pace budget (the real failure is "too far for remaining budget," not "not adjacent"). No client code currently branches on the literal string (verified — no match in `packages/client`), so this is not a live bug, but it will confuse anyone debugging a `GAME_ERROR` log or adding client-side error-specific UX later.
**Fix:** Split into two reasons (e.g. `'NOT_ADJACENT'` for `'strict-1'`, `'PACE_EXCEEDED'`-style or a new `'OUT_OF_RANGE'` for `'range'` mode), or rename the single shared reason to something mode-agnostic like `'INVALID_DISTANCE'`.

## Info

### IN-01: Shot-path deflection threshold formula (`die === 5 || die === 6 || die + tackling >= 10` for Set A; `die === 6 || die + tackling >= 10` for Set B) is hand-duplicated in 4 places with no shared constant

**File:** `packages/server/src/gameEngine.ts:3112-3115` (`computeShotPathDeflection`); `packages/server/src/gameHandlers.ts:910-913` (SNAPSHOT_DEFLECT end-turn inline loop) and `:1525-1528` (GAME_SHOT inline loop); `packages/client/src/components/ActionLog.tsx:295` (`hasBonus`, Set A only, used for display text)
**Issue:** The same deflection-threshold predicate is implemented four separate times across three files. `gameHandlers.ts`'s two inline loops (lines 908-924 and 1523-1539) build a `deflectEvents`/`deflectEventsShot` array by re-deriving `didDeflect` per defender using the exact formula, immediately before calling `computeShotPathDeflection(snapDefInputs)`/`computeShotPathDeflection(defInputs)` — the canonical helper that already encodes this formula (gameEngine.ts:3108-3126) and is imported into the same file. The inline loops exist solely to build per-defender `DEFLECT_ATTEMPT` log events (one event per defender, with an early `break` after the first deflection) where `computeShotPathDeflection` only returns the single winning result — but the duplicated boolean expression itself, rather than a shared one-line helper call, is what's repeated. `ActionLog.tsx`'s `hasBonus` independently re-derives the Set A half of the same formula for display purposes. All four copies currently agree (verified during this review), but nothing prevents future drift — a rules tweak to one copy (e.g. raising the Set A bare-die threshold) requires remembering all four call sites.
**Fix:** Export a small `isDeflected(band: 'A' | 'B', die: number, tackling: number): boolean` helper from `gameEngine.ts` (or `packages/shared/src`, if it needs to be usable from `ActionLog.tsx` directly) and have all four sites call it instead of re-deriving the boolean inline.

### IN-02: `validateHeading`'s `excludedPieceIds` (HEAD-05) is computed but never consumed by either production caller

**File:** `packages/shared/src/headingValidator.ts:84`; `packages/server/src/gameEngine.ts:2148-2156, 2852-2864`
**Issue:** `validateHeading`'s contested-result branch builds `excludedPieceIds: string[] = [challenger.id, ...otherIds]` specifically so "the Phase 4 FSM can enforce the 'player who headed cannot head again this sequence' rule" (per the function's own doc comment, HEAD-05). Both production call sites in `gameEngine.ts` destructure only `headResult.penaltyModifier` from the result and never read `headResult.excludedPieceIds`. The actual HEAD-05-equivalent exclusion in the engine is implemented via a separately-derived `contestedIds = [...attackerContestantIds, ...defenderContestantIds]` (gameEngine.ts:2161, written to `state.contestedPieceIds` and checked by `applyMove`'s `CONTESTED_PIECE` guard) — a parallel mechanism that happens to achieve a similar effect through different code, rather than consuming the validator's own purpose-built output. This is the same "two independent implementations of the same rule" pattern this phase exists to clean up, just one level removed (the validator's documented contract vs. its actual integration).
**Fix:** Either wire `headResult.excludedPieceIds` into the `contestedPieceIds` assignment (replacing the separately-derived `contestedIds`, since they should be equivalent sets), or remove `excludedPieceIds` from `HeadingResult`'s contested variant and update the doc comment to stop claiming the FSM consumes it, since it currently doesn't.

### IN-03: `pieceColorOf`/`pieceName`/`slotTeamColor` read `useGameStore.getState()` directly inside render-path helper functions

**File:** `packages/client/src/components/ActionLog.tsx:9-38`
**Issue:** These module-level helpers call `useGameStore.getState()` synchronously rather than receiving `selectedTeams`/`pieces`/`attackingTeam` as parameters. This is a one-time read, not a subscription, and `ActionLog`'s component body separately subscribes to `gameState.eventLog` and `gameState.selectedTeams` (lines 738-740) to force a re-render when either changes — currently consistent, not a bug. It is a fragile pattern, though: any new field these helpers start depending on (e.g. if `pieceName` started reading something beyond `gameState.pieces`) must be manually added to the component's subscription list, or the log will silently render stale data on a state change that doesn't touch `eventLog`/`selectedTeams`.
**Fix:** No functional change required; add a comment near line 738 enumerating exactly which module-level helpers' inputs are covered by these two subscriptions, so future additions to `pieceColorOf`/`pieceName`/`slotTeamColor` are reminded to update the subscription list too.

### IN-04: Pace-cap magic numbers (`1`, `2`, `3`, `6`) are duplicated across client and server with no shared constant

**File:** `packages/client/src/store/useGameStore.ts:496, 568, 590, 618, 520, 766, 785`; `packages/server/src/gameHandlers.ts:403, 443, 474, 514`
**Issue:** The pace caps for each response-move phase (`HIGH_PASS_MOVE`=3, `FIRST_TIME_PASS_MOVE`=1, `GK_KICK_MOVE`=3, `SNAPSHOT_DEFLECT`=2, `FREE_MOVE_*`=6) are repeated as literal numbers in both `useGameStore.ts`'s `ResponseMoveValidHexConfig`/inline-filter call sites and `gameHandlers.ts`'s `ResponseMoveConfig` call sites, with no shared constant tying them together. They currently agree, but nothing enforces that — a rules change to one of these caps requires remembering to update both files (plus `useGameStore.test.ts`'s and `HexGrid.test.tsx`'s hardcoded expectations), and a mismatch would silently let the client display the wrong valid-move set without any compile-time or runtime signal.
**Fix:** Define the per-phase pace caps once in `packages/shared/src` (e.g. `RESPONSE_MOVE_PACE_CAPS`) and import on both sides.
