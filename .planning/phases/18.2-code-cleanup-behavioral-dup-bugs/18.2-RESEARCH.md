## Summary

This phase has two distinct workstreams that must be sequenced carefully: (1) a low-risk dead-code/duplicate-logic sweep (DESIGN-03/04) confined to genuinely inert code, and (2) three precise behavioral bug fixes (BUG-08, BUG-09, BUG-11) that follow established patterns already shipped elsewhere in the codebase. All three bugs are "duplicate-logic gaps" — each is a case where an existing, working pattern (carrier exclusion, slot-hand-off detection, ZoI tint filtering) was correctly implemented for one code path but never extended to a structurally identical sibling path. The fix for each bug is therefore a mechanical mirror of code that already exists and already works elsewhere in the same file.

Direct source inspection (not just CONTEXT.md's claims) was performed for every bug and every dead-code candidate, per the explicit lesson from Phase 18.1 (where a prior phase's research wrongly asserted `GK_KICK` was dead code, causing a real regression). Two important corrections to CONTEXT.md's assumptions surfaced during this verification: **BUG-11's "touch point 2"** (a delivery-occupant-lookup exclusion) does not exist as a code path for `HIGH_PASS_MOVE` — the HP flow never reaches a direct occupant-pickup branch, it always routes through `applyRoll`'s accuracy-check → HEADER/LOOSE_BALL transition, which explicitly skips the occupant-pickup logic for `HIGH_PASS` (`gameEngine.ts:1579`). And **BUG-08's described validator/tint-filter logic is already present and already correct** in the current codebase (commits `73a46cb`, `519c7cc`, `c69418b` from the 17.1-09 gap-closure cycle) — the bug-bash report may describe a symptom from before that fix landed, or a narrower edge case not yet covered by tests. The planner must treat BUG-08 as "verify with a fresh repro, then decide" rather than "known code defect, apply known fix."

**Primary recommendation:** Sequence the phase as (1) BUG-11 mechanical 2-touch-point fix (server reject + client mirror; drop the non-existent third touch point), (2) BUG-09 broadened `slotChanged`→multi-field staleness rewrite in `useGameStore.ts`, (3) BUG-08 fresh-repro verification followed by either "no code change, add regression test" or a scoped fix if a real gap is found, (4) DESIGN-03 duplicate-logic consolidation across the 4 structurally-identical response-move handler families, (5) DESIGN-04 dead-code removal limited to the 3 confirmed-zero-callsite candidates found below. Run the bug fixes (and their regression tests) before the cleanup pass, since DESIGN-03's consolidation will touch the exact same files BUG-09/BUG-11 modify — fixing behavior first avoids consolidating a confirmed-buggy pattern into a shared helper.

### Pattern 1: Carrier-Exclusion Lifecycle (BUG-11's template)

**What:** A "carrier id" field is set on `GameState` at the moment a pass transitions into its response-move sub-phase, consulted by the server's `GAME_MOVE` handler to reject the original passer's own piece from repositioning, mirrored (UX-only, non-authoritative) on the client, and cleared once the ball is delivered.

**When to use:** Any response-move phase where the player who triggered the sub-phase (the passer/kicker) must not be allowed to reposition onto/reclaim their own pass target.

**Example (already shipped for FIRST_TIME_PASS_MOVE — `gameHandlers.ts:505-514`):**

```typescript
// Cycle-4 self-pass-reclaim finding (D-03, Phase 17.1-16): the original passer may
// not reposition their own piece during FTP repositioning — doing so would let them
// move onto the (empty) passTargetHex and have the delivery lookup hand the ball
// straight back to them. Mirrors how highPassCarrierId identifies the kicker; this is
// the authoritative server-side guard (the client selectPiece mirror is defense-in-depth).
if (pieceId === ftpState.firstTimePassCarrierId) {
  socket.emit(ServerEvents.GAME_ERROR, 'WRONG_PIECE');
  broadcastState(io, room);
  return;
}
```

**BUG-11 application:** Add the structurally identical block to the `HIGH_PASS_MOVE` branch of the `GAME_MOVE` handler (`gameHandlers.ts:280-343`), checking `pieceId === hpState.highPassCarrierId`, placed before the existing lock-check at line 295. Mirror identically in `useGameStore.ts`'s `selectPiece` `HIGH_PASS_MOVE` branch (the FTP mirror is at `useGameStore.ts:474-481`).

**IMPORTANT — touch point 2 does not transfer as literally described in CONTEXT.md.** FTP's "delivery occupant lookup excludes the passer" touch point (`gameHandlers.ts:758-767`) only exists because FTP's defender-slot completion directly looks up an occupant at `passTargetHex` and hands them the ball (`gameHandlers.ts:742-791`). **HIGH_PASS_MOVE has no equivalent code path.** Its defender-slot completion (`gameHandlers.ts:675-709`) restores `ball.carrierId` to `highPassCarrierId` and calls `applyRoll(stateForRoll, ...)`, which runs the HIGH_PASS accuracy check and then — confirmed at `gameEngine.ts:1579` (`if (newLastActionType !== 'HIGH_PASS')`) — explicitly **skips** the generic occupant-pickup branch for HIGH_PASS, routing instead to the HEADER/LOOSE_BALL transition (`gameEngine.ts:1614-1651`) with `ball.carrierId: null`. There is no occupant lookup to exclude the passer from, because HP never delivers the ball to an occupant directly — it always lands as a loose/contestable ball. **Touch point 1 (GAME_MOVE rejection) is BUG-11's real and only server-side gap; touch point 3 (clearing `highPassCarrierId: null` at delivery) is already implemented** (`gameHandlers.ts:695`, confirmed pre-existing). The planner should scope BUG-11 as 2 touch points (server GAME_MOVE rejection + client `selectPiece` mirror), not 3.

### Anti-Patterns to Avoid

- **Trusting a "dead code" / "already fixed" claim without grepping construction sites across all 3 packages (including test files):** This exact mistake caused a regression in Phase 18.1 (`GK_KICK` falsely declared dead code). Every dead-code and "already fixed" claim in this document was independently re-verified by direct source read and exhaustive grep before being included — the planner should hold execution to the same standard for any new claims that surface during implementation.
- **Building a templating/abstraction layer for the DESIGN-03 consolidation:** The 4 response-move phase handler families are similar but not identical (SNAPSHOT_DEFLECT allows multi-hex single clicks; the others are strict 1-hex-per-click). A shared _parameterized helper function_ (data-driven, like the existing `PHASE_LABEL`-style lookup pattern already used elsewhere in this codebase) is appropriate; a generic phase-handling framework is not — keep consolidation mechanical and narrow.

## Duplicate Logic Inventory (DESIGN-03)

Five confirmed duplication clusters, verified by direct read of all listed line ranges:

### Cluster 1 — Server `GAME_MOVE` response-move branches (`gameHandlers.ts`)

- `HIGH_PASS_MOVE` branch: lines 280-343 (64 lines)
- `GK_KICK_MOVE` branch: lines 423-486 (64 lines, near byte-identical to HIGH_PASS_MOVE except field names)
- `FIRST_TIME_PASS_MOVE` branch: lines 488-564 (77 lines — adds the carrier-exclusion guard, otherwise identical shape)
- `SNAPSHOT_DEFLECT` branch: lines 345-421 (77 lines — same shape, but allows multi-hex single-click distance instead of strict adjacency)

All four follow the identical sequence: active-player guard → piece-ownership guard → single-piece lock guard → pace-cap guard → distance guard → pitch-boundary guard → occupancy guard → state update. **Recommendation:** extract a shared helper (e.g. `validateResponseMoveStep(state, pieceId, to, config)`) parameterized by the per-phase field names (`lockedPieceIdKey`, `paceUsedKey`, `paceCapKey`, `movementSlotKey`, optional `carrierExclusionKey`) and the click-distance mode (strict-1 vs. range). Each of the 4 branches becomes a thin call into the shared helper plus its own state-merge shape.

### Cluster 2 — Server `GAME_END_TURN` response-move slot-transition branches (`gameHandlers.ts`)

- `HIGH_PASS_MOVE` slot-transition: lines 649-711
- `FIRST_TIME_PASS_MOVE` slot-transition: lines 713-798 (also handles delivery — more divergent than Cluster 1, lower-priority consolidation target)

These two share the ATTACKER→DEFENDER hand-off shape but diverge meaningfully at the defender-slot-complete step (HP rolls accuracy via `applyRoll`; FTP does a direct occupant delivery). Recommend extracting only the shared ATTACKER-slot transition logic (logging + slot/pace reset), not attempting to unify the divergent defender-slot completion logic — forcing that into one function would re-introduce the exact "treating different things as the same" risk this phase's BUG-11 investigation just uncovered for HP vs. FTP.

### Cluster 3 — Client `selectPiece` response-move branches (`useGameStore.ts`)

- `HIGH_PASS_MOVE` branch: lines 508-537 (mirrors GK_KICK_MOVE almost exactly)
- `GK_KICK_MOVE` branch: lines 508-537 region (confirmed near-identical to HIGH_PASS_MOVE — same own-team/lock/pace/adjacent-hex-compute shape)
- `FIRST_TIME_PASS_MOVE` branch: lines 462-506 (adds carrier exclusion, otherwise identical)
- `SNAPSHOT_DEFLECT` branch: lines 539-574 (same shape, range-based distance instead of strict adjacency)

**Recommendation:** extract a shared `computeResponseMoveValidHexes(piece, gameState, config)` helper used by all four branches, parameterized the same way as Cluster 1's server-side helper.

### Cluster 4 — Client `setGameState` sticky-selection branches (`useGameStore.ts`)

- Lines 643-684 (`HIGH_PASS_MOVE`/`GK_KICK_MOVE`/`FIRST_TIME_PASS_MOVE` combined ternary block — already partially consolidated into one conditional, but the embedded ternaries (`paceRemaining`, `lockedId`) duplicate the same per-phase field lookup logic that Cluster 3 needs) — natural candidate to share a lookup table with Cluster 3's extraction.
- Lines 686-715 (`FREE_MOVE_ATTACK`/`FREE_MOVE_DEFENSE` — intentionally separate per its own code comment at line 686-690, explaining why it is NOT folded into the block above; **do not merge this one** — the comment is correct and current).

### Cluster 5 — `validMoveHexes`/`tackleRiskHexes` derivation (`useGameStore.ts` lines 576-588 vs. lines 717-733)

The plain `MOVEMENT` phase's `selectPiece` valid-hex computation (lines 576-588) and `setGameState`'s plain-MOVEMENT sticky-selection recompute (lines 717-733) are byte-for-byte identical logic (map `hexesInRange` → `validateMove` → filter ok/effect-type). **Recommendation:** extract a shared `computeMovementValidHexes(piece, gameState)` helper — this is the most mechanical, lowest-risk extraction in the whole inventory since the two call sites are already provably identical (confirmed by direct read).

**Key insight:** None of these 5 clusters are accidental near-duplicates that merely look similar — they are intentional structural copies that have already drifted twice (FTP added carrier-exclusion that HP didn't get; SNAPSHOT_DEFLECT added range-click that the others didn't get). Consolidating them now, after the BUG-09/BUG-11 fixes land, prevents the next phase from re-discovering the same kind of "fixed in A, forgotten in B" gap a fourth time.

## BUG-09 Root Cause

**Confirmed via direct read of `packages/client/src/store/useGameStore.ts:595-637` (`setGameState`):**

```typescript
// Determine whether to retain or clear selection (D-17, D-18, D-19)
const slotChanged = newState.movementSlot !== prevState.movementSlot;
const phaseChanged = newState.phase !== prevState.phase;
const pieceStillExists =
  prevSelectedId !== null && newState.pieces.some((p) => p.id === prevSelectedId);
const activationComplete =
  prevSelectedId !== null && newState.movedPieceIds.includes(prevSelectedId);

if (
  slotChanged ||
  phaseChanged ||
  !pieceStillExists ||
  prevSelectedId === null ||
  activationComplete
) {
  // clears selection
}
```

`slotChanged` compares **only** `GameState.movementSlot`, the plain `MOVE`-phase 4-5-2 slot field. It does NOT compare `firstTimePassMovementSlot`, `highPassMovementSlot`, or `gkKickMovementSlot` — confirmed by grep: none of those three field names appear anywhere in `useGameStore.ts`. Likewise `activationComplete` checks only `movedPieceIds`, not any of the phase-specific pace-exhaustion fields (`firstTimePassPaceUsed`, `highPassPaceUsed`, `gkKickPaceUsed`, `snapDeflectPaceUsed`) or the phase-specific locked-piece fields (`firstTimePassMovedPieceId`, `highPassMovedPieceId`, `gkKickMovedPieceId`, `snapDeflectMovedPieceId`).

The separate `HIGH_PASS_MOVE`/`GK_KICK_MOVE`/`FIRST_TIME_PASS_MOVE` sticky-selection block (lines 643-684) does correctly recompute `validMoveHexes` based on `paceRemaining`/`lockedId` for those three phases when the selection is NOT cleared — but the outer clear-condition gate that decides _whether_ to enter that block (vs. the unconditional clear block above it) never fires for slot-only hand-offs or pace-exhaustion in those phases, because `slotChanged`/`activationComplete` don't see those fields. This means: when a piece's phase-specific pace is exhausted, or when an ATTACKER→DEFENDER hand-off happens within `HIGH_PASS_MOVE`/`FIRST_TIME_PASS_MOVE`/`GK_KICK_MOVE`, the selection survives into the sticky-selection block, which then computes `validMoveHexes` against the **new** state for the **same previously-selected piece** — which may now belong to the wrong team's turn (a stale, clickable highlight, exactly as both the original todo and BUG-09 describe).

**`HEADER`, `SNAPSHOT_DEFLECT`, and `FREE_KICK_SETUP` are NOT included in the lines-643-684 sticky-selection special-case block at all** — they fall through to the final generic sticky-selection block (lines 717-733), which calls `validateMove(newState, piece, hex)` — a function whose `WRONG_SLOT` guard (`moveValidator.ts:60`) requires `state.movementSlot !== null`. Since none of `HEADER`/`SNAPSHOT_DEFLECT`/`FREE_KICK_SETUP` ever set `movementSlot`, this call always returns `WRONG_SLOT` (`ok: false`) for every candidate hex, producing an empty `validMoveHexes` — which incidentally happens to "look correct" (no stale highlight) for these three phases today, but only as an accidental side effect of a guard never matching, not because BUG-09's staleness logic was extended to cover them. CONTEXT.md's instruction to cover `HEADER`/`SNAPSHOT_DEFLECT`/`FREE_KICK_SETUP` "stages" should be re-scoped: confirm with a fresh check whether these three phases need the _selection-clearing_ fix at all (since their `validMoveHexes` already comes out empty via the `WRONG_SLOT` fallthrough) or whether the real BUG-09 gap for them is something narrower — e.g., the _selected piece itself_ staying visually "selected" (its ring/highlight state) even with an empty `validMoveHexes` set, which is a `PieceOverlay.tsx` `selectionState` question, not a `validMoveHexes` question. Verify this distinction during planning rather than assuming all listed phases need identical treatment.

**Recommended fix shape:** Broaden `slotChanged` (rename to something like `responseMoveStateChanged`, matching CONTEXT.md's own suggested rename) into an OR-chain covering:

- `newState.movementSlot !== prevState.movementSlot` (existing, keep)
- `newState.firstTimePassMovementSlot !== prevState.firstTimePassMovementSlot`
- `newState.highPassMovementSlot !== prevState.highPassMovementSlot`
- `newState.gkKickMovementSlot !== prevState.gkKickMovementSlot`

And broaden `activationComplete`-style pace-exhaustion detection into a second OR-chain (or fold into the same one) covering whichever of `firstTimePassPaceUsed`/`highPassPaceUsed`/`gkKickPaceUsed`/`snapDeflectPaceUsed` applies to `newState.phase`, comparing against that phase's known cap (1/3/3/2 respectively — confirmed in `useGameStore.ts`'s own `selectPiece` branches at lines 488, 520, 552, and `gameHandlers.ts`'s matching server-side caps).

## BUG-11 Root Cause

**Confirmed via direct read of `packages/server/src/gameHandlers.ts:280-343` (`HIGH_PASS_MOVE` `GAME_MOVE` branch) compared against lines 488-564 (`FIRST_TIME_PASS_MOVE` `GAME_MOVE` branch):**

The HIGH_PASS_MOVE branch has **no equivalent block anywhere in its 64 lines** — confirmed by full read of lines 280-343. `highPassCarrierId` is set (`gameHandlers.ts:1366`, at the `GK_RESTART`→`HIGH_PASS_MOVE` transition... actually at the PASS-phase HP-kick-declaration site) and consumed only for restoring `ball.carrierId` before the accuracy roll (line 690) and cleared at line 695 — it is never read inside the `GAME_MOVE` handler's `HIGH_PASS_MOVE` branch at all. **As established in Pattern 1 above, this is a 2-touch-point fix, not 3:**

1. **Server `GAME_MOVE` rejection** (real gap — add the guard, mirroring FTP's exact shape, checking `hpState.highPassCarrierId`)
2. **Client `selectPiece` UX mirror** (real gap — `useGameStore.ts`'s `HIGH_PASS_MOVE` branch, lines ~508-537, has no equivalent to FTP's carrier-exclusion check at lines 478-481; add the mirror)
3. ~~Delivery occupant lookup exclusion~~ — **does not apply**; HIGH_PASS_MOVE has no delivery-occupant-lookup code path (see Pattern 1 above for the full trace through `applyRoll`). `highPassCarrierId: null` clearing at delivery (the literal touch-point-3 wording) is **already implemented** at `gameHandlers.ts:695` — no action needed there.

**Why the self-pass-reclaim risk is lower for HP than it was for FTP (context for the planner, not a reason to skip the fix):** Since HP always routes to HEADER/LOOSE_BALL (never a direct silent ball-return), the original passer reclaiming the ball during HP repositioning is less severe than FTP's silent self-pass-reclaim (which handed the ball straight back with zero contest). For HP, even if the kicker's own piece ends up on the landing hex, the subsequent HEADER phase still runs a contest (or LOOSE_BALL if no one's in range) before any possession is finalized — so the exploit's _impact_ is narrower. This does not change the fix requirement (CONTEXT.md's D-07 confirms it's in scope regardless), but the planner should not expect the regression test to look identical to FTP's self-pass-reclaim test — the HP version should assert the `GAME_MOVE` rejection itself (`WRONG_PIECE`), not a downstream possession outcome.

## Common Pitfalls

### Pitfall 1: Assuming CONTEXT.md's stated fix template applies byte-for-byte

**What goes wrong:** CONTEXT.md (correctly, for FTP) describes a 3-touch-point fix pattern and asks the planner to mirror it for HP. A planner that copies the pattern without re-verifying against current HP code would either (a) try to add a delivery-occupant-exclusion block to a code path that doesn't exist, wasting effort, or (b) miss that HP's `applyRoll` routing means the "exploit" surface is structurally different.
**Why it happens:** Patterns that look identical at the CONTEXT.md description level (one sentence: "carrier id field, excluded from repositioning, cleared at delivery") can diverge once the actual downstream control flow is traced — FTP and HP look like siblings but resolve completely differently after their respective repositioning slots complete.
**How to avoid:** Always trace the actual downstream code path (not just the touch points named in the decision doc) before writing a plan task. This research already did that tracing for BUG-11 — the planner should write the 2-touch-point version, not the 3-touch-point version.
**Warning signs:** A "mirror this fix" instruction that references line numbers/touch points in a sibling code path — always re-grep those exact line numbers in the target path before assuming they exist.

### Pitfall 2: Treating "validator code looks correct" as "bug confirmed fixed"

**What goes wrong:** For BUG-08, every piece of code this research read matches the documented correct-fix shape. A planner might conclude "no fix needed, close as already-resolved." But the bug was filed the same day (2026-06-20) the fix shipped — there's a real possibility the report describes a narrower scenario this research didn't reproduce (this research did not run the game live; it read source and existing automated tests only).
**Why it happens:** Source-level correctness does not guarantee behavioral correctness across all game-state permutations — especially multi-defender/multi-step move sequences this phase's `moveValidator.test.ts`/`HexGrid.test.tsx` don't yet exercise.
**How to avoid:** Schedule a verification task (manual repro or new targeted regression test covering the tackle-tint client path, which currently has zero test coverage) as BUG-08's first task, separate from "apply the known fix" — because there may be no fix to apply, only a test gap to close.
**Warning signs:** A bug report with no attached reproduction steps that exactly matches a recently-shipped fix's described mechanism — could be stale, could be a near-miss edge case.

### Pitfall 3: Over-consolidating structurally similar-but-not-identical code (DESIGN-03)

**What goes wrong:** `HIGH_PASS_MOVE` and `FIRST_TIME_PASS_MOVE`'s `GAME_END_TURN` slot-transition handlers look similar at the ATTACKER-slot step but diverge completely at the DEFENDER-slot-complete step (one calls `applyRoll`, the other does a direct occupant-delivery). Forcing both into one shared function would require either (a) leaky abstraction parameters that defeat the purpose of consolidating, or (b) literally recreating the BUG-11 class of bug (a fix applied to one path silently not applying to the "consolidated" sibling, because the abstraction hid the divergence).
**Why it happens:** Surface-level code similarity (same comment style, same variable naming convention, same line-count ballpark) is not the same as semantic identity.
**How to avoid:** Only consolidate the clusters this research identified as structurally identical (Clusters 1, 3, 5) — explicitly do NOT attempt to merge Cluster 2's defender-slot-complete logic (HP's accuracy-roll path vs. FTP's direct-delivery path), per the inventory's own recommendation.
**Warning signs:** A consolidation candidate that would need a conditional branch inside the "shared" helper to handle one phase differently from the others — that's a sign the cases aren't actually identical.

### Pitfall 4: Deleting a dead-code candidate without removing its dedicated tests

**What goes wrong:** `applyDeclareHeaderTarget` has 4 dedicated tests in `gameEngine.phase10.test.ts` (lines 558-583). Deleting the function without deleting/updating those tests leaves a compile error (the test file imports the now-missing export), which would surface as a broken build, not a clean removal.
**Why it happens:** Dead-code removal naturally focuses on the dead production code; its test file is easy to forget since it's in a different directory (`__tests__/`) and doesn't show up in the same grep pass unless explicitly included.
**How to avoid:** This research already confirmed the test file location and line range — the planner's task description for this removal must explicitly include deleting `gameEngine.phase10.test.ts:558-583` (the `describe('HEAD-03: header target hex selection (applyDeclareHeaderTarget)', ...)` block) in the same task as the production-code removal.
**Warning signs:** Any dead-code removal task that doesn't mention a corresponding test-file edit — always grep the function name across `__tests__`/`*.test.ts` files specifically, not just production source, before finalizing a removal task.
