## Decisions Made

- Task 1's trace conclusively resolved the open question by reading code, not by assumption: `moveValidator.ts`'s `validateMove` rejects with `WRONG_SLOT` as its very first guard when `state.movementSlot === null` (confirmed at `moveValidator.ts:60`). HEADER has no dedicated `selectPiece` branch in `useGameStore.ts` and falls through to the generic block that calls `validateMove` per candidate hex — `movementSlot` stays null throughout HEADER, so every candidate is rejected and `validMoveHexes` is already empty. FREE_KICK_SETUP has its own `selectPiece` branch (uses `freeKickStageTeam`/`freeKickHex` geometry, no `validateMove` call) but its `setGameState` sticky path has no dedicated branch either, so it too falls through to the generic `validateMove`-driven block, which also yields `WRONG_SLOT` → empty `validMoveHexes`. Neither phase needed a new clear-condition term.
- SNAPSHOT_DEFLECT is structurally different: it IS tracked via its own pace field (`snapDeflectPaceUsed`, cap 2, confirmed at `useGameStore.ts` line 560's `selectPiece` branch: `2 - (gameState.snapDeflectPaceUsed ?? 0)`), so it belongs in the pace-exhaustion OR-chain even though it has no corresponding `*MovementSlot` field (single-piece-per-action, no ATTACKER/DEFENDER hand-off concept for this phase).
- Per D-08 (minimal naming churn), only the directly-relevant local (`slotChanged` → `responseMoveStateChanged`) was renamed; no unrelated locals in the function were touched.
