**Added a SNAPSHOT_DEFLECT branch to `setGameState`'s sticky-selection block that routes through `computeResponseMoveValidHexes` instead of falling through to the always-empty generic fallthrough, closing the last open BUG-09 verification gap.**

## Accomplishments

- Fixed the SNAPSHOT_DEFLECT non-exhausted sticky-recompute case: after a defender uses 1 of 2 pace hexes in one click, the piece now stays selected AND retains a non-empty `validMoveHexes` on the next server broadcast.
- Added a regression test (Test 7) in the existing BUG-09 describe block that locks in this behavior and would fail if the fix were reverted.
- Verified zero regression to the already-shipped BUG-09 "clear" half (Tests 1-4, 6) and the HIGH_PASS_MOVE sticky-recompute lock enforcement (Test 5).

## Files Created/Modified

- `packages/client/src/store/useGameStore.ts` - Added a standalone `if (newState.phase === 'SNAPSHOT_DEFLECT')` branch in `setGameState`'s sticky-selection block (after the HIGH_PASS_MOVE/GK_KICK_MOVE/FIRST_TIME_PASS_MOVE block, before FREE_MOVE), routing through `computeResponseMoveValidHexes` with `lockedPieceIdField: 'snapDeflectMovedPieceId'`, `paceUsedField: 'snapDeflectPaceUsed'`, `paceCap: 2`, `clickDistanceMode: 'range'`, with an inline lock check mirroring the existing HP/GK_KICK/FTP pattern.
- `packages/client/src/store/useGameStore.test.ts` - Added Test 7 (regression guard) to the BUG-09 describe block: asserts `selectedPieceId` retention and non-empty `validMoveHexes` after a `SNAPSHOT_DEFLECT` broadcast with `snapDeflectPaceUsed: 1` (not exhausted).

## Decisions Made

- **Option A (minimal/isolated) chosen over Option B (consolidated).** The plan explicitly recommended Option A for a gap-closure plan because it doesn't touch the already-verified HIGH_PASS_MOVE/GK_KICK_MOVE/FIRST_TIME_PASS_MOVE code. Implemented as a standalone `if` block placed after that existing block and before the FREE_MOVE_ATTACK/FREE_MOVE_DEFENSE block, exactly per Option A's instructions.
- **WR-01 lock-check caveat honored without modifying `computeResponseMoveValidHexes`.** The new SNAPSHOT_DEFLECT branch computes `locked = lockedId !== null && lockedId !== prevSelectedId` itself (same as the existing HP/GK_KICK/FTP block does), and only calls the helper when not locked. No change to `ResponseMoveValidHexConfig` or the helper's signature was needed — consistent with the plan's "Option A introduces no type changes" note.
