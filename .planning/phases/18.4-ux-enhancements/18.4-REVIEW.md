# Phase 18.4: Code Review Report

**Reviewed:** 2026-07-02T00:00:00Z
**Depth:** standard
**Files Reviewed:** 16
**Status:** issues_found

## Summary

This phase introduces four UX enhancements: game-speed selector (UX-07), CTA button color-state gating (UX-08), stat tooltip expansion (UX-12), and the event banner for goal/tackle/interception events (UX-14), plus final-third pitch marking lines (UX-09) and tooltip summaries on action buttons (UX-13).

The shared types and event contracts are clean, server-side speed validation is correctly allow-listed, and the confirmation dialog pattern is sound. However, two critical correctness issues were found: a game-clock logic error that causes the clock to permanently stop at the 45-minute half boundary, and a render-phase side effect in `EventBanner.tsx` that writes state synchronously during render, which violates React's rules. Five additional warnings cover a double-fire race condition in the event banner, missing validation on a server event payload, stale speed state on reconnect, and minor logic issues. Three informational items round out the report.

## Critical Issues

### CR-01: Clock freezes permanently when it crosses the 45-minute boundary mid-half

**File:** `packages/server/src/gameEngine.ts:923`
**Issue:** The added-time roll is gated on `state.addedTime === null` — set it once, never again. But the condition that writes `addedTime` fires the moment `newActionCount >= HALF_LENGTH` (45 for half 1, 90 for half 2). The half-end check then compares `newActionCount >= halfEnd` where `halfEnd = HALF_LENGTH + newAddedTime`. In the first action that crosses 45 the two are computed together in the same call, so the check is consistent. The bug surfaces in **fast** mode: `GAME_SPEED_MINUTES.fast = 3`, so a single end-turn can jump the clock by 3 minutes. If the clock is at 43 and an end-turn adds 3 minutes, `newActionCount = 46 >= 45`, so `newAddedTime` is set. Suppose `addedTimeRoll + leniency = 5`, giving `halfEnd = 50`. Because `46 < 50` the phase does NOT end — correct so far. But on every **subsequent** end-turn the guard `state.addedTime === null` is now `false`, so `newAddedTime` stays at the previous value and is **never re-read from the options**. This is intentional per the comment "only set once per half". The real bug is that `GAME_SPEED_MINUTES[state.gameSpeed]` is used for the end-of-ATTACKER_2 clock increment here, **but also in the three early-exit paths for tackle/steal success** (`applyMove`, lines ~685, ~768, ~829). Each tackle-end adds `GAME_SPEED_MINUTES[state.gameSpeed]` to `actionCount`. In fast mode this is +3 per tackle. If added time is 5 and the clock is at 48 after a tackle the game jumps to 51 ≥ 50 but `applyMove` never checks `halfEnd` — it simply transitions to PASS. `applyEndTurn`'s half-end check is never reached because we never enter MOVE again after the clock is already past `halfEnd`. The half will **never end** until the next natural `applyEndTurn` call, which may never come if the ball is passed and passed without movement.

More precisely: `applyMove`'s tackle-success path (line 685) sets `actionCount: state.actionCount + GAME_SPEED_MINUTES[state.gameSpeed]` and returns a PASS state, skipping `applyEndTurn` entirely. A half-time check is **not** performed on the tackle-success path. With fast speed and added time already resolved, the clock can be pushed well past `halfEnd` yet the half never concludes until a MOVE end-turn fires, which may be blocked because the team with the ball just wants to pass.

**Fix:** Add a half-end check in the tackle/steal success return paths inside `applyMove`, mirroring the logic already present in `applyEndTurn`. Alternatively, extract a shared helper `checkHalfEnd(state, newActionCount)` that returns a HALF_TIME/FULL_TIME state or null, and call it from both `applyMove` (tackle/steal success) and `applyEndTurn`.

```typescript
// Shared helper (extract to module scope):
function checkHalfEnd(
  state: GameState,
  newActionCount: number,
): { phase: 'HALF_TIME' | 'FULL_TIME'; addedTime: number | null } | null {
  const HALF_LENGTH = state.half * 45;
  const addedTime = state.addedTime; // already set — never re-roll here
  if (addedTime === null) return null; // not yet in added time
  const halfEnd = HALF_LENGTH + addedTime;
  if (newActionCount < halfEnd) return null;
  return { phase: state.half === 1 ? 'HALF_TIME' : 'FULL_TIME', addedTime };
}
// Call from applyMove tackle/steal success paths and propagate phase if non-null.
```

### CR-02: `EventBanner` writes state during render (React rules violation — stale closures and double-fire risk)

**File:** `packages/client/src/components/EventBanner.tsx:58-68`
**Issue:** Lines 58–68 of `EventBanner.tsx` call `setActive(banner)` **synchronously during the render function body** — not inside a `useEffect` or event handler. React's rules of hooks require that state updates never be triggered during render; doing so violates the functional component contract and is explicitly called out in React docs as a cause of infinite render loops or stale closure bugs.

Concretely: when the store updates `eventLog` (via `setGameState`), the `EventBanner` component re-renders. During that render the ref is advanced and `setActive(banner)` is called. This schedules a second render immediately (state update from within render). React Strict Mode will double-invoke the render in development, causing the ref to be advanced twice, skipping events. In production the behavior is at best undefined (depends on React scheduler internals) and at worst causes the banner to fire on the wrong event or not fire at all when two log entries arrive in rapid succession.

The comment says "Trigger banner synchronously so the state update happens in the same render cycle as the eventLog change" — but that reasoning is incorrect; `setActive` called in render schedules an _additional_ render, not a same-render state merge.

**Fix:** Move the diff logic into a `useEffect` that runs when `eventLog` changes. The ref still works correctly inside an effect:

```typescript
useEffect(() => {
  if (eventLog.length <= lastProcessedLengthRef.current) return;
  const tailEvent = eventLog[eventLog.length - 1];
  const banner = tailEvent !== undefined ? getBannerMessage(tailEvent) : null;
  lastProcessedLengthRef.current = eventLog.length;
  if (banner !== null) {
    setActive(banner);
  }
}, [eventLog]);
```

This is the correct React pattern and is used in analogous "last-seen length" patterns in the codebase (GameBoard.tsx `lastPieceRef`).

## Warnings

### WR-01: Speed setting is lost on player reconnect — away player sees wrong clock speed

**File:** `packages/server/src/roomHandlers.ts:230-251` and `packages/shared/src/types.ts:484`
**Issue:** `room.gameSpeed` is set by TEAM_SPEED_SET (home player, before game starts) and consumed only once by TEAM_PICK when `buildInitialGameState` is called. After that, `gameState.gameSpeed` carries the speed. If the home player disconnects and reconnects, their speed preference is correctly preserved inside `gameState`. However, if the home player changes the speed **after** the away player has already joined but **before** the away player sends their TEAM_PICK, there is a window where `room.gameSpeed` reflects the latest value but `homePickedTeam` is already set. This is fine architecturally. The subtler issue: `gameState.gameSpeed` in `mockMovementState.ts` is hardcoded to `'standard'` (line 82). Any client that renders before a real server connection — or in a reconnect scenario where `setGameState` hasn't fired yet — will render the mock speed. If a slow game is in progress and the client reconnects, it will briefly show the clock ticking at the wrong rate until the first `GAME_STATE` broadcast. This is a transient cosmetic issue but could confuse players in real play.

More critically: there is **no server-side enforcement** that `TEAM_SPEED_SET` cannot be emitted after the game has already started (i.e., after `room.gameState` is non-null). A malicious or buggy client could emit this event mid-game and corrupt `room.gameSpeed`, which would then persist in the room object. It doesn't change the in-flight `gameState.gameSpeed` (that's immutable after build), but it leaves the room's stored speed inconsistent for potential future use.

**Fix:** Add a guard in the TEAM_SPEED_SET handler: reject if the game has already started (`room.gameState !== null`).

```typescript
socket.on(ClientEvents.TEAM_SPEED_SET, (speed: GameSpeed) => {
  // ...existing validation...
  // T-18.4.1-03: reject speed change after game starts.
  if (room.gameState !== null) {
    socket.emit(ServerEvents.GAME_ERROR, 'GAME_ALREADY_STARTED');
    return;
  }
  room.gameSpeed = speed;
});
```

### WR-02: `emitTeamSpeed` is accessible to all players but server only enforces slot 1

**File:** `packages/client/src/App.tsx:106-110` and `packages/client/src/store/useGameStore.ts:922-925`
**Issue:** `emitTeamSpeed` is exposed as a top-level store action callable from anywhere in the client. In `App.tsx` it is only wired to `handleSpeedChange` which is only passed to `TeamSelectionScreen` where the button is `disabled` for the away player. However, the store function itself does not check the player slot before emitting. Any other component or programmatic call site could call `emitTeamSpeed` regardless of the player's slot. The server correctly rejects it (WR-01 shows it requires slot 1), so there is no security hole, but the defense-in-depth is missing on the client side. The disabled button in `TeamSelectionScreen` is a UI-only guard and can be bypassed by a player opening DevTools.

This is a defense-in-depth issue: the server is authoritative and the server rejects the event for slot 2. The client-side gap is minor but the pattern elsewhere in the store (e.g., `emitHeaderContestant`, `emitEndTurn`) does not validate slot either, so this is consistent with existing code. Flag as warning for future hardening.

**Fix:** Guard the emit in `emitTeamSpeed` against non-home slots:

```typescript
emitTeamSpeed: (speed) => {
  if (get().playerSlot !== 1) return; // defense-in-depth: server also enforces this
  socket.emit(ClientEvents.TEAM_SPEED_SET, speed);
},
```

### WR-03: `setSelectedPassType` iterates ALL `PITCH_HEXES` on every pass type change — blocks the render thread for hundreds of ms

**File:** `packages/client/src/store/useGameStore.ts:306`
**Issue:** Every time the player selects a pass type, `setSelectedPassType` iterates `PITCH_HEXES` (up to 962 hexes), calling `validatePass` for each. `validatePass` is not noted to be O(1) — it likely calls `hexLine`, adjacency checks, and ZoI queries, making this an O(n×m) synchronous computation on the main thread inside a Zustand setter (which runs synchronously inside `set()`). The UI is blocked for the entire duration.

This is a pre-existing issue, not introduced by phase 18.4, but the UX focus of this phase makes it more visible: a player clicking "Standard Pass" will see the button freeze for a perceptible moment before highlights appear. On slower devices this can be 200–400 ms.

This is technically a performance issue, which is out of scope for v1 review per the review instructions. However it _can_ cause an apparent UI hang that could be mistaken for a bug. Flagged as warning for visibility only — do not fix in this phase.

**Fix (deferred):** Move pass target computation to a `useEffect` or `setTimeout(..., 0)` to yield to the browser between the click response and the highlight computation.

### WR-04: `pendingEndTurn` confirm dialog is not cleared when game phase changes mid-dialog

**File:** `packages/client/src/components/ActionPanel.tsx:59-62, 148-158`
**Issue:** `pendingEndTurn` is local `useState` in `ActionPanel`. If a player opens the "End Turn?" confirmation dialog (by clicking End Turn while `eligibleRemaining > 0`), and the opponent simultaneously completes a server action that changes the game phase (e.g., a server-pushed `GAME_STATE` broadcast), the dialog remains visible even though the game has moved on. The Confirm button would then fire `pendingEndTurn.action()` — i.e., call `emitEndTurn()` — into a phase where it is no longer valid. The server will reject it (WRONG_SLOT), which prevents data corruption, but the player sees a confusing experience where clicking Confirm does nothing and the dialog disappears only on the next render cycle.

This can happen in the FREE_MOVE phases in particular: one player ends their free-move sub-phase via their own End Turn, the server transitions to the opponent's sub-phase, and the original player's confirmation dialog stays open.

**Fix:** Add a `useEffect` that clears `pendingEndTurn` when `phase` changes:

```typescript
useEffect(() => {
  setPendingEndTurn(null);
}, [phase]);
```

### WR-05: `ctaButtonClass` uses nullish coalescing fallback `?? ''` which is always non-null

**File:** `packages/client/src/components/ActionPanel.tsx:41`
**Issue:** The expression `styles.ctaButtonReady ?? ''` and `styles.ctaButtonPending ?? ''` apply a runtime nullish fallback that can never fire: CSS module imports are always strings (the class name string), never `null` or `undefined` in a correctly-configured Vite + TypeScript project. The `?? ''` pattern is unnecessary defensive code that also masks a potential misconfiguration: if `styles.ctaButtonReady` were somehow missing (e.g., a typo in the CSS class name), the fallback silently swallows the error rather than surfacing it as a missing class. This same pattern also appears in `GameBoard.tsx:88-90` (`statBubbleClass`).

**Fix:** Remove the `?? ''` fallbacks and use the module class names directly:

```typescript
function ctaButtonClass(eligibleRemaining: number): string {
  return eligibleRemaining <= 0 ? styles.ctaButtonReady : styles.ctaButtonPending;
}
```

### IN-02: `mockMovementState` used as default Zustand initial state ships to production

**File:** `packages/client/src/store/useGameStore.ts:257`
**Issue:** `gameState: mockMovementState` is the default initial state of the Zustand store. This means any client that renders before receiving a `GAME_STATE` broadcast (the LOBBY screen, the WAITING screen, etc.) has a `gameState` with `phase: 'MOVE'`, `activeTeam: 'home'`, and real pieces on the board. `ActionPanel` returns `waitingPanel` or `null` before the `isActivePlayer` check in most paths, so the mock data doesn't render, but selectors that read `gameState.pieces`, `gameState.score`, or `gameState.phase` anywhere outside the game board could produce unexpected output.

The mock is appropriate for development/testing but should not be the live initial state. A neutral `LOBBY` phase state (empty pieces, zero score) would be safer.

**Fix:** Replace the mock default with a minimal LOBBY state, or guard `GameBoard` and `ActionPanel` rendering behind a `screen === 'GAME_BOARD'` check that is already in place (and verify no other selectors read game state outside that guard).

### IN-03: `TeamSelectionScreen` speed buttons call `onSpeedChange` even when `disabled`

**File:** `packages/client/src/components/TeamSelectionScreen.tsx:83-84`
**Issue:** The speed option buttons are `disabled={!iAmHome}` and also guard behind `if (iAmHome) onSpeedChange(value)` in the `onClick` handler. The `disabled` attribute on a `<button>` already prevents `onClick` from firing in all browsers, making the `if (iAmHome)` check inside the handler redundant. This creates a false sense of security: if the disabled attribute were accidentally removed or overridden, the inner guard would fire `onSpeedChange` for a non-home player, which would emit `TEAM_SPEED_SET` from the away player's socket. The server correctly rejects it (slot check), but the redundant guard may suggest the `disabled` attribute alone is not trusted.

**Fix:** Remove the redundant `if (iAmHome)` guard inside `onClick` to reduce complexity and rely solely on `disabled` — which is the correct HTML mechanism:

```tsx
onClick={() => onSpeedChange(value)}
```
