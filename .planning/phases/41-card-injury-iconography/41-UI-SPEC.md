## Spacing Scale

Declared values (must be multiples of 4), confirming the project's existing scale:

| Token | Value | Usage                                                                                                      |
| ----- | ----- | ---------------------------------------------------------------------------------------------------------- |
| xs    | 4px   | Icon-internal gaps, badge stroke/inset spacing                                                             |
| sm    | 8px   | Gap between badge and adjacent row element (matches existing `.cardChip`/`.injuryChip` `margin-left: 8px`) |
| md    | 16px  | Default element spacing (not directly used by this phase's new component)                                  |
| lg    | 24px  | Section padding (unaffected by this phase)                                                                 |
| xl    | 32px  | Layout gaps (unaffected)                                                                                   |
| 2xl   | 48px  | Major section breaks (unaffected)                                                                          |
| 3xl   | 64px  | Page-level spacing (unaffected)                                                                            |

**Exceptions:** Badge glyph geometry itself (the `CardInjuryBadge`/`CardInjuryBadgeGroup` SVG dimensions — viewBox size, rect width/height, cross bar length/thickness) is icon-internal geometry and is exempt from the 4px grid, matching the existing exemption already implicit in `MiniTokenBadge` (20×20 `<svg>`, `r=9`) and `NationFlag` (`size=20` / `size=14` depending on surface). Default standalone badge size: **16px** square (matches the dual-export component shape in RESEARCH.md's Pattern 1 code example), scaling up to 20px on surfaces whose existing row height is already built around 20px icons (e.g. `PlayerStatsPanel`'s header row, which already uses `NationFlag size={20}` and `MiniTokenBadge` at 20×20) — exact per-surface pixel value is CONTEXT.md's Claude's Discretion (D-05 note), not a vision decision; 16px is the default absent a surface-specific reason to deviate.

## Typography

This phase introduces **no new text**. D-01 explicitly replaces the existing text-chip treatments (`"YELLOW"`/`"RED"`/`"INJ"`/`"INJ ×2"`) with a wordless shape+color glyph. The table below documents the **existing, unchanged** typography of the row context the badge is inserted into, so the badge's vertical sizing/alignment stays visually compatible — not new typographic decisions.

| Role                                                                 | Size | Weight     | Line Height                                                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------- | ---- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Name-row label (name/role/jersey#)                                   | 13px | 700 (bold) | single-line, no explicit line-height (inline flex row)                                                                                                                                                                                                                                  |
| Bench status text badge (`OUT`/`RED CARD`, unaffected by this phase) | 9px  | 700        | single-line                                                                                                                                                                                                                                                                             |
| (Removed by this phase) card/injury text chip                        | 11px | 400        | single-line — chip text and its CSS classes (`cardChip`/`injuryChip` in `PlayerStatsPanel.module.css` and `LineupAssignmentScreen.module.css`) become dead code once no consumer renders text through them; verify via `knip`/grep post-implementation (RESEARCH.md "State of the Art") |

**Accessibility requirement (not optional):** because D-01 removes all readable badge text, every rendered badge (both `CardInjuryBadgeGroup` and standalone `CardInjuryBadge`) MUST carry a `title` attribute (and/or `aria-label` on the wrapping element) describing its state in words — e.g. `"Yellow card"`, `"Red card"`, `"Injured"`, `"Injured ×2"` (see Assumption below on ×2 — the _visual_ glyph is binary per D-01/pitch-token precedent, but the accessible label MAY still say "×2" since that costs nothing and preserves information a sighted colorblind user or screen-reader user would otherwise lose). This mirrors the already-established `title={fullLabel}` pattern on `STAT_LABELS` stat chips (`PlayerStatsPanel.tsx`).

| Element                                       | Copy                                                                                                                                                                       |

## Component & Data Contract

_(Additional section beyond the base template — carries forward RESEARCH.md decisions that materially affect what "identical iconography" means across the four surfaces; the planner and executor need these locked, not re-litigated.)_

### Shared component shape (locks RESEARCH.md's recommendation)

- **One module, two named exports:** `CardInjuryBadgeGroup` (raw SVG primitives, composes into an existing `<svg>` — used by `PieceOverlay.tsx`) and `CardInjuryBadge` (self-contained `<svg viewBox>` wrapper — used by the three DOM-context surfaces), plus a co-located `cardColorFor(piece)` derivation function, all in `packages/client/src/components/CardInjuryBadge.tsx`.
- **Glyph shape is fixed, not redesigned:** colored rectangle (yellow/red) for card status, plain white cross for injury status — extracted verbatim from `PieceOverlay.tsx`'s existing, already-tested geometry (D-01). Any deviation from this shape is a red flag requiring explicit justification, not a routine implementation choice.
- **Position rule (D-02/D-03):** on the three name-row surfaces (scoreboard player-stats card, roster/lineup card, bench card), the badge renders immediately after the existing `#{jerseyNumber}` element in the `flag · role · #number` header row — the same anchor point the current text chips already use. The on-pitch `PieceOverlay` SVG token is exempt from this rule (D-03): it keeps its existing corner-anchor position opposite the ball-possession dot, unchanged by this phase.
- **Simultaneous card + injury (D-04):** both badges render side by side (not merged into one glyph) on all three name-row surfaces, and in the pitch token's existing layered-but-shape-distinguished treatment. Never invent a combined glyph.
- **Injury count visual treatment:** the glyph is **binary** (present/absent) — do not attempt to visually distinguish `injuryCount === 1` from `injuryCount >= 2` on the glyph itself (matches the pitch token's existing behavior, the source of truth per D-01). This is a deliberate loss of the old chip system's "×2" distinction; recover it only in the accessible label (see Copywriting Contract above), never in the glyph shape/size/color.

### Bench surface — data-model decision (locks the RESEARCH.md Open Question)

RESEARCH.md flagged this as an explicit required decision and defaulted, cautiously, to the zero-engine-change option. **That default is overridden here** by ROADMAP.md's own Phase 41 Success Criterion 2, which is unambiguous: _"A bench player who has been booked **or injured** now shows that status on the bench, which it never did before."_ Red-card-only bench iconography would not satisfy this criterion.

- **Decision: implement RESEARCH.md's Option 1.** Extend `BenchEntry` (`packages/shared/src/types.ts`) with two new optional fields — `yellowCards?: 0 | 1 | 2` and `injuryCount?: number` — populated at the two exact call sites RESEARCH.md identified: `relocateRedCardedToBench` (`gameEngine.ts:773-793`, copy from the departing `piece`) and the substitution bench-entry rewrite inside `applySubstitution` (`gameEngine.ts:3126-3138`, copy from `outPiece`). This is a small, additive, server-side task — flag it as its own explicit plan task, not silent client-only work.
- A `redCarded` bench entry derives its red-card glyph from `status === 'redCarded'` alone (zero new plumbing needed for that specific case) — but a booked-not-sent-off or injured `subbedOut`/`available` player needs the new fields above to show anything at all.

### Bench surface — coexistence with the existing `RED CARD`/`OUT` status badge

Locks RESEARCH.md's Open Question 2: **coexist, do not replace.** `BenchEntryStatus`'s `RED CARD`/`OUT` text badge (`DraftPackCarousel.tsx`'s `DraftCardBody`, `redCardBadge`/`outBadge` classes) answers a different question ("why is this player unavailable — roster availability") than the new card/injury glyph ("what's their disciplinary/fitness status"). Render order in the bench card's header row: `flag · role · #number · [CardInjuryBadge glyph] · [RED CARD / OUT status text badge]` — the glyph occupies the same "immediately after jersey number" anchor point as the other three surfaces (consistency per ICON-02), and the pre-existing status text badge trails it unchanged.

### Post-implementation verification (carried from RESEARCH.md, load-bearing for ICON-01)

A grep for `redCarded === true ?` across `packages/client/src/components/*.tsx` (excluding `CardInjuryBadge.tsx` itself) MUST return zero matches once this phase is complete — that is the concrete, checkable definition of "single shared component" (ICON-01).
