# Phase 47 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase is a pure interaction-model swap (native HTML5 drag-and-drop → click-to-select) on four existing roster/lineup surfaces in `LineupAssignmentScreen.tsx`. It introduces **zero new domain UI** (no new screens, no new copy surfaces, no new brand colors) — the design contract below exists almost entirely to pin down (a) the exact card visual-state treatment for select/eligible/ineligible, ported from the pitch's already-locked `HIGHLIGHT_STYLES`/`RING_STYLES` tokens per CONTEXT.md D-03, and (b) the two open discretionary questions RESEARCH.md flagged (exact blue swatch, CSS-literal-vs-token-import approach). All other template sections (Typography, Copywriting, Registry) are largely "inherited, unchanged" because this phase does not touch them.

## Spacing Scale

This phase does not introduce a new spacing scale — it reuses the existing `LineupStatCard` geometry (`LineupAssignmentScreen.module.css` `.statCardBase`, lines 144-154) verbatim. No card dimensions, padding, or gaps change; only border/box-shadow treatment (below) is added.

| Token | Value | Usage |
|-------|-------|-------|
| Card padding | `6px 8px` | Existing `.statCardBase` padding — **pre-existing exception to the 4px scale**, not introduced or altered by this phase |
| Card internal gap | `8px` | Existing `.statCardBase`/`.cardBody` gap — unchanged |
| Card min-width | `260px` | Existing `.statCardBase` — unchanged; click target = full card `<div>`, same as today's `draggable` div, so no new hit-target sizing work is needed |
| Selection ring border | `2px` | New — matches the existing `.statCardDropTarget` gold-ring precedent (`border: 2px solid ...`) exactly, so the new green/blue rings sit at the same visual weight as the treatment they replace |
| Selection ring glow offset | `2px` | New — matches existing `.statCardDropTarget`'s `box-shadow: 0 0 0 2px ...` glow offset exactly |

Exceptions: `6px` card padding (pre-existing, inherited, out of this phase's scope to change). `2px` ring border/glow (new, but matches an established in-file precedent rather than introducing a new arbitrary value).

## Color

### Chrome background system (unchanged, for context only)

The 60/30/10 chrome backdrop this phase's cards sit on is established (Phase 33/34) and untouched here:

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-bg-page` (`#121212`) | Page/screen background |
| Secondary (30%) | `--color-bg-surface` (`#1c1c1c`) / `--color-bg-surface-alt` (`#262626`) | Card surfaces, panels |
| Accent (10%) | `--color-accent-gold` (`#f5c518`) | Confirmation/required-action affordances only (e.g. Confirm Lineup button, kickoff "place here" ring) — **not used for card selection state this phase**, see below |
| Destructive | `--color-danger` (`#ef4444`) | Destructive/error text and disabled states only — not touched by this phase |

Accent (gold) reserved for: Confirm/required-action controls and the pre-existing kickoff/pass "confirmed" ring (`RING_STYLES.required`/`RING_STYLES.confirmed` in `HexCell.tsx`). Card selection in this phase deliberately does **not** use gold — D-03 explicitly rejects reusing the drag-era gold `.statCardDropTarget` treatment for the new eligible-target state, to keep "eligible target" and "confirm/required" visually distinct app-wide.

### Selection state tokens (locked this phase — D-03 + resolved discretionary questions)

| State | Color | Source token | Hex |
|-------|-------|---------------|-----|
| 🟢 Selected card | Green | `PieceOverlay.tsx` `selectionState="active"` / `ACTIVE_RING_STROKE` | `#22c55e` |
| 🔵 Eligible-target card | Blue | `PieceOverlay.tsx` `selectionState="selectable"` | `#60a5fa` |
| ⚪ Ineligible/blocked card (e.g. red-carded, GK in positioning mode) | No new color — retains existing `.statCardSubBlocked`-equivalent dimmed treatment | `opacity: 0.7` | — |

**Resolved: exact blue swatch (RESEARCH.md Open Question / Assumption A1).** Locked to `#60a5fa` (`PieceOverlay`'s `selectable` ring blue), **not** `#3b82f6` (`HIGHLIGHT_STYLES.kickoff`'s saturated blue) or the sky-blue `gk-kick-target` variant. Rationale: a card selection ring is structurally a *piece-ring* analog (a ring around one discrete selectable unit), not a *hex-tint* analog (a zone/placement-guidance fill) — `#60a5fa` is the piece-ring family's blue and is the closer semantic match for "you may click this to act," exactly as RESEARCH.md's own assumption reasoned. This decision closes the open question; no further confirmation needed downstream.

**Resolved: CSS-literal vs. token-import approach (RESEARCH.md Open Question 2).** Locked to **CSS Module classes with literal color values** matching the pitch tokens (`#22c55e` green, `#60a5fa` blue), consumed the same way every other class in `LineupAssignmentScreen.module.css` already is — **not** a cross-import of `HIGHLIGHT_STYLES`/`RING_STYLES` objects from `HexCell.tsx` into inline `style` props. Rationale: no component in this file currently consumes `HexCell.tsx`'s exported constants directly (they're SVG-only, inline-styled, no CSS Modules involvement); introducing a cross-file TS import for two color values is more indirection than value here. D-03's requirement is satisfied by value-matching the hex literals, not by object-identity reuse. If a third card-selection consumer emerges in a future phase, revisit centralizing into a shared constant — not required now.

### New CSS classes required (`LineupAssignmentScreen.module.css`)

Replace `.statCardDragging` / `.statCardDropTarget` / `.statCardSubTarget` (all removed per ROSTER-06) with exactly two new classes, applied via the existing conditional-class-append pattern already used in this file:

```css
/* Selected card — green, mirrors PieceOverlay active ring (#22c55e) */
.statCardSelected {
  border: 2px solid #22c55e;
  box-shadow: 0 0 0 2px rgba(34, 197, 94, 0.4);
}

/* Eligible-target card — blue, mirrors PieceOverlay selectable ring (#60a5fa) */
.statCardEligible {
  border: 2px solid #60a5fa;
  box-shadow: 0 0 0 2px rgba(96, 165, 250, 0.4);
}
```

One shared `.statCardEligible` class replaces both former near-duplicate `.statCardDropTarget`/`.statCardSubTarget` (RESEARCH.md explicitly flags these as duplicating each other's body today) — a single eligible-target class used identically across all four surfaces (mid-match positioning, mid-match substitution, Standard pregame, draft), per D-10's "one shared rendering path" discretion.

`.statCard`'s base `cursor: grab` becomes `cursor: pointer` (no drag gesture remains). `.statCardDragging` is deleted outright — there is no mid-gesture state to visualize under click-select. `.statCardSubBlocked`'s `cursor: not-allowed` becomes `cursor: default` (D-04: an ineligible click is a silent no-op, not a blocked-cursor affordance — "not-allowed" over-communicates for a card that simply doesn't respond to hover/click).

### Card state matrix (all four surfaces)

| Visual state | Class applied | When |
|---|---|---|
| Idle / unselected / not eligible | `.statCard` (base only) | Default — nothing selected, or something is selected and this card isn't a legal target |
| Selected | `.statCard .statCardSelected` | This card is the current green selection (positioning source, or substitution bench source) |
| Eligible target | `.statCard .statCardEligible` | Something is selected and this card is a legal completion target (blue) |
| Locked (GK in positioning mode; slot 0 in pregame/draft) | `.statCardLocked` (existing, unchanged) | Card can never be selected — D-09. Never gains `.statCardSelected`/`.statCardEligible` |
| Blocked (red-carded / no active piece) | `.statCardSubBlocked`-equivalent (existing, cursor updated per above) | Never a valid target in the current mode |
| SENT OFF placeholder — positioning mode | Gets `.statCardEligible` when it's a legal reposition target (D-05) | Bespoke `<div>`, not `LineupStatCard` — must be wired into the same eligible-target computation explicitly (RESEARCH.md Pitfall 3); this is the single easiest state to silently drop during the port |
| SENT OFF placeholder — substitution mode | Never gets `.statCardEligible` (D-05) | Same bespoke `<div>`; substitution mode has no active player there to sub out |

### Card interaction/hover affordance

No new hover-specific color is introduced. `cursor: pointer` on any selectable/eligible card communicates clickability; unselectable/ineligible cards keep `cursor: default`, matching D-04's "silent no-op" framing (no hover feedback promises an action that won't happen).

### Accessibility (resolves RESEARCH.md Open Question 1 — Claude's Discretion)

Locked decision: add minimal keyboard/ARIA affordance on top of the pitch's click-only precedent, since DOM `<div>` cards (unlike the pitch's raw SVG `<polygon>`/`<circle>` elements) support this cheaply and it costs nothing to add. Selectable/eligible cards get `role="button"` `tabIndex={0}` and an `onKeyDown` handler that triggers the same `onClick` logic on `Enter`/`Space`. Locked/blocked cards get no `tabIndex` (not reachable by keyboard, matching their non-clickable state). This is a deliberate, minor departure from the pitch's current lack of keyboard support — not a blocking requirement, but the contract's answer to the open discretion question so planner/executor don't re-litigate it.

## Copywriting Contract

This phase introduces no new user-facing copy. All existing copy (Confirm button labels, swap-rejection messages, `pendingSub` staging popup text) is unchanged — only the input gesture that triggers these existing flows changes.

| Element | Copy |
|---------|------|
| Primary CTA | Unchanged — existing "Confirm Lineup" / "Substitute" / mode-toggle buttons, not touched this phase |
| Empty state heading | Not applicable — no new empty state introduced |
| Empty state body | Not applicable |
| Error state | Not applicable — an ineligible click is a **silent no-op** (D-04), matching the pitch's click-to-move convention exactly. No error text, toast, or shake animation is shown for an ineligible click. (Existing GK-lock/`rejectForGKRule` rejection messages in draft mode are unchanged — those already exist and fire from the same click-completion point, just triggered by `onClick` instead of `onDrop`.) |
| Destructive confirmation | Not applicable — no new destructive action introduced. The existing `pendingSub` staged-substitution confirm/cancel popup is unchanged in copy or mechanic, only in what populates it (a click, not a drop). |
