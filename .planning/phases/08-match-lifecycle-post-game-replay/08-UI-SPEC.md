## New Screen Specifications

Phase 8 adds four new screens to the `screen` routing in Zustand: `KICK_OFF_SETUP`, `HALF_TIME`, `FULL_TIME`, `REPLAY`. These map directly to `GameState.phase` values. The `onGameState` handler in App.tsx drives screen transitions.

### Screen 1: KICK_OFF_SETUP

**Trigger:** `GameState.phase === 'KICK_OFF_SETUP'` → App.tsx sets `screen = 'GAME_BOARD'` (the pitch remains visible). KICK_OFF_SETUP is not a full-screen modal — it uses the existing GAME_BOARD layout with the pitch visible and sidebar updated.

**Rationale:** Players need to see and click hexes to reposition their pieces. The full pitch must remain visible. The sidebar shows the new KickOffSetupPanel instead of ActionPanel.

#### Layout

Use the existing GameBoard layout (header + pitch + sidebar) unchanged. Replace the ActionPanel in the sidebar with a `KickOffSetupPanel` component. TurnIndicator and ActionLog remain in place.

Header: show score and match time as normal. Connection status unchanged.

#### Kick-Off Zone Hex Tinting

Valid placement hexes are indicated by a semi-transparent fill overlay drawn on top of the base hex fill, via an additional `<polygon>` element in the SVG (same DOM-order z-layering pattern as PieceOverlay).

| Condition                                                          | Overlay fill          | Overlay opacity | Notes                                                    |
| ------------------------------------------------------------------ | --------------------- | --------------- | -------------------------------------------------------- |
| Hex is in MY team's valid placement zone                           | `#1a56b0` (home-blue) | 0.25            | Subtle blue tint for own valid zone (home team)          |
| Hex is in MY team's valid placement zone (away team)               | `#c0392b` (away-red)  | 0.25            | Subtle red tint for own valid zone (away team)           |
| Hex is in OPPONENT's valid placement zone                          | no overlay            | —               | Opponent zone shows no tint (clutter reduction)          |
| Hex is INVALID for placement by either team (occupied/out of zone) | no overlay            | —               | No tint; piece placement rejected by server if attempted |
| Centre hex (`q:18, r:13`) — required for attacking team            | `#f5c518` (gold)      | 0.50            | Prominent gold fill; see ring marker below               |

**Centre hex required marker:** In addition to the gold fill overlay, draw a 2px gold ring (`stroke: #f5c518`, `strokeWidth: 2`, `fill: none`) around the centre hex polygon. This ring is a separate `<polygon>` element appended immediately after the fill overlay element in DOM order. The ring is visible regardless of zone context to clearly signal the MATCH-03 placement rule.

**Occupied hex during setup:** When a player piece is placed on a hex, the hex returns to its normal fill (the piece overlay covers it). The zone tinting only applies to unoccupied hexes in the valid zone.

**Invalid placement feedback:** If a player drags/clicks a piece to an invalid hex during setup, the server rejects the placement. The client receives a `game:error` event. Display the error text in KickOffSetupPanel at 13px / 400 / `#ef4444`. Auto-clear when the next `game:state` arrives.

#### Hex Click Routing During KICK_OFF_SETUP

| Click target                          | Action                                                                               |
| ------------------------------------- | ------------------------------------------------------------------------------------ |
| Own team piece (selected state)       | `store.selectPiece(id)` — highlights all valid placement hexes in the valid zone     |
| Valid zone hex (while piece selected) | `socket.emit(GAME_MOVE, { pieceId, to: hex })` — repositions piece; server validates |
| Any other hex                         | no-op                                                                                |
| Opponent piece                        | no-op (cannot move opponent pieces during setup)                                     |

**Valid zone hex highlights during KICK_OFF_SETUP:** When a piece is selected, every hex in that team's valid zone (that is currently unoccupied) renders an additional highlight ring: `stroke: #f5c518`, `strokeWidth: 1.5`, same hex polygon shape, no fill change. This is the same `isHighlighted` pattern already used in MOVEMENT phase. The same `validMoveHexes` store slice is reused — populated server-side with the valid zone hexes after piece selection.

#### KickOffSetupPanel Component

**Location:** Sidebar, replacing ActionPanel during KICK_OFF_SETUP.

**Container:** Same `.panel` style as ActionPanel — `background: #16213e; border: 1px solid #0f3460; border-radius: 4px; padding: 16px; display: flex; flex-direction: column; gap: 8px`.

**Contents:**

1. Panel heading: "Kick-Off Setup" at 13px / 700 / `#e0e0e0`.
2. Instruction body: "Place your players in your permitted zone. One player must be on the centre hex." at 13px / 400 / `#a0a0a0`. Line-height 1.5.
3. Constraint status row: displays live constraint check results (see below).
4. "Ready" button — primary CTA.

**Constraint status rows:**

| Constraint                          | Met display                                      | Unmet display                                               |
| ----------------------------------- | ------------------------------------------------ | ----------------------------------------------------------- |
| Attacking team: centre hex occupied | "Centre hex: occupied" at 13px / 400 / `#a0a0a0` | "Centre hex: EMPTY — required" at 13px / 400 / `#ef4444`    |
| All pieces placed in valid zone     | "Placement: valid" at 13px / 400 / `#a0a0a0`     | "Placement: X pieces out of zone" at 13px / 400 / `#ef4444` |

Only the attacking team sees the centre hex constraint row. The defending team sees only the zone placement constraint.

**"Ready" button:**

- Label: "Ready"
- Style: same `.ctaButton` — `background: #0f3460; color: #ffffff; border-radius: 4px; padding: 10px 20px; font-size: 13px; font-weight: 700`
- Disabled state: `opacity: 0.5; cursor: default` — disabled when ANY constraint is unmet
- Enabled state: all constraints met for this player's team
- `title` attribute when disabled (attacking team): `"Place a player on the centre hex first"`
- `title` attribute when disabled (defending team): `"Move all players to your own half outside the centre circle"`
- Emits: `socket.emit('game:ready')` — no payload required

**Opponent waiting state:** When the local player has clicked Ready but the opponent has not yet confirmed, the Ready button changes label to "Waiting for opponent…" at 13px / 400 / `#a0a0a0` and is disabled. The button background stays `#0f3460`. No spinner needed.

**Non-active player note:** Both players are active during KICK_OFF_SETUP — both can reposition pieces and both must click Ready. The KickOffSetupPanel renders for both players.

### Screen 2: HALF_TIME

**Trigger:** `GameState.phase === 'HALF_TIME'` → App.tsx sets `screen = 'HALF_TIME'`.

**Layout:** Full-screen centred card. Same pattern as lobby screens.

```
page: min-height 100vh, display flex, align-items center, justify-content center, background #1a1a2e
card: width 100%, max-width 440px, background #16213e, border 1px solid #0f3460, border-radius 4px, padding 24px, gap 16px
```

**Contents (top to bottom):**

1. Heading: "Half Time" at 20px / 700 / `#e0e0e0`.
2. Half indicator: "End of 1st Half" at 13px / 400 / `#a0a0a0`. (Always the first half — second half ends at FULL_TIME, not HALF_TIME.)
3. Score display: `{homeScore} – {awayScore}` at 28px / 700 / `#e0e0e0`, monospace (`'Courier New', Courier, monospace`), centred. Team labels flanking the score: "Home" in `#1a56b0` and "Away" in `#c0392b` at 13px / 400 in the same row.
4. Added time played note: "Added time played: +{addedTime}'" at 13px / 400 / `#a0a0a0`. Only shown when `addedTime > 0`. Uses the existing `GameState.addedTime` field. The `addedTime` value is the total added time rolled at 45 min, not minutes remaining.
5. Kick-off assignment notice: "2nd half kick-off: {teamName}" at 13px / 400 / `#a0a0a0`. Team name in `#1a56b0` or `#c0392b` matching team colour. The team displayed is the one that did NOT kick off first (D-26). This is informational — no player choice required.
6. "Start 2nd Half" button:
   - Label: "Start 2nd Half"
   - Style: `.ctaButton`
   - Disabled for the team that kicked off in the first half (`playerSlot` corresponds to `GameState.kickOffTeam`)
   - Enabled only for the team that did NOT kick off first
   - Disabled style: `opacity: 0.5; cursor: default`
   - `title` attribute when disabled: "Only the 2nd half kick-off team can start"
   - Emits: `socket.emit('game:half-time-start')`

**No transition delay.** The HALF_TIME screen stays visible until the active player clicks "Start 2nd Half". No auto-advance timer.

### Screen 3: FULL_TIME

**Trigger:** `GameState.phase === 'FULL_TIME'` → App.tsx sets `screen = 'FULL_TIME'`.

**Auto-transition:** The FULL_TIME screen displays for exactly 3 seconds, then App.tsx transitions automatically to `screen = 'REPLAY'` when `GameState.phase === 'REPLAY'` is received. No manual dismiss button. The transition is driven by the server emitting `phase: 'REPLAY'` — client does not use `setTimeout`.

**Layout:** Full-screen centred card. Same dimensions and container as HALF_TIME.

**Contents (top to bottom):**

1. Heading: "Full Time" at 20px / 700 / `#e0e0e0`.
2. Score display: `{homeScore} – {awayScore}` at 28px / 700 / `#e0e0e0`, monospace, centred. Team labels at 13px / 400 flanking the score.
3. Result line:
   - If `homeScore > awayScore`: "Home wins" at 13px / 700 / `#1a56b0`
   - If `awayScore > homeScore`: "Away wins" at 13px / 700 / `#c0392b`
   - If scores equal: "Draw" at 13px / 700 / `#e0e0e0`
4. Transition notice: "Replay starting…" at 13px / 400 / `#a0a0a0`. Static text — no animation. Appears immediately on screen mount and remains visible until transition.

### Screen 4: REPLAY

**Trigger:** `GameState.phase === 'REPLAY'` → App.tsx sets `screen = 'REPLAY'`.

**Layout:** The full GAME_BOARD layout is used (header + pitch + sidebar). The pitch renders each replay frame as `HexGrid` does normally — same component, same rendering. The sidebar shows `ReplayPanel` instead of ActionPanel. TurnIndicator and ActionLog are replaced by ReplayPanel in the sidebar. The header shows the final score and match title as normal. ConnectionStatus remains in the header.

**Why full board layout:** Replay must show piece positions changing on the pitch. Full-screen card would not show the board.

#### Replay Sidebar — ReplayPanel Component

**Container:** Same `.panel` style — `background: #16213e; border: 1px solid #0f3460; border-radius: 4px; padding: 16px; display: flex; flex-direction: column; gap: 8px`.

**Contents:**

1. Panel heading: "Replay" at 13px / 700 / `#e0e0e0`.
2. Final score: `{homeScore} – {awayScore}` persistent display at 13px / 700 / `#e0e0e0`. Team names in `#1a56b0` / `#c0392b`. Same row layout as TurnIndicator score.
3. Replay position counter: "Action {current} of {total}" at 13px / 400 / `#f5c518` (accent-gold). Accent-gold signals progress status.
4. Running indicator: "Playing…" at 13px / 400 / `#a0a0a0` — displayed while replay is in progress (any frame before the last). When replay finishes: text changes to "Replay complete." at 13px / 400 / `#a0a0a0`.
5. "Play Again" button — visible ONLY when replay finishes (all frames exhausted):
   - Label: "Play Again"
   - Style: `.ctaButton`
   - Always enabled when shown
   - Click action: `store.setScreen('CREATE_ROOM')` — no socket event needed (server-side cleanup via disconnect/timeout; see D-32)

**No pause, scrub, or step controls.** Auto-play only (deferred per CONTEXT.md).

**Replay running indicator update:** The `current` counter increments with each `game:state` frame received while `phase === 'REPLAY'`. The `total` is derived from the final replay `game:state` frame's metadata (server includes `replayTotal` in the broadcast). If `replayTotal` is not available, render "Action {current}" without the "of N" suffix.

## Match Time Display Extension (GameBoard header)

Phase 8 adds a match time display to the existing GAME_BOARD header bar.

**Location:** Between the score and ConnectionStatus in the header flex row. The header currently shows `[Title] ... [Score] [ConnectionStatus]`. Phase 8 changes it to: `[Title] ... [Score] [Time] [ConnectionStatus]`.

**Element:** A `<span>` inside the header with class `.headerTime`.

**Visual spec:**

- Font: 13px / 700
- Color: `#f5c518` (accent-gold — signals active match time, distinct from score text)
- Content format: `{actionCount}'` during normal play (e.g., "42'")
- Content format when added time active: `{45 + addedTime}'` final display is the running total — e.g., if `actionCount = 47` and `addedTime = 3`, display "45+2'" where the suffix shows minutes consumed of added time. Precise formula: `{45}'` base + `+{actionCount - 45}'` suffix when `actionCount > 45 && addedTime !== null`. Example: actionCount=47, addedTime=3 → "45+2'".
- During second half: same format but counting from 0 again — display as `{actionCount}'` for the second half.
- Not shown during KICK_OFF_SETUP, HALF_TIME, FULL_TIME, REPLAY screens (those screens use the non-GameBoard layout or the time is irrelevant).
- Gap between score and time: 16px (`md`).

## Action Button Eligibility (Phase 8 Extension to ActionPanel)

Phase 8 enforces action sequence validation server-side (`lastActionType` + eligibility table D-07/D-08). The client reflects this via disabled button states in ActionPanel. This section specifies the client-side button state logic — do NOT implement client-side sequence validation; only reflect server state.

**New action buttons added to ActionPanel in Phase 8:**

| Button          | Label       | Visible When                                                        | Disabled When                                | Emits           |
| --------------- | ----------- | ------------------------------------------------------------------- | -------------------------------------------- | --------------- |
| Snapshot        | "Snapshot"  | phase === `SNAPSHOT` AND active player                              | never (if visible, always enabled)           | `game:snapshot` |
| Header          | "Header"    | phase === `HEADER` AND active player                                | never (if visible, always enabled)           | `game:header`   |
| Roll (extended) | "Roll Dice" | phase IN [`PASS`, `SHOT`, `HEADER`, `LOOSE_BALL`] AND active player | already specified (Phase 7 — never disabled) | `game:roll`     |

**Action button disabling based on eligibility:**

The eligibility table (D-08) must be reflected visually. Invalid next-action buttons are disabled (not hidden) so the player can see what is unavailable and why.

The ActionPanel receives `lastActionType` from the store (`useGameStore(s => s.gameState.lastActionType)`). The `ELIGIBLE_NEXT_ACTIONS` constant (a `Record<LastActionType, Set<string>>` in `packages/shared/src/actionSequence.ts`) determines which buttons are enabled.

**Disabled button appearance:** Same as the existing disabled style — `opacity: 0.5; cursor: default`. Use the HTML `disabled` attribute.

**Disabled button tooltip:** Use the `title` attribute to explain why. Standard message for all disabled action buttons: `"Not available after {lastActionType}"`. The exact copy per action type:

| Button         | `title` when disabled                                    |
| -------------- | -------------------------------------------------------- |
| Start Movement | "Not available after a High Pass — must head the ball"   |
| Roll (Pass)    | "Cannot pass directly after {lastActionType}"            |
| Snapshot       | "Cannot take a snapshot after {lastActionType}"          |
| Roll (Shot)    | Shots can only be attempted after movement or a snapshot |
| Roll (Header)  | "Header only valid after a High Pass or Long Ball"       |

**High Pass special case:** When `lastActionType === 'HIGH_PASS'`, ONLY the Header button/phase is valid. The client must not show any other action buttons in the HEADER phase — phase gating already handles this (ActionPanel only renders the Roll button during `HEADER` phase). No additional disabling needed beyond phase gating.

**Note:** The Phase 8 button changes are additive. All Phase 7 ActionPanel buttons remain exactly as specified.

## Hex Interaction States — Phase 8 Additions

Phase 6/7 hex states are frozen. Phase 8 adds three new SVG overlay states.

| New state                             | Fill             | Opacity | Stroke    | Stroke width | When active                                                                           |

**Implementation pattern:** All new overlays follow the existing `isHighlighted` overlay approach — additional `<polygon>` elements in the same SVG group, rendered after the base hex fill polygon. DOM order determines z-order. Pass a `kickOffZoneColor` prop to HexCell (or handle in HexGrid by generating fill+opacity directly) to avoid coupling zone logic into HexCell.
