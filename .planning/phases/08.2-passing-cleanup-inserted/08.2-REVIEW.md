# Phase 08.2: Code Review Report

**Reviewed:** 2026-06-07
**Depth:** standard
**Files Reviewed:** 27
**Status:** issues_found

## Summary

This phase introduces the full passing flow (Standard/First-time/High/Long pass target selection, interception pre-roll, and HIGH_PASS_MOVEMENT repositioning), the HEADER contestant selection two-step, and various handler wiring improvements. The architecture is sound — server-authoritative state, pure-function engine, injected dice — but the review surfaces four blockers: goals scored are never written to the event log (making replay scores wrong), an intra-team tiebreak in HEADER uses `Math.random()` (non-deterministic inside a supposedly pure function), missing `broadcastState` snap-backs on several error paths leave clients desynced, and a `KICK_OFF_SETUP` zone validation flaw allows the defending team to stand on the centre-hex boundary line.

## Critical Issues

### CR-01: GOAL events never appended to eventLog — replay scores always 0–0

**File:** `packages/server/src/gameEngine.ts:1013-1031`

**Issue:** The `SHOT` branch in `applyRoll` handles `outcome === 'GOAL'` by incrementing `state.score` and transitioning to `KICK_OFF_SETUP`, but it spreads `...state` without appending any event to `eventLog`. The `buildReplayFrames` function reconstructs scores by replaying `GOAL` events from the log (line 1910–1921). Because no `GOAL` event is ever appended, replay always shows 0–0 for both teams regardless of what happened during the match. The `REPLAY_ELIGIBLE_TYPES` set at line 1832 includes `'GOAL'`, confirming the intent was to log it.

**Fix:**

```typescript
// In the GOAL outcome block, append a GOAL event before returning:
if (shotResultWithPenalty.outcome === 'GOAL') {
  const newScore = {
    ...state.score,
    [state.attackingTeam]: state.score[state.attackingTeam] + 1,
  };
  const goalEvent: ActionEvent = {
    type: 'GOAL',
    scoringTeam: state.attackingTeam,
    timestamp: Date.now(),
  };
  return {
    ok: true,
    state: {
      ...state,
      phase: 'KICK_OFF_SETUP',
      score: newScore,
      ball: { position: state.ball.position, carrierId: null },
      lastDiceRoll: { rolls: [shooterDice, gkDice, handlingDice], context: 'SHOT_DUEL' },
      lastActionType: null,
      snapshotPenalty: false,
      eventLog: [...state.eventLog, goalEvent],
    },
  };
}
```

### CR-02: `Math.random()` inside pure engine function — non-deterministic intra-team tiebreak

**File:** `packages/server/src/gameEngine.ts:1143`

**Issue:** `pickWinner()` uses `Math.floor(Math.random() * tied.length)` to break same-score ties among contestants on the same team. The engine is documented as "pure — ARCH-01" and all other stochastic operations use injected dice. This call to `Math.random()` means:

1. The function is not deterministic; passing the same dice array twice can produce different outcomes.
2. The winning contestant ID logged in the HEADER event may not match the contestant that `pickWinner` returns in a test environment — tests cannot reproduce tiebreak scenarios reliably.
3. The injected `dice` array already provides a natural per-contestant tiebreak (earliest contestant in the array wins on true equality of heading+die). Using it avoids the non-determinism.

**Fix:** Replace `Math.random()` with a stable tiebreak — use the first tied entry (earliest in contestant list order), which is deterministic and reproducible from the same dice array:

```typescript
const pickWinner = (results: CR[]): CR | undefined => {
  if (results.length === 0) return undefined;
  const max = Math.max(...results.map((r) => r.raw));
  return results.find((r) => r.raw === max); // stable: first highest wins
};
```

### CR-03: Missing `broadcastState` snap-back in `GAME_RESTART_MOVEMENT` error paths — client desync

**File:** `packages/server/src/gameHandlers.ts:502-513`

**Issue:** The `GAME_RESTART_MOVEMENT` handler emits `GAME_ERROR` on three failure paths (null gameState, wrong phase, wrong team, engine rejection) but never calls `broadcastState`. All other handlers in this file call `broadcastState(io, room)` after emitting an error to snap the offending client back to the authoritative state. Without the snap-back, a client that sends an illegal `GAME_RESTART_MOVEMENT` emits an error toast but its local Zustand store retains whatever optimistic state it applied, diverging from the server's state.

**Fix:** Add `broadcastState(io, room)` after each `socket.emit(ServerEvents.GAME_ERROR, ...)` call in the handler (lines 503, 507, 512):

```typescript
if (room.gameState === null || room.gameState.phase !== 'MOVEMENT') {
  socket.emit(ServerEvents.GAME_ERROR, 'WRONG_PHASE');
  broadcastState(io, room); // snap-back
  return;
}
if (!isActivePlayer(socket, room)) {
  socket.emit(ServerEvents.GAME_ERROR, 'WRONG_TEAM');
  broadcastState(io, room); // snap-back
  return;
}
const result = applyRestartMovement(room.gameState);
if (!result.ok) {
  socket.emit(ServerEvents.GAME_ERROR, result.reason);
  broadcastState(io, room); // snap-back
  return;
}
```

### CR-04: `KICK_OFF_SETUP` zone validation off-by-one — defending team can stand on centre hex boundary

**File:** `packages/server/src/gameEngine.ts:1726-1733`

**Issue:** `applyKickOffReady` checks the defending team's half-zone constraint as:

- `home` defending: `piece.position.q > limit` where `limit = kickOffHex.q - 1 = 17` → rejects if `q > 17`, i.e. allows `q = 17`.
- `away` defending: `piece.position.q < limit` where `limit = kickOffHex.q + 1 = 19` → rejects if `q < 19`, i.e. allows `q = 19`.

But `kickOffHex.q = 18` is the centre hex. The defending team is **not** allowed on `q = 18` (the centre hex boundary), only pieces strictly in their own half. The check should reject defenders at `q >= 18` (for home defending) and `q <= 18` (for away defending). As written, a home-defending piece at `q = 17` is allowed — that is correct — but the centre hex itself (`q = 18`) is excluded from the attacking team's validation only. The defending team at `q = 18` is separately caught by `IN_CENTRE_CIRCLE` only if that hex is in the centre circle. The centre hex `{q:18, r:13}` is in the centre circle so this specific hex is caught, but hexes on the centre line at `q = 18` with other `r` values are NOT in the centre circle and pass the check incorrectly. The client `selectPiece` logic in `useGameStore.ts` line 309 correctly applies `q < 18` for defending home and `q > 18` for defending away, exposing the server/client inconsistency.

**Fix:** The defending team limit should use strict `kickOffHex.q` boundaries:

```typescript
for (const piece of teamPieces) {
  if (team === 'home') {
    // Attacking: q <= 18; defending: strictly q < 18 (out of attacking half)
    const limit = isAttacking ? kickOffHex.q : kickOffHex.q - 1;
    if (piece.position.q > limit) return { ok: false, reason: 'OUT_OF_ZONE' };
  } else {
    // Attacking: q >= 18; defending: strictly q > 18 (out of attacking half)
    const limit = isAttacking ? kickOffHex.q : kickOffHex.q + 1;
    if (piece.position.q < limit) return { ok: false, reason: 'OUT_OF_ZONE' };
  }
}
```

This is the existing logic and is actually correct for those hexes not on the centre line. The bug is that defending pieces at exactly `q=18` (other than the kickOffHex `r=13`) are not rejected by `OUT_OF_ZONE` (limit is 17, so `q=18 > 17` would reject — wait, this is `piece.position.q > limit`, and limit for home defending is `kickOffHex.q - 1 = 17`. So if `piece.position.q = 18`, then `18 > 17 = true` → rejected. The logic is actually correct. Withdraw this finding — the `q > 17` guard correctly catches `q = 18`. The client uses `q < 18` which is also correct (excludes 18 and above). The server uses `limit = 17`, reject if `q > 17` which equals reject if `q >= 18`. These are equivalent.

**Revised assessment:** CR-04 is retracted — the zone guard is correct. Replacing it with the info-level observation below.

### WR-01: HEADER LOOSE_BALL case sets `lastActionType: 'HEADER'` — wrong, should be `'DEFLECTION'`

**File:** `packages/server/src/gameEngine.ts:1162-1175`

**Issue:** When neither team selects a header contestant (case `c`), the code transitions to `LOOSE_BALL` with `lastActionType: 'HEADER'`. `ELIGIBLE_NEXT_ACTIONS['HEADER']` returns `{MOVEMENT, FIRST_TIME_PASS, SNAPSHOT}` — it does NOT include `LONG_BALL` or `STANDARD_PASS`. But after a LOOSE_BALL resolves, the correct next-action set is `ELIGIBLE_NEXT_ACTIONS['DEFLECTION']`. The LOOSE_BALL `applyRoll` branch already sets `lastActionType: 'DEFLECTION'` when it resolves, so the HEADER→LOOSE_BALL transition's `lastActionType` is overwritten on the next roll. However, if the client reads `ELIGIBLE_NEXT_ACTIONS['HEADER']` before the LOOSE_BALL roll happens (which won't happen in practice for LOOSE_BALL since ActionPanel auto-emits), this is technically incorrect. It represents a latent correctness issue.

**Fix:**

```typescript
// case (c): neither team selected → LOOSE_BALL
lastActionType: 'DEFLECTION', // correct for LOOSE_BALL entry
```

### WR-02: `applyRoll` PASS branch re-runs `validatePass` after carrier position may have changed (HIGH_PASS path)

**File:** `packages/server/src/gameEngine.ts:830-836`

**Issue:** In the accurate-pass path, `applyRoll` calls `validatePass(state, carrier, carrier.position, targetHex, validatePassType)`. For HIGH_PASS, `state.ball` has already been moved to `targetHex` (the handler sets `ball: { position: targetHex, carrierId: null }` at line 663 before entering `HIGH_PASS_MOVEMENT`). When the defender-slot end-turn triggers `applyRoll`, the `stateForRoll` has `ball.carrierId` restored from `highPassCarrierId` but the `carrier` lookup at line 758 will find the carrier piece still at its original position (the piece wasn't moved — only `ball.position` changed). So `validatePass` receives the correct `carrier.position`. This is benign in practice, but it means the server re-validates the original pass path even though both teams have repositioned during `HIGH_PASS_MOVEMENT`. The interception check in step 5 of `validatePass` runs against the ORIGINAL piece positions, not the post-repositioning positions. This means post-repositioning interception opportunities may not be caught.

**Fix:** For HIGH_PASS, the interception loop in `applyRoll` should use the current `state.pieces` (post-repositioning), which it does — but `validatePass` uses `state` from `stateForRoll` which has the repositioned pieces (restored from `hpState`). This is correct. However, the pass-path blocking check in `validatePass` step 3 uses `hexLine(from, to)` with the original piece positions — repositioned defenders on the path line would not be detected as blockers since the adjacency check at line 1 of the path is the only one applied for HIGH_PASS. This is functionally consistent with the comment at line 83 ("only an opponent immediately adjacent to the kicker on the path blocks") so blocking is not a real issue. The interception result (`interceptors`) from the re-run `validatePass` call at line 830 is used for the interception loop, but `preGeneratedInterceptionDice` was set at the time of the INITIAL pass request (before repositioning). If a defender moved into interception range during `HIGH_PASS_MOVEMENT`, they would not be in `preGeneratedInterceptionDice`, and the interception dice loop at line 868 would use `?? 3` (default die) rather than a newly rolled die. This inconsistency means defenders who moved into position DURING repositioning get a free default-3 die rather than a proper random roll.

**Fix:** Pre-generate interception dice inside the defender-slot end-turn handler, after `stateForRoll` is constructed, using the post-repositioning piece positions. Currently dice are generated at the INITIAL pass roll (before repositioning) and stashed in `preGeneratedInterceptionDice`.

### WR-03: `GAME_SHOT` handler never calls `broadcastState` even on the error path — client may desync on malformed payloads

**File:** `packages/server/src/gameHandlers.ts:756-781`

**Issue:** The `GAME_SHOT` handler intentionally skips `broadcastState` after accepting the shot target (as documented in the comment: "Intentionally no broadcastState call"). However, the error paths for `WRONG_PHASE`, `WRONG_TEAM`, and `INVALID_TARGET` also skip `broadcastState`. While this is intentional for the success path (the shot is merely bookkeeping), on error paths there is no snap-back. Other handlers consistently call `broadcastState` after emitting errors. If the client is in an unexpected phase (e.g. due to a race condition), not receiving a snap-back means the client's stale state is never corrected. This is a lower-severity inconsistency because `GAME_SHOT` is bookkeeping-only, but the pattern breaks the ARCH-04 invariant for error paths.

**Fix:** Add snap-back `broadcastState` calls to the three error-return paths in the handler. The "no snap-back" comment should be scoped to the success path only.

### WR-05: `confirmPassTarget` auto-emits for all pass types including HIGH_PASS before repositioning — correct but brittle

**File:** `packages/client/src/store/useGameStore.ts:243-263`

**Issue:** `confirmPassTarget` emits `GAME_ROLL` immediately for all pass types including `HIGH_PASS`. This is correct — the server handler processes HIGH_PASS by entering `HIGH_PASS_MOVEMENT` immediately. But the comment at lines 245-247 says "no Roll Dice button" for all types. The danger is that if `selectedPassType` is `null` at the time `confirmPassTarget` fires (possible if the state cleared it from a prior `setGameState` call in a rapid render), the `GAME_ROLL` is emitted without a `passType`, triggering `MISSING_PASS_TYPE` on the server. The condition at line 247 guards all four explicit pass type strings, so `null` is excluded. However, the early guard at line 247 does not have an `else` branch that prevents falling through to `set({ passTargetHex: hex })` on an unknown passType — but since the function is only reachable with a valid `selectedPassType`, this is low risk. Still, the `else` branch at line 261 is reachable when `selectedPassType` is a non-null value not in the four listed strings (only possible if the TypeScript types are widened), which would silently set `passTargetHex` without emitting anything.

**Fix:** Add a TypeScript exhaustive check or narrow the condition to avoid the silent-fallthrough else:

```typescript
confirmPassTarget: (hex) => {
  const { selectedPassType } = get();
  if (selectedPassType === null) return; // guard added
  socket.emit(ClientEvents.GAME_ROLL, selectedPassType, hex);
  set({ selectedPassType: null, validPassTargetHexes: [], interceptionRiskHexes: [], passTargetHex: null });
},
```
