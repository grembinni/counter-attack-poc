## Summary

Phase 8.2 is an engine-and-UI wiring phase with no new infrastructure: all primitive functions (`validatePass`, `validatePassAccuracy`, `hexLine`, `getZoIDefenders`, `computeCombinedScore`, `validateHeading`) exist and are correct or nearly so. The deliverables are:

1. **One validator fix** — `validatePassAccuracy` uses `piece.dribbling` for Long Pass types; change to `piece.highPass`. One line.
2. **`applyRoll` PASS branch rewrite** — the branch currently always calls `validatePassAccuracy(carrier, 'HIGH', d1, [])` regardless of pass type. It must branch on `state.lastActionType` to apply accuracy only for HIGH/LONG types, skip accuracy for STANDARD/FIRST_TIME, move the ball to `targetHex` on success, and run the interception auto-roll loop before the accuracy check.
3. **`game:roll` payload extension** — extend the client emit and server handler to carry `targetHex: HexCoord` when `phase === 'PASS'`. Server validates target via `validatePass` before `applyRoll`.
4. **Three-step ActionPanel** — add a target hex selection step between pass type choice and Roll.
5. **HexGrid pass target highlighting** — green for safe targets, amber for interception-risk (reuse `hexZoIRisk` CSS class).
6. **Header contestant selection UI** — HEADER phase shows a contestant-selection period for both teams before "Contest" button resolves the duel. Uses the existing `applyRoll` HEADER branch but wires a new selection state layer around it.
7. **HEAD-04/HEAD-05 server guards** — `contestedPieceIds` tracked on GameState; Movement Phase skips contested pieces.
8. **LOOSE_BALL trajectory walk** — current `applyRoll` LOOSE_BALL branch calls `computeLooseBall` and lands at a hex directly; D-23 adds a hex-by-hex walk that stops on the first occupied hex.

The single largest design decision is the header contestant selection UI: it requires both teams to act before the roll resolves, which means the HEADER phase must wait for two `game:header-select` (or equivalent) events before `game:roll` becomes valid. The existing `applyRoll` HEADER branch can handle the duel once both teams have confirmed their selections; the new work is the pre-roll selection protocol.

**Primary recommendation:** Extend `GameState` with `passTargetHex`, `validPassTargetHexes`, `interceptionRiskHexes`, and `headerContestants` (per-team selected piece IDs), then wire each layer independently, finishing with tests at each step.

### Pattern 1: applyRoll PASS Branch — Per-Type Accuracy Branching

**What:** The current PASS branch always calls `validatePassAccuracy(carrier, 'HIGH', d1, [])`. Phase 8.2 replaces this with a switch on `state.lastActionType`.

**When to use:** Every `applyRoll` call with `state.phase === 'PASS'`.

**Current code (gameEngine.ts ~line 728) — the PROBLEM:**

```typescript
// BUG: always uses HIGH accuracy regardless of pass type
const accuracyResult = validatePassAccuracy(carrier, 'HIGH', d1, []);
```

**Fixed pattern:**

```typescript
// Source: CONTEXT.md D-01 through D-05; validatePassAccuracy signature (passValidator.ts:135)
case 'PASS': {
  const carrier = state.pieces.find((p) => p.id === state.ball.carrierId);
  if (!carrier) return { ok: false, reason: 'WRONG_PHASE' };
  if (!state.passTargetHex) return { ok: false, reason: 'MISSING_TARGET' };

  const passTimeCost = state.lastActionType === 'FIRST_TIME_PASS' ? 0 : 1;
  const newLastActionType = (state.lastActionType as LastActionType) ?? 'STANDARD_PASS';

  // D-01/D-02: Standard and First-time always reach target — skip accuracy check
  const requiresAccuracyCheck = newLastActionType === 'HIGH_PASS' || newLastActionType === 'LONG_BALL';
  let accurate = true;

  if (requiresAccuracyCheck) {
    // D-03: HIGH threshold 8; D-04: LONG threshold 9 (both use carrier.highPass)
    const accuracyType = newLastActionType === 'HIGH_PASS' ? 'HIGH' : 'LONG_SAME_THIRD';
    const accuracyResult = validatePassAccuracy(carrier, accuracyType, d1, []);
    accurate = accuracyResult.accurate;
  }

  if (accurate) {
    // Run interception loop BEFORE committing ball delivery (D-11)
    // ... (see Pattern 2)
    const targetHex = state.passTargetHex;
    const teammateAtTarget = state.pieces.find(
      (p) => p.teamId === carrier.teamId && p.position.q === targetHex.q && p.position.r === targetHex.r
    );
    const newPhase: GamePhase = newLastActionType === 'HIGH_PASS' ? 'HEADER' : 'PASS';
    return {
      ok: true,
      state: {
        ...state,
        phase: newPhase,
        ball: { position: targetHex, carrierId: teammateAtTarget?.id ?? null },
        lastActionType: newLastActionType,
        actionCount: state.actionCount + passTimeCost,
        passTargetHex: null,  // clear after delivery
      },
    };
  } else {
    // Inaccurate → LOOSE_BALL (existing pattern, D-05)
    return {
      ok: true,
      state: {
        ...state,
        phase: 'LOOSE_BALL',
        ball: { position: state.ball.position, carrierId: null },
        lastDiceRoll: { rolls: [d1], context: 'PASS_ACCURACY' },
        actionCount: state.actionCount + passTimeCost,
      },
    };
  }
}
```

### Pattern 2: Interception Auto-Roll Loop

**What:** Before committing ball delivery on an accurate pass, roll for each interceptor. Mirrors the steal mechanic from Phase 8.1.

**When to use:** After accuracy check passes (or skipped for STANDARD/FIRST_TIME), before updating `ball`.

```typescript
// Source: CONTEXT.md D-11/D-12; mirrors applyMove STEAL_ATTEMPT (PATTERNS.md 08.1)
// Interceptors already computed by validatePass — passed in via state.passTargetHex resolution
const passResult = validatePass(state, carrier, carrier.position, state.passTargetHex, passType);
const interceptors = passResult.ok ? passResult.interceptors : [];

for (let i = 0; i < interceptors.length; i++) {
  const interceptor = interceptors[i]!;
  const die = interceptionDice[i] ?? 3; // pre-generated in handler
  const combined = computeCombinedScore(interceptor.tackling, die, []);
  const intercepted = die === 6 || combined >= 10; // same as steal rule (D-11)
  if (intercepted) {
    return {
      ok: true,
      state: {
        ...state,
        phase: 'PASS',
        ball: { position: interceptor.position, carrierId: interceptor.id },
        attackingTeam: interceptor.teamId, // possession changes team
        lastActionType: 'SUCCESSFUL_TACKLE',
        actionCount: state.actionCount + passTimeCost,
        passTargetHex: null,
      },
    };
  }
}
// No interception — proceed to ball delivery
```

### Pattern 3: Pass Target Hex Storage in GameState

**What:** Store `passTargetHex` on `GameState` so `applyRoll` can consume it without requiring an additional parameter. This follows the existing `shotTarget` pattern on the Room object (gameHandlers.ts ~line 536) — the difference being that `passTargetHex` must survive into `applyRoll` whereas `shotTarget` is cosmetic.

**Two viable approaches:**

Option A is cleaner: `applyRoll` is already pure (reads from `state`), and all other contextual state (like `snapshotPenalty`) uses this pattern. [ASSUMED]

### Pattern 4: pass target highlighting (client-side)

**What:** Compute valid pass targets when pass type is selected. Split into safe (green) and interception-risk (amber) subsets.

**When to use:** When `selectedPassType` changes in the ActionPanel flow.

```typescript
// Source: CONTEXT.md D-07/D-09; mirrors selectPiece's hexesInRange + validateMove pattern (08.1-PATTERNS.md)
// In useGameStore — new action: setSelectedPassType(type)
setSelectedPassType: (passType) => {
  const { gameState } = get();
  const carrier = gameState.pieces.find((p) => p.id === gameState.ball.carrierId);
  if (!carrier) return;

  const opponents = gameState.pieces.filter((p) => p.teamId !== carrier.teamId);
  const validTargets: HexCoord[] = [];
  const interceptionRisk: HexCoord[] = [];

  for (const hex of PITCH_HEXES) {
    const result = validatePass(gameState, carrier, carrier.position, hex, passType);
    if (!result.ok) continue;
    validTargets.push(hex);
    // D-09: interception-risk = any intermediate path hex has an adjacent opponent
    const path = hexLine(carrier.position, hex).slice(1, -1);
    const atRisk = path.some((pathHex) => getZoIDefenders(pathHex, opponents).length > 0);
    if (atRisk) interceptionRisk.push(hex);
  }

  set({ selectedPassType: passType, validPassTargetHexes: validTargets, interceptionRiskHexes: interceptionRisk });
},
```

**Performance note:** PITCH_HEXES has 962 hexes. `validatePass` is O(1) to O(n) per call (path check). Worst case: 962 \* Long Pass validation. Long Pass skips path blocking, only checks distance and landing constraints — fast. Standard Pass path check uses `hexLine` which is O(distance). At most 36 hexes per path. This is well within browser budget for a one-time computation on user input. [ASSUMED — no profiling done, but grid is small and game is click-driven]

### Pattern 5: Header Contestant Selection Protocol

**What:** Both teams select a piece (or decline) before the header roll resolves. The existing `applyRoll` HEADER branch needs to know which pieces were selected. The current implementation uses nearest-defender auto-selection.

### Anti-Patterns to Avoid

- **Always-HIGH accuracy check:** The current `applyRoll` PASS branch applies `validatePassAccuracy(carrier, 'HIGH', d1, [])` for every pass type. Standard and First-time passes must NOT call `validatePassAccuracy` at all.
- **Rolling dice in applyRoll:** `applyRoll` is pure. All dice (including interception dice) must be pre-generated in the handler and passed in. Follow the existing `dice = [d1, d2, d3]` varargs pattern or extend the function signature.
- **Client-side ball authority:** `passTargetHex` received from the client must be server-validated via `validatePass` before being trusted. The client pre-validates for UX, but the server is authoritative (ARCH-01).
- **Iterating all 962 PITCH_HEXES in a re-render hot path:** Compute `validPassTargetHexes` only on pass type selection, not on every render tick. Store the result in Zustand and clear it on phase change.
- **Re-rendering whole HexGrid on target hover:** Use the O(1) Set membership pattern (`validPassTargetHexSet.has(hexId)`) as done for `validMoveHexSet`.
- **Using nearest-defender auto-select for header duel after 8.2:** The existing `applyRoll` HEADER branch finds the nearest defender automatically. Phase 8.2 replaces this with `headerContestants` from `GameState`. The old auto-select code must be removed or gated.

## Common Pitfalls

### Pitfall 1: Accuracy Check for Standard and First-time Passes

**What goes wrong:** Calling `validatePassAccuracy` for STANDARD or FIRST_TIME pass types (which always succeed). The current code already does this for HIGH.
**Why it happens:** The `applyRoll` PASS branch was written when only HIGH passes existed in tests.
**How to avoid:** Gate the accuracy check behind `if (lastActionType === 'HIGH_PASS' || lastActionType === 'LONG_BALL')`.
**Warning signs:** Unit tests for STANDARD pass showing inaccurate rolls.

### Pitfall 2: Ball Does Not Move on Accurate Pass (Existing Bug)

**What goes wrong:** After an accurate pass, `applyRoll` currently only changes `phase` and `lastActionType`. `ball.position` stays at the passer's hex. This means every "accurate" pass in the current code leaves the ball where it was.
**Why it happens:** Target hex was never stored; the engine had no destination to write.
**How to avoid:** Ensure `state.passTargetHex` is set by the handler before `applyRoll` is called. Assert in tests that `result.state.ball.position` equals `targetHex` after accurate pass.

### Pitfall 3: Client Trusting Its Own validatePass Result as Server Authoritative

**What goes wrong:** Client highlights valid targets, player clicks one, but server rejects it as invalid (race condition: state changed between highlight computation and roll emit).
**How to avoid:** Server always re-runs `validatePass` on the incoming `targetHex` (D-10). Client must handle `INVALID_TARGET` error by snapping back and re-computing highlights.

### Pitfall 4: Interception Dice Pre-Generation

**What goes wrong:** `applyRoll` is called with `d1, d2, d3` (3 dice). But the interception loop may need up to 10 dice (one per interceptor). If dice are not pre-generated in the handler, the engine would need to generate them internally — violating the pure-function constraint (Pitfall 1 from Phase 8.1 RESEARCH.md).
**How to avoid:** Pre-generate an interception dice pool in the handler (e.g., `interceptionDice: number[]` with one die per potential interceptor, computed after `validatePass` identifies the interceptors). Either pass them through `state.preGeneratedInterceptionDice` or extend the `applyRoll` signature. Pattern: same as the `tackleDie + carrierDie` approach in Phase 8.1.

### Pitfall 5: Header HEADER Phase — Both Teams Must Act Before Roll

**What goes wrong:** The active team can click Roll immediately when `phase === 'HEADER'`, before the opponent has selected their contestant.
**How to avoid:** The Roll button must check that both `state.headerConfirmed.home` and `state.headerConfirmed.away` are true before enabling. Server must reject `game:roll` for HEADER phase if `headerConfirmed` is not complete.

### Pitfall 6: contestedPieceIds Cleared at Wrong Time (HEAD-05)

**What goes wrong:** If `contestedPieceIds` is cleared immediately after the header duel (instead of after the subsequent Movement Phase), HEAD-05 is never enforced.
**How to avoid:** Clear in `applyStartMovement` (or `applyEndTurn` at ATTACKER_2 end), not in `applyRoll` HEADER branch. The field persists through the PASS action-choice phase that follows the header.

### Pitfall 7: hexLine slice(1,-1) Returns Empty for Short Passes

**What goes wrong:** A pass to an adjacent hex (distance 1) has `hexLine(from, to)` = `[from, to]`. `slice(1, -1)` returns `[]`. This is correct — no intermediate hexes to check for interception risk, and no path-blocking intermediate hexes.
**Why it matters:** The interception-risk highlight logic must handle this correctly (empty intermediate path = safe path, no interception risk). The existing `validatePass` already handles this correctly; the client-side highlight logic must not assume a non-empty intermediate path.

### Pitfall 8: ELIGIBLE_NEXT_ACTIONS.LONG_BALL Includes HEADER (Already Done)

**What might go wrong:** Assuming the LONG_BALL → HEADER eligibility isn't yet in the table. Inspection confirms: `LONG_BALL: new Set(['MOVEMENT', 'HEADER'])` in `actionSequence.ts:85`. No changes needed here.

### Pitfall 9: The Existing applyRoll HEADER Branch Auto-Selects Nearest Defender

**What goes wrong:** After Phase 8.2, the HEADER branch currently picks the nearest defending outfielder automatically. If the new `headerContestants` state is not set (e.g., if game transitions to HEADER via the old code path), the duel will fail with a missing contestant.
**How to avoid:** Guard in `applyRoll` HEADER branch: if `state.headerContestants` is undefined or unset, fall back to the existing nearest-defender logic for backward compat during transition, or hard-reject with WRONG_PHASE. Recommendation: use the fallback during the transition and add a TODO.

// Source: CONTEXT.md D-23; uses hexLine from hex.ts
// After computeLooseBall resolves direction + distance to a landing hex:
case 'LOOSE_BALL': {
  const landingHex = computeLooseBall(
    state.ball.position,
    d1 as 1|2|3|4|5|6,
    d2 as 1|2|3|4|5|6,
  );
  // D-23: walk the trajectory hex-by-hex from ball.position toward landing
  // hexLine includes start and end; we walk from index 1 to end inclusive
  const trajectory = hexLine(state.ball.position, landingHex).slice(1);
  let finalPosition = landingHex;
  let finalCarrierId: string | null = null;
  for (const hex of trajectory) {
    const occupant = state.pieces.find((p) => p.position.q === hex.q && p.position.r === hex.r);
    if (occupant) {
      finalPosition = hex;
      finalCarrierId = occupant.id;
      break;
    }
  }
  // D-24: if landing on empty hex, last-controlling attackingTeam can only start Movement Phase
  return {
    ok: true,
    state: {
      ...state,
      phase: 'MOVEMENT',  // or 'PASS' depending on D-24 ownership rule
      movementSlot: 'ATTACKER_4',
      movedPieceIds: [],
      paceUsedByPieceId: {},
      ball: { position: finalPosition, carrierId: finalCarrierId },
      lastDiceRoll: { rolls: [d1, d2], context: 'LOOSE_BALL' },
      lastActionType: 'DEFLECTION',
    },
  };
}

## Open Questions (RESOLVED)

1. **HEAD-05 clearing timing**
   - What we know: contested pieces must be excluded from the Movement Phase _after_ the header.
   - What's unclear: If the attacking team wins the header and the game enters PASS phase, then the team starts a Movement Phase — `applyStartMovement` fires. Should `contestedPieceIds` be cleared _before_ or _after_ the exclusion check in that call?
   - Recommendation: Clear at the end of `applyStartMovement` after using the list to build exclusions for that particular movement. This ensures one Movement Phase is blocked, then cleared.
