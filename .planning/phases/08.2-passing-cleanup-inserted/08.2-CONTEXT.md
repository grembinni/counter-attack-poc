<domain>
## Phase Boundary

Deliver end-to-end passing: player selects a target hex on the board, accuracy checks use the correct attribute per pass type, the ball moves to target on an accurate/successful pass, adjacent defenders auto-intercept, and header duels (HEAD-01/02/04/05) resolve after High Pass and Long Ball.

**In scope:**

- Target hex selection UI — choose pass type → board highlights valid targets → click hex → Roll enables
- Accuracy checks: Standard and First-time always reach target; High Pass `highPass + die >= 8`; Long Pass `highPass + die >= 9`
- **Correction to `passValidator.ts`:** Long Pass accuracy currently uses `piece.dribbling` — must change to `piece.highPass`
- Ball delivery: after accurate pass, `ball.position` = `targetHex`, `ball.carrierId` = teammate at target (or null if empty)
- High Pass → HEADER phase (mandatory heading contest)
- Long Ball → PASS action choice includes Header button
- Header selection UI: both teams select eligible players (green ring); deselect by clicking again; warn if no selection; if neither team selects → LOOSE_BALL
- Header duel (HEAD-01/02): 1-hex range = normal roll; 2-hex range = -1 penalty; uncontested = attacker auto-wins (HEAD-02)
- HEAD-04: no two consecutive headed passes
- HEAD-05: players who challenged a header cannot participate in the next Movement Phase
- Interception: auto server-roll for each interceptor in `interceptors[]` (die=6 OR tackling+die≥10); first success transfers possession
- Interception-risk visual: pass targets reachable only via an interception-risk path shown in amber (same color as Phase 8.1 ZoI/tackle-risk hexes)
- Loose Ball trajectory: server checks each path hex in sequence; first occupied hex = ball stops there, that player takes possession
- Loose Ball landing on empty hex: last-controlling team can only start Movement Phase; if opposing team has a player there, they take possession

**Out of scope (deferred to Phase 8.3):**

- HEAD-03: headed attempt at goal (headed shot → GK save)
- Shot target selection UI
- Cross-third Long Pass threshold distinction (9 vs 10 by pitch region)
- SNAP-02, SNAP-03, remaining shot flows
- Code review debt (CR-01, WR-01..04)

<decisions>
## Implementation Decisions

### Pass Accuracy — Attribute + Threshold per Type

- **D-01:** **Standard Pass** — no accuracy check. Ball always reaches the target hex (subject to path validation). `validatePassAccuracy` is NOT called for STANDARD. The existing `validatePass` path-blocking check (PASS-01: cannot pass through any occupied hex) still applies.

- **D-02:** **First-time Pass** — no accuracy check. Ball always reaches the target hex. Range ≤6 hexes. The `FIRST_TIME_PLAYER_MOVES` effect from `validatePass` must be handled by the engine (see Claude's Discretion).

- **D-03:** **High Pass** — accuracy check: `carrier.highPass + die >= 8`. The existing `validatePassAccuracy(carrier, 'HIGH', d1, [])` call is correct for attribute and threshold. Inaccurate → LOOSE_BALL phase.

- **D-04:** **Long Pass** — accuracy check: `carrier.highPass + die >= 9`. **Correction required:** `validatePassAccuracy` currently uses `piece.dribbling` for Long Pass types. Change to `piece.highPass`. The threshold 9 applies for now (same-third vs cross-third distinction to 8.3). Inaccurate → LOOSE_BALL phase.

- **D-05:** The `applyRoll` PASS branch must branch on `state.lastActionType` to apply the correct accuracy logic per pass type, replacing the current always-HIGH check.

### Target Hex Selection Flow

- **D-06:** Three-step flow in PASS phase: (1) player chooses pass type in ActionPanel; (2) board highlights all valid target hexes for that type (computed client-side); (3) player clicks a valid target hex to confirm target; Roll button enables. Pass type + target hex are both required before Roll is active.

- **D-07:** Valid target computation — client iterates all pitch hexes, calls `validatePass(state, carrier, carrier.position, hex, passType)` for each. Hexes returning `ok: true` are highlighted. Computed on pass type selection; cleared when pass type changes or is deselected.

- **D-08 [informational]:** Pass range constants (from passValidator.ts — no changes needed): Standard ≤11, First-time ≤6, High ≤15, Long uncapped. These are enforced inside `validatePass` and do not need to be re-checked client-side.

- **D-09:** Interception-risk visual — when computing valid target hexes, also compute the travel path (`hexLine(from, target)`) and check if any path hex is within 1 hex of an opponent. Targets whose travel paths are interception-risk are shown in amber (same color as Phase 8.1 ZoI/tackle-risk hexes, D-20 from `08.1-CONTEXT.md`). Safe targets are green. A target can be both reachable and at-risk simultaneously.

- **D-10:** Target hex sent to server — client emits the target hex alongside the roll (`game:roll` payload extended with `{ passType, targetHex: HexCoord }` when `phase === 'PASS'`). Server validates target before applying roll (calls `validatePass` server-side as the authoritative check before `applyRoll`).

### Interception Resolution

- **D-11:** **Auto server-roll** — when `validatePass(state, carrier, from, targetHex, passType)` returns `interceptors[]` (non-empty), the server rolls for each interceptor in list order: `die === 6 OR (tackling + die >= 10)` → success. First successful interceptor becomes the new ball carrier. Mirrors Phase 8.1 steal mechanic (D-05/D-06 in `08.1-CONTEXT.md`). No client interaction required.

- **D-12:** Post-interception state: `ball.carrierId = interceptor.id`, `ball.position = interceptor.position`, `phase = 'PASS'`, `lastActionType = 'SUCCESSFUL_TACKLE'`. The intercepting team gets the same eligible next actions as after a successful tackle per `ELIGIBLE_NEXT_ACTIONS`.

- **D-13 [informational]:** No interception for Long Pass (PASS-04 / already enforced in `passValidator.ts` — Long Pass returns `interceptors: []` always).

### Ball Delivery on Accurate Pass

- **D-14:** After a successful/accurate pass (no interception): `ball.position = targetHex`. If a teammate occupies `targetHex`, `ball.carrierId = teammate.id`. If `targetHex` is empty, `ball.carrierId = null` (ball loose at that hex). Phase transitions to PASS (action choice) for the attacking team, EXCEPT:
  - After High Pass: phase = HEADER (mandatory heading contest)
  - After Long Ball where `lastActionType = 'LONG_BALL'`: phase = PASS (Header is one eligible action)

- **D-15:** `lastActionType` after accurate pass: `STANDARD_PASS`, `FIRST_TIME_PASS`, `HIGH_PASS`, or `LONG_BALL` respectively.

### Header Logic (HEAD-01/02/04/05 — Phase 8.2 scope)

- **D-16:** **Header phase entry** — HEADER phase is entered after:
  - Accurate High Pass → `applyRoll` PASS branch sets `phase: 'HEADER'` (already coded)
  - Long Ball where the ball-carrier's team chooses "Header" as next action from PASS phase (ActionPanel shows a Header button when `lastActionType === 'LONG_BALL'`)

- **D-17:** **Player selection UI** — when `phase === 'HEADER'`, both teams enter a contestant selection period. Each team can click any of their eligible pieces (within 2 hexes of `ball.position`) to toggle a green ring indicator. Clicking a selected piece removes the ring. No auto-advance — players confirm their selection via a "Contest" (or "Pass" for "don't contest") button.

- **D-18:** **Eligible distance rules (HEAD-01)**:
  - ≤1 hex from `ball.position`: eligible, no dice penalty
  - ≤2 hexes from `ball.position` (and > 1 hex): eligible, -1 dice penalty

- **D-19:** **Duel resolution**:
  - Both teams select: duel between the selected attacker and selected defender. If a team selects multiple (edge case): use the nearest piece to `ball.position`.
  - Combined score: `heading + die` (with -1 if the piece is 2 hexes away)
  - Attacker wins on tie or if highest score
  - Uncontested (attacker selects, defender doesn't): attacker wins automatically (HEAD-02, no dice roll)
  - Defender selects but attacker doesn't: attacker wins by default (they have possession)
  - Neither team selects: warn, then → LOOSE_BALL from `ball.position`

- **D-20:** **HEAD-04** — Consecutive headed passes are not allowed. Server guards: if `lastActionType === 'HEADER'`, `HEADER` action is not in `ELIGIBLE_NEXT_ACTIONS`. Reject `game:header` attempts when `lastActionType === 'HEADER'`.

- **D-21:** **HEAD-05** — Pieces that contested a header (were selected and rolled) cannot participate in the subsequent Movement Phase. Server tracks contested piece IDs from the header event. When `applyStartMovement` fires, contested pieces are excluded from `movablePieceIds` for that movement sequence only.

- **D-22:** **HEAD-03 deferred** — Headed attempt at goal (attacker wins duel → GK save attempt) is Phase 8.3. For Phase 8.2, if attacker wins the header duel: ball possession transfers to attacker at `ball.position`, game enters PASS phase (action choice).

### Loose Ball Trajectory Enhancement

- **D-23:** When LOOSE_BALL direction+distance resolves, server walks the trajectory hex-by-hex from `ball.position`. For each hex in order: if any piece occupies that hex, the ball stops there. That piece (regardless of team) becomes `ball.carrierId`, `ball.position = that hex`, game enters PASS phase with all post-movement eligible actions (same as SUCCESSFUL_TACKLE).

- **D-24:** If the ball reaches its final landing hex with no piece there: `ball.carrierId = null`. `lastActionType = 'DEFLECTION'`. Phase = PASS. The team that last controlled the ball before the Loose Ball (`attackingTeam` remains theirs) can ONLY start a Movement Phase. If the opposing team has a piece at the landing hex, they take possession (PASS phase, post-movement eligible actions).

### Claude's Discretion

- **FIRST_TIME_PLAYER_MOVES effect** — `validatePass` returns `effect: { type: 'FIRST_TIME_PLAYER_MOVES' }` for First-time Pass (PASS-02: each team moves 1 player 1 hex as the ball travels). If implementing this mid-pass player move creates significant scope risk for Phase 8.2, Claude may defer it to Phase 8.3 and mark it as a `// TODO: FIRST_TIME_PLAYER_MOVES` in the engine. The core First-time Pass delivery (always accurate, ≤6 hexes) must be done in Phase 8.2.
- **Header selection simultaneous vs sequential** — Whether both teams select simultaneously (no waiting) or sequentially (attacker selects, then defender) is Claude's UX call. Simultaneous (both teams reveal selection at the same time) avoids gaming the selection. Implementation detail.
- **Target hex validation on Roll** — Whether the server re-runs `validatePass` on the `game:roll` handler (before calling `applyRoll`) or trusts the client pre-validation is Claude's call. Server-side validation is the more correct approach.
- **game:roll payload extension** — Claude determines the exact shape for passing `targetHex` through the `game:roll` event (or whether a separate `game:select-pass-target` event is cleaner). Follow the existing pattern in `gameHandlers.ts`.
- **HEAD-05 tracking structure** — Where to store "pieces that contested the header" (e.g., on `GameState` as `contestedPieceIds: string[]` or on the Room object) is Claude's call. It must be cleared after the movement phase that follows the header.

</decisions>

## Specific Ideas

- **Three-step ActionPanel flow for PASS phase:**
  1. Choose pass type (existing choose-phase buttons)
  2. Board highlights valid targets (green for safe, amber for interception-risk); player clicks one
  3. Roll button activates with label "Roll for [Pass Type]" — for Standard/First-time where no accuracy check exists, could be relabeled "Execute Pass" but Roll is fine since interception is still auto-rolled

- **Interception-risk highlighting logic (D-09):** For each valid target hex, compute `hexLine(carrier.position, targetHex).slice(1, -1)` (intermediate hexes). If any intermediate hex has `getZoIDefenders(hex, opponents).length > 0` (i.e., an opponent is adjacent to the travel path), mark as `isInterceptionRisk`. Apply `hexZoIRisk` CSS class (same amber from Phase 8.1).

- **Long Pass accuracy attribute fix:** One-line change in `validatePassAccuracy` for `passType === 'LONG_SAME_THIRD'` and `'LONG_CROSS_THIRD'`: change `piece.dribbling` → `piece.highPass`.

- **Header contestant green ring:** SVG `<circle>` or `<rect>` stroke drawn around the piece circle, filled `none`, stroke `#22c55e` (or equivalent green). Toggled by clicking the piece when `phase === 'HEADER'`. Client-only — no server event needed until both teams confirm their selection.

- **LOOSE_BALL trajectory walk implementation:** After direction + distance dice resolve, compute the landing hex. Walk each step from `ball.position` in the direction. At each intermediate hex, check `state.pieces.some(p => p.position.q === hex.q && p.position.r === hex.r)`. First match → stop, that player picks up ball. No match at end → ball lands unclaimed.
