<objective>
Revert the D-19 selectedIsMoving counter implementation from Plan 25-03 (Task 3) and fix the Undo button gate — both surfaced as bugs during the Plan 05 UAT.

Three bugs confirmed:

- Bug A: The counter decrements when a piece is SELECTED, but it should only decrement when a move is COMMITTED (piece reaches its destination). Plan 25-03's `selectedIsMoving` decrement-on-selection must be removed entirely.
- Bug B: The current behavior is backwards — count goes DOWN when a player is selected, then BACK UP when they actually move. This is because `selectedIsMoving` goes false as soon as `paceUsedByPieceId` is updated (move committed), removing the -1 while the move hasn't yet crossed into `currentSlotLockedCount` (pace not yet exhausted). The result is a flickering counter that feels wrong.
- Bug C: The Undo button should be DISABLED when no move has been committed yet in the current slot. The current event-log boundary approach allows undoing moves from previous turns because the SLOT_ADVANCE / KICK_OFF boundary events do not correctly bound the start of every new MOVE phase (e.g. the transition between Team A's turn end and Team B's turn start has no boundary event in the log).

The fix is a targeted revert of Task 3 from Plan 25-03 plus a simple paceUsedByPieceId guard added to the shared canUndo IIFE.

Purpose: Restore correct counter behavior (commit-only decrement) and gate the Undo button so it cannot reach across turn boundaries.
Output: selectedIsMoving removed, remaining formula restored, canUndo MOVE-phase guard added. No server changes, no new files.
</objective>
