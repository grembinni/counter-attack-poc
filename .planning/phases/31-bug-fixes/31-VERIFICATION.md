### Gaps Summary

Two of the four observable truths this phase was scoped to deliver are not actually achieved in the live codebase, despite both plans' own regression suites passing and both SUMMARY.md files reporting success:

1. **BUG-30 (replay reconstruction) is only 2/5 fixed.** The two `gameEngine.ts` GOAL construction sites correctly populate `piecesAfter`, and `buildReplayFrames` correctly applies it — this part of the fix is solid and verified. But three separate, independently-reachable GOAL construction sites in `gameHandlers.ts` (all "GK too far out of range to reach the shot path" auto-goal branches — a normal, non-exotic outcome, not an edge case) still construct their `GOAL` event without `piecesAfter`. `buildReplayFrames` has no fallback for a GOAL event missing this field, so replays of goals scored via any of these 3 paths still show every player frozen at stale pre-goal positions — the exact symptom BUG-30 was filed to fix, left open for a common code path. This gap was known and explicitly documented as unresolved in the 31-01 SUMMARY's own "Known Follow-up Gap" section, but no later plan in this phase closed it.

2. **The folded header-winner eligibility todo (BUG-31 family) does not survive into the Movement Phase it is meant to protect.** `applyResolveHeaderTarget`'s fix is correctly implemented as specified — it appends the winner's id to `movedPieceIds` while transitioning to the `PASS` phase. However, `applyStartMovement`, which is the only function in the codebase that transitions `PASS` (or `KICK_OFF`/`LOOSE_BALL`) into the `MOVE` phase, unconditionally resets `movedPieceIds: []` with no special-case for ids added by a preceding header resolution. This was independently confirmed by chaining the two functions with the project's own test fixtures: the winner's id is present immediately after `applyResolveHeaderTarget` and is gone by the time `applyStartMovement` produces the `MOVE`-phase state. The 4 new regression tests added by plan 31-04 only assert the intermediate `PASS`-phase return value directly from `applyResolveHeaderTarget` and never pipe that state through `applyStartMovement`, so the suite is green despite the defect persisting in the real game flow (client `canSelect` gates and phase-completion checks both key off `movedPieceIds`, so the header-winning piece is fully selectable again once the Movement Phase actually begins).

Both gaps were independently re-derived from the codebase (not copied from `31-REVIEW.md`) via direct file reads and, for the header-winner gap, an empirical chained-function execution — confirming the code review's CR-01 and CR-02 findings are accurate and unresolved as of this verification.

REQUIREMENTS.md's `[x]` Complete markers for BUG-30 (and, depending on how the folded todo is attributed, BUG-31) do not match the current codebase state and should not be trusted as evidence of closure.

Both gaps have a documented, minimal fix path already spelled out in `31-REVIEW.md`'s "Fix" sections (CR-01, CR-02) and should be closed via `/gsd-plan-phase 31 --gaps`.
