# Phase 7.1: Code Review Report

**Reviewed:** 2026-06-03T00:00:00Z
**Depth:** standard
**Files Reviewed:** 15
**Status:** issues_found

## Summary

Reviewed 15 files covering the Phase 7.1 UI cleanup: pitch markings, goal nets, difficult-angle indicators, player stats panel, team positions, lobby screen, and shared pitch/team data. The implementation is generally sound in structure. Three blockers were identified: stale selection state persisting across server-pushed game state updates, an uncleared timeout leaking across component unmounts, and a silent type safety hole in the stats panel that will render meaningless output for non-numeric attributes at runtime. Four warnings cover logic gaps in SHOT-phase highlighting, missing accessibility on interactive SVG elements, a wrong-team navigation guard for player 2 in the lobby, and a validation gap in `hexesInRange` for a pace of 0.

## Critical Issues

### CR-01: `setGameState` does not clear `selectedPieceId` / `validMoveHexes` — stale highlights persist after server update

**File:** `packages/client/src/store/useGameStore.ts:97`

**Issue:** `setGameState` replaces game state wholesale but does not reset `selectedPieceId` or `validMoveHexes`:

```ts
setGameState: (state) => set({ gameState: state }),
```

After the server broadcasts a new `GameState` (e.g., after an opponent moves, or after a phase transition to `SHOT`), the client can still have a piece selected from the previous turn and a stale set of valid-move hexes highlighted. Consequences:

- A hex that was a valid move in the previous turn can still appear gold after the opponent's move completes and positions have changed.
- In a `SHOT` phase the `validMoveHexes` array is meaningless yet the highlights are visible, visually conflicting with the red goal-hex highlights.
- `selectPiece` recomputes `validMoveHexes` via `validateMove(gameState, ...)` — if `selectedPieceId` is not cleared, the stale piece ID will be read back by `PlayerStatsPanel` and `HexGrid` without revalidation.

**Fix:**

```ts
setGameState: (state) =>
  set({ gameState: state, selectedPieceId: null, validMoveHexes: [] }),
```

### CR-02: `CopyButton` `setTimeout` leaks on unmount — state update on unmounted component

**File:** `packages/client/src/components/LobbyScreen.tsx:14-16`

**Issue:** `CopyButton` schedules a 2-second `setTimeout` to reset the label back to `'Copy Code'` but never cancels it on unmount. If the user clicks "Copy Code" and then navigates away (e.g., the game starts and the screen transitions to `GAME_BOARD`) before the 2 seconds expire, the timeout callback fires and calls `setLabel('Copy Code')` on an unmounted component. In React 18 strict mode this is a warning; in all React versions it is a state update on a dead component reference that can cause subtle bugs.

```ts
function handleClick() {
  void navigator.clipboard?.writeText(code ?? '').catch(() => undefined);
  setLabel('Copied!');
  setTimeout(() => {
    // ← no ref stored, never cancelled
    setLabel('Copy Code');
  }, 2000);
}
```

**Fix:**

```tsx
import { useState, useEffect, useRef } from 'react';

function CopyButton({ code }: { code: string | null }) {
  const [label, setLabel] = useState<'Copy Code' | 'Copied!'>('Copy Code');
  const timerRef = useRef<ReturnType<typeof setTimeout> | null>(null);

  useEffect(() => {
    return () => {
      if (timerRef.current !== null) clearTimeout(timerRef.current);
    };
  }, []);

  function handleClick() {
    void navigator.clipboard?.writeText(code ?? '').catch(() => undefined);
    setLabel('Copied!');
    if (timerRef.current !== null) clearTimeout(timerRef.current);
    timerRef.current = setTimeout(() => {
      setLabel('Copy Code');
      timerRef.current = null;
    }, 2000);
  }

  return (
    <button className={styles.ctaButton} onClick={handleClick}>
      {label}
    </button>
  );
}
```

### CR-03: `PlayerStatsPanel` casts non-numeric attributes with `as number` — silent wrong output

**File:** `packages/client/src/components/PlayerStatsPanel.tsx:50`

**Issue:** `STAT_LABELS` is typed `Array<[keyof PlayerPiece, string]>`, which includes string keys such as `id`, `teamId`, `name`, and `role`. The cast `piece[attr] as number` silences TypeScript but does not prevent accessing those string fields at runtime. If a future developer adds a non-numeric key to `STAT_LABELS` by mistake (or if the type definition of `PlayerPiece` changes), the panel will silently render `"home"`, `"GK"`, etc. as stat values with no compile-time error.

The current `STAT_LABELS` only contains numeric keys, so this is latent rather than an immediate display bug — but the cast removes all safety.

**Fix:** Constrain the key type to only numeric fields of `PlayerPiece`:

```ts
type NumericPieceKey = {
  [K in keyof PlayerPiece]: PlayerPiece[K] extends number ? K : never;
}[keyof PlayerPiece];

const STAT_LABELS: Array<[NumericPieceKey, string]> = [
  ['pace', 'Pace'],
  ['shooting', 'Shooting'],
  // ... etc
];

// Render without cast — TS now knows piece[attr] is number:
<span className={styles.statValue}>{piece[attr]}</span>
```

## Warnings

### WR-01: `shotTargetHighlight` is never cleared when game state changes phase out of `SHOT`

**File:** `packages/client/src/components/HexGrid.tsx:57, 89-91, 99-102`

**Issue:** `shotTargetHighlight` is local `useState` in `HexGrid`. It is set when the player clicks a goal hex during the `SHOT` phase, but it is never cleared. When the server transitions out of `SHOT` phase (e.g., to `MOVEMENT` after a save, or `GOAL` after a score) and sends a new `GameState`, `phase` changes but `shotTargetHighlight` remains set. On the next render the condition on line 110 becomes:

```ts
highlightColor={isGoalHex || isShotTarget ? '#ef4444' : undefined}
```

`isGoalHex` is now `false` (phase is no longer `SHOT`), but `isShotTarget` is still `true` for the previously targeted hex. That hex will keep a red tint and remain visually highlighted even after the shot resolves.

**Fix:** Clear `shotTargetHighlight` in response to the game phase changing out of `SHOT`. Since `phase` is read from the store, a `useEffect` is the right tool:

```ts
useEffect(() => {
  if (phase !== 'SHOT') setShotTargetHighlight(null);
}, [phase]);
```

### WR-02: `onRoomJoined` only transitions to `WAITING` for player 1 — player 2 stays on `JOIN_ROOM` after joining

**File:** `packages/client/src/App.tsx:39`

**Issue:**

```ts
if (slot === 1 && s === 'CREATE_ROOM') setScreen('WAITING');
```

This guard correctly moves the room creator (slot 1) from `CREATE_ROOM` to `WAITING`. But when player 2 successfully joins, `slot === 2`, so no navigation happens — player 2 stays on the `JOIN_ROOM` screen indefinitely. The game will start correctly when both are connected (because `onGameState` transitions to `GAME_BOARD`), but player 2 will see the raw `JOIN_ROOM` form while waiting for the game to begin, rather than a "Waiting for game to start…" state. This is a UX correctness bug: the `WAITING` screen (which exists for this purpose) is never shown to player 2.

**Fix:**

```ts
if (slot === 1 && s === 'CREATE_ROOM') setScreen('WAITING');
if (slot === 2 && s === 'JOIN_ROOM') setScreen('WAITING');
```

### WR-03: `hexesInRange` is called with `pace: 0` for GK `highPass` — returns center hex only, but this may generate misleading valid-move highlights if pace is 0

**File:** `packages/client/src/store/useGameStore.ts:92-93`, `packages/shared/src/teams.ts:30`

**Issue:** GK players have `highPass: 0`. The `selectPiece` logic uses `piece.pace` (not `highPass`) so this is not triggered by selection, but GK's `pace` is 2 (`home-0`) and 3 (`away-0`) so `hexesInRange` works for movement. However, outfield players have `handling: 0` and `aerialAbility: 0`. These zeros are correctly not used in movement logic now, but `STAT_LABELS` in `PlayerStatsPanel` displays them as `0` in the UI panel without any "N/A" indication. A value of `0` out of a 1–10 scale is misleading to players: they will read `Handling: 0` and `Aerial Ability: 0` as the player being terrible at those skills, when the correct interpretation is "not applicable".

**Fix:** Render `—` (em dash) instead of `0` for attributes that represent "not applicable":

```tsx
<span className={styles.statValue}>
  {(piece[attr] as number) === 0 ? '—' : (piece[attr] as number)}
</span>
```

### WR-04: Interactive SVG piece circles lack `aria-label` / `role` — keyboard and screen-reader inaccessible

**File:** `packages/client/src/components/PieceOverlay.tsx:42-54`

**Issue:** The base piece `<circle>` is the interactive click target for piece selection, but it has no `role`, `aria-label`, or `tabIndex`. SVG `<circle>` elements are not focusable by default. Players using keyboard navigation cannot select pieces, and screen readers receive no information about what the element represents. The `<polygon>` in `HexCell` similarly receives click handlers without accessibility attributes (line 39).

**Fix:** For `PieceOverlay`:

```tsx
<circle
  cx={cx}
  cy={cy}
  r={10}
  fill={fill}
  stroke={stroke}
  strokeWidth={1.5}
  role="button"
  tabIndex={isClickable ? 0 : -1}
  aria-label={`${piece.name} (${piece.role})`}
  style={{ cursor: isClickable ? 'pointer' : 'default' }}
  onClick={() => {
    onInspect();
    if (isClickable) onClick();
  }}
  onKeyDown={(e) => {
    if (e.key === 'Enter' || e.key === ' ') {
      onInspect();
      if (isClickable) onClick();
    }
  }}
/>
```

### IN-01: `validMoveHexSet` is rebuilt on every render of `HexGrid`

**File:** `packages/client/src/components/HexGrid.tsx:60`

**Issue:**

```ts
const validMoveHexSet = new Set(validMoveHexes.map((h) => `${h.q},${h.r}`));
```

This `Set` construction runs inside the component body on every render. Because `HexGrid` subscribes to several store slices, any store change (ball position, active team, phase change) triggers a re-render and rebuilds the Set even when `validMoveHexes` itself has not changed. This is not a performance blocker (the set is at most ~37 entries and construction is O(n)), but it is wasteful.

**Fix:** Memoize with `useMemo`:

```ts
const validMoveHexSet = useMemo(
  () => new Set(validMoveHexes.map((h) => `${h.q},${h.r}`)),
  [validMoveHexes],
);
```

### IN-02: Formation comment says "4-5-2 (1 GK, 4 DEF, 3 MID, 2 FWD)" but teams have 11 players including 3 FWD

**File:** `packages/shared/src/teams.ts:11`

**Issue:** The comment reads:

```
// Formation: 4-5-2 (1 GK, 4 DEF, 3 MID, 2 FWD — note: 3 MID + 2 FWD = 5 outfield attackers).
```

Both squads actually have 3 FWD players (ids `home-8`, `home-9`, `home-10` / `away-8`, `away-9`, `away-10`), making the formation 4-3-3 by player count, not 4-5-2. The note trying to reconcile "3 MID + 2 FWD = 5" is arithmetically correct only if one of the FWDs is counted as a MID, which is not reflected in the `role` fields. This creates confusion between the game's canonical formation (4-5-2) and the actual data.

**Fix:** Update the comment to match reality:

```
// Formation: 4-3-3 as coded (1 GK, 4 DEF, 3 MID, 3 FWD = 11 players).
// The board game specifies 4-5-2; upgrade formation data in a later phase if needed.
```

### IN-03: `GoalNets` uses hardcoded magic pixel coordinates with no derivation comment

**File:** `packages/client/src/components/GoalNets.tsx:17-18, 29-30`

**Issue:** The rect coordinates (`y={346.4}`, `height={242.5}`, `x={1110}`) are not derived from `HEX_SIZE` or any documented formula. The goal net rects must align with the actual goal hexes (q=0/q=36, r=10–16). If `HEX_SIZE` is ever changed from 20, these coordinates will be wrong and the nets will mis-align. `PitchMarkings.tsx` has the same issue with its hardcoded coordinates but at least has a comment explaining it was derived from real board measurements; `GoalNets` has no such derivation.

**Fix:** Derive from `HEX_SIZE` and the goal row range (r=10 to r=16), or at minimum add a comment showing the formula:

```ts
// y = axialToPixel(0, 10).cy - HEX_SIZE * sqrt(3)/2 ≈ 346.4 at HEX_SIZE=20
// height = axialToPixel(0, 16).cy - axialToPixel(0, 10).cy + HEX_SIZE * sqrt(3) ≈ 242.5
// Recompute if HEX_SIZE changes.
```
