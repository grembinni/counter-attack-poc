## Summary

Phase 7.1 is a UI polish pass with no new server logic, no new socket events, and no FSM changes. Every deliverable is a pure client or shared-data change. The work divides into four independent tracks: (1) data corrections in `packages/shared` (team positions, difficult angle hexes), (2) SVG overlay additions in `HexGrid.tsx` (pitch line markings, goal nets), (3) new `PlayerStatsPanel` component wired to `selectedPieceId`, and (4) lobby UX micro-improvements plus debug cleanup.

All pixel coordinates for SVG markings are computed deterministically from the existing `axialToPixel` formula (HEX_SIZE=20, flat-top, ODD-Q offset). The pitch SVG spans absolute x∈[10,1110] and y∈[34.6,900.7] in SVG viewport space (after the `<g translate(20, 17.32)>` transform). Markings are placed inside the same `<g>` so they share that transform and clip path automatically.

The stats panel integrates cleanly: `useGameStore((s) => s.selectedPieceId)` already exists and drives movement highlights; the panel adds a second consumer of the same selector without modifying the store. The panel renders only when a piece is selected — `null` otherwise — and sits between `<ActionPanel>` and `<ActionLog>` in the `GameBoard` sidebar.

**Primary recommendation:** Implement all four tracks as independent, sequential tasks within a single wave. No task depends on another; they can be reviewed and committed individually.

### Pattern 1: SVG Pitch Markings as a Sub-Component

**What:** A `PitchMarkings` function component returns a React fragment of SVG elements placed as Layer 4 inside the existing `<g>` in `HexGrid.tsx`. It receives no props — all coordinates are constants derived from `axialToPixel`.

**When to use:** Any new cosmetic pitch overlay element goes into `PitchMarkings`.

### Pattern 2: PlayerStatsPanel Component

**What:** A named-export React component that reads `selectedPieceId` and `gameState.pieces` from Zustand and renders a stat card. Returns `null` when no piece is selected.

**When to use:** Any component that needs to display a piece's attributes follows this pattern.

```tsx
// Source: useGameStore.ts — per-slice selectors (Pitfall 6 avoidance)
export function PlayerStatsPanel() {
  const selectedPieceId = useGameStore((s) => s.selectedPieceId);
  const pieces = useGameStore((s) => s.gameState.pieces);

  if (!selectedPieceId) return null;
  const piece = pieces.find((p) => p.id === selectedPieceId);
  if (!piece) return null;

  return (
    <div className={styles.panel}>
      <div className={styles.panelHeader}>
        {piece.name} — {piece.role}
      </div>
      {/* attribute rows */}
    </div>
  );
}
```

**Store change:** No store modification needed. `selectedPieceId` is already set by `selectPiece()` (which clears on toggle) and cleared on `emitMove()`. The stats panel is purely additive — it reads the existing selector.

**D-06 detail:** The active player uses `selectedPieceId` to compute `validMoveHexes`. The non-active player can also click any piece to trigger `selectPiece()` — but because `canSelect` in `PieceOverlay` is gated to `isActivePlayer && phase === 'MOVEMENT'`, non-active-player clicks need a separate click handler on `PieceOverlay`. See Pitfall 2 below.

### Pattern 3: LobbyScreen Join Loading State

**What:** Add local `isJoining` state to `JoinRoomScreen`. Set to `true` on submit, reset to `false` when `roomError` arrives (via a `useEffect` watching `roomError`). On success the screen navigates away, so no reset needed on the success path.

```tsx
// Source: LobbyScreen.tsx — existing handleSubmit pattern
const [isJoining, setIsJoining] = useState(false);
const roomError = useGameStore((s) => s.roomError);

// Reset loading state when server returns an error
useEffect(() => {
  if (roomError) setIsJoining(false);
}, [roomError]);

function handleSubmit() {
  if (input.length === 0 || isJoining) return;
  setRoomError(null);
  setIsJoining(true);
  socket.emit(ClientEvents.ROOM_JOIN, input);
}
```

Button renders as `disabled={input.length === 0 || isJoining}` with label `isJoining ? 'Joining...' : 'Join Game'`.

### Anti-Patterns to Avoid

- **Second SVG root for overlays:** Never add a second `<svg>` for pitch markings. All overlay elements live inside the same `<svg>` root (established pattern, HexGrid.tsx comment). [VERIFIED: codebase]
- **Axial arithmetic for ODD-Q rendering:** Pixel positions for markings come from `axialToPixel()`, not from raw axial arithmetic. The `axialToPixel` function already handles ODD-Q offset stagger. [VERIFIED: hexToPixel.ts]
- **Emitting piece selection to server:** Stats panel piece selection is local state only (D-06). Never add `socket.emit` to the stats inspection click path.
- **Modifying selectedPieceId store shape:** Do not add a separate `inspectedPieceId` store field. Re-use `selectedPieceId` — it already holds what the stats panel needs.
- **clipPath coordinates in absolute SVG space:** The `clipPath` element uses `local` coordinate space (inside `<g translate(20, 17.32)>`). New pitch markings also live inside that `<g>` and must use the same local coordinate space. Pass `local` coords (pre-translate) to SVG elements inside `<g>`. [VERIFIED: HexGrid.tsx CLIP_X comment]

## Common Pitfalls

### Pitfall 1: Goal Hex Fill Not Updating After D-10

**What goes wrong:** `HexCell` has `const isGoal = isInRegion(hex, 'homeGoal') || isInRegion(hex, 'awayGoal')` and `baseFill = isGoal ? '#1a1a1a' : ...`. Removing the `'#1a1a1a'` override is the full change — the ODD-Q 3-colour formula `isDark = (2r + q%2) % 3 === 2` already computes the correct grass colour for goal hexes. [VERIFIED: HexCell.tsx line 31]

**How to avoid:** Delete the `isGoal` const and the `isGoal ? '#1a1a1a' :` ternary in `baseFill`. No other changes needed.

**Warning sign:** If goal hexes still render dark after the change, check that `HexGrid.tsx` is not overriding `highlightColor` for goal hexes during non-SHOT phases. Looking at the code: `highlightColor` is only set to `'#ef4444'` when `phase === 'SHOT'` — no conflict.

### Pitfall 2: Non-Active Player Cannot Click Pieces to View Stats

**What goes wrong:** `PieceOverlay` wraps click handlers behind `canSelect` (which requires `isActivePlayer && phase === 'MOVEMENT'`). If stats panel relies only on the existing `selectPiece` pathway, non-active players cannot open stats.

**How to avoid:** Add a second click handler on `PieceOverlay` that is ALWAYS wired (regardless of `canSelect`) and calls a `setInspectedPiece(id)` action — OR — change the `selectedPieceId` semantics so it is always settable by any client.

**D-06 resolution:** The context says `selectedPieceId` continues to drive movement highlights and stats display is "additive". The cleanest implementation: always attach an `onClick` to `PieceOverlay` that calls `selectPiece(piece.id)`, and make `selectPiece` toggle correctly. The valid-move computation inside `selectPiece` is harmless for non-moveable pieces (returns empty array). Current `selectPiece` already handles toggling. The problem is `PieceOverlay.onClick` is conditionally `() => undefined` for non-active players.

**Recommended fix:** Pass an `onInspect` prop to `PieceOverlay` that calls `selectPiece(piece.id)` unconditionally. `canSelect` controls whether the piece is highlighted as "moveable"; `onInspect` fires regardless.

### Pitfall 3: Pitch Markings in Wrong Coordinate Space

**What goes wrong:** Pixel coordinates computed via `axialToPixel` (which starts from `cx = HEX_SIZE*(3/2)*q`) are local to the `<g>` transform. The `<g translate(20, 17.32)>` adds (TX=20, TY=17.32) to everything inside. Markings added inside `<g>` must use the raw `axialToPixel` output (NOT adding TX/TY again). If you add TX/TY, all markings shift by 20px right and 17px down.

**How to avoid:** Use `axialToPixel(q, r)` directly for all coordinates of SVG elements placed inside `<g>`. The translate is already applied by the `<g>` tag.

**Computed local coordinates (inside `<g>`):**

- Halfway line: `x1=540 y1=17.3 x2=540 y2=883.3`
- Centre circle: `cx=540 cy=450.3 r≈103.9`
- Home penalty box: `x=-10 y=173.2 w=210 h=536.9`
- Away penalty box: right edge at `x_right=1090`
- Home 6-yard box: `x=-10 y=294.4 w=80 h=329.1`
- Home goal net: `x=-30 y=346.4 w=20 h=242.5`

### Pitfall 4: pitch.test.ts Hardcodes Old Difficult Angle Hexes

**What goes wrong:** `pitch.test.ts` line 87 asserts `isDifficultAngle({ q: 3, r: 7 })` returns `true`. After D-11 moves all hexes to corners, `{q:3,r:7}` is no longer a difficult angle hex and the test fails.

**How to avoid:** Update `pitch.test.ts` to test a corner hex (e.g. `{q:0,r:0}`) instead of the old penalty-area hex. The count test (16 hexes) still passes — no structural change.

### Pitfall 5: teams.test.ts Has No Position Validation

**What goes wrong:** No existing test checks that positions are within the 37×26 grid bounds. An out-of-range position (e.g. `r:26`) will not be caught by current tests.

**How to avoid:** When updating teams.ts, verify all positions manually (or add a brief test). The computed positions all have q∈[1,35] and r∈[6,20] — well within [0,36]×[0,25]. [VERIFIED: computation above]

### Pitfall 6: WaitingScreen "Share code" Text Duplication

**What goes wrong:** `CreateRoomScreen` already has `<p className={styles.body}>Share this code with your opponent.</p>`. `WaitingScreen` currently has `Share this code to invite someone:`. D-04 adds "Share the code above with your opponent." to WaitingScreen. This is consistent with `CreateRoomScreen` but not a duplicate — they are separate sub-screens.

**How to avoid:** Replace the WaitingScreen body text exactly as specified: `"Share the code above with your opponent."` No other text changes needed in that sub-screen.

   - What we know: `PieceOverlay.onClick` is `canSelect ? () => selectPiece(piece.id) : () => undefined`. `canSelect` requires `isActivePlayer && phase === 'MOVEMENT'`.

   - Recommendation: Read `PieceOverlay.tsx` before implementing D-06. If the SVG `<circle>` has no onClick in non-select mode, add one unconditionally.

2. **Goal net position — inside or outside clip boundary?**
   - What we know: The clip rect left edge is at local x=-10, right edge at x=1090. The home goal net at x=-30 width=20 sits at x∈[-30,-10] — OUTSIDE the clip boundary.
   - What's unclear: Goal nets are intentionally "just outside the pitch boundary" per D-09, which implies they should NOT be clipped.
   - Recommendation: Place goal net `<rect>` elements OUTSIDE the `<g clipPath="url(#pitch-clip)">` but still inside the outer `<g translate>`. Or render them before the clipPath `<g>` starts. This ensures they are visible at the pitch ends.
