# Phase 17.1 Plan 13: FIRST_TIME_PASS interception-loop bypass (CR-02-new) Summary

**Extended the applyRoll PASS-case interception bypass guard (previously header-pass-only) to also exclude FIRST_TIME_PASS, so an accurate first-time pass aimed near a defender now reaches FIRST_TIME_PASS_MOVE instead of being silently intercepted into SUCCESSFUL_TACKLE.**

## Accomplishments

- Closed CR-02-new: a FIRST_TIME_PASS aimed within interception range of an opposing defender (on
  the pass path or within ZoI of the path/target) no longer gets short-circuited into
  `SUCCESSFUL_TACKLE` by the autoIntercepts/rollIntercepts loop before the
  `FIRST_TIME_PASS_MOVE` transition is ever reached.
- Verified the fix does not regress STANDARD_PASS auto-interception (BUG-04/D-10), header-pass
  bypass (BUG-01), HIGH_PASS/LONG_BALL interception-skip (passValidator's pre-existing
  LONG/HIGH guard), or the accurate-FTP-no-defender D-03 path.
- Added two regression tests: one proving the new FTP-near-defender bypass, one proving
  STANDARD_PASS near the identical defender position/dice still auto-intercepts (no-regression
  guard for the unmodified branch).

## Files Created/Modified

  tests: the FTP-near-defender bypass assertion, and a STANDARD_PASS-near-the-same-defender
  no-regression assertion.

## Decisions Made

- Chose the bypass-guard extension (verifier's option (a)) over reordering the transition block
  (option (b)): lower risk, minimal diff, leaves `passValidator.ts` and the transition block's
  dependent setup (`newLastActionType`, `passTargetHex`, `eventLog`) untouched.
- Did not reuse the existing `firstTimePassState` fixture (homeFWD q:10,r:7 → homeMID q:17,r:7,
  distance 7) for the new regression test: that distance exceeds the FIRST_TIME pass range cap of
  6, so `validatePass` returns `RANGE_EXCEEDED` and `passResult.ok` is `false`, which makes
  `autoIntercepts`/`rollIntercepts` empty (`[]`) regardless of where a defender is placed — this
  fixture cannot exercise the bypass at all. Built a new fixture with the FTP target at distance 4
  (q:14,r:7) instead, matching the existing `headerPassState`/`passToDefenderState` target-hex
  convention, with the defender placed at ZoI distance 1 from the target
  (passValidator.ts:154-162's destination-ZoI scan) so `rollIntercepts` is genuinely populated.
- Used `newLastActionType` (post-resolution, already computed at gameEngine.ts:1103) rather than
  `state.lastActionType` for the new guard, matching the same variable the
  `FIRST_TIME_PASS_MOVE` transition check at line 1237 uses, per the plan's explicit instruction.

## Deviations from Plan

None - plan executed exactly as written. The plan's suggested fixture-derivation note ("Build a
FIRST_TIME_PASS state derived from firstTimePassState") was a non-binding suggestion qualified by
"or adjacent to" sourcing; the plan's own acceptance criteria required the seeded scenario to
"produce a non-empty intercept list in passValidator," which the existing `firstTimePassState`
fixture cannot do (out-of-range distance empties the lists unconditionally). Building a new
in-range fixture from the same shared piece literals satisfies both the letter and intent of the
plan without deviating from its design.

## Issues Encountered

- Discovered during fixture construction that the existing `firstTimePassState` fixture (used by
  the already-abandoned PASS-02 stub test at line ~537) has a passer-to-target distance of 7,
  exceeding the FIRST_TIME pass range cap of 6. This means `validatePass` already returns
  `RANGE_EXCEEDED` for that fixture, and (separately, out of this plan's scope) `applyRoll` does
  not check `passResult.ok` before proceeding — it falls through with empty intercept lists
  regardless. This pre-existing latent issue is unrelated to CR-02-new and was not touched (it sits
  in the already-documented abandoned `firstTimePassStep` stub scope, which the plan explicitly says
  not to touch). Resolved for this plan's purposes by building a new in-range fixture rather than
  reusing the out-of-range one.
