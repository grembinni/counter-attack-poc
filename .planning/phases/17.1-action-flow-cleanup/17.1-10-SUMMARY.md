# Phase 17.1 Plan 10: Shot-Range Highlight Filter Summary

**Client-side regular-shot goal-line highlight now gates on hexDistance(shooter.position, hex) <= 11, matching the server's existing applyDeclareShot D-09 range gate — fixes UAT Test 7 where all 7 goal-line hexes lit up regardless of shooter position.**

## Accomplishments

- Fixed the diagnosed root cause from `.planning/debug/shot-range-gate-no-filter.md`: `isShootingModeGoalHex`'s regular-shot branch (`shootingMode ||`) had no distance filter, unconditionally highlighting all 7 goal-line hexes whenever shooting mode was active for the active player.
- Added `regularShooter` resolution (`ball.carrierId ? pieces.find(...) : null`) mirroring the existing `snapCarrier` pattern, and gated the regular-shot branch on `hexDistance(regularShooter.position, hex) <= 11` — the exact same threshold the server's `applyDeclareShot` (gameEngine.ts) already enforces.
- Added 7 regression tests to `HexGrid.test.tsx` covering: far-shooter baseline (no goal hexes highlighted), in-range goal hex (distance exactly 11 — boundary case), out-of-range count (only 2 of 7 goal hexes highlighted for the reported shooter position), and a SNAPSHOT_TARGET no-regression check (sibling branch's existing 6-hex gate unaffected).
- Confirmed via direct `hexDistance` calculation (Node REPL) that the reported bug scenario (shooter at `(11,5)`, attacking the q=0 goal) produces exactly 2 in-range goal hexes — `(0,10)` and `(0,11)`, both at distance 11 — versus 5 out-of-range hexes at distances 12-16.

## Decisions Made

- Resolved the regular shooter using the identical `ball.carrierId ? pieces.find((p) => p.id === ball.carrierId) : null` pattern already used for `snapCarrier`, named `regularShooter` to keep both resolutions distinct within the same ternary scope — avoids shadowing or ambiguity since both branches can be evaluated in the same render pass.
- Chose to assert on the rendered `'goal'` highlightType fill color (`rgba(220,50,50,1)`, read directly from `HIGHLIGHT_STYLES` in `HexCell.tsx`) rather than inspecting `onClick` handler identity — this is the actual visual signal a player sees, and is what the bug report and plan's `must_haves.truths` describe ("highlighted as selectable shot targets").
- Used the plan's exact example shooter position `(11,5)` for the primary regression tests (traceable directly to the plan and the original UAT bug report), but computed exact in/out-of-range hex sets via direct `hexDistance` calculation rather than trusting the plan's loosely-worded prose range ("(0,10)-(0,12)") — verified the actual boundary is `(0,10)` and `(0,11)` at distance 11 (IN), with `(0,12)` at distance 12 (OUT).

## Deviations from Plan

None - plan executed exactly as written. The plan's prescribed condition shape (`(shootingMode && regularShooter != null && hexDistance(regularShooter.position, hex) <= 11) || (phase === 'SNAPSHOT_TARGET' && ...)`) was implemented verbatim.

## Issues Encountered

- The plan's prose description of the expected post-fix highlight set for shooter `(11,5)` ("only goal hexes (0,10)-(0,12) should highlight") was imprecise — direct `hexDistance` calculation showed `(0,12)` is at distance 12 (out of range), not 11. Resolved by computing exact distances via the actual `hexDistance`/`toCube` implementation (`packages/shared/src/hex.ts`) before writing test assertions, ensuring tests encode the mathematically correct boundary rather than the plan's approximate prose. This did not require a deviation rule (no code change beyond what the plan specified) — only the test's expected hex set was corrected to match verified math.
