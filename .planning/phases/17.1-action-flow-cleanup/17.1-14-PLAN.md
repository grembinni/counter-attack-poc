<objective>
Close Review-CR-01 (Gap A of the third Phase 17.1 verification cycle): undoing an FTP_MOVE or HP_MOVE
during the FIRST_TIME_PASS_MOVE / HIGH_PASS_MOVE repositioning phase reverts the piece position and the
event log but never resets the phase-specific repositioning lock fields, permanently dead-ending the
slot after a single Undo.

Root cause (independently confirmed by the verifier against the live codebase, 17.1-VERIFICATION.md
gaps block, lines 14, 22-23, 110): applyUndo (gameEngine.ts:818-918) returns a new state that resets
the GENERIC movement fields (paceUsedByPieceId, movedPieceIds, eventLog, pendingFreeMove, ball) at
lines 906-917, but never touches firstTimePassMovedPieceId / firstTimePassPaceUsed (or the
highPassMovedPieceId / highPassPaceUsed equivalents). The verifier traced every site that sets these
fields (gameHandlers.ts:544-545 sets FTP, gameHandlers.ts:333-334 sets HP) and every site that clears
them (gameEngine.ts:1257-1258 on the initial FTP transition; gameHandlers.ts:626-627, 649-650,
693-694, 721-722 on end-turn slot advances) — applyUndo is conspicuously absent from the clearing list.

Consequence: after one Undo during FTP_MOVE, both the client gate (useGameStore.ts:383-392) and the
server GAME_MOVE gate (gameHandlers.ts:502-512) still read firstTimePassMovedPieceId as a locked piece
and firstTimePassPaceUsed >= 1 as pace-exhausted, so no further piece can be selected or moved — the
only escape is End Turn, which then logs an FTP_REPOSITION event citing a piece that never completed its
move. This keeps success criterion 3 FAILED because Undo is explicitly named in the criterion as a
normal action that must remain usable.

Fix: in applyUndo's returned state object, also reset the phase-specific lock fields based on
state.phase. When state.phase === 'FIRST_TIME_PASS_MOVE', add firstTimePassMovedPieceId: null and
firstTimePassPaceUsed: 0. When state.phase === 'HIGH_PASS_MOVE', add highPassMovedPieceId: null and
highPassPaceUsed: 0. Use exactly the null / 0 reset shape already used at gameEngine.ts:1257-1258 and
gameHandlers.ts:693-694/721-722. For all other phases, leave these fields untouched. This is the
minimal, surgical fix; do not alter the move-type lookup (CR-01-old, plan 17.1-11), the slot-boundary
detection, or any other applyUndo logic.

Purpose: make Undo a durable, repeatable action during FTP/HP repositioning instead of a one-shot
dead-end.
Output: the phase-conditional lock-field reset in applyUndo plus regression tests that assert the lock
fields (not just piece position) are reset after Undo.
</objective>

| Boundary                          | Description                                                                                                                                                                                                                                                                                                                                  |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| client (GAME_UNDO emit)           | The client emits GAME_UNDO to reverse its last repositioning move; the server (applyUndo, invoked from gameHandlers GAME_UNDO) is the sole authority for what state results. This plan changes only which fields applyUndo resets in its returned state; it adds no new client-supplied input and no new emit.                               |
| server (applyUndo returned state) | applyUndo executes entirely server-side on the authoritative gameState; the result is broadcast through the existing broadcastState path. The fix widens the set of fields reset on undo (adds the phase-specific lock/pace fields) but never reads client input to decide them — the reset is driven solely by server-resolved state.phase. |
