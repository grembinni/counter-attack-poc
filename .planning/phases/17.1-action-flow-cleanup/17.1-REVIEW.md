# Phase 17.1: Code Review Report

**Reviewed:** 2026-06-19T00:00:00Z
**Depth:** standard
**Files Reviewed:** 35

## Summary

This review re-examines the action-flow-cleanup phase after two gap-closure plans landed on top of the previously-reviewed code: 17.1-12 (client `FIRST_TIME_PASS_MOVE` piece-selection wiring) and 17.1-13 (server interception-loop bypass for `FIRST_TIME_PASS`).

**Both previously-filed Critical findings are confirmed fixed:**

- **CR-01-new (client piece-selection missing for `FIRST_TIME_PASS_MOVE`)** — `useGameStore.ts` `selectPiece()` now has a dedicated `FIRST_TIME_PASS_MOVE` branch (lines 375-406) mirroring `HIGH_PASS_MOVE`, and `HexGrid.tsx` wires `canSelectFirstTimePassMove` / `firstTimePassMovedPieceId` subscriptions and click handlers (lines 86-87, 598-603, 673-674). Confirmed correct.
- **CR-02-new (interception loop shadowing the FTP transition)** — `gameEngine.ts` `applyRoll`'s PASS branch now checks `isFirstTimePass` (line 1158) and skips the auto/roll interception loops for `FIRST_TIME_PASS` (line 1159), routing straight to the `FIRST_TIME_PASS_MOVE` transition (lines 1243-1263). Confirmed correct and covered by a new regression test (`gameEngine.phase17.test.ts:739-767`) plus a same-shape regression guard proving `STANDARD_PASS` still intercepts normally.

While verifying these fixes, this review found **two new Critical-tier defects introduced or exposed by the FTP repositioning flow** that are not covered by any existing test, plus two Warnings and one Info item.

## Critical Issues

### CR-01: `GAME_UNDO` during `FIRST_TIME_PASS_MOVE` (and `HIGH_PASS_MOVE`) permanently locks the repositioning slot

**File:** `packages/server/src/gameEngine.ts:818-917` (`applyUndo`)
**Issue:**
`applyUndo` correctly reverses the piece's _position_ and removes the `FTP_MOVE`/`HP_MOVE` event from `eventLog`, and it correctly updates the generic `paceUsedByPieceId` / `movedPieceIds` fields (lines 873-886). However, the `FIRST_TIME_PASS_MOVE` and `HIGH_PASS_MOVE` flows do **not** use those generic fields for gating — they use the phase-specific `firstTimePassMovedPieceId` / `firstTimePassPaceUsed` (and `highPassMovedPieceId` / `highPassPaceUsed`) fields, which `applyUndo` never touches.

Concretely, after a player moves a piece in `FIRST_TIME_PASS_MOVE` and then calls Undo:

- The piece's position is reverted and the `FTP_MOVE` event is removed from the log (looks like a clean undo).
- `firstTimePassMovedPieceId` is still set to the undone piece's ID, and `firstTimePassPaceUsed` is still `1` (the cap).
- On the client, `useGameStore.ts` `selectPiece()` (FIRST_TIME_PASS_MOVE branch, lines 375-406) computes `paceRemaining = 1 - firstTimePassPaceUsed = 0`, so re-selecting the same piece yields `validMoveHexes: []`, and `lockedId !== id` rejects selecting any other piece (lines 382-387).
- The `GAME_MOVE` handler's `FIRST_TIME_PASS_MOVE` branch (`gameHandlers.ts:508-512`) also rejects any further move with `PACE_EXCEEDED` because `paceUsed >= 1` is still true.

The repositioning slot is now permanently stuck: the only way to proceed is `End Turn`, which logs an `FTP_REPOSITION` event still carrying the **undone** piece's ID (`gameHandlers.ts:684`, `ftpEndState.firstTimePassMovedPieceId`) even though that piece's final position is back at its origin and it never actually completed a move in the slot. This silently fabricates a misleading audit-log entry and denies the player the repositioning action they were entitled to.

This is the same defect for `HIGH_PASS_MOVE` (`highPassMovedPieceId` / `highPassPaceUsed` are equally untouched by `applyUndo`), so it is not new to FTP, but the FTP gap-closure plan (17.1-12/13) added the only test coverage for FTP undo (`gameEngine.phase17.test.ts:668-702`, `game.integration.test.ts:378-413`) and neither test asserts the slot-tracking fields are reset — both only check `piece?.position`. The bug is real and reachable in normal play (move during ATTACKER slot → Undo → stuck).

**Fix:** `applyUndo` must clear the phase-specific lock/pace fields when undoing an `FTP_MOVE` or `HP_MOVE`, mirroring how it already resets the generic fields:

```ts
// inside applyUndo, after computing moveToUndo:
const extraReset =
  state.phase === 'FIRST_TIME_PASS_MOVE'
    ? { firstTimePassMovedPieceId: null, firstTimePassPaceUsed: 0 }
    : state.phase === 'HIGH_PASS_MOVE'
      ? { highPassMovedPieceId: null, highPassPaceUsed: 0 }
      : {};

return {
  ok: true,
  state: {
    ...state,
    pieces: newPieces,
    paceUsedByPieceId: newPaceUsed,
    movedPieceIds: newMovedPieceIds,
    eventLog: newEventLog,
    pendingFreeMove: undoPendingFreeMove,
    ball: newBallAfterUndo,
    ...extraReset,
  },
};
```

Add a regression test that, after `applyUndo` on an FTP_MOVE/HP_MOVE, asserts `firstTimePassMovedPieceId === null` / `firstTimePassPaceUsed === 0` (and the HP equivalents) so the player can re-select and re-move within the same slot.

### CR-02: `FIRST_TIME_PASS_MOVE` ball delivery ignores a defender repositioned onto the target hex

**File:** `packages/server/src/gameHandlers.ts:707-718` (`GAME_END_TURN`, `FIRST_TIME_PASS_MOVE` DEFENDER-slot-complete branch)
**Issue:**
When the DEFENDER repositioning slot completes, the handler delivers the ball to `passTargetHex` by searching only for an **attacking-team** occupant:

```ts
const receiver = ftpEndState.pieces.find(
  (p) =>
    p.teamId === ftpEndState.attackingTeam &&
    p.position.q === targetHex.q &&
    p.position.r === targetHex.r,
);
room.gameState = {
  ...
  ball: { position: targetHex, carrierId: receiver?.id ?? null },
  ...
};
```

This is inconsistent with the equivalent occupant-aware delivery logic in `gameEngine.ts` `applyRoll` for `STANDARD_PASS`/`LONG_BALL` (the "BUG-04" fix, `gameEngine.ts:1265-1297`), which finds **any** occupying piece regardless of team and flips possession if the occupant is on the opposing team.

During the DEFENDER repositioning slot, a defender can legally move up to 1 hex (`gameHandlers.ts:514-531` only checks the destination against other pieces' _current_ positions — it does not exclude `passTargetHex`), and the target hex is frequently within 1 hex of a defender, since the FTP target is often near where the original interceptor/defender was standing (this is exactly the scenario CR-02-new's own fixture proves is reachable — see `gameEngine.phase17.test.ts:710-737`, defender 1 hex from target). If a defender repositions exactly onto `targetHex`:

- `receiver` evaluates to `undefined` (the `find` only matches `attackingTeam`).
- The ball is delivered with `carrierId: null` at a hex that is, in fact, occupied by the defender.
- Possession is left with the attacking team (`activeTeam`/`attackingTeam` unchanged) even though a defending piece is standing on the ball.
- The next `MOVE`/`PASS` action will see a "loose ball" on a hex with a piece already on it — an invalid/ambiguous board state that has no equivalent anywhere else in the codebase (every other delivery path treats "any occupant" as authoritative for pickup).

**Fix:** Mirror the BUG-04 occupant-any-team lookup used elsewhere in the FTP delivery path:

```ts
const occupant = ftpEndState.pieces.find(
  (p) => p.position.q === targetHex.q && p.position.r === targetHex.r,
);
const possessionChanges = occupant !== undefined && occupant.teamId !== ftpEndState.attackingTeam;
room.gameState = {
  ...ftpEndState,
  phase: 'PASS',
  ball: { position: targetHex, carrierId: occupant?.id ?? null },
  attackingTeam: possessionChanges ? occupant!.teamId : ftpEndState.attackingTeam,
  activeTeam: possessionChanges ? occupant!.teamId : ftpEndState.attackingTeam,
  lastActionType: possessionChanges ? 'SUCCESSFUL_TACKLE' : 'FIRST_TIME_PASS',
  ...
};
```

Add an integration test seeding a defender exactly on `passTargetHex` after the DEFENDER repositioning slot and asserting the ball/possession transfers to the defender.

## Warnings

### WR-01: `ActionLog.tsx` does not consolidate consecutive `FTP_MOVE` events into a path

**File:** `packages/client/src/components/ActionLog.tsx:74-153` (`consolidateEvents`)
**Issue:** `consolidateEvents` has dedicated grouping branches for `MOVE`, `GK_KICK_MOVE`, and `HP_MOVE` (each collapses consecutive same-piece/same-slot moves into a single path entry), but no equivalent branch for `FTP_MOVE` — it falls through to the generic `items.push({ kind: 'event', event })` path at line 149. Although the FTP repositioning slot currently caps pace at 1 hex (so there is normally only one `FTP_MOVE` per slot today), this is a latent inconsistency: if the FTP pace cap is ever raised (the HP cap is 3, suggesting FTP may follow), the log will silently regress to one un-consolidated line per hex instead of a single path line, unlike every other movement type in this codebase.
**Fix:** Add an `FTP_MOVE` branch to `consolidateEvents` mirroring the existing `HP_MOVE` block (groupKey `FTP_${event.slot}:${event.pieceId}`, prefix derived from `SLOT_PREFIX`-style mapping), for parity with `HP_MOVE`/`MOVE`/`GK_KICK_MOVE`.

### WR-02: No visual signal that landing on the FTP target hex during the DEFENDER slot determines ball possession

**File:** `packages/server/src/gameHandlers.ts:514-531` (`GAME_MOVE`, `FIRST_TIME_PASS_MOVE` branch); `packages/client/src/components/HexGrid.tsx`
**Issue:** The occupancy check at `gameHandlers.ts:524-531` only rejects moves onto hexes occupied by _other pieces_; it has no awareness that `passTargetHex` (the ball's eventual landing spot) is a special hex. This is what makes CR-02 reachable: nothing in the move-acceptance path signals to either client that moving onto `passTargetHex` will determine ball possession at delivery time. Compare to `GK_DIVE`/`SNAPSHOT_DEFLECT`, where the UI explicitly highlights the relevant shot-path/landing hexes (`HexGrid.tsx` `gkDiveTargetSet`, `snapDeflectPathSet`) so the acting player understands the consequence of their click. No equivalent highlight exists for the FTP target hex during the DEFENDER slot.
**Fix:** Once CR-02 is fixed server-side, add a visual highlight (gold/orange tint, matching the existing pattern in `HexGrid.tsx`) on `passTargetHex` while `firstTimePassMovementSlot === 'DEFENDER'`, so defenders understand that landing there will intercept the pass. This is a UX clarity issue, not a correctness bug on its own — filed as a Warning because it compounds the severity/discoverability of CR-02.

## Info

### IN-01: Client/server Undo-eligibility logic is duplicated and will silently mask CR-01's failure mode

**File:** `packages/client/src/components/ActionPanel.tsx:109-128`, `packages/server/src/gameEngine.ts:818-850`
**Issue:** The slot-boundary detection logic (`SLOT_ADVANCE | KICK_OFF | HP_REPOSITION-in-HIGH_PASS_MOVE | FTP_REPOSITION-in-FIRST_TIME_PASS_MOVE`) and the phase-to-move-type mapping (`HIGH_PASS_MOVE → HP_MOVE`, `FIRST_TIME_PASS_MOVE → FTP_MOVE`, else `MOVE`) are implemented twice with comments cross-referencing each other ("mirrors applyUndo's boundary logic" / "CR-01 (17.1-11): mirror applyUndo's phase-aware move-type mapping"). This duplication is an acceptable client/server split (the client copy is UX-only, per the file's own security note), but it interacts with CR-01 above in a way worth flagging: once a player hits CR-01's stuck-slot state (Undo already consumed the only `FTP_MOVE`/`HP_MOVE` in the log), `canUndo` on the client correctly returns `false` (no more move event to undo), so the Undo button disables itself — but no error message or visual cue tells the player the slot itself is now stuck and only `End Turn` will recover (with the silent stale-pieceId log entry from CR-01).
**Fix:** No code change required immediately; flagged for awareness when fixing CR-01 — consider whether the client should surface a distinct message when `firstTimePassMovedPieceId`/`highPassMovedPieceId` is non-null but `canUndo` is false and pace is exhausted, to avoid a confusing silent dead end for the player. This will become moot once CR-01 is fixed (the slot will no longer get stuck).
