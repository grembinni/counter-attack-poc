# Phase 17.1: Code Review Report

**Reviewed:** 2026-06-19T00:00:00Z
**Depth:** standard

## Summary

Reviewed the action-flow cleanup phase covering the `MOVEMENT→MOVE`/`GK_DIVING→GK_DIVE`/etc. phase-name rename, the new `FIRST_TIME_PASS_MOVE` two-slot repositioning flow (D-03), the GK-in-own-area `GK_RESTART` routing (D-06), the save-spill→`GK_RESTART` change (D-07), the loose-ball scatter clamp fix (D-08), the regular-shot 11-hex range gate (D-09), the steal/tackle "already attempted" exclusion rework (D-02 17.1-09), the snapshot-shot single-click repositioning UX fix, and the `heading`→`aerialAbility` field rename across `PlayerPiece`/`ActionEvent`.

The rename and most engine logic changes are internally consistent and exercised by reasonably thorough unit tests. However, one BLOCKER was found by tracing the actual event types emitted by `gameHandlers.ts` against what `applyUndo` (server) and the `canUndo` computation (client `ActionPanel.tsx`) search for in the event log — they search for the wrong event type and the only tests that exercise this path use hand-fabricated event-log fixtures that do not match what production code actually emits, fully masking the regression. Several `*.test.ts` fixtures in `packages/shared/src` were left with a stale `PlayerPiece`/`GameState` shape (pre-dating this rename) that no longer compiles under the real exported types, but the project's `tsconfig.json` excludes `*.test.ts` from `tsc --noEmit`, so this never surfaces in CI — flagged as a quality/maintainability gap, not a runtime defect.

## Critical Issues

### CR-01: Undo is non-functional in HIGH_PASS_MOVE and FIRST_TIME_PASS_MOVE — `applyUndo`/`canUndo` search for the wrong ActionEvent type

**File:** `packages/server/src/gameEngine.ts:838-852`
**File:** `packages/client/src/components/ActionPanel.tsx:109-120`
**Issue:**
`gameHandlers.ts` emits piece-repositioning events during `HIGH_PASS_MOVE` and `FIRST_TIME_PASS_MOVE` with the discriminants `'HP_MOVE'` (gameHandlers.ts:322) and `'FTP_MOVE'` (gameHandlers.ts:534) — never `'MOVE'`. `MOVE` is reserved for the regular Movement Phase (`applyMove` in gameEngine.ts).

Both `applyUndo` (server) and the client's shared `canUndo` computation search the event log for `evt.type === 'MOVE'` to find the move to undo / to decide whether Undo should be enabled:

```ts
// gameEngine.ts:839-841
const lastMoveRelIdx = currentSlotEvents.reduce<number>((acc, evt, idx) => {
  return evt.type === 'MOVE' ? idx : acc;
}, -1);
```

```ts
// ActionPanel.tsx:119
return eventLog.slice(lastBoundaryIdx + 1).some((e) => e.type === 'MOVE');
```

Because the actual repositioning events are `HP_MOVE`/`FTP_MOVE`, this predicate is never true in either phase. The practical effect:

- Client: the Undo button renders permanently `disabled` in `HIGH_PASS_MOVE`/`FIRST_TIME_PASS_MOVE` even right after a player repositions a piece.
- Server: even if a client somehow emitted `GAME_UNDO` anyway, `applyUndo` falls through to `lastMoveRelIdx === -1` → `hasPriorMoves` check (also searching for `'MOVE'`, never found) → returns `{ ok: false, reason: 'NOTHING_TO_UNDO' }`.

This directly contradicts the explicit intent recorded in comments at both call sites — `BUG-03 (Phase 17 D-07): Undo available in HIGH_PASS_MOVEMENT with same boundary logic` and `D-03 (Phase 17.1): Undo available with FTP_REPOSITION as the slot boundary` — neither of which is actually true at runtime.

This is masked by the test suite: `gameEngine.phase17.test.ts` (`highPassMovementStateWithMove` at line 215-255, and `ftpMoveStateWithMove` at line 667-700) hand-builds event logs using `{ type: 'MOVE', pieceId: 'home-9', ... }` to simulate the repositioning step, instead of the `HP_MOVE`/`FTP_MOVE` shape that `gameHandlers.ts` actually produces. The unit tests for `applyUndo` therefore pass against a fixture that can never occur in real gameplay, while the real code path is never exercised end-to-end (no `gameHandlers.*.test.ts` sends `GAME_UNDO` during either of these phases).

**Fix:** Make the event-type check phase-aware (mirroring the boundary-detection pattern already used a few lines above it):

```ts
// gameEngine.ts — applyUndo
const moveTypeForPhase =
  state.phase === 'HIGH_PASS_MOVE'
    ? 'HP_MOVE'
    : state.phase === 'FIRST_TIME_PASS_MOVE'
      ? 'FTP_MOVE'
      : 'MOVE';

const lastMoveRelIdx = currentSlotEvents.reduce<number>((acc, evt, idx) => {
  return evt.type === moveTypeForPhase ? idx : acc;
}, -1);
```

The piece-reversal logic below it also needs adjusting since it currently casts to `Extract<ActionEvent, { type: 'MOVE' }>` and reads `.from`/`.to` — `HP_MOVE`/`FTP_MOVE` carry the same `pieceId`/`from`/`to` shape so the cast/reversal logic itself can be reused, but the discriminant and the `hasPriorMoves` fallback check both need the same phase-aware type. Apply the equivalent fix to `ActionPanel.tsx`'s `canUndo`. Then replace the two hand-fabricated `MOVE`-event test fixtures in `gameEngine.phase17.test.ts` with `HP_MOVE`/`FTP_MOVE` events so the regression cannot reappear silently.

### WR-02: `applyEndTurn`'s GK_RESTART early-return leaves `attackingTeam` stale relative to the new `activeTeam`

**File:** `packages/server/src/gameEngine.ts:709-730`
**Issue:** When the GK's team is in their own penalty area at the end of `ATTACKER_2`, this branch sets `activeTeam: carrier.teamId` but does **not** set `attackingTeam` — the spread `...state` carries forward whatever `attackingTeam` was before the slot ended. Every other transition into `GK_RESTART` elsewhere in the file (e.g. `applyRoll`'s SHOT branch, save-spill D-07 path) explicitly sets both `attackingTeam` and `activeTeam` to `gk.teamId`. In every code path that can currently reach this specific branch, `attackingTeam` already equals `carrier.teamId` by construction (a defending GK can only end up holding the ball via a D-30 loose-ball pickup, which already flips `attackingTeam`, or a steal/tackle/interception, all of which transition straight to `PASS` and bypass `applyEndTurn` entirely) — so this is not currently reachable as a live bug. It is, however, an inconsistent invariant: a future change to the FSM (e.g. a new path that lets a GK end up holding the ball without `attackingTeam` flipping) would silently desync `attackingTeam` from `activeTeam`/`ball.carrierId` in this one branch only.
**Fix:** Set `attackingTeam: carrier.teamId` alongside `activeTeam: carrier.teamId` here for consistency with every other `GK_RESTART` entry point, removing the implicit dependency on caller invariants:

```ts
state: {
  ...state,
  phase: 'GK_RESTART',
  movementSlot: null,
  attackingTeam: carrier.teamId,
  activeTeam: carrier.teamId,
  ...
}
```

### WR-03: Save-spill now silently grants the GK a clean catch instead of a contested loose ball, with the simplification only documented in a one-line comment

**File:** `packages/server/src/gameEngine.ts:1595-1614`
**Issue:** D-07 changed handling-check failure ("spill") from `LOOSE_BALL` (contestable by both teams via the loose-ball scatter mechanic) to `GK_RESTART` with `ball.carrierId: gk.id` — i.e. a spilled save now behaves identically to a clean catch. The comment acknowledges this is provisional (`pending out-of-bounds rules — spill treated as clean catch for now`), but the rule change is a meaningful gameplay simplification (a "spilled" save should, by the rulebook's intent, produce a loose ball that either team can contest, not free possession for the GK) that isn't called out anywhere outside this one inline comment, and is asserted as correct behavior by the test at `gameEngine.phase17.test.ts:773-788` without any caveat. A future contributor reading the test in isolation would reasonably conclude this is the final intended behavior.
**Fix:** No code change required if this is an accepted interim simplification, but the test name/describe block and any user-facing changelog/UAT notes should make the "spill == catch, contest deferred" simplification explicit so it isn't mistaken for a permanent rule, and a tracking item should exist for the deferred "spill is contestable" behavior referenced in the comment.

### IN-01: `ActionEventType`/`ActionEvent` for `HP_MOVE`/`FTP_MOVE`/`HP_REPOSITION`/`FTP_REPOSITION`/`HEADER`/`GK_KICK`/`DEFLECT_ATTEMPT` lack `ballAfter`

**File:** `packages/shared/src/types.ts:244-290`
**Issue:** Most `ActionEvent` variants carry a `ballAfter: { position; carrierId }` field used by `buildReplayFrames`'s universal `if ('ballAfter' in event)` ball-position update. `HP_MOVE`, `FTP_MOVE`, `HP_REPOSITION`, `FTP_REPOSITION`, `HEADER`, `DEFLECT_ATTEMPT`, and `GK_KICK`/`GK_KICK_MOVE` do not. This is currently harmless (those types are either excluded from `REPLAY_ELIGIBLE_TYPES` or the `'ballAfter' in event` guard correctly skips them), but it is an easy trap for a future replay/log feature that iterates `ActionEvent` generically and assumes `ballAfter` is universal. Consider either adding `ballAfter` consistently or documenting on the `ActionEvent` union itself which variants intentionally omit it and why.
**Fix:** Add a short doc comment above the `ActionEvent` union noting which discriminants intentionally omit `ballAfter` (board-state-neutral events) so the omission reads as a deliberate decision rather than an oversight.

### IN-03: `SNAPSHOT_ELIGIBLE_PASS_TYPES` constant duplicates the `ELIGIBLE_NEXT_ACTIONS` source of truth

**File:** `packages/server/src/gameEngine.ts:61-70`
**Issue:** The module-level `SNAPSHOT_ELIGIBLE_PASS_TYPES` set is hand-maintained in parallel with `ELIGIBLE_NEXT_ACTIONS` (imported from `@counter-attack/shared`), which already presumably encodes which `LastActionType`s permit a `SNAPSHOT` follow-up (the code elsewhere checks `eligible.has('SNAPSHOT')` against `ELIGIBLE_NEXT_ACTIONS`). Maintaining a second, independently-curated allowlist for the same semantic question is a drift risk — the explanatory comment about `HIGH_PASS` being "intentionally omitted" because it's structurally unreachable is good practice, but it underscores that this list requires careful manual reasoning that `ELIGIBLE_NEXT_ACTIONS.has('SNAPSHOT')` would otherwise centralize.
**Fix:** Confirm whether `ELIGIBLE_NEXT_ACTIONS[lastActionType].has('SNAPSHOT')` is equivalent to membership in `SNAPSHOT_ELIGIBLE_PASS_TYPES` for every `LastActionType`; if so, drop the local set and use the shared table directly (the `applySnapshot` sequence guard at line 2320-2325 already does this for the general case — this module-level set appears to only matter for the PASS-phase position-check branch at line 2361).
