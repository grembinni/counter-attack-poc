# Phase 17.1: Code Review Report (Cycle 5 — Deep Pass)

**Reviewed:** 2026-06-20T02:29:02Z
**Depth:** deep (cross-file call-chain analysis: types.ts ↔ gameEngine.ts ↔ gameHandlers.ts ↔ useGameStore.ts)
**Files Reviewed:** 36
**Status:** issues_found

## Summary

This is the fifth consecutive review cycle on the FIRST_TIME_PASS_MOVE (FTP) / HIGH_PASS_MOVE (HP)
repositioning feature. Cycles 1–4 closed four real defects (phase-aware undo lookup, missing client
piece-selection wiring, server interception-loop shadowing, missing FTP/HP lock-field reset on undo,
team-restricted receiver lookup, and the FTP self-pass-reclaim exploit closed in 17.1-16). This cycle
traced the full call chain `types.ts` (GameState fields) → `gameEngine.ts` (`applyRoll` PASS branch,
`applyUndo`) → `gameHandlers.ts` (`GAME_MOVE`/`GAME_END_TURN`/`GAME_UNDO` handlers) → `useGameStore.ts`
(`selectPiece`/`setGameState`) specifically for FTP and HP.

The server-side logic for FTP and HP is now structurally sound and almost fully symmetric. The one
remaining server-side asymmetry — HIGH_PASS_MOVE's `GAME_MOVE` handler still lacks the
`highPassCarrierId` repositioning-exclusion that FTP gained in 17.1-16 — is **already documented** as a
deferred parallel finding in `17.1-16-PLAN.md`'s `<artifacts_produced>` block and is not re-flagged here
as new, per the review brief.

This cycle's new finding is on the **client**, in a code path none of the prior four cycles inspected:
`useGameStore.ts`'s `setGameState` reducer computes `slotChanged` from `GameState.movementSlot` only.
`movementSlot` is a MOVE-phase-only field and stays `null` for the entire duration of
`FIRST_TIME_PASS_MOVE` / `HIGH_PASS_MOVE` / `GK_KICK_MOVE` — including across the internal
ATTACKER→DEFENDER sub-slot transition, which is tracked by a _different_ pair of fields
(`firstTimePassMovementSlot` / `highPassMovementSlot`). Because `setGameState` never reads those fields
when deciding whether to clear `selectedPieceId`, a player's already-used piece stays "selected" (with
live valid-move highlights) on their own screen through the opponent's repositioning turn. This is a
genuine, previously-unexamined bug — classified BLOCKER because it produces incorrect, clickable UI
state that a player can act on (the click itself is safely rejected server-side, but the user-visible
game state is wrong, which is a real game-state bug per project conventions, not a style nit).

Three further WARNING-level findings and one INFO (dead code) finding round out this cycle. No new
defects were found in `gameEngine.ts`'s `applyRoll`/`applyUndo` core transition logic, in the
`GAME_UNDO` handler, or in the `HP_REPOSITION`/`FTP_REPOSITION` slot-boundary treatment — those areas
are now consistent and symmetric between the two phases.

## Critical Issues

### CR-01: `setGameState` never detects the FTP/HP/GK-kick internal slot transition — stale piece selection and live move-highlights persist into the opponent's turn

**File:** `packages/client/src/store/useGameStore.ts:511`
**Issue:**
`slotChanged` is computed as:

```ts
const slotChanged = newState.movementSlot !== prevState.movementSlot;
```

`movementSlot` is the 4-5-2 MOVE-phase slot field (`'ATTACKER_4' | 'DEFENDER_5' | 'ATTACKER_2' | null`).
During `FIRST_TIME_PASS_MOVE` and `HIGH_PASS_MOVE` (and `GK_KICK_MOVE`), `movementSlot` is `null` for the
_entire_ phase — confirmed by the comment at `useGameStore.ts:373-374` ("movementSlot stays null here")
and by `gameHandlers.ts`'s `GAME_END_TURN` HIGH_PASS_MOVE/FIRST_TIME_PASS_MOVE branches
(`gameHandlers.ts:616-764`), which never reference `movementSlot` at all. The actual ATTACKER→DEFENDER
sub-slot transition within these phases is tracked by `firstTimePassMovementSlot` /
`highPassMovementSlot`, which `slotChanged` never inspects.

Trace of the concrete defect:

1. Attacking-team client has `selectedPieceId` set to the piece they just repositioned during the
   ATTACKER slot (sticky selection set by the prior `setGameState` call via the branch at
   `useGameStore.ts:551-592`).
2. Attacker clicks End Turn. Server (`gameHandlers.ts:689-707` for FTP, `:623-639` for HP) flips
   `firstTimePassMovementSlot`/`highPassMovementSlot` to `'DEFENDER'`, `activeTeam` to the defending
   team, and resets `firstTimePassMovedPieceId`/`highPassMovedPieceId` to `null` — but `phase` is
   unchanged (`'FIRST_TIME_PASS_MOVE'`/`'HIGH_PASS_MOVE'` stays the same) and `movementSlot` is
   untouched (still `null`).
3. Back in the attacker's `setGameState`: `slotChanged = null !== null = false`; `phaseChanged = false`;
   `pieceStillExists = true`; `activationComplete = newState.movedPieceIds.includes(prevSelectedId)` —
   and `movedPieceIds` (the MOVE-phase field) is never written by the FTP/HP `GAME_MOVE` handlers
   (confirmed: no `movedPieceIds:` assignment anywhere in the HIGH_PASS_MOVE/FIRST_TIME_PASS_MOVE
   `GAME_MOVE` branches at `gameHandlers.ts:277-339` / `:488-560`), so `activationComplete` is always
   `false` here regardless of pace used.
4. None of the four clear-conditions at `useGameStore.ts:519-525` are true → the **sticky-selection
   branch runs instead of the clear branch**. `lockedId` is recomputed from the just-reset
   `firstTimePassMovedPieceId`/`highPassMovedPieceId` (now `null`), so `locked = false`; `paceRemaining`
   is recomputed from the just-reset pace field (now the full budget) — so `stickyValid` becomes a
   **non-empty** list of "valid" adjacent hexes for the attacker's already-spent piece, set via
   `useGameStore.ts:584-591`.
5. The attacking player's pitch view (`HexGrid.tsx`) now shows their own already-moved piece in the
   `'active'` selection ring with live yellow "safe" highlight hexes — _during the defending team's
   repositioning turn_. If the attacker clicks one of these highlighted hexes, `HexGrid.tsx:406`'s
   generic `isValidMove && selectedPieceId` handler fires `emitMove`, which the server correctly
   rejects (`isActivePlayer` check at `gameHandlers.ts:489`/`:617` → `WRONG_TEAM`) — so there is no
   server-side exploit — but the click silently no-ops with a snap-back, which is a confusing, broken
   UX state: the board visibly invites and then refuses an action the UI itself displayed as legal.

This is exploitable to view incorrect state and click invitations on _every single_ FTP/HP repositioning
sequence in the game (it is the ordinary ATTACKER→DEFENDER hand-off, not an edge case), confirmed absent
from test coverage — no existing test calls `setGameState` twice in sequence to simulate this exact
slot hand-off for FTP/HP/GK_KICK_MOVE (`useGameStore.test.ts`, `useGameStore.rule11.test.ts`, and
`HexGrid.test.tsx`'s FTP suite only exercise a single `selectPiece` call against a hand-built state, never
a `setGameState` transition).

**Fix:** Extend `slotChanged` to also cover the three repositioning-phase slot fields:

```ts
const slotChanged =
  newState.movementSlot !== prevState.movementSlot ||
  newState.firstTimePassMovementSlot !== prevState.firstTimePassMovementSlot ||
  newState.highPassMovementSlot !== prevState.highPassMovementSlot ||
  newState.gkKickMovementSlot !== prevState.gkKickMovementSlot;
```

This makes the clear-branch fire correctly on every ATTACKER→DEFENDER hand-off for all three
repositioning phases, matching the same intent the existing `phaseChanged` check already has for
whole-phase transitions.

## Warnings

### WR-01: `selectPiece`'s FTP/HP/GK-kick branches never check `activeTeam` — defense-in-depth gap (currently masked by `HexGrid.tsx`, but real)

**File:** `packages/client/src/store/useGameStore.ts:337-368` (HIGH_PASS_MOVE), `:375-414` (FIRST_TIME_PASS_MOVE)
**Issue:** The `HIGH_PASS_MOVE` and `FIRST_TIME_PASS_MOVE` branches of `selectPiece` gate only on
`piece.teamId !== myTeam` (team ownership), the per-slot lock, and remaining pace. Neither branch checks
whether `myTeam` is actually the side whose `highPassMovementSlot`/`firstTimePassMovementSlot` (and
therefore `activeTeam`) is currently active. Contrast with `HexGrid.tsx`'s `canSelectHighPassMove`
(`HexGrid.tsx:574-579`) and `canSelectFirstTimePassMove` (`:598-603`), which both correctly require
`isActivePlayer` (`myTeam === activeTeam`) before exposing the click handler — so in the current
production UI, `selectPiece` is only ever invoked from an already-gated call site
(`HexGrid.tsx:668-682`), and the gap is not reachable through the rendered UI today.

However, `selectPiece` is a public store action (also called directly in unit tests, e.g.
`useGameStore.test.ts:86,93`, `HexGrid.test.tsx:275,290,305,323`), and the existing test named "does NOT
select any piece for the non-active player during FIRST_TIME_PASS_MOVE"
(`useGameStore.test.ts:296-309`) does not actually test an active/inactive-slot distinction — it passes
a piece of the same team as `playerSlot` while `activeTeam` differs only via the team-ownership
mismatch (the test sets `playerSlot: 2` i.e. `myTeam = 'away'` and selects a `'home'` piece), so it is
silently exercising the team-ownership check (`piece.teamId !== myTeam`), not an active-team check,
because no active-team check exists. The test's name asserts a guarantee the implementation does not
provide.

**Fix:** Add an explicit `activeTeam` check, mirroring `HexGrid.tsx`'s `isActivePlayer`, to both branches:

```ts
if (gameState.phase === 'HIGH_PASS_MOVE') {
  const myTeam = playerSlot === 1 ? 'home' : 'away';
  if (piece.teamId !== myTeam || myTeam !== gameState.activeTeam) {
    set({ selectedPieceId: null, validMoveHexes: [] });
    return;
  }
  // ...
}
```

Apply the same `myTeam !== gameState.activeTeam` check to the `FIRST_TIME_PASS_MOVE` and
`GK_KICK_MOVE` branches for consistency, and add a regression test that selects an own-team piece while
`activeTeam` is the _other_ side (e.g. home player selecting a home piece during the DEFENDER slot when
the attacking team is home) to actually cover the case the existing test's name claims to cover.

### WR-02: FIRST_TIME_PASS can deliver the ball directly to a GK standing in their own penalty area, bypassing GK_RESTART — a gap HIGH_PASS structurally cannot hit

**File:** `packages/server/src/gameHandlers.ts:708-757` (FTP delivery); `packages/server/src/gameEngine.ts:704-730` (GK_RESTART trigger)
**Issue:** `GK_RESTART` is only ever entered from two call sites: `applyEndTurn`'s ATTACKER_2→PASS
transition when the ball carrier is a GK standing in their own penalty area
(`gameEngine.ts:704-730`, comment: "Must run BEFORE the normal 'PASS' branch"), and shot-save resolution
(`gameEngine.ts:1623`, `:1641`). The FTP delivery branch in `gameHandlers.ts` (lines 738-757) constructs
the post-delivery state directly — it does not call `applyEndTurn` and has no equivalent GK-in-own-box
check — so if a first-time pass is delivered to a teammate who happens to be the team's own GK standing
in their own penalty area (a short backward one-touch to the keeper is a realistic, legal target per
`passValidator.ts`'s FIRST_TIME range/path rules), the GK becomes ball carrier in plain `PASS` phase with
no kick/throw/move restart options — just an ordinary carrier subject to
`ELIGIBLE_NEXT_ACTIONS['FIRST_TIME_PASS']`.

This pre-existing gap is shared with `STANDARD_PASS`/`LONG_BALL` delivery in `gameEngine.ts`
(`:1290-1314`, the BUG-04 team-agnostic occupant lookup also has no GK/penalty-area check), so it is not
introduced by this phase's work. It is flagged here specifically because it manifests as an **asymmetry
between FTP and HP**: `HIGH_PASS` can never hit this gap because it always routes through the `HEADER`
phase before any possible GK possession (`gameEngine.ts:1327-1373`), so a GK can only receive a high pass
via a header contest, never a silent direct handoff. FTP has no such intermediate gate, so the gap is
reachable for FTP (and STANDARD_PASS/LONG_BALL) but not for HP. No test in `gameEngine.phase17.test.ts`
or `game.integration.test.ts` covers a pass (of any type) delivered directly to a GK in their own box.

**Fix:** Either (a) accept this as out-of-scope for 17.1 (it is a pre-existing, cross-cutting gap, not a
17.1 regression) and track it as a separate ticket touching `STANDARD_PASS`/`LONG_BALL`/`FIRST_TIME_PASS`
delivery uniformly, or (b) if fixed now, factor the GK-in-own-area check from
`gameEngine.ts:704-730` into a shared helper and call it from both the FTP delivery branch in
`gameHandlers.ts` and the STANDARD_PASS/LONG_BALL occupant-delivery branch in `gameEngine.ts`, routing to
`GK_RESTART` instead of `PASS` whenever the new carrier is a GK in their own penalty area.

### WR-03: `applyUndo`'s generic pace/movedPieceIds bookkeeping silently no-ops for FTP_MOVE/HP_MOVE undo — correct today only because the two field sets never overlap

**File:** `packages/server/src/gameEngine.ts:873-886`
**Issue:** `applyUndo` unconditionally manipulates `state.paceUsedByPieceId` and `state.movedPieceIds`
(the MOVE-phase tracking fields) for _every_ undo, including when `moveToUndo` is an `HP_MOVE` or
`FTP_MOVE` event (lines 863-866 resolve `moveToUndo` to one of `'MOVE' | 'HP_MOVE' | 'FTP_MOVE'`). The
HIGH_PASS_MOVE/FIRST_TIME_PASS_MOVE `GAME_MOVE` handlers in `gameHandlers.ts` never write to
`paceUsedByPieceId`/`movedPieceIds` (they use `highPassPaceUsed`/`firstTimePassPaceUsed` and
`highPassMovedPieceId`/`firstTimePassMovedPieceId` instead), and the FTP/HP phase-entry transitions in
`gameEngine.ts`/`gameHandlers.ts` never explicitly reset `paceUsedByPieceId`/`movedPieceIds` either — they
rely on those fields already being `{}`/`[]` by inheritance from the preceding PASS-phase reset. This
currently produces a harmless no-op (`currentPace` reads `0` from the always-empty
`paceUsedByPieceId`, so `delete newPaceUsed[pieceId]` deletes a key that was never present, and
`movedPieceIds.filter(...)` filters an already-empty array) — but it is accidental correctness, not
designed correctness: nothing prevents a future code path from entering `FIRST_TIME_PASS_MOVE`/
`HIGH_PASS_MOVE` with non-empty `paceUsedByPieceId`/`movedPieceIds` left over from a prior MOVE phase
(there is no explicit reset at the FTP/HP phase-entry transition the way `applyStartMovement` explicitly
resets them at `gameEngine.ts:243-244`), at which point this code would start mutating fields it has no
business touching during FTP/HP undo.

**Fix:** Either (a) explicitly reset `paceUsedByPieceId: {}` and `movedPieceIds: []` at both phase-entry
transitions (the FTP transition at `gameEngine.ts:1256-1280` and the HP transition at
`gameHandlers.ts:1299-1309`) so the invariant is enforced rather than assumed, or (b) make
`applyUndo`'s lines 873-886 conditional on `state.phase === 'MOVE'`, matching the already-conditional
`lockReset` block immediately below it (lines 911-916) so the function doesn't touch MOVE-phase-only
bookkeeping fields while in a non-MOVE phase.

## Info

### IN-01: `ActionLog.tsx`'s `formatEvent` cases for `HP_REPOSITION`/`FTP_REPOSITION` are unreachable dead code

**File:** `packages/client/src/components/ActionLog.tsx:389-402`
**Issue:** `consolidateEvents` (line 78) filters out every `HP_REPOSITION` and `FTP_REPOSITION` event
with `continue` before it ever pushes an `EventItem` — these event types can never reach
`formatEvent`, which is only invoked on `item.event` for `EventItem`s (line 525). The `case
'HP_REPOSITION'` (389-395) and `case 'FTP_REPOSITION'` (396-402) branches in `formatEvent` are therefore
dead code; the switch remains exhaustive only because TypeScript's narrowing doesn't know about the
upstream filter.
**Fix:** Either remove the two dead `case` branches from `formatEvent` (and instead let TypeScript's
exhaustiveness check fail loudly if a future refactor stops filtering these events upstream, prompting a
deliberate decision about whether they should render), or add a one-line comment at the top of each dead
case explaining why it's intentionally unreachable, so a future reader doesn't waste time trying to
trigger it.
