# Phase 17.1: Code Review Report

**Reviewed:** 2026-06-19T12:30:00Z
**Depth:** standard
**Files Reviewed:** 35
**Status:** issues_found

## Summary

This is a re-review of the action-flow cleanup phase: the `MOVEMENT`→`MOVE`/`GK_DIVING`→`GK_DIVE`/`HIGH_PASS_MOVEMENT`→`HIGH_PASS_MOVE`/`SNAP_DEFLECT`→`SNAPSHOT_DEFLECT`/`QUICK_THROW`→`GK_QUICK_THROW`/`GK_KICK_MOVEMENT`→`GK_KICK_MOVE` phase-name rename, the `heading`→`aerialAbility` field rename, the new `FIRST_TIME_PASS_MOVE` two-slot repositioning flow (D-03), GK-in-own-area→`GK_RESTART` auto-routing (D-06), save-spill→`GK_RESTART` (D-07), the parity-independent loose-ball scatter fix (D-08), the regular-shot 11-hex range gate (D-09), the steal/tackle "already attempted" exclusion rework (D-02 17.1-09), and the split of pass interception into `autoIntercepts`/`rollIntercepts`.

A prior review pass found and the project subsequently fixed a BLOCKER where `applyUndo`/`canUndo` searched for `'MOVE'` events instead of the phase-appropriate `HP_MOVE`/`FTP_MOVE` discriminants — that fix is confirmed present and correct in the current code (`gameEngine.ts:840-845`, `ActionPanel.tsx:121-126`), and is no longer flagged here.

This pass found three new BLOCKER-level issues. First, the new `FIRST_TIME_PASS_MOVE` phase is fully implemented server-side and in `ActionPanel.tsx`, but `HexGrid.tsx`/`useGameStore.ts` were never updated to let a player actually select a piece or click a destination hex during this phase — the feature is server- and panel-complete but unusable end-to-end in the browser. Second, a `FIRST_TIME_PASS` aimed near a defender can be silently intercepted before the new `FIRST_TIME_PASS_MOVE` branch is ever reached, because the interception loop in `applyRoll` runs first. Third, running the server test suite in scope for this phase (`packages/server`) currently reports 4 failing tests — 2 directly caused by stale tests asserting an abandoned pre-17.1 design for first-time-pass delivery, and 2 pre-existing (`FREE_MOVE`/MOVE-06) failures left red in a file this phase modified extensively. The previously-reported stale-test-fixture warning (`moveValidator.test.ts`/`passValidator.test.ts`/`snapshotValidator.test.ts` still using the removed `heading`/`name` fields and missing required `GameState` fields) remains unresolved and is carried forward.

## Critical Issues

### CR-01: FIRST_TIME_PASS_MOVE has no client-side piece-selection support — feature is unusable in the browser

**File:** `packages/client/src/components/HexGrid.tsx` (entire file), `packages/client/src/store/useGameStore.ts:296-451` (`selectPiece`), `packages/client/src/store/useGameStore.ts:457-557` (`setGameState`)
**Issue:** The new `FIRST_TIME_PASS_MOVE` phase is fully implemented server-side (`gameHandlers.ts:488-550` for `GAME_MOVE`, `:672-734` for `GAME_END_TURN`) and in `ActionPanel.tsx` (lines 162-183, rendering "First-time pass! Move 1 player to receive the ball." with Undo/End Turn buttons), but `HexGrid.tsx` has zero references to `FIRST_TIME_PASS_MOVE` anywhere — unlike the structurally identical `HIGH_PASS_MOVE`, `GK_KICK_MOVE`, and `SNAPSHOT_DEFLECT` phases, each of which has a dedicated `canSelectXxx` boolean, valid-destination-hex computation, and click handler in `HexGrid.tsx` (`canSelectHighPassMove` at line 572, `canSelectGKKickMove` at line 588, `canSelectSnapDeflect` at line 580). `useGameStore.ts`'s `selectPiece` action likewise has dedicated branches for `KICK_OFF_SETUP`, `HIGH_PASS_MOVE`, `GK_KICK_MOVE`, and `SNAPSHOT_DEFLECT`, but none for `FIRST_TIME_PASS_MOVE`.

Clicking a piece during `FIRST_TIME_PASS_MOVE` falls through to the generic "Normal MOVEMENT phase" branch in `selectPiece` (line 438-450), which calls `validateMove(gameState, piece, hex)`. `validateMove`'s first guard is `if (state.movementSlot === null) return { ok: false, reason: 'WRONG_SLOT' }`, and `movementSlot` is always `null` during `FIRST_TIME_PASS_MOVE` (this phase tracks its own slot via `firstTimePassMovementSlot` instead). `validMoveHexes` is therefore always empty, and `HexGrid.tsx` never marks any piece as clickable for this phase either (`isClickable` only checks `canSelect`/`canSelectKickOff`/`isHeaderEligible`/`canSelectHighPassMove`/`canSelectSnapDeflect`/`canSelectGKKickMove` — none of which match). The `setGameState` sticky-selection logic (line 506) that re-derives valid hexes after each server broadcast also only special-cases `'HIGH_PASS_MOVE' || 'GK_KICK_MOVE'`.

Net effect: a player who reaches `FIRST_TIME_PASS_MOVE` cannot select or move any piece in either repositioning slot. They can only press End Turn (skipping their turn with no piece moved) or Undo (always a no-op since nothing was ever moved). This is confirmed by `HexGrid.test.tsx` (added in this phase) having no coverage of this phase at all, and by `ActionPanel.test.tsx`'s `FIRST_TIME_PASS_MOVE` tests only covering button enablement, never an actual piece move.
**Fix:** Add a `FIRST_TIME_PASS_MOVE` branch to `selectPiece` mirroring the existing `HIGH_PASS_MOVE` branch (1 piece per team, max 1 hex, pace field `firstTimePassPaceUsed`/`firstTimePassMovedPieceId`):

```ts
if (gameState.phase === 'FIRST_TIME_PASS_MOVE') {
  const myTeam = playerSlot === 1 ? 'home' : 'away';
  if (piece.teamId !== myTeam) {
    set({ selectedPieceId: null, validMoveHexes: [] });
    return;
  }
  const lockedId = gameState.firstTimePassMovedPieceId ?? null;
  if (lockedId !== null && lockedId !== id) {
    set({ selectedPieceId: null, validMoveHexes: [] });
    return;
  }
  const paceRemaining = 1 - (gameState.firstTimePassPaceUsed ?? 0);
  if (paceRemaining <= 0) {
    set({ selectedPieceId: id, validMoveHexes: [] });
    return;
  }
  const valid = hexesInRange(piece.position, 1).filter((hex) => {
    if (!PITCH_HEXES.some((h) => h.q === hex.q && h.r === hex.r)) return false;
    if (
      gameState.pieces.some((p) => p.id !== id && p.position.q === hex.q && p.position.r === hex.r)
    )
      return false;
    return hexDistance(piece.position, hex) === 1;
  });
  set({ selectedPieceId: id, validMoveHexes: valid });
  return;
}
```

Add the equivalent `canSelectFirstTimePassMove` derivation and click wiring in `HexGrid.tsx` (mirroring `canSelectHighPassMove`), and extend `setGameState`'s sticky-selection branch condition from `newState.phase === 'HIGH_PASS_MOVE' || newState.phase === 'GK_KICK_MOVE'` to also include `'FIRST_TIME_PASS_MOVE'`.

### CR-02: FIRST_TIME_PASS can be intercepted near a defender, bypassing FIRST_TIME_PASS_MOVE entirely

**File:** `packages/server/src/gameEngine.ts:1149-1257`
**Issue:** In `applyRoll`'s `'PASS'` case, the `FIRST_TIME_PASS` → `FIRST_TIME_PASS_MOVE` transition (`if (newLastActionType === 'FIRST_TIME_PASS') { ... }`, line 1237) runs _after_ the `autoIntercepts`/`rollIntercepts` interception loops (lines 1153-1227). `validatePass` (`passValidator.ts`) still computes `rollIntercepts` for `FIRST_TIME` pass type — it only skips interception entirely for `HIGH`/`LONG` pass types (`if (passType !== 'LONG' && passType !== 'HIGH') { ... }`) — and `GAME_ROLL`'s handler in `gameHandlers.ts:1246-1248` pre-generates interception dice for `rollIntercepts` regardless of pass type. So if any opposing piece is within Zone of Influence (1 hex) of the first-time-pass travel path or target hex, the interception loop can fire and `return` early with `lastActionType: 'SUCCESSFUL_TACKLE'` — the `FIRST_TIME_PASS_MOVE` branch is never reached. The comment at line 1230-1233 explicitly anticipated and fixed this exact unreachability problem for the _occupant-pickup check_ further down, but the same reasoning was not applied to the interception loop above it, which runs earlier and can intercept first. This defeats the two-slot repositioning feature for the realistic common case of a first-time pass played near a defender (which is precisely when a first-time pass is most useful).
**Fix:** Either (a) treat `FIRST_TIME_PASS` as unblockable in flight, consistent with how `isHeaderPass` already bypasses the same loop (`const isHeaderPass = state.lastActionType === 'HEADER'; if (!isHeaderPass) { ... }` — extend this condition to also exclude `FIRST_TIME_PASS`), or (b) move the `FIRST_TIME_PASS_MOVE` early-return above the interception loop so the repositioning phase always happens first and any contest is resolved as part of/after that phase. Add a regression test seeding a defender within 1 hex of a `FIRST_TIME_PASS` target to lock in whichever behavior is chosen.

### CR-03: Server test suite has 4 failing tests, 2 caused by this phase's stale tests

**File:** `packages/server/src/__tests__/gameEngine.phase17.test.ts:538-554`, `packages/server/src/__tests__/gameHandlers.phase17.test.ts:289-307`
**Issue:** `vitest run` in `packages/server` currently reports 4 failures. Two are directly attributable to this phase:

- `gameEngine.phase17.test.ts:538` ("FIRST_TIME_PASS delivery enters attacker repositioning step") asserts `result.state.phase === 'PASS'` and `result.state.firstTimePassStep === 'ATTACKER'`. The actual `applyRoll` implementation in this phase sets `phase: 'FIRST_TIME_PASS_MOVE'` and never sets `firstTimePassStep`/`firstTimePassPath` anywhere — these fields are vestiges of an earlier single-step design that the two-slot `FIRST_TIME_PASS_MOVE` model (added in this phase, exercised correctly by the newer tests starting at line 603) superseded. The old test was not deleted.
- `gameHandlers.phase17.test.ts:289` ("SNAP_DEFLECT end-turn resolves as pass when lastActionType=FIRST_TIME_PASS") seeds a `SNAPSHOT_DEFLECT` state using the same abandoned `firstTimePassPath`/`firstTimePassStep` fields and expects the result phase to be `LOOSE_BALL`/`PASS`; it actually resolves to `KICK_OFF_SETUP` (the out-of-range auto-goal path), confirming the seeded scenario no longer maps to any reachable production code path.
  The remaining 2 failures (`gameEngine.phase17.test.ts` MOVE-06 `FREE_MOVE` transition tests) pre-date this phase (confirmed present against the parent commit) — `applyEndTurn` never reads `pendingFreeMove` to route into a `FREE_MOVE` phase — but they sit in the same test file this phase changed by 376 lines and were not triaged, removed, or quarantined.

Either way, a CI run or reviewer running `pnpm test` against this submission sees real, named failures rather than a clean baseline, in files this phase is responsible for.
**Fix:** Delete or rewrite the two `firstTimePassStep`/`firstTimePassPath`-based tests to assert the actual `FIRST_TIME_PASS_MOVE` model (the tests at `gameEngine.phase17.test.ts:603+` already do this and can serve as the template). For the two `FREE_MOVE` failures, either implement the `pendingFreeMove` → `FREE_MOVE` transition in `applyEndTurn`, or mark those two tests `.skip`/`.todo` with a tracking reference so the suite reports green for everything that is actually implemented.

### WR-02: `applyEndTurn`'s GK_RESTART branch leaves `attackingTeam` unset, relying on caller invariants

**File:** `packages/server/src/gameEngine.ts:709-730`
**Issue:** When a GK carrier is found in their own penalty area at the end of `ATTACKER_2`, this branch sets `activeTeam: carrier.teamId` but not `attackingTeam` — the latter carries forward from `...state`. Every other `GK_RESTART` entry point in the file (`applyRoll`'s SHOT branch, the save-spill D-07 path) explicitly sets both `attackingTeam` and `activeTeam` to `gk.teamId`. Today this branch is only reachable when `attackingTeam` already equals `carrier.teamId` by construction, so it's not a live bug, but it's an inconsistent invariant relative to every other `GK_RESTART` transition and would silently desync `attackingTeam` if a future FSM change lets a defending GK end up holding the ball at this point without `attackingTeam` already having flipped.
**Fix:** Add `attackingTeam: carrier.teamId` alongside `activeTeam: carrier.teamId` for consistency with every other `GK_RESTART` entry point.

### WR-03: GK_KICK_MOVE → PASS delivery does not reset stealAttemptedByIds/tackleAttemptedByIds

**File:** `packages/server/src/gameHandlers.ts:779-795`
**Issue:** Every other `phase: 'PASS'` transition across `gameEngine.ts`/`gameHandlers.ts` resets `stealAttemptedByIds: []`/`tackleAttemptedByIds: []` (explicitly commented "D-02: reset at every 'PASS' transition" at every other site). The `GK_KICK_MOVE` accurate-delivery branch (the `accurate` case inside the OPP-slot `GAME_END_TURN` handling) is the sole exception. Currently harmless because the next `MOVE`-phase entry (`applyStartMovement`) unconditionally resets both fields again regardless of entry path, but it's an inconsistent pattern that would silently carry stale tracking data into `PASS` phase if any future logic reads these fields there.
**Fix:** Add `stealAttemptedByIds: []` / `tackleAttemptedByIds: []` to the accurate-delivery state object in `gameHandlers.ts:779-795`, matching the surrounding convention.

### WR-04: ActionLog's FTP_MOVE events are not consolidated into a path, unlike MOVE/HP_MOVE/GK_KICK_MOVE

**File:** `packages/client/src/components/ActionLog.tsx:74-153`
**Issue:** `consolidateEvents` has dedicated grouping logic for `MOVE`, `GK_KICK_MOVE`, and `HP_MOVE` (collapsing consecutive same-piece/same-slot moves into one path entry), but no equivalent branch for `FTP_MOVE` — it falls through to the generic single-event path even though `formatEvent` has a dedicated `FTP_MOVE` case clearly written to mirror `HP_MOVE`. No visible symptom today because `firstTimePassPaceUsed` is capped at 1 hex per slot (never more than one `FTP_MOVE` per slot to consolidate), but it's an inconsistent implementation of an otherwise fully-mirrored feature pair (`HP_MOVE`/`FTP_MOVE`, `HP_REPOSITION`/`FTP_REPOSITION` are mirrored everywhere else in this file) that will produce inconsistent log output if the FTP pace cap is ever raised.
**Fix:** Add an `FTP_MOVE` branch to `consolidateEvents` mirroring the existing `HP_MOVE` block, using a `groupKey` such as `` `FTP_${event.slot}:${event.pieceId}` ``.

### IN-04: Duplicated deflection/GK-range-check logic across GAME_SHOT, SNAPSHOT_DEFLECT, and GAME_HEADER_TARGET handlers

### IN-05: `SNAPSHOT_ELIGIBLE_PASS_TYPES` duplicates the `ELIGIBLE_NEXT_ACTIONS` source of truth
