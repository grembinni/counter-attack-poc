# Phase 17.1: Code Review Report

**Reviewed:** 2026-06-19T00:00:00Z
**Depth:** standard
**Files Reviewed:** 35
**Status:** issues_found

## Summary

This pass re-reviews the action-flow-cleanup phase after gap-closure plans 17.1-14 and 17.1-15
landed on top of a prior review that found two Blockers in this exact area:

- **CR-01 (prior review): `applyUndo` permanently locks the FTP/HP repositioning slot.** Fixed by
  17.1-14.
- **CR-02 (prior review): FTP delivery occupant lookup was team-restricted (attacking-team only),
  silently dropping a defender who repositioned onto the target hex.** Fixed by 17.1-15.

**Both are confirmed resolved on this pass:**

- `applyUndo` (`gameEngine.ts:906-916`) now resets `firstTimePassMovedPieceId` /
  `firstTimePassPaceUsed` (when `state.phase === 'FIRST_TIME_PASS_MOVE'`) or
  `highPassMovedPieceId` / `highPassPaceUsed` (when `state.phase === 'HIGH_PASS_MOVE'`), gated
  purely on `state.phase`, with the lock-reset object empty (`{}`) for any other phase. Verified
  this does not leak across phases — only one phase is ever active at a time, and a dedicated
  no-regression test (`gameEngine.phase17.test.ts:716-746`) asserts a plain-`MOVE`-phase undo
  leaves `firstTimePassMovedPieceId`/`highPassMovedPieceId` untouched (`undefined`, matching the
  input state). The FTP and HP undo-then-reselect tests (`gameEngine.phase17.test.ts:674-714`,
  `400-414`) both assert the lock fields are cleared after undo.
- The FTP delivery occupant lookup (`gameHandlers.ts:707-720`) is now team-agnostic — `find` has no
  `teamId` filter — mirroring the BUG-04 pattern already used for STANDARD_PASS/LONG_BALL in
  `gameEngine.ts:1285-1288`. Both the possession-transfers and possession-unchanged-on-empty-hex
  cases are covered by new integration tests (`game.integration.test.ts:415-509`), and those tests
  explicitly assert the fix is reachable through the real `GAME_END_TURN` wire path, not just unit
  state.

**However, the act of widening the occupant search (17.1-15) introduced a new, untested gap that
the original team-restricted version structurally could not produce: the FTP delivery and
repositioning logic never excludes the original passer's own piece from either "who can move during
the ATTACKER slot" or "who counts as the occupant at delivery."** Because HIGH_PASS tracks
`highPassCarrierId` specifically so the kicker can be excluded/restored, but FIRST_TIME_PASS has no
equivalent `firstTimePassCarrierId` field, the passer's piece — still on the pitch with
`ball.carrierId` cleared to `null` — can be the piece chosen to reposition onto the (otherwise empty)
`passTargetHex` during the ATTACKER slot, and at delivery the now-team-agnostic occupant lookup will
find the passer standing on the target hex and hand them the ball back. This is detailed in CR-01
below. No existing test (including the new 17.1-15 tests) exercises this path, because both new
tests seed the occupant via direct room-state mutation rather than driving the passer through the
real repositioning `GAME_MOVE` handler.

No interaction bug was found between the two fixes themselves (applyUndo's lock-reset is keyed
purely on `state.phase` and does not depend on which team's slot most recently moved, so an Undo
during the DEFENDER slot of FTP correctly clears the same `firstTimePassMovedPieceId` field that an
Undo during the ATTACKER slot would, with no leakage into the delivery occupant logic).

## Critical Issues

### CR-01: FTP passer can reposition onto the empty target hex and reclaim their own pass

**File:** `packages/server/src/gameHandlers.ts:488-550` (`FIRST_TIME_PASS_MOVE` repositioning
handler) and `packages/server/src/gameHandlers.ts:707-720` (delivery occupant lookup)

**Issue:** During `FIRST_TIME_PASS_MOVE`, the ATTACKER-slot branch of the `GAME_MOVE` handler
(lines 488-550) accepts any piece belonging to `ftpState.activeTeam` as the one piece allowed to
reposition — including the piece that just made the first-time pass (the ball's prior carrier).
Unlike `HIGH_PASS`, which stores `highPassCarrierId` specifically so the kicker can be
identified/excluded later (`gameEngine.ts:1269`, `gameHandlers.ts:646,651`), there is no
`firstTimePassCarrierId` (or equivalent) field for FIRST_TIME_PASS — confirmed by searching
`types.ts` and `gameEngine.ts` for any FTP-specific carrier-tracking field; none exists.

If the passer's piece starts within 1 hex of `passTargetHex` and the target hex is unoccupied when
the ATTACKER slot begins (a realistic situation — first-time passes are frequently short, and the
passer is often standing adjacent to their intended target), the passer can select themselves as
the piece to move and step onto `passTargetHex` during their own team's repositioning turn. At
DEFENDER-slot completion, the now-team-agnostic occupant lookup added by 17.1-15
(`gameHandlers.ts:714-716`):

```ts
const occupant = ftpEndState.pieces.find(
  (p) => p.position.q === targetHex.q && p.position.r === targetHex.r,
);
```

finds the passer's own piece sitting on `passTargetHex` and assigns them `ball.carrierId`, with
`possessionChanges` computed as `false` (same team as `attackingTeam`). This lets the acting player
fully undo the risk/reward of a first-time pass — the rule's intent (deliver the ball to a
_different_ piece without an interception check) is bypassed by simply repositioning the passer back
onto the ball's landing spot. Before 17.1-15's team-agnostic widening this exact outcome was also
reachable for the _attacking_ team (the lookup was already attacking-team-filtered, and the passer
is on the attacking team), so this is not strictly new to 17.1-15 — but 17.1-15's fix was scoped and
tested only for the defending-team-occupant case, and no test in the reviewed suite (old or new)
exercises the passer-reclaim path through the real `GAME_MOVE`/`GAME_END_TURN` handlers. The two new
Review-CR-02 (17.1-15) tests in `game.integration.test.ts` (lines 415-509) seed the occupant directly
via `room.gameState = { ...pieces: ... }`, never by driving the passer through the repositioning
handler, so this gap has zero test coverage in either direction.

**Fix:** Track the original passer's ID when entering `FIRST_TIME_PASS_MOVE` (mirroring
`highPassCarrierId`), and exclude that piece from both the repositioning handler and the delivery
occupant lookup:

```ts
// gameEngine.ts — applyRoll FIRST_TIME_PASS branch (mirror highPassCarrierId, line ~1256)
if (newLastActionType === 'FIRST_TIME_PASS') {
  return {
    ok: true,
    state: {
      ...state,
      phase: 'FIRST_TIME_PASS_MOVE',
      ball: { position: targetHex, carrierId: null },
      firstTimePassCarrierId: carrier.id, // NEW — mirrors highPassCarrierId
      // ...unchanged fields
    },
  };
}
```

```ts
// gameHandlers.ts:495-500 — FIRST_TIME_PASS_MOVE GAME_MOVE handler
const piece = ftpState.pieces.find((p) => p.id === pieceId);
if (
  !piece ||
  piece.teamId !== ftpState.activeTeam ||
  pieceId === ftpState.firstTimePassCarrierId // NEW — passer may not be the repositioned piece
) {
  socket.emit(ServerEvents.GAME_ERROR, 'WRONG_TEAM');
  broadcastState(io, room);
  return;
}
```

```ts
// gameHandlers.ts:714-716 — delivery occupant lookup
const occupant = ftpEndState.pieces.find(
  (p) =>
    p.id !== ftpEndState.firstTimePassCarrierId && // NEW — passer cannot "receive" their own pass
    p.position.q === targetHex.q &&
    p.position.r === targetHex.r,
);
```

Add `firstTimePassCarrierId` to `GameState` (optional, nullable, mirroring `highPassCarrierId`'s
type) and clear it alongside the other FTP fields at delivery (`gameHandlers.ts:731-733`). Add a
regression test that seeds the passer adjacent to an empty `passTargetHex`, drives them through the
ATTACKER-slot `GAME_MOVE` onto the target hex, and asserts the delivery does NOT hand them the ball
(or that the move itself is rejected, depending on which half of the fix is implemented).

## Warnings

### WR-01: `applyUndo` writes to `paceUsedByPieceId` during FIRST_TIME_PASS_MOVE/HIGH_PASS_MOVE even though those phases never read or write it elsewhere

**File:** `packages/server/src/gameEngine.ts:873-880`

**Issue:** `applyUndo` unconditionally reads/writes `state.paceUsedByPieceId[moveToUndo.pieceId]`
(decrementing or deleting the entry) regardless of `state.phase`. During `FIRST_TIME_PASS_MOVE` and
`HIGH_PASS_MOVE`, piece-movement pace is tracked exclusively via the dedicated
`firstTimePassPaceUsed` / `highPassPaceUsed` scalar fields — confirmed by grep that neither
repositioning handler in `gameHandlers.ts` ever writes to `paceUsedByPieceId`. This means `applyUndo`
is mutating a map that is irrelevant to the current phase. It is currently harmless because the map
is empty by the time FTP/HP_MOVE phases are entered (cleared on the preceding PASS transition), but
it is a latent trap introduced by extending `applyUndo` to these two new phases (17.1-11 and
17.1-14): if a future change ever populates `paceUsedByPieceId` for an unrelated reason while a game
is in one of these phases, an Undo would silently corrupt that unrelated state with no test
currently capable of catching it, since no test seeds a non-empty `paceUsedByPieceId` alongside an
FTP/HP undo scenario.

**Fix:** Gate the generic `paceUsedByPieceId` mutation by phase, the same way the new `lockReset`
already is:

```ts
const currentPace = state.phase === 'MOVE' ? (state.paceUsedByPieceId[moveToUndo.pieceId] ?? 0) : 0;
const newPaceUsed =
  state.phase === 'MOVE'
    ? (() => {
        const next = { ...state.paceUsedByPieceId };
        if (currentPace > 1) next[moveToUndo.pieceId] = currentPace - 1;
        else delete next[moveToUndo.pieceId];
        return next;
      })()
    : state.paceUsedByPieceId;
```

### WR-02: FTP repositioning and delivery apply no role-based restriction — a GK can be the FTP-repositioned/receiving piece with no rulebook citation either way

**File:** `packages/server/src/gameHandlers.ts:488-550`, `packages/server/src/gameHandlers.ts:714-720`

**Issue:** The task asked specifically whether the team-agnostic occupant search handles "edge cases
like the GK." It does, in the sense that it applies uniformly — a GK can be selected as the piece
repositioned during either FTP slot, and the occupant lookup at delivery will hand the ball to a GK
standing on `passTargetHex` exactly like any outfielder, with no special case either excluding or
specifically allowing this. This mirrors the existing STANDARD_PASS/LONG_BALL BUG-04 occupant
behavior (which has the same property), so it is consistent with established precedent rather than a
new regression — flagged as a Warning only because no comment or rulebook citation in the codebase
states whether this is intended for first-time passes specifically, and the combination with CR-01
above (GK is also not excluded from being the _passer_ who reclaims their own pass) means a GK who
starts a short give-and-go adjacent to the target can reposition onto it just as easily as an
outfielder.

**Fix:** No code change required unless product intent restricts FTP receivers by role; if so, add
an explicit role check at the occupant lookup and document the rulebook citation in a comment
(matching the codebase's D-xx/BUG-xx citation convention used throughout `gameEngine.ts`).

## Info

### IN-01: `moveTypeForPhase` and `lockReset` are two separate phase-discriminant switches that must be kept in sync by hand

**File:** `packages/server/src/gameEngine.ts:840-845` and `packages/server/src/gameEngine.ts:911-916`

**Issue:** `applyUndo` computes `moveTypeForPhase` from `state.phase` (lines 840-845) and,
separately, `lockReset` from `state.phase` again (lines 911-916), using the same three-way
MOVE/HIGH_PASS_MOVE/FIRST_TIME_PASS_MOVE discriminant in two different `switch`-shaped expressions.
Both are internally consistent today (verified by tracing all three branches), but the duplication
is a minor maintainability smell introduced across the 17.1-11/17.1-14 gap-closure plans: a
hypothetical future repositioning phase (e.g. a `LONG_BALL_MOVE`) would require updating both
ternary chains in lockstep, and nothing besides code review enforces that they stay aligned.

**Fix:** Optional refactor — derive both values from a single lookup table keyed by phase:

```ts
const REPOSITION_PHASE_CONFIG: Partial<
  Record<GamePhase, { moveType: ActionEvent['type']; lockFields: Partial<GameState> }>
> = {
  HIGH_PASS_MOVE: {
    moveType: 'HP_MOVE',
    lockFields: { highPassMovedPieceId: null, highPassPaceUsed: 0 },
  },
  FIRST_TIME_PASS_MOVE: {
    moveType: 'FTP_MOVE',
    lockFields: { firstTimePassMovedPieceId: null, firstTimePassPaceUsed: 0 },
  },
};
const moveTypeForPhase = REPOSITION_PHASE_CONFIG[state.phase]?.moveType ?? 'MOVE';
// ...
const lockReset = REPOSITION_PHASE_CONFIG[state.phase]?.lockFields ?? {};
```
