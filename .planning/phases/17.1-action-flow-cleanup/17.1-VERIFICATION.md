## Gaps Summary

4 of 5 ROADMAP success criteria are fully verified against the live codebase, including the GamePhase rename, the aerial-stat consolidation, the ZoI tackle/steal exclusion symmetry, all GK_RESTART/loose-ball/shot-range mechanics, and the three-case pass-interception model. The 4 UAT-diagnosed gap-closure plans (07-10) were independently verified against the running code, not just trusted from their SUMMARYs — in particular the loose-ball scatter fix was reproduced at runtime against the exact originally-reported bug coordinates.

The one gap is success criterion 3's undo clause: **"undo is available at the FTP_REPOSITION boundary" is false**. This is the pre-existing CR-01 finding from 17.1-REVIEW.md, and this verification independently reproduced it at runtime (not merely citing the review) by constructing the exact event-log shape `gameHandlers.ts` produces in production and feeding it to the real `applyUndo` function from the built dist — it returns `NOTHING_TO_UNDO` instead of reversing the move. The same defect exists in the client's `canUndo` computation. Both `applyUndo` (server) and `canUndo` (client) check for a literal `'MOVE'` event type, but the actual events emitted during `FIRST_TIME_PASS_MOVE` repositioning are `'FTP_MOVE'` (and during `HIGH_PASS_MOVE`, `'HP_MOVE'`) — so the boundary-detection logic correctly identifies `FTP_REPOSITION` as a slot boundary, but the subsequent "is there a move to undo" check never finds one, and the Undo button renders permanently disabled.

This is not a new regression introduced by this phase's work — CR-01 affects the pre-existing `HIGH_PASS_MOVE` phase too — but Phase 17.1 is the phase that explicitly claims "undo is available at the FTP_REPOSITION boundary" as a success criterion, and that claim does not hold. The code review (17.1-REVIEW.md) already fully diagnosed the root cause and proposed a concrete fix (phase-aware event-type lookup), and flagged that the only test exercising this path uses a hand-fabricated fixture that doesn't match real gameplay events — also independently confirmed in this verification.

This gap should be closed with a small, well-scoped gap-closure plan before the phase is considered complete, since it speaks directly to one of the five contractual success criteria. Alternatively, if the team decides the FTP/HP undo behavior is acceptable to ship broken (e.g., deferred to a follow-up phase with an explicit override), an override entry should be added to this VERIFICATION.md's frontmatter documenting that decision.

**This looks like a real gap, not an intentional deviation** — there is no alternative implementation achieving the same intent; the feature is simply non-functional. No override is suggested.
