## Gaps Summary

This is the final gap-closure plan (17.1-11) for the prior verification cycle's single documented gap: "undo is available at the FTP_REPOSITION boundary" was FALSE at runtime (old CR-01). That specific defect is now genuinely fixed — `applyUndo` and `canUndo` are both phase-aware, de-masked unit fixtures use real `HP_MOVE`/`FTP_MOVE` event shapes, and two new wire-level integration tests prove the fix end-to-end through a real socket connection. This part of the work is solid and independently re-confirmed by this verification, not merely trusted from the SUMMARY.

However, a fresh code review (17.1-REVIEW.md, run after plan 17.1-11 landed) surfaced two NEW Critical findings that this verification independently confirmed against the live codebase — not merely cited from the review:

1. **CR-01-new (review numbering):** `HexGrid.tsx` and `useGameStore.ts` were never extended with `FIRST_TIME_PASS_MOVE` piece-selection support, unlike the three structurally identical phases (`HIGH_PASS_MOVE`, `GK_KICK_MOVE`, `SNAPSHOT_DEFLECT`) that each have a dedicated `canSelectXxx` boolean and `selectPiece` branch. Confirmed by direct grep (zero matches for `FIRST_TIME_PASS_MOVE` in either file) and by reading `selectPiece`'s fall-through path: a click during this phase reaches the generic MOVE-phase branch, which calls `validateMove`, whose very first guard (`state.movementSlot === null → WRONG_SLOT`) always fires because this phase tracks its own slot via `firstTimePassMovementSlot`, never the shared `movementSlot` field. Net effect: a player cannot select or move any piece during FIRST_TIME_PASS_MOVE in the browser. Confirmed this is a genuine scope gap, not a regression — plan 17.1-06 (which built the ActionPanel UI for this phase) explicitly scoped only `ActionPanel.tsx`, never `HexGrid.tsx`/`useGameStore.ts`; no commit in the phase's history ever touched either file for this purpose.

2. **CR-02-new:** `gameEngine.ts`'s `applyRoll` PASS case runs the `autoIntercepts`/`rollIntercepts` interception loop (lines 1153-1227) before the `FIRST_TIME_PASS → FIRST_TIME_PASS_MOVE` transition check (line 1237). `passValidator.ts` populates the interception lists for `FIRST_TIME` pass type identically to `STANDARD` (line 140), and the only pre-loop bypass is `isHeaderPass` — `FIRST_TIME_PASS` is not excluded. Confirmed by direct code read of both files: a first-time pass aimed near a defender (the realistic scenario a first-time pass exists to serve) can return early with `SUCCESSFUL_TACKLE` before the repositioning phase is ever reached, contradicting success criterion 3's explicit "delivers the ball without interception" clause. No regression test exists for this scenario — confirmed by reading every FTP-related test in `gameEngine.phase17.test.ts`; all either start already inside `FIRST_TIME_PASS_MOVE` or use a target hex with no nearby defender.

A third finding (CR-03, 4 failing server tests) was also independently re-run and confirmed: the same 4 failures already documented as known/pre-existing/out-of-scope in the prior 17.1-VERIFICATION.md (2 MOVE-06 FREE_MOVE gaps, 2 abandoned `firstTimePassStep` design stubs). The fresh review's framing is consistent with — not a change to — that prior assessment; these 4 failures are not new and do not block this verification's status determination beyond what was already accepted as out-of-scope/pre-existing in the prior cycle.

**Net result:** the prior cycle's gap (undo) is closed, but success criterion 3 cannot be marked VERIFIED because two newly-discovered, independently-confirmed defects mean the repositioning and no-interception clauses of the same criterion are false for realistic gameplay. This phase is not yet complete. A new gap-closure plan addressing CR-01-new (client-side piece selection) and CR-02-new (interception loop ordering/exclusion) is required before Phase 17.1 can be considered to have achieved its goal.

**This does not look like an intentional deviation.** There is no alternative implementation achieving the same intent for either defect — FIRST_TIME_PASS_MOVE repositioning is simply unreachable for a human player via click, and the no-interception delivery guarantee is simply not honored for the defender-nearby case. No override is suggested for either gap.
