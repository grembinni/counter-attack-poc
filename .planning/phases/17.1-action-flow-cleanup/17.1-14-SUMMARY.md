# Phase 17.1 Plan 14: Reset FTP/HP Repositioning Lock Fields on Undo Summary

**applyUndo now clears firstTimePassMovedPieceId/firstTimePassPaceUsed (or highPassMovedPieceId/highPassPaceUsed) when undoing within the matching repositioning phase, closing Review-CR-01's one-shot Undo dead-end.**

## Accomplishments

- Fixed the root cause diagnosed in 17.1-VERIFICATION.md (Review-CR-01 / Gap A): `applyUndo` reset the generic
  movement fields (paceUsedByPieceId, movedPieceIds, eventLog, pendingFreeMove, ball) but never reset the
  phase-specific repositioning lock fields, leaving the FTP/HP repositioning slot permanently locked after a
  single Undo.
- `applyUndo`'s returned state now includes a phase-conditional `lockReset`: `firstTimePassMovedPieceId: null` /
  `firstTimePassPaceUsed: 0` when `state.phase === 'FIRST_TIME_PASS_MOVE'`, and `highPassMovedPieceId: null` /
  `highPassPaceUsed: 0` when `state.phase === 'HIGH_PASS_MOVE'` — using exactly the null/0 shape already used at
  the canonical slot-clear sites (gameEngine.ts:1257-1258, gameHandlers.ts:693-694/721-722).
- Added regression assertions to the existing FTP undo test and the existing HP undo test confirming the
  lock-field reset (not just piece-position restore) — both would fail against the pre-fix `applyUndo`.
- Added a new no-regression test confirming a plain `MOVE`-phase undo leaves the FTP/HP lock fields completely
  untouched (verifying the phase-gating is exact, no spurious resets).

## Files Created/Modified

- `packages/server/src/gameEngine.ts` - `applyUndo` returned state now spreads a phase-conditional `lockReset`
  object after `...state`, resetting `firstTimePassMovedPieceId`/`firstTimePassPaceUsed` or
  `highPassMovedPieceId`/`highPassPaceUsed` to null/0 depending on `state.phase`. No other field in the
  function changed (move-type lookup at 838-845, slot-boundary detection at 822-829, and all guards are
  unchanged).
- `packages/server/src/__tests__/gameEngine.phase17.test.ts` - Extended the existing FTP undo test (line ~668)
  and the existing HP undo test (line ~401) with lock-field assertions; added a new test
  (`applyUndo during regular MOVE phase does not touch FTP/HP lock fields`) as a no-regression guard.

## Decisions Made

- Implemented the fix as a small `Partial<GameState>` ternary (`lockReset`) spread last into the returned
  state object, rather than branching the entire `return` statement per phase — keeps the diff minimal and
  the override behavior obvious (matches the plan's suggested implementation shape exactly).
- Used `'ATTACKER_4'` + a synthetic `ballAfter` value for the new no-regression test's `MOVE` event fixture,
  since the `MOVE` `ActionEvent` variant requires `slot` and `ballAfter` (discovered via typecheck — see
  Deviations).
