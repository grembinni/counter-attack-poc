<objective>
Close CR-02-new (the second of the two newly-confirmed Phase 17.1 verification gaps): a FIRST_TIME_PASS
aimed near a defender is silently intercepted (returns SUCCESSFUL_TACKLE) before FIRST_TIME_PASS_MOVE
is ever reached, contradicting success criterion 3's explicit "delivers the ball without interception"
clause for the realistic case the repositioning feature exists to serve.

Root cause (confirmed by the verifier against the live codebase, 17.1-VERIFICATION.md gaps block):
gameEngine.ts's applyRoll PASS case runs the autoIntercepts / rollIntercepts interception loop
(lines 1153-1227) BEFORE the FIRST_TIME_PASS → FIRST_TIME_PASS_MOVE transition check (line 1237).
passValidator.ts groups FIRST_TIME with STANDARD for interception-list population (line 140:
`if (passType !== 'LONG' && passType !== 'HIGH')`), so autoIntercepts / rollIntercepts are non-empty
for a FIRST_TIME_PASS near a defender. The only pre-loop bypass today is isHeaderPass (line 1152);
FIRST_TIME_PASS is not excluded, so the loop can return early with SUCCESSFUL_TACKLE and the
repositioning phase is never entered.

Fix (option (a) from the verifier — the structurally cleaner of the two): extend the existing
isHeaderPass bypass to also bypass the interception loop for a FIRST_TIME_PASS. This is a single
guard change at gameEngine.ts:1152-1153, leaves passValidator.ts untouched (its FIRST_TIME-with-
STANDARD grouping remains correct for the interception-list shape; we simply do not consume those
lists for a first-time pass), and leaves the STANDARD / HIGH / LONG / header behaviors exactly as
they are. After the bypass, control falls through to the existing FIRST_TIME_PASS → FIRST_TIME_PASS_MOVE
transition at line 1237, which already delivers the ball without interception per D-03.

Rationale for option (a) over option (b) (reorder): the FIRST_TIME_PASS transition block at 1237
already sits immediately after the interception loop and is keyed on newLastActionType. Extending the
one-line bypass guard is lower-risk than relocating the transition block above the loop (which would
require moving the newLastActionType / passTargetHex / eventLog setup it depends on). Both achieve the
same observable result; the bypass is the minimal diff.

Purpose: guarantee an accurate FIRST_TIME_PASS always reaches FIRST_TIME_PASS_MOVE, even with a
defender in interception range, satisfying success criterion 3's no-interception clause.
Output: the extended bypass guard plus a regression test for the defender-nearby scenario (zero
coverage today).
</objective>
