# Phase 17.1 Plan 08: Loose-Ball Scatter Geometry Fix Summary

**Rewrote computeLooseBall from fixed axial-style offset deltas to true cube-coordinate unit vectors, fixing systematic overshoot on NE/SW scatter rolls and unifying gameEngine.ts's board-edge clamp walk onto the same corrected trajectory.**

## Accomplishments

- Root cause (diagnosed in `.planning/debug/loose-ball-scatter-rolls.md`) fully resolved: `LOOSE_BALL_DIRECTIONS` was a table of stale axial-style `(q,r)` deltas applied directly to the live ODD-Q offset pitch grid, causing NE/SW scatter rolls to overshoot true hex distance on every multi-step roll (distance >= 2)
- `computeLooseBall` now converts `from` to cube coordinates, adds a parity-independent cube-direction unit vector scaled by `distance`, and converts back — mirroring `hexLine`'s established offset-to-cube-and-back pattern
- `gameEngine.ts`'s D-08 board-edge clamp walk no longer duplicates fixed-delta math inline; it calls `computeLooseBall(from, direction, step)` per step, so the clamp walk and the raw scatter formula are guaranteed to stay in sync (single source of truth)
- Added a 72-case regression test (6 directions x 2 column parities x 6 distances) asserting `hexDistance(from, computeLooseBall(from, direction, distance)) === distance` for every combination
- Manually verified the originally reported case: from (21,4), direction=NE (die=2), distance=3 now produces a hex exactly 3 true hexes away (`{q:24,r:3}`), not the previous buggy `{q:24,r:1}` (which was actually 5 true hexes away)

## Decisions Made

- **Cube-direction table derivation:** The 6 compass-direction cube unit vectors were derived by evaluating `hexNeighbors({q:0,r:0})` (an even-q hex) and converting both the hex and each neighbor to cube via `toCube`, taking the difference. This is parity-independent by construction (cube coordinates have no column-parity concept), so a single fixed cube delta per direction is valid from any starting hex.
- **Geometric verification method:** Rather than trusting `hexDistance` equality alone (which the old buggy code also satisfied for some cases), each direction's cube-vector path was cross-checked against `hexLine`'s own offset-to-cube-and-back straight-line algorithm at every intermediate step, and against `axialToPixel`'s pixel-space output, to confirm the cube-vector walk traces the actual geometrically straight line on the rendered pitch — not just a hex that happens to be the right `hexDistance` away.
- **Pre-existing test fixtures with stale row-preserving assumptions were corrected, not preserved.** Several existing tests (SW distance=1 from origin, E distance=6 from origin, the PASS-05 D-23 trajectoryBlocker fixture, and the D-08 board-edge clamp tests) encoded an implicit assumption that "axis-aligned E/W holds r constant" — disproven by `axialToPixel.ts`, which shows odd columns are pixel-shifted down by half a row, meaning a genuine straight "due east" line from an odd-q hex must drift in `r`. These fixtures were corrected to the geometrically true values rather than left as stale tests of the old (also buggy) behavior.
