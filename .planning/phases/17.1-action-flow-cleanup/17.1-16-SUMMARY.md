# Phase 17.1 Plan 16: First-Time Pass Self-Pass-Reclaim Fix Summary

**Added `firstTimePassCarrierId` to GameState and wired server + client exclusions so the original passer can no longer reposition onto their own pass target and reclaim the ball — closing the cycle-4 verifier's CR-01 Elevation-of-Privilege finding.**

## Performance

- **Duration:** ~10 min
- **Completed:** 2026-06-19
- **Tasks:** 2
- **Files modified:** 6

## Accomplishments

- Added `firstTimePassCarrierId?: string | null` to `GameState` (types.ts), mirroring
  `highPassCarrierId` in type, JSDoc, and lifecycle.
- Set the field to the passer's piece id at the FIRST_TIME_PASS transition in
  `gameEngine.ts` (`applyRoll` PASS branch), and confirmed `applyUndo`'s `lockReset` does
  NOT clear it — an FTP_MOVE undo must leave the carrier id intact because the pass is
  still in flight.
- Added an authoritative server-side rejection in the `GAME_MOVE` FIRST_TIME_PASS_MOVE
  handler (`gameHandlers.ts`): `pieceId === firstTimePassCarrierId` → `GAME_ERROR
'WRONG_PIECE'`, checked before the lock/pace/adjacency gates.
- Excluded the passer from the FTP delivery occupant lookup (defense in depth) and added
  `firstTimePassCarrierId: null` to the delivery clear block, mirroring the HIGH_PASS clear
  pattern.
- Mirrored the exclusion on the client `selectPiece` FIRST_TIME_PASS_MOVE branch
  (`useGameStore.ts`) as non-authoritative defense-in-depth UX.
- Added 3 new server integration tests (passer rejected with position unchanged, non-passer
  accepted, and a gate-ordering re-confirmation) and 2 new client unit tests (passer not
  selectable, non-passer selectable).

## Task Commits

Each task was committed atomically:

1. **Task 1: Add firstTimePassCarrierId field + server set/exclude/clear sites + server regression test** — `6769636` (feat, tdd)
2. **Task 2: Mirror the passer exclusion on the client selectPiece FTP branch + client test** — `69dcdf1` (feat, tdd)

were implemented and verified together as a tight loop rather than as separate RED/GREEN

(`highPassCarrierId`), and the existing codebase convention for this category of fix (see
17.1-09, 17.1-11, 17.1-14, 17.1-15) is a single `feat` commit per task containing both the
fix and its regression test. No `test(...)`-only commit was created._

## Decisions Made

- Mirrored the existing `highPassCarrierId` pattern exactly rather than inventing a new
  design, per the plan's explicit directive — same field type, same set/exclude/clear
  lifecycle shape, same JSDoc structure.
- Confirmed (by reading `applyUndo`'s `lockReset` at gameEngine.ts:911-916) that
  `firstTimePassCarrierId` must NOT be added to the undo lock-reset: undoing a single
  `FTP_MOVE` reverses only the repositioning step, not the in-flight pass itself, so the
  carrier id must survive.
- Left `HIGH_PASS_MOVE`'s identical defect unfixed, as directed — `highPassCarrierId` is set
  but never consumed as an exclusion in the `HIGH_PASS_MOVE` `GAME_MOVE` handler. This is
  recorded as a deferred parallel finding for a future cycle (see `<artifacts_produced>` in
  the plan and the "Documented but NOT fixed here" note below).

## Deviations from Plan

None — plan executed exactly as written. Both source-file edits and both regression test
additions match the plan's specified line ranges, field names, and exclusion logic shape.

## Issues Encountered

- Initial `pnpm --filter @counter-attack/server typecheck` failed with `firstTimePassCarrierId
does not exist on type 'GameState'` even after editing `types.ts`, because the server
  package consumes `@counter-attack/shared` via its built `dist/` output, not the source
  directly. Resolved by running `pnpm --filter @counter-attack/shared build` before
  re-running the server typecheck — not a plan deviation, just the expected monorepo build
  order (shared must be rebuilt before consumers pick up new exported types).

## Documented but NOT fixed here (deferred parallel finding)

`HIGH_PASS_MOVE` has the **identical** missing repositioning-exclusion defect: although
`highPassCarrierId` is declared and SET at the HIGH_PASS transition, it is only CONSUMED to
restore the kicker's id for the accuracy-stat lookup in `applyRoll` — it is NEVER consumed as
an exclusion in the `HIGH_PASS_MOVE` `GAME_MOVE` handler, which gates only on
team/lock/pace/adjacency/pitch/occupied-by-other, exactly like the FTP handler did before
this plan. A high pass aimed within 3 hexes of the kicker could let the kicker reposition
toward/onto the target similarly. Per the gap-closure scope directive, HIGH_PASS is **NOT**
fixed in this plan; this is recorded as a separate, deferred finding for a future cycle.
