## Item 1: Game Settings Back Button

### Source of truth: reuse the existing `LobbyScreen` Back pattern verbatim

`LobbyScreen.tsx` already implements an identical "Back to Landing" affordance on three sibling pre-game screens (`CreateRoomScreen`, `JoinRoomScreen`, `WaitingScreen`) via a shared `useLobbyBack()` hook and a `.subLink` button styled `← Back`. `GameSettingsScreen.module.css`'s own file header states it "duplicates relevant tokens from LobbyScreen.module.css (`.page`/`.card`/`.ctaButton`) ... per project convention (no shared CSS partial)" — this phase extends that same duplication convention to the Back button.

**Decision: do not invent a new button style.** Add a `.subLink` class (copied verbatim from `LobbyScreen.module.css:90-103`) to `GameSettingsScreen.module.css`, and render a `← Back` button using the exact same markup shape as `LobbyScreen.tsx`'s existing Back buttons.

### Component contract

| Property            | Value                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Label               | `← Back` (literal: `&larr; Back` HTML entity + text, matching `LobbyScreen.tsx:75,88,147,170` verbatim)                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Placement           | Last element inside `.card`, **after** the `Confirm Settings` CTA button — mirrors the established order in every `LobbyScreen` sub-screen (primary CTA first, `.subLink` Back last)                                                                                                                                                                                                                                                                                                                                                             |
| Visibility          | Always visible/enabled, unconditional of `room.status`, `teamType`, `hasConfirmed`, or any other local state (D-05: no away-player-joined guard needed)                                                                                                                                                                                                                                                                                                                                                                                          |
| Style class         | `.subLink` — `background: none; border: none; color: var(--color-text-secondary); font-size: 13px; cursor: pointer; text-decoration: underline; padding: 0; align-self: flex-start;` with `:hover { color: var(--color-text-primary); }` — copied identically from `LobbyScreen.module.css:90-103`                                                                                                                                                                                                                                               |
| Confirmation dialog | **None.** Mirrors `CreateRoomScreen`/`JoinRoomScreen`/`WaitingScreen`'s existing Back buttons, none of which show a destructive-confirm dialog even though they also cause room state to be abandoned/torn down. D-05 already resolved the away-player race as a non-issue at this screen. No `window.confirm`, no modal overlay, no `withEndTurnConfirm`-style gate (that pattern is reserved for in-game turn-ending actions, not pre-game navigation).                                                                                        |
| Click behavior      | Emits the new `LEAVE_ROOM` socket event (D-03), which the server handles by calling `deleteRoom(roomCode)` synchronously (reusing the existing `roomStore.ts` teardown function per "Reusable Assets"), then the client clears `sessionStorage`'s `ca_session_token` and transitions `screen` back to `'LANDING'` — functionally the same client-side reset shape as `useLobbyBack()` (clear session token, reset local settings state), but additionally emitting `LEAVE_ROOM` first instead of relying on socket disconnect/reconnect cycling. |
| Icon                | None beyond the `←` (`&larr;`) glyph inline with the label text — no separate icon component                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Touch target        | Text-only link, no minimum 44px enforcement needed (desktop-first pre-game screen, consistent with existing `.subLink` instances which carry no explicit touch-target sizing)                                                                                                                                                                                                                                                                                                                                                                    |

### Explicit non-scope (per D-04)

This Back button pattern is added **only** to `GameSettingsScreen.tsx`. Do **not** add it to `UniformSelectionScreen.tsx`, `LineupAssignmentScreen.tsx`, `TeamSelectionScreen.tsx`, or any other pre-game screen — even though they share a structurally similar `.page`/`.card` layout. This was an explicit user decision during `/gsd-discuss-phase`, not an oversight.

### CSS addition (executor reference)

Add to `GameSettingsScreen.module.css` (append after `.ctaButton:disabled`, mirroring `LobbyScreen.module.css`'s block verbatim):

```css
.subLink {
  background: none;
  border: none;
  color: var(--color-text-secondary);
  font-size: 13px;
  cursor: pointer;
  text-decoration: underline;
  padding: 0;
  align-self: flex-start;
}

.subLink:hover {
  color: var(--color-text-primary);
}
```

No new tokens, no new colors — reuses `--color-text-secondary` and `--color-text-primary` already defined in `tokens.css`.

### Markup shape (executor reference)

```tsx
<button className={styles.subLink} onClick={handleLeaveRoom}>
  &larr; Back
</button>
```

Placed as the final child inside `.card`, after the existing `{!hasConfirmed && <button className={styles.ctaButton} ...>Confirm Settings</button>}` block — rendered unconditionally (not gated by `hasConfirmed`, unlike the Confirm Settings button, since D-05 requires it always visible).

## Items 4 & 5: Confirmed No New UI Contract Needed

### Item 4 — Loose-ball path origin on blocked shot

Investigated `HexGrid.tsx` (`BallMarker`, `lastShotPath` hex-tint rendering) — the client already renders the ball at whatever position/path data the server sends (`ball.position` via `<BallMarker ball={ball} />`, shot-path hex tinting via `lastShotPathSet`). D-14's fix is a server-side data-correctness change to `computeShotPathDeflection`/`computeLooseBall`'s origin hex — no client rendering code changes, no new visual states, no copywriting changes. Once the origin hex is corrected server-side, existing rendering displays it correctly with zero UI work.

### Item 5 — Undo boundary at dice-roll action

Investigated `ActionPanel.tsx`'s `canUndo` computation (lines 251-287) and its consuming `<button>` elements (e.g. lines 307-314). The Undo button already has a static tooltip (`title={ACTION_SUMMARY['Undo']}` = `"Undo your last move this phase."`) and standard `disabled={!canUndo}` styling that is already token-driven (Phase 33/34 CTA button tokens) — this pattern applies uniformly regardless of _why_ Undo is disabled. D-13's fix only changes the boundary-event set used inside `canUndo`'s scan (adding `TACKLE_ATTEMPT`/`STEAL_ATTEMPT` as boundary events) — it does not add a new disabled-reason, new copy, or new visual state. The existing generic tooltip copy remains accurate and does not need updating.

**No UI-SPEC content applies to items 2, 3, 4, or 5.**

## Spacing Scale

Declared values (must be multiples of 4) — unchanged from project-wide convention already in effect on `GameSettingsScreen.module.css` (see its file header: "Spacing: new elements use only 4/8/16/24/32"):

| Token | Value | Usage                                                         |
| ----- | ----- | ------------------------------------------------------------- |
| xs    | 4px   | Icon gaps, inline padding                                     |
| sm    | 8px   | Compact element spacing (`.section` gap, `.speedOptions` gap) |
| md    | 16px  | Default element spacing (`.card` gap)                         |
| lg    | 24px  | Section padding (`.card` padding)                             |
| xl    | 32px  | Layout gaps (not used on this screen)                         |

Exceptions: none. The new `.subLink` Back button uses `padding: 0` (link-style, not button-chrome) — consistent with its existing `LobbyScreen` precedent, not a spacing-scale violation since it carries no internal padding to begin with.
