## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** All 9 player attributes use a **1–6 scale**. Outfield players retain `handling: 0`, `saving: 0`, `aerialAbility: 0` (GK-only attributes — 0 = not applicable). GK retains `shooting: 1` (minimum valid). `highPass: 0` on GKs is preserved (D-04 from Phase 7.1).
- **D-02:** 1–6 range applies to role-relevant attributes. Tier totals count all 9 attributes (0s count as 0).
- **D-03:** Squad tier distribution: Tier 1 (34+) × 1, Tier 2 (32–33) × 2, Tier 3 (30–31) × 3, Tier 4 (28–29) × 3, Tier 5 (26–27) × 2 = 11 total.
- **D-04:** GK tier calculated from GK-relevant attributes (Saving, Handling, Aerial Ability, Pace, Tackling, Resilience).
- **D-05:** Steal = solo defender roll: die===6 OR tackling+die≥10 → SUCCESS. No carrier dribbling involvement.
- **D-06:** Bug fix: `applyMove` currently checks `combined >= 10` only; fix to `(die === 6 || combined >= 10)`.
- **D-07:** `STEAL_ATTEMPT` ActionEvent extended with `defenderDie`, `defenderCombined`.
- **D-08:** `applyMove` must NOT call `rollDice()` internally (Pitfall 1). Caller (`gameHandlers.ts` GAME_MOVE handler) pre-generates steal die + tackle dice; passes them via options param (same pattern as `addedTimeRoll` in `applyEndTurn`).
- **D-09:** Tackling = mirror of stealing. Fires when a DEFENDER steps adjacent to ball carrier. Duel: `defender.tackling + die` vs `carrier.dribbling + die`; defender wins on tie.
- **D-10:** TACKLE_ATTEMPT effect returned from `validateMove` (or `applyMove`) when moving piece is NOT ball carrier AND destination is adjacent to ball carrier.
- **D-11:** TACKLE_ATTEMPT resolution: defender always moves; duel determines possession. SUCCESS: possession to defender, ball follows, phase ends. FAIL: defender moved, carrier keeps ball. Event records: `defenderId`, `carrierId`, `defenderDie`, `carrierDie`, `defenderCombined`, `carrierCombined`, `result`.
- **D-12:** Caller pre-generates 2 dice per move: stealDie (for steal) + tackleDie+carrierDie (for tackle). Engine selects based on effect type.
- **D-13:** Ball position bug: `applyMove` never updates `state.ball.position` when carrier moves. Fix: `if (state.ball.carrierId === pieceId) → ball = { ...state.ball, position: to }`.
- **D-14:** `ball.position` always equals carrier's piece position when `ball.carrierId !== null`.
- **D-15:** Ball possession dot: SVG `<circle>` on carrier piece at 45° toward scoring goal. Home (attacks right): `dx = +radius * 0.6, dy = +radius * 0.6`. Away (attacks left): `dx = -radius * 0.6, dy = +radius * 0.6`. Dot radius ≈ 20–25% of piece radius.
- **D-16:** Dot rendered in existing piece overlay logic in HexGrid.tsx or PieceOverlay. Client-only.
- **D-17:** After valid move broadcast in MOVEMENT phase, selected piece stays selected; `validMoveHexes` recomputed from new position with remaining pace (`piece.pace - paceUsedByPieceId[piece.id]`).
- **D-18:** Selection clears when: movementSlot changed OR phase changed OR selectedPieceId no longer in `state.pieces`.
- **D-19:** Sticky selection recomputes using `hexesInRange(piece.position, remainingPace)` filtered by `validateMove`. Same logic as `selectPiece` but with remaining pace.
- **D-20:** ZoI-risk hexes (adjacent to ≥1 opponent piece) display distinct visual style vs safe move hexes. Uses `getZoIDefenders(hex, opponents).length > 0`.
- **D-21:** ZoI visual is display-only client-side. Server independently validates steal/tackle.

## Summary

Phase 8.1 is a focused bug-fix and mechanic-completion phase covering four tightly interconnected areas. No new packages are required — every change works within the existing TypeScript monorepo using already-installed libraries.

The root cause of most bugs is a single architectural violation: `applyMove` calls `rollDice()` internally (breaking the pure-function contract), and it never updates `ball.position` when the carrier moves. Fixing these two issues simultaneously enables the correct steal mechanic, sets up the new tackle mechanic, and resolves the ball position display bug.

The player stats redesign is a data-only change (teams.ts) with existing test infrastructure that will fail on the current 1–10 values — the tests must be updated to assert the 1–6 ceiling instead of 10.

The client-side changes (sticky selection, ZoI tinting, ball possession dot) are pure UI additions with no server interaction. They consume already-exported shared utilities (`getZoIDefenders`, `hexesInRange`) and follow the existing SVG/Zustand patterns.

**Primary recommendation:** Fix `applyMove` first (dice refactor + ball position + steal die=6), then add TACKLE_ATTEMPT in `validateMove` + resolution in `applyMove`, then redesign teams.ts, then client UX. This ordering minimizes test breakage per commit.

### Pattern 1: Pre-Generated Dice (existing pattern, extended)

**What:** Caller pre-generates all dice before calling pure engine functions. Engine receives dice as parameters.
**When to use:** Any engine function that needs randomness (Pitfall 1).
**Established precedent:** `applyEndTurn` receives `addedTimeRoll` via options. `applyRoll` receives `...dice` spread. `applyGKRestart` receives `rollDie: () => number`.

const tackleDie = rollDice(); // used if TACKLE_ATTEMPT fires (defender)
const carrierDie = rollDice(); // used if TACKLE_ATTEMPT fires (carrier)
const result = applyMove(room.gameState, pieceId, to, { stealDie, tackleDie, carrierDie });

### Pattern 2: Discriminated Union Effect from validateMove (existing pattern, extended)

**What:** `validateMove` returns `{ ok: true; effect: { type: 'TACKLE_ATTEMPT'; carrierId: string } }` — mirror of existing `STEAL_ATTEMPT` effect.
**When to use:** When a move has a side effect that requires resolution in the engine.

```typescript
// Source: packages/shared/src/moveValidator.ts (EXTENDED MoveResult)
export type MoveResult =
  | { ok: false; reason: ... }
  | { ok: true }
  | { ok: true; effect: { type: 'STEAL_ATTEMPT'; defenders: PlayerPiece[] } }
  | { ok: true; effect: { type: 'TACKLE_ATTEMPT'; carrierId: string } }  // NEW
  | { ok: true; effect: { type: 'SNAPSHOT_AVAILABLE' } };
```

The TACKLE_ATTEMPT trigger in `validateMove` fires when:

1. `state.ball.carrierId !== null` (there is a carrier)
2. `piece.teamId !== carrierTeam` (moving piece is NOT the carrier's team)
3. `hexDistance(to, carrier.position) === 1` (destination is adjacent to carrier)

Note: the existing STEAL_ATTEMPT check (`state.ball.carrierId === piece.id`) and the TACKLE_ATTEMPT check are mutually exclusive — a piece cannot simultaneously be the carrier and not be the carrier.

### Pattern 3: Zustand setGameState Sticky Selection (existing pattern, modified)

**What:** `setGameState` compares incoming state's `movementSlot`/`phase` against the previous state before deciding whether to clear selection.
**When to use:** After every server broadcast while in MOVEMENT phase.

```typescript
// Source: packages/client/src/store/useGameStore.ts (setGameState — REFACTORED)
setGameState: (newState) => {
  const prev = get();
  const prevState = prev.gameState;
  const prevSelectedId = prev.selectedPieceId;

  // Determine whether to retain or clear selection
  const slotChanged = newState.movementSlot !== prevState.movementSlot;
  const phaseChanged = newState.phase !== prevState.phase;
  const pieceStillExists = prevSelectedId !== null &&
    newState.pieces.some(p => p.id === prevSelectedId);

  if (slotChanged || phaseChanged || !pieceStillExists || prevSelectedId === null) {
    // Clear selection on phase/slot transitions or missing piece
    set({ gameState: newState, selectedPieceId: null, validMoveHexes: [] });
    return;
  }

  // Sticky selection: recompute validMoveHexes with remaining pace
  const piece = newState.pieces.find(p => p.id === prevSelectedId)!;
  const remainingPace = piece.pace - (newState.paceUsedByPieceId[prevSelectedId] ?? 0);
  const candidates = hexesInRange(piece.position, remainingPace);
  const valid = candidates.filter(hex => validateMove(newState, piece, hex).ok);
  set({ gameState: newState, validMoveHexes: valid });
},
```

### Anti-Patterns to Avoid

- **Rolling dice inside applyMove:** Current code calls `rollDice()` at line 227 of gameEngine.ts inside the STEAL_ATTEMPT block. This is the violation D-08 fixes. Never add dice calls inside engine functions.
- **Reading `state.ball.carrierId` without updating `ball.position`:** The current applyMove updates `pieces` (line 210) but never touches `ball`. After the fix, ball.position update must be in the normal-move return AND the steal-success return AND the tackle-success return.
- **Checking `combined >= 10` without die===6:** Current applyMove line 230 misses die===6. The fix is a one-liner: `(die === 6 || combined >= 10)`.
- **Using `piece.pace` instead of remaining pace in sticky selection:** `hexesInRange` must use `piece.pace - paceUsedByPieceId[piece.id]` not `piece.pace` — otherwise already-moved hexes remain highlighted.
- **Clearing selection in emitMove and setGameState:** Currently `emitMove` clears selection (line 174 of useGameStore.ts) AND `setGameState` clears selection. After D-17, `emitMove` should still clear locally (optimistic), but `setGameState` decides based on slot/phase changes whether to restore sticky selection.
- **Rendering ZoI dot for non-active players:** The ZoI-risk computation in HexGrid uses `validMoveHexes` which is only populated for the active player's selected piece — so non-active players get empty sets naturally.

## Common Pitfalls

### Pitfall 1: Ball Position Not Updated in All Branches

**What goes wrong:** After fixing the carrier-normal-move case, developers miss that the steal-success branch and the new tackle-success branch also need `ball.position = to` (or `ball.position = defenderTo`).
**Why it happens:** Multiple return sites in `applyMove`.
**How to avoid:** Search for all `return { ok: true, state: { ...state, ...` patterns in `applyMove`. Each must include `ball` in its spread if the carrier moved or possession changed.
**Warning signs:** Ball display stays at old position after a successful steal/tackle in live play.

### Pitfall 2: emitMove Clears Selection Too Aggressively

**What goes wrong:** `emitMove` (line 174 of useGameStore.ts) clears `selectedPieceId` and `validMoveHexes` immediately before the server broadcast. This is correct as an optimistic clear. The sticky selection is RESTORED by `setGameState` when the broadcast arrives — not prevented. If `setGameState` still clears unconditionally, sticky selection never works.
**Why it happens:** Both functions currently clear selection; the D-17 fix is only in `setGameState`.
**How to avoid:** `emitMove` keeps its optimistic clear. `setGameState` then conditionally restores when slot/phase is unchanged. The net effect: brief flash of no-selection between emit and broadcast, then sticky selection restored.
**Warning signs:** Selection never sticks — piece deselects on every move.

### Pitfall 3: Tier Total Calculation Scope

**What goes wrong:** Computing tier totals as sum of ALL 9 attributes including the 0s (`handling: 0, aerialAbility: 0, saving: 0` for outfielders), which makes outfielder totals appear low (total = sum of 6 role-relevant + 3 zeros = same as sum of 6 relevant). This is correct per D-02 — the 0s count and already total the same as the relevant-attribute sum.
**Why it happens:** Confusion about whether 0 = "not applicable" vs "missing from total".
**How to avoid:** Per D-02, tier totals include all 9 attributes. For outfield players: total = pace + shooting + tackling + dribbling + heading + resilience + 0 + 0 + 0 = sum of 6 role attributes. For GK: total = pace + shooting(1) + tackling + dribbling(deemphasized) + heading + saving + handling + resilience + aerialAbility.
**Warning signs:** Squad fails tier distribution test — wrong number of players per tier.

### Pitfall 4: TACKLE_ATTEMPT Triggering for Ball Carrier's Own Team

**What goes wrong:** The TACKLE_ATTEMPT trigger in `validateMove` fires when ANY piece moves adjacent to the carrier — including the carrier's own team members.
**Why it happens:** Forgetting to check that `piece.teamId !== carrier.teamId`.
**How to avoid:** Trigger condition: `state.ball.carrierId !== null AND piece.teamId !== carrier.teamId AND hexDistance(to, carrier.position) === 1`. Same structure as the STEAL_ATTEMPT check (`state.ball.carrierId === piece.id` is the offense trigger; `piece.teamId !== carrierTeamId` is the defense trigger).
**Warning signs:** Own-team pieces moving near the carrier trigger phantom tackle duels.

### Pitfall 5: Dice Consumption Mismatch in applyMove

**What goes wrong:** Handler pre-generates 3 dice (`stealDie`, `tackleDie`, `carrierDie`). The engine must use `stealDie` for steal attempts and `tackleDie`/`carrierDie` for tackle attempts — never the same die for both. If a move triggers neither effect, all 3 dice are unused (no problem). If both effects could theoretically fire (they cannot: STEAL fires when carrier moves; TACKLE fires when non-carrier moves), that would be a conflict.
**Why it happens:** STEAL and TACKLE are mutually exclusive by design (carrier vs non-carrier), so the die pools never overlap. But incorrect implementation might share a die.
**How to avoid:** The engine inspects `result.effect.type` and selects the correct dice sub-pool. The handler always pre-generates all 3 regardless of which effect fires (D-12).
**Warning signs:** Steal uses `tackleDie` or tackle uses `stealDie`.

### Pitfall 6: teams.test.ts Still Asserts `<= 10`

**What goes wrong:** After rewriting teams.ts to 1–6 scale, the existing test at line 44–45 (`expect(val).toBeLessThanOrEqual(10)`) still passes (6 ≤ 10 is true), masking that the test should now enforce the 6 ceiling.
**Why it happens:** The test was written for the original 1–10 scale. After the redesign, it needs updating to `toBeLessThanOrEqual(6)` plus a new tier distribution assertion.
**How to avoid:** Update the test ceiling from 10 → 6 AND add a tier total assertion for each player. The test also lacks assertions for the squad-level tier distribution (1/2/3/3/2) — add that too.
**Warning signs:** Tests pass after rewrite, but a player with value 8 (old scale) wasn't caught.

### Pitfall 7: highPass Range Constraint Conflict

**What goes wrong:** Phase 8 CONTEXT D-07 specified outfield highPass ranges: DEF 3–5, MID 5–7, FWD 4–6. On a 1–6 scale, MID max of 7 exceeds the scale cap of 6. D-07 from the prior phase was written for the 1–10 scale.
**Why it happens:** Prior-phase D-07 ranges are incompatible with the 1–6 cap decided in Phase 8.1.
**How to avoid:** On 1–6 scale, the adjusted ranges should be: DEF highPass 2–4, MID highPass 3–5 (max 5, not 7), FWD highPass 3–5. These are Claude's discretion per CONTEXT.md — keep them role-realistic within the 1–6 cap. The tests only assert `<= 6` (after fix); the specific range is not test-enforced.
**Warning signs:** MID highPass = 7 violates the 1–6 constraint and breaks the updated test.

### Pitfall 8: PieceOverlay Already Has a Ball Carrier Indicator

**What goes wrong:** The current `PieceOverlay` already renders a ball carrier inner ring (`<circle cx={cx} cy={cy} r={5} fill="#f5f0dc" fillOpacity={0.6} />`). D-15 replaces this with the directional white dot — it is NOT an addition alongside it.
**Why it happens:** Missing that the inner-ring placeholder was already implemented.
**How to avoid:** Remove the existing inner-ring render and replace it with the directional dot. Both serve the same purpose; the dot conveys direction information additionally.

// Tier ranges: Tier1=34+, Tier2=32-33, Tier3=30-31, Tier4=28-29, Tier5=26-27

## Open Questions

1. **Should TACKLE_ATTEMPT also terminate movement on FAIL (defender used a move hex)?**
   - What we know: D-11 says on FAIL "defender moved, ball carrier keeps ball, movement continues normally." The defender's move still counts against their paceUsed.
   - What's unclear: Does the defender still expend the hex move on a TACKLE_ATTEMPT (always yes per D-11) even on fail?
   - Recommendation: Yes — defender always moves to destination regardless of duel outcome (D-11 explicitly: "Defender moves to destination hex unconditionally"). The duel only determines possession.

2. **Does a TACKLE_ATTEMPT during DEFENDER_5 slot end DEFENDER_5 early on success?**
   - What we know: D-11 says "possession transfer, movement phase ends immediately, `lastActionType: 'SUCCESSFUL_TACKLE'`." This mirrors steal.
   - What's unclear: "Movement phase ends immediately" — does this skip remaining DEFENDER_5 moves and jump to ATTACKER_2, or skip all remaining slots?
   - Recommendation: Match steal behavior exactly. Steal ends the entire 4-5-2 sequence when it fires. Apply the same to TACKLE: full movement phase ends, not just the current slot. The new ball-owning team gets all post-movement actions (same as D-05 steal success).

3. **Does the ball possession dot change sides mid-possession if the defending team steals/tackles?**
   - What we know: D-15/D-16 say the dot direction is based on the carrier's team identity and `attackingTeam`. After a steal, the `attackingTeam` in `GameState` may still be the original attacker until the phase transitions.
   - Recommendation: Use the carrier's `teamId` identity to determine dot direction, independent of `attackingTeam`. Home team carrier → dot at `+x,+y` always (attacks right). Away team carrier → dot at `-x,+y` always (attacks left). This is correct regardless of which team is "attacking" at the moment.
