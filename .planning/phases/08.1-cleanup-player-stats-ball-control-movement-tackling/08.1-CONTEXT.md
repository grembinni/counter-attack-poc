# Phase 8.1: cleanup player stats, ball control, movement, tackling - Context

**Gathered:** 2026-06-05
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix six foundational gameplay issues that make the game unplayable in its current state:

1. **Player stats** — All 9 attributes must use a 1–6 scale (not 1–10). Current values in teams.ts are wrong. Both squads must be rebalanced using the Counter Attack tier system.
2. **Steal mechanic** — When the OFFENSIVE player (ball carrier) moves into a hex adjacent to a defender, the defender rolls: die=6 OR (tackling + die) ≥ 10 → steal. The current code is missing the die=6 auto-steal.
3. **Tackling mechanic (new)** — When a DEFENDER moves into a hex adjacent to the ball carrier during a movement slot, a tackle attempt fires: tackling + die vs dribbling + die (duel). Higher combined score wins; defender wins on tie → possession transfer. This is the mirror of stealing: offense triggers steal, defense triggers tackle.
4. **Ball position tracking (bug)** — `ball.position` does not update when the carrier moves. The ball stays at the kick-off hex regardless of where the carrier walks.
5. **Ball possession visual (new)** — No indicator shows which piece has the ball. A small white dot at 45° toward the scoring goal (bottom-right for home team, bottom-left for away team) on the piece SVG identifies the ball carrier.
6. **Movement UX** — After a step move, the piece must stay selected so players can chain moves without re-clicking. ZoI hexes (adjacent to opponents) must be visually distinct to warn of steal/tackle risk.

**In scope:**

- Redesign both HOME_SQUAD and AWAY_SQUAD in `packages/shared/src/teams.ts` — 1–6 scale, tier-balanced (11 players per squad)
- Fix `applyMove` in `packages/server/src/gameEngine.ts` — add die=6 auto-steal (bug fix); add TACKLE_ATTEMPT when a defender moves adjacent to the ball carrier; fix `ball.position` to follow the carrier
- Fix `setGameState` in `packages/client/src/store/useGameStore.ts` — keep selected piece across state broadcasts during the same movement slot
- Add ZoI visual indicator in `packages/client/src/components/HexGrid.tsx` — different highlight color for ZoI-risk hexes
- Add ball possession indicator in `packages/client/src/components/HexGrid.tsx` (or `PieceOverlay`) — small white dot on ball carrier

**Out of scope (deferred to later phases):**

- Passing cleanup (target selection, accuracy per pass type, ball movement on accurate pass, interception) → Phase 8.2
- Shot declaration flow, all remaining broken action flows → Phase 8.3
- Code review debt (CR-01 timer leak, WR-01..WR-04 warnings) → Phase 8.3

<decisions>
## Implementation Decisions

### Player Stats — Scale and Validation

- **D-01:** All 9 player attributes use a **1–6 scale**. This is the Counter Attack rulebook constraint. Any value > 6 in the current teams.ts is invalid. Outfield-players retain `handling: 0`, `saving: 0`, and `aerialAbility: 0` (these are GK-only attributes — 0 means "not applicable", not a skill value). GK retains `shooting: 1` (minimum valid value — GKs can technically shoot). The `highPass: 0` on GKs is preserved (D-04 from Phase 7.1: GKs use a separate GK kick accuracy check, not the highPass attribute).

- **D-02:** The 1–6 range applies to all attributes that are relevant to the player's role. Tier totals count all 9 attributes (0s count as 0). For outfield players, their 6 role-relevant attributes (Pace, Shooting, Tackling, Dribbling, Heading, Resilience) drive the tier total; the 3 GK-only attributes (Saving, Handling, Aerial Ability) are 0 and still count.

### Player Stats — Squad Tier Distribution

- **D-03:** Each squad of 11 players must be balanced using the Counter Attack tier system:

  | Tier | Talent Level  | Total Pts | Count per squad |
  | ---- | ------------- | --------- | --------------- |
  | 1    | World Class   | 34+       | 1               |
  | 2    | International | 32–33     | 2               |
  | 3    | Top Flight    | 30–31     | 3               |
  | 4    | Respected Pro | 28–29     | 3               |
  | 5    | Journeyman    | 26–27     | 2               |
  |      | **Total**     |           | **11**          |

  Both home and away squads must each have this distribution. The two squads should be distinct — different names, different attribute profiles — but matched in overall tier balance so neither team has an unfair advantage.

- **D-04:** The GK's tier should be calculated on their GK-relevant attributes: Saving, Handling, Aerial Ability, Pace, Tackling, Resilience (Heading may be included). The GK's tier generally sets the "ceiling" for each team's defence. Claude determines the precise GK tier placement to make each squad feel realistic (e.g., a Tier 2 GK with high Saving and Handling).

### Steal Mechanic — Defender Solo Roll (Rulebook Correct)

- **D-05:** The steal attempt when the ball carrier moves into a hex adjacent to a defender is a **solo defender roll**. The ball carrier's dribbling attribute plays no role in the steal check. The correct Counter Attack rulebook mechanic:
  - Defender rolls 1 die
  - **Steal SUCCESS** if `die === 6` (auto-steal, regardless of Tackling) OR `tackling + die >= 10`
  - **Steal FAIL** otherwise — ball carrier keeps the ball, movement continues
  - On SUCCESS: defender's team gains possession, current movement phase ends immediately, `lastActionType` set to `'SUCCESSFUL_TACKLE'`
  - On SUCCESS: all post-movement actions are available to the new ball-carrier's team (Movement ✓, Std Pass ✓, High Pass ✓, Long Ball ✓, Snapshot ✓ — per ELIGIBLE_NEXT_ACTIONS table)

- **D-06:** **Bug fix in current code:** `applyMove` in `gameEngine.ts` currently only checks `combined >= 10` and misses the `die === 6` auto-steal. The fix is: `const stealResult = (die === 6 || combined >= 10) ? 'SUCCESS' : 'FAIL'`.

- **D-07:** The `STEAL_ATTEMPT` ActionEvent in `packages/shared/src/types.ts` should include the defender's die roll and combined score for the event log and replay. Add: `defenderDie`, `defenderCombined` to the discriminant (no carrier fields needed).

- **D-08:** The `applyMove` function currently calls `rollDice()` internally for the steal — violating Pitfall 1 (pure engine functions must not generate dice). Refactor: caller (`gameHandlers.ts` GAME_MOVE handler) pre-generates dice (steal die + tackle dice) before calling `applyMove`, passes them in via an options parameter (same pattern as `addedTimeRoll` in `applyEndTurn`). `applyMove` becomes fully deterministic.

### Tackling Mechanic (Defender Moves Adjacent to Ball Carrier)

- **D-09:** **Tackling** is the mirror of stealing. Where stealing fires when the OFFENSIVE ball carrier steps into a defender's adjacent hex, **tackling fires when a DEFENDER steps into a hex adjacent to the ball carrier** during any movement slot. The distinction:
  - **Steal:** Offense moves → defender's solo roll (die=6 OR tackling+die≥10)
  - **Tackle:** Defense moves → duel: `defender.tackling + die` vs `carrier.dribbling + die`; defender wins if their combined score ≥ ball carrier's combined score (defender wins on tie)

- **D-10:** TACKLE_ATTEMPT trigger in `validateMove` (or `applyMove`): if the moving piece is NOT the ball carrier AND the destination hex is adjacent to the ball carrier → return `{ ok: true, effect: { type: 'TACKLE_ATTEMPT', carrierId } }`. This mirrors the existing STEAL_ATTEMPT effect return.

- **D-11:** TACKLE_ATTEMPT resolution in `applyMove` (gameEngine.ts):
  - Defender moves to destination hex (piece position updates unconditionally — defender always moves)
  - Duel: `tackling + defenderDie` vs `carrier.dribbling + carrierDie`
  - Tackle SUCCESS (defender's combined ≥ carrier's combined): defender's team gains possession, `ball.carrierId` set to defender, `ball.position` set to defender's new hex, movement phase ends immediately, `lastActionType: 'SUCCESSFUL_TACKLE'`
  - Tackle FAIL (carrier's combined > defender's combined): defender moved, ball carrier keeps ball, movement continues normally
  - The `TACKLE_ATTEMPT` ActionEvent must record: `defenderId`, `carrierId`, `defenderDie`, `carrierDie`, `defenderCombined`, `carrierCombined`, `result: 'SUCCESS' | 'FAIL'`

- **D-12:** The caller (GAME_MOVE handler) pre-generates 2 dice for each move: `stealDie` (for steal attempts) and `tackleDie + carrierDie` (for tackle attempts). The engine selects which dice to use based on which effect fires. All dice pre-generated upfront before calling `applyMove` (Pitfall 4).

### Ball Position Tracking Fix

- **D-13:** **Bug:** `applyMove` in `gameEngine.ts` never updates `state.ball.position` when the carrier moves. The ball visually stays at the starting hex regardless of where the carrier walks. Fix: in the return value of `applyMove`, if `state.ball.carrierId === pieceId`, update `ball` to `{ ...state.ball, position: to }`. This applies to both the steal-success branch and the normal move return.

- **D-14:** `ball.position` must always equal the carrier's piece position when `ball.carrierId !== null`. After the fix, `ball.position` and `pieces.find(p => p.id === ball.carrierId).position` are always in sync for every broadcast state.

### Ball Possession Visual Indicator

- **D-15:** A small white filled circle (SVG `<circle>`) is drawn on top of the ball carrier's piece to indicate possession. The dot is positioned at 45° toward the side of the pitch the carrier's team is attacking:
  - **Home team** attacks right (toward high q / away goal at q=35): dot at bottom-right of the piece circle (offset `+x, +y` in SVG, approximately `dx = +radius * 0.6, dy = +radius * 0.6`)
  - **Away team** attacks left (toward low q / home goal at q=1): dot at bottom-left (`dx = -radius * 0.6, dy = +radius * 0.6`)
  - The dot radius is approximately 20–25% of the piece circle radius (Claude's discretion for exact sizing, consistent with piece scale)

- **D-16:** The dot is rendered in the existing piece overlay logic in `HexGrid.tsx` (or the `PieceOverlay` component if one exists). It is client-only — no server change. The `attackingTeam` from `GameState` determines which side is "attacking" for the current ball carrier's team. Specifically: if `ball.carrierId` belongs to the `attackingTeam`, the dot goes toward the opponent's goal; if it belongs to the defending team (who just stole/tackled), same rule applies by team identity.

### Movement UX — Sticky Selection

- **D-17:** After a valid move is broadcast in MOVEMENT phase, the selected piece must remain selected and `validMoveHexes` must be recomputed from the piece's **new position** with its **remaining pace** (i.e., `piece.pace - paceUsedByPieceId[piece.id]`).

- **D-18:** Selection clears in `setGameState` when:
  - The `movementSlot` changed (slot advance → different team or fresh ATTACKER_2 slot)
  - The `phase` changed (e.g., MOVEMENT → PASS)
  - An existing `selectedPieceId` is no longer in `state.pieces` (piece removed — shouldn't happen in normal play)
  - Otherwise: keep `selectedPieceId`, recompute `validMoveHexes` using the updated `GameState`.

- **D-19:** The `selectPiece` logic in useGameStore already computes `hexesInRange(piece.position, piece.pace)` and filters by `validateMove`. After a state update with sticky selection, the recomputation uses the same logic but with `piece.pace - paceUsedByPieceId[piece.id]` as the effective range so only remaining moves are highlighted.

### Movement UX — ZoI Visual Indicator

- **D-20:** Valid move hexes that are in an opponent's ZoI (adjacent to ≥1 opponent piece) display a distinct visual style compared to safe move hexes:
  - Safe hexes: existing green/standard highlight
  - ZoI-risk hexes: amber or red-tinted outline/fill (specific colour/class: Claude's discretion, consistent with existing `HexGrid` CSS module)
  - Determination: for each `validMoveHex`, call `getZoIDefenders(hex, opponents).length > 0` (already exported from `packages/shared/src/hex.ts`)

- **D-21:** The ZoI visual indicator is **display-only on the client**. The server independently validates steal and tackle triggers — no server change needed for the visual.

### Claude's Discretion

- The exact tier placement of each individual player (e.g., which DEF is Tier 3 vs Tier 4) is Claude's call, provided the overall squad distribution follows D-03.
- Specific attribute values per player within the 1–6 range are Claude's call, provided they are role-realistic (GK: high Saving/Handling; DEF: high Tackling; FWD: high Pace/Shooting) and the tier totals satisfy D-03.
- CSS class name and colour for the ZoI-risk hex highlight — consistent with existing `HexGrid.module.css` conventions.
- Whether `applyMove` receives dice as separate named params or inside an options struct — mirrors the cleanest pattern in the existing codebase (`addedTimeRoll` in `applyEndTurn`).
- Exact radius and offset of the ball possession dot (D-15) — size should be clearly visible without obscuring the piece number/letter.

</decisions>
