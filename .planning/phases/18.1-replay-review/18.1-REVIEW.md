# Phase 18.1: Code Review Report

**Reviewed:** 2026-06-21T18:14:38Z
**Depth:** standard
**Files Reviewed:** 4
**Status:** issues_found

## Summary

This phase fixes two REPLAY-06 root causes: (1) `HEADED_PASS`/`GK_PUNT` events were never folded
into `REPLAY_ELIGIBLE_TYPES`, so their ball movement produced no visible replay frame, and (2) the
`MOVE` event appended on a successful steal/tackle carried a stale pre-contest `ballAfter`
snapshot instead of the post-contest carrier. Both are fixed correctly in `gameEngine.ts`, with
solid test coverage in `replay.integration.test.ts` driving the real `applyMove` code path rather
than a hand-crafted event log. `HexGrid.tsx` separately adds a `phase === 'REPLAY'` guard that
correctly short-circuits the three previously-ungated interactive derivations
(`validMoveHexSet`, `zoiRiskSet`, `tackleRiskSet`) and the entire onClick/`isClickable` cascade;
this was verified against the client store's phase-change reset logic (`shootingMode`,
`passTargetHex`, `selectedPassType`, etc. are all cleared on every phase transition), so no
stale-state visual leak materializes during replay in practice.

The principal issue is that the new `REPLAY_ELIGIBLE_TYPES` comment claims `GK_KICK` is
"dead code, zero construction sites" — this is factually incorrect. `GK_KICK` is constructed in
`gameHandlers.ts` and represents a live, reachable feature (the GK long-kick-to-target flow). As a
direct consequence, GK kicks that deliver the ball anywhere on the pitch remain invisible during
post-match replay, which is the exact class of bug this phase claims to close. A related,
lower-severity gap (`LOOSE_BALL_LAND`, pre-existing) was also missed by the same enumeration.

## Critical Issues

### CR-01: `GK_KICK` mis-documented as dead code; ball delivery invisible during replay

**File:** `packages/server/src/gameEngine.ts:3986-3992`
**Issue:** The comment added by this phase states:

```ts
// GK_KICK is intentionally excluded (dead code, zero construction sites — Pitfall 5,
// deferred to DESIGN-04). HEADER is intentionally excluded (carries no ballAfter by design).
```

This is incorrect. `GK_KICK` IS constructed, at `packages/server/src/gameHandlers.ts:828-836`,
as part of the live GK_KICK_TARGET → GK_KICK_MOVE flow (wired client-side via
`gkKickTargetSet`/`emitGKKickTarget` in `HexGrid.tsx:257-269,551-561`). This event delivers the
ball to a new position and carrier (`gameHandlers.ts:843-859`) exactly like `HEADED_PASS`/
`GK_PUNT`, which this same phase fixed for the identical defect. Because (a) `GK_KICK` lacks a
`ballAfter` field in its type definition (`packages/shared/src/types.ts:280-288`) and (b) it is
excluded from `REPLAY_ELIGIBLE_TYPES`, a GK long kick produces zero replay frames — the ball will
appear to teleport on whatever the next eligible event's frame is, with no transition shown. This
is the same root-cause class (REPLAY-06) that this phase's commit message claims to have fully
fixed ("fix both REPLAY-06 root causes"), but it was missed for this case, and the incorrect
"dead code" justification will mislead the next person who reads this comment into believing the
gap doesn't exist.

**Fix:** Add `ballAfter` to the `GK_KICK` event type, populate it at both `gameHandlers.ts:828`
construction sites with the resolved `{ position: targetHex, carrierId }` (or `{ position:
targetHex, carrierId: null }` on the inaccurate/loose-ball path), and add `'GK_KICK'` to
`REPLAY_ELIGIBLE_TYPES`:

```ts
// types.ts
| {
    type: 'GK_KICK';
    gkId: string;
    targetHex: HexCoord;
    accurate: boolean;
    kickDie: number;
    kickScore: number;
    timestamp: number;
    ballAfter: { position: HexCoord; carrierId: string | null };
  }
```

```ts
// gameHandlers.ts — accurate branch
const kickEvent: ActionEvent = {
  type: 'GK_KICK',
  gkId: gkEndState.gkKickGkId ?? '',
  targetHex,
  accurate,
  kickDie,
  kickScore,
  timestamp: Date.now(),
  ballAfter: accurate
    ? { position: targetHex, carrierId: receiver?.id ?? null }
    : { position: targetHex, carrierId: null },
};
```

```ts
// gameEngine.ts REPLAY_ELIGIBLE_TYPES
'HEADED_PASS',
'GK_PUNT',
'GK_KICK', // corrected — reachable via GK_KICK_TARGET, not dead code
```

## Warnings

### WR-01: `LOOSE_BALL_LAND` shares the same replay-invisibility gap, missed by this phase's enumeration

**File:** `packages/server/src/gameEngine.ts:3971-3992`
**Issue:** `LOOSE_BALL_LAND` (constructed at `gameEngine.ts:2353-2358`) changes the ball's position
and frequently its carrier (loose-ball scatter landing on an occupant, `gameEngine.ts:2344-2351`),
exactly like the cases this phase fixed. It has no `ballAfter` field
(`packages/shared/src/types.ts:279`) and is not in `REPLAY_ELIGIBLE_TYPES`, so a loose-ball
scatter is also invisible during replay. This is pre-existing (not introduced by this diff), but
the new doc comment at `gameEngine.ts:3970` claims to document "Non-SLOT_ADVANCE event types that
produce replay frames" as if it were a complete, audited list — it is not, and this phase was the
opportunity to close it given the closely related fix already in flight.
**Fix:** Add a `ballAfter` field to `LOOSE_BALL_LAND`, populate it at the construction site with
`{ position: finalPosition, carrierId: finalCarrierId }`, and add `'LOOSE_BALL_LAND'` to
`REPLAY_ELIGIBLE_TYPES`. If deliberately deferred, update the comment to say so explicitly instead
of implying the enumeration is exhaustive.

### WR-02: Disconnect-clears-replayTimer test can never fail

**File:** `packages/server/src/__tests__/replay.integration.test.ts:324-351`
**Issue:** The test sets `intervalCleared = true` in **both** branches of the `if`/`else`:

```ts
if (room.replayTimer !== null) {
  clearInterval(room.replayTimer);
  intervalCleared = true;
} else {
  intervalCleared = true; // handler cleared it
}
expect(intervalCleared).toBe(true);
```

Regardless of whether the disconnect handler actually clears `room.replayTimer`, `intervalCleared`
ends up `true` on both paths, so `expect(intervalCleared).toBe(true)` can never fail. The test
currently provides zero verification of its stated purpose (T-08-15: "disconnect handler clears
replayTimer when set") — a regression that re-introduces a timer leak on disconnect would pass
this test silently. This test is pre-existing in the file under review, not newly introduced by
this phase, but the file is in scope and the defect directly undermines confidence in the
replay-timer-lifecycle coverage this phase's tests build on.
**Fix:** Assert directly on `room.replayTimer`, not a tautological local flag:

```ts
clientA.disconnect();
await disconnectPromise;
expect(room.replayTimer).toBeNull(); // fails if the handler didn't clear it
```

## Info

### IN-01: `REPLAY_ELIGIBLE_TYPES` comment placement makes the HEADER exclusion easy to misread

**File:** `packages/server/src/gameEngine.ts:3986-3992`
**Issue:** The comment block bundles three unrelated claims into one note: (a) why
`HEADED_PASS`/`GK_PUNT` were added, (b) why `GK_KICK` is excluded (incorrectly, per CR-01), and
(c) why `HEADER` is excluded. Bundling a correct rationale (HEADER carries no `ballAfter` by
design — confirmed in `types.ts:234-249`) next to an incorrect one (GK_KICK) makes the false claim
look equally authoritative and harder to catch on review.
**Fix:** Once CR-01 is fixed, split this into one comment per excluded/included type so each
rationale can be independently verified against the codebase, e.g.:

```ts
// HEADED_PASS, GK_PUNT (18.1-01): ball-movement events with ballAfter — now included.
// HEADER: by design carries no ballAfter (contest-outcome only) — correctly excluded.
```
