# Phase 18.1 Plan 01: REPLAY-06 Ball-Tracking Root Cause Fixes Summary

**Fixed two server-side REPLAY-06 root causes in gameEngine.ts: HEADED_PASS/GK_PUNT now produce visible replay frames, and a MOVE ending in a successful steal/tackle now records the post-contest ball carrier on its own frame instead of a stale pre-contest snapshot.**

## Accomplishments

- `REPLAY_ELIGIBLE_TYPES` (gameEngine.ts) now includes `'HEADED_PASS'` and `'GK_PUNT'` — both event types were added by quick-task `260621-b8f` with a correctly-populated `ballAfter` field but were never folded into the replay-eligible set, so their ball movement was silently absorbed into internal reconstruction state with no visible replay frame (the ball appeared to teleport across header deliveries and GK punts).
- `applyMove`'s steal-success and tackle-success return paths now immutably rewrite the already-appended `MOVE` event's `ballAfter` to the post-contest carrier (defender or tackler) before returning, eliminating the one-frame stale-carrier glitch that previously appeared on every successfully-contested pickup.
- Two new `REPLAY-06:`-prefixed regression tests added to `replay.integration.test.ts`: one drives `applyMove` directly (with controlled positions and dice) to validate the actual fix location for the steal/tackle case, and one hand-crafts an `eventLog` to validate `buildReplayFrames`' frame-visibility behavior for the `HEADED_PASS`/`GK_PUNT` case.
- Full server test suite (465 tests, 1 pre-existing skip, 1 pre-existing todo) passes with zero new failures after both fixes.

## Decisions Made

- **Test design deviation for Case A (steal/tackle):** The plan's literal Task 1 instruction was to hand-craft an `eventLog` containing a stale `MOVE.ballAfter` followed by a `SUCCESS` `STEAL_ATTEMPT`/`TACKLE_ATTEMPT`, then call `buildReplayFrames` and assert self-correction. Running this against current code confirmed the RED state correctly (frame showed stale carrier), but Task 2's actual fix (per its own explicit instructions) lives inside `applyMove`'s steal/tackle success return paths — not in `buildReplayFrames`. A hand-crafted-eventLog-only test bypasses `applyMove` entirely and can never observe the Task 2 fix taking effect, since the test constructs the "already correct" `STEAL_ATTEMPT`/`TACKLE_ATTEMPT` ballAfter manually rather than letting `applyMove` derive it. Rewrote Case A to drive `applyMove` directly (mirroring the established `gameEngine.phase8.test.ts` "applyMove — STEAL_ATTEMPT lastActionType + time" pattern) with controlled piece positions/dice to force a deterministic SUCCESS outcome, then assert the **returned** `state.eventLog`'s MOVE event has the corrected `ballAfter`, plus a downstream `buildReplayFrames` check for end-to-end confidence. This is a Rule 1 (bug fix) deviation: the original test would have been a false-positive validator (it could pass without Task 2's fix ever running, since the corrected `ballAfter` was hand-written into the fixture rather than derived). Case B (HEADED_PASS/GK_PUNT) was left exactly as the plan specified — that fix (`REPLAY_ELIGIBLE_TYPES` membership) IS correctly observable via a hand-crafted eventLog + `buildReplayFrames`, since `buildReplayFrames` is the only place that set is consulted.
- `'GK_KICK'` and `'HEADER'` confirmed absent from `REPLAY_ELIGIBLE_TYPES` per plan instruction (Pitfall 5 dead-code exclusion and by-design no-`ballAfter` exclusion respectively) — verified via grep.

### Auto-fixed Issues

**1. [Rule 1 - Bug] Task 1's Case A regression test rewritten to drive `applyMove` directly instead of a hand-crafted eventLog**

- **Found during:** Task 1 (writing the RED regression tests), confirmed during Task 2 verification
- **Issue:** The plan's literal instruction for Case A constructs the `STEAL_ATTEMPT`/`TACKLE_ATTEMPT` event's correct `ballAfter` by hand in the test fixture, then calls `buildReplayFrames` directly on the hand-crafted `eventLog`. This produces a test that is RED before the fix (correctly observes the stale `MOVE.ballAfter`) but would also be GREEN before the fix is even applied to `applyMove`, if the test had instead asserted on the `STEAL_ATTEMPT` frame rather than the `MOVE` frame — and more importantly, it can never actually exercise the Task 2 code change (`applyMove`'s success-path rewrite), because the test never calls `applyMove`. A test that doesn't exercise the fix location is not a valid regression guard against future re-introduction of the bug.
- **Fix:** Rewrote the test to construct a real `GameState` (with controlled piece positions to trigger ZoI/adjacency) and call `applyMove(state, pieceId, to, dice)` directly with `stealDie: 6` / `tackleDie: 6` to force deterministic SUCCESS outcomes (matching `validateMove`'s D-06/D-09 success conditions). Asserted both that the returned `state.eventLog`'s `MOVE` event carries the corrected `ballAfter`, and that `buildReplayFrames(result.state)` produces a frame matching that corrected ball — covering both the engine-level fix and its downstream replay-visibility effect in one test.
- **Files modified:** `packages/server/src/__tests__/replay.integration.test.ts`
- **Verification:** Confirmed RED before Task 2's fix (test failed with `carrierId: 'home-0'` received vs `'away-0'` expected, matching the predicted Pitfall 3 symptom exactly); confirmed GREEN after Task 2's fix; confirmed the full server suite (465 tests) has zero new failures.
- **Committed in:** `5dc9dd8` (Task 1, RED) and `572d1cb` (Task 2, GREEN — test was further corrected in this commit when the initial RED-state test design was found invalid)
