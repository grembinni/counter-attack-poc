# Phase 18.1: Replay Review - Research

**Researched:** 2026-06-21
**Domain:** React/Zustand client re-render audit + server-side replay event-log reconstruction correctness (Socket.io full-snapshot broadcast architecture)
**Confidence:** HIGH

## Summary

This phase has no external library research surface — it is a clean-room code audit of existing, already-implemented replay machinery (introduced in Phase 8, iterated in Phase 14, partially regressed by a later quick-task). All findings below are derived directly from reading the actual source files named in CONTEXT.md, cross-referenced against Phase 14's design-intent artifacts. Both DESIGN-02 and REPLAY-06 have concrete, file:line-referenced root causes — no vague "investigate X" gaps remain.

**DESIGN-02 (re-render/socket-emission audit):** Server-side socket emission is clean — exactly one `io.to().emit()` per 500ms replay tick, no duplicate broadcasts. The real waste is entirely client-side: `HexGrid.tsx`'s render body unconditionally executes its full 962-hex highlight/click-handler derivation loop and its 22-piece selectability loop on every received `GAME_STATE` frame, including all ~50-150+ frames of a post-game replay, even though `phase === 'REPLAY'` makes every one of those derived booleans false/inert. `setGameState` in `useGameStore.ts` is **not** the bottleneck — its expensive `hexesInRange`/`validateMove` sticky-selection branches are gated behind `prevSelectedId !== null`, which is always null throughout replay (confirmed by trace), so they never execute during REPLAY frames today.

**REPLAY-06 (live-session ball tracking):** Two concrete, demonstrable root causes were found in `buildReplayFrames`/`applyMove` in `packages/server/src/gameEngine.ts`: (1) a successful steal/tackle during movement appends the `MOVE` event with a **stale pre-resolution** `ballAfter` before the correcting `STEAL_ATTEMPT`/`TACKLE_ATTEMPT` event is appended one entry later, producing a one-frame ball-position glitch on every contested pickup; (2) `HEADED_PASS` and `GK_PUNT` — two event types added by quick-task `260621-b8f` (2026-06-21, **after** Phase 14's REPLAY-06 ballAfter migration closed) — both carry a correctly-populated `ballAfter` field but were never added to `REPLAY_ELIGIBLE_TYPES`, so the entire header-delivery and GK-punt ball movement is silently absorbed into internal reconstruction state with **no visible replay frame at all** — the ball appears to teleport across the header/punt sequence.

**Primary recommendation:** Fix DESIGN-02 by adding a `phase === 'REPLAY'` early-exit branch to `HexGrid.tsx`'s highlight/click computation (rendering only `PITCH_HEXES`'s base fill, `BallMarker`, and plain non-interactive `PieceOverlay`s), and fix REPLAY-06 by (a) adding `'HEADED_PASS'` and `'GK_PUNT'` to `REPLAY_ELIGIBLE_TYPES`, and (b) re-deriving the MOVE event's `ballAfter` in `applyMove` to reflect the post-steal/tackle-resolution ball state rather than the pre-resolution snapshot taken before the effect block runs.

### Pattern 1: Phase-gated render branching (existing codebase idiom)

**What:** Throughout `HexGrid.tsx`, expensive per-hex/per-piece derived booleans are already gated behind `phase === 'X'` checks (e.g., `gkDiveTargetSet` only populates `if (phase === 'GK_DIVE' ...)`, `highPassContestZoneSet` only populates `if (phase === 'HIGH_PASS_MOVE')`).
**When to use:** This is the established pattern for "this derived value is only relevant in phase Y" — extend it with a `phase === 'REPLAY'` guard that short-circuits the entire interactive-derivation block, not just one highlight set.
**Example:**

```typescript
// Source: packages/client/src/components/HexGrid.tsx:196-204 (existing pattern to extend)
const highPassContestZoneSet = new Set<string>();
if (phase === 'HIGH_PASS_MOVE') {
  for (const h of PITCH_HEXES) {
    if (hexDistance(h, ball.position) <= 2) {
      highPassContestZoneSet.add(`${h.q},${h.r}`);
    }
  }
}
```

### Pattern 2: Zustand default reference-equality bailout (already working correctly for ActionLog)

**What:** Zustand v4's `create()` uses `Object.is` per-selector equality by default. `ActionLog`'s `useGameStore((s) => s.gameState.eventLog)` does NOT re-render during replay because `buildReplayFrames` initializes `current.eventLog = []` once (gameEngine.ts:4013) and that same `[]` reference is carried, unmutated, through every `{...current, ...}` spread for the lifetime of one `buildReplayFrames()` call — so every emitted frame shares the identical `eventLog` array reference.
**When to use:** This is evidence the codebase doesn't need a wholesale memoization overhaul — selective fixes (HexGrid's REPLAY branch) following the same reference-stability principle are sufficient and idiomatic.
**Verification:** `grep -n "eventLog" packages/server/src/gameEngine.ts` confirms `current.eventLog` is set once at line 4013 and never reassigned anywhere in `buildReplayFrames` (lines 3994-4130).

### Anti-Patterns to Avoid

- **Introducing `React.memo` as the fix for DESIGN-02:** This codebase has zero existing `React.memo` usage. A `phase === 'REPLAY'` early-return inside `HexGrid`'s render body (skipping straight to a minimal hex-fill + BallMarker + plain-PieceOverlay render) is more consistent with the existing phase-branching idiom, smaller in diff size, and avoids introducing prop-identity-sensitivity bugs that memoization can cause if `HexGrid`'s many inline-computed props (sets, closures) aren't also stabilized.
- **"Fixing" `setGameState`/`useGameStore.ts` for DESIGN-02 without re-verifying the trace:** It is tempting to assume the store's `setGameState` is the bottleneck (it does run on every frame and does branch on `phase`/`movementSlot`). Tracing the actual REPLAY behavior shows `prevSelectedId` is `null` for the entire replay (no `selectPiece` call ever fires during REPLAY), so the expensive `hexesInRange`/`validateMove` sticky-selection paths (lines 640-733) are dead code during replay — they take the early-clear branch (lines 611-637) every time. Spending plan effort "optimizing" `setGameState` would not move the needle; the 962-hex `HexGrid` body is the actual cost center.
- **Adding `HEADED_PASS`/`GK_PUNT` to `REPLAY_ELIGIBLE_TYPES` without checking `flushMoveGroup()` ordering:** Both event types are appended to `eventLog` immediately following (in `headedPassEventLegacy`/`headedPassEvent`/`puntEvent`'s construction sites) other events that may be mid-movement-group accumulation in some call paths. Adding them to `REPLAY_ELIGIBLE_TYPES` will correctly trigger `flushMoveGroup()` (since they're non-MOVE/non-SLOT_ADVANCE events, the existing generic branch at gameEngine.ts:4097 already calls `flushMoveGroup()` for any event not explicitly skipped) — verify with a test that a movement phase immediately followed by a header-delivery still flushes and renders both correctly.

## Common Pitfalls

### Pitfall 1: Assuming `setGameState` is the DESIGN-02 bottleneck

**What goes wrong:** A naive read of `useGameStore.ts`'s `setGameState` (which does branch on `phase`/`movementSlot` and calls `hexesInRange`/`validateMove` in some branches) suggests it's doing unnecessary work every replay frame.
**Why it happens:** The function is large (140 lines) and its various branches aren't obviously dead-during-replay without tracing `prevSelectedId`'s lifecycle.
**How to avoid:** Trace forward from the FULL_TIME→REPLAY transition: `phaseChanged` fires once (clearing `selectedPieceId` to `null`), and since nothing in `ReplayPanel.tsx` or any REPLAY-phase code path ever calls `selectPiece`/`inspectPiece`, `prevSelectedId` stays `null` for the rest of the replay — the function takes the cheap early-clear branch (lines 611-637) every single frame.
**Warning signs:** If a future change adds piece-click interactivity during replay (e.g., "click a piece mid-replay to inspect stats"), this pitfall analysis would need to be re-verified — `setGameState`'s expensive branches would become reachable.

### Pitfall 2: Confusing "redundant socket emissions" with "expensive render per emission"

**What goes wrong:** CONTEXT.md's D-05 framing ("redundant socket emissions") could lead an implementer to look for duplicate `io.emit()` calls server-side.
**Why it happens:** The phrase groups two distinct concerns (network traffic volume vs. client render cost) under one bullet.
**How to avoid:** This research confirms there are zero duplicate emissions — every `startReplayStream` call path that reaches `FULL_TIME` does exactly one `broadcastState` for the FULL_TIME frame itself, then the 3s-delayed `setInterval` does exactly one `io.to().emit()` per 500ms tick, bounded by `frames.length` (the interval clears itself once exhausted). The "waste" is 100% on the client render side (HexGrid's per-frame recomputation), not network-side duplication.
**Warning signs:** None currently — this is a closed finding, included here so the planner doesn't waste a task searching for a non-existent server-side double-emit bug.

### Pitfall 3: Stale `ballAfter` recorded before a contested-pickup effect resolves

**What goes wrong:** In `applyMove` (gameEngine.ts ~line 465-481), the `MOVE` event's `ballAfter` field is computed and the event is pushed to `eventLog` (line 483) **before** the STEAL_ATTEMPT (line 552) or TACKLE_ATTEMPT (line 589) effect blocks run and compute the _actual_ post-contest ball state. On a successful steal/tackle, the `MOVE` event's `ballAfter` reflects the pre-contest ball (old carrier, old position) while the immediately-following `STEAL_ATTEMPT`/`TACKLE_ATTEMPT` event correctly carries the new carrier. In `buildReplayFrames`, the `MOVE` event is accumulated into `moveGroup` with this stale `ballAfter` (gameEngine.ts:4092) and used as `stepBall` for that movement step's frame (gameEngine.ts:4052-4061) — producing a one-frame ball-position glitch on every successfully-contested movement step, immediately self-corrected by the next frame.
**Why it happens:** The event-construction order in `applyMove` mirrors the code's natural execution order (move first, then resolve contest), but `ballAfter` is meant to capture the _final_ ball state for that recorded action, not an intermediate snapshot.
**How to avoid:** Defer the `MOVE` event's `ballAfter` computation until after the steal/tackle effect block has determined the outcome, or compute it from the same `stealSuccessBall`/`tackleSuccessBall`/`state.ball` values used in the final `ok:true` return for that code path (the values already exist in scope at each return statement — lines 681, 631/659, 487).
**Warning signs:** A replay test seeding a movement phase ending in a successful steal/tackle, asserting that the MOVE event's frame already shows the new carrier (not just the immediately-following STEAL_ATTEMPT/TACKLE_ATTEMPT event's frame), will fail until this is fixed.

### Pitfall 4: New replay-eligible-shaped event types silently excluded from `REPLAY_ELIGIBLE_TYPES`

**What goes wrong:** `HEADED_PASS` (gameEngine.ts:2205, 3093) and `GK_PUNT` (gameEngine.ts:2538) were added by quick-task `260621-b8f` (2026-06-21) with a `ballAfter` field matching the exact shape Phase 14 defined for replay-eligible events — but the developer (correctly) did not need to touch `REPLAY_ELIGIBLE_TYPES` to make `ActionLog`/gameplay work (the field's universal-ballAfter-update branch in `buildReplayFrames`, gameEngine.ts:4112-4115, applies regardless of REPLAY_ELIGIBLE_TYPES membership for `current.ball`'s internal bookkeeping). The omission only manifests as a missing _visible frame_ — easy to miss without specifically testing post-game replay across a header sequence.
**Why it happens:** `REPLAY_ELIGIBLE_TYPES` (gameEngine.ts:3955-3970) and the `ballAfter`-bearing-type list in `types.ts` are two independently-maintained lists with no compiler-enforced link between them. Phase 14's original migration made `ballAfter` required (TypeScript-enforced) on exactly 13 types, which is necessary but not sufficient for replay visibility — frame-push additionally requires manual membership in `REPLAY_ELIGIBLE_TYPES`.
**How to avoid:** Add `'HEADED_PASS'` and `'GK_PUNT'` to `REPLAY_ELIGIBLE_TYPES` (gameEngine.ts:3955-3970). Consider a defensive lint/test going forward: a unit test asserting every `ActionEvent` union member with a `ballAfter` field is also present in `REPLAY_ELIGIBLE_TYPES`, so future additions can't silently repeat this gap. (`HEADER` is the one expected, intentional exception — it carries no `ballAfter` and correctly produces no frame; only the _delivery_ events that follow a header duel need replay visibility.)
**Warning signs:** A replay test seeding an eventLog containing a HEADER win followed immediately by a HEADED_PASS, with the next eligible event being a later MOVE, would currently show the ball "jump" from its pre-header position straight to wherever that later MOVE's ballAfter places it — skipping the header-delivery hex entirely.

### Pitfall 5: `GK_KICK` event type has no construction site (latent dead code, not a replay bug)

**What goes wrong:** `GK_KICK` is declared in the `ActionEvent` union (types.ts:281-288) with no `ballAfter` field and is absent from `REPLAY_ELIGIBLE_TYPES`, which could look like a third replay gap.
**Why it happens:** `grep -n "type: 'GK_KICK',"` against `gameEngine.ts` returns zero construction sites — this event type appears to be superseded entirely by `GK_PUNT` (added later) and is never actually emitted in the current codebase.
**How to avoid:** Do not spend a plan task "fixing" `GK_KICK`'s replay eligibility — it cannot occur in eventLog today. Flag it as a DESIGN-04 (dead-code-removal) candidate instead; it is out of scope for Phase 18.1 (DESIGN-04 is Phase 18.2's responsibility per REQUIREMENTS.md traceability).
**Warning signs:** None — this is a closed, no-action finding included so the planner doesn't misallocate effort here.

### Current applyMove MOVE-event ballAfter computation (the exact site to fix for Pitfall 3)

```typescript
// Source: packages/server/src/gameEngine.ts:465-481 (current state, as read this session)
// PROBLEM: this snapshot is taken BEFORE the STEAL_ATTEMPT/TACKLE_ATTEMPT effect block
// (lines 552-676) runs and determines the actual post-contest ball state.
const ballAfterMove: { position: HexCoord; carrierId: string | null } =
  state.ball.carrierId === pieceId
    ? { position: to, carrierId: pieceId }
    : state.ball.carrierId === null &&
        to.q === state.ball.position.q &&
        to.r === state.ball.position.r
      ? { position: to, carrierId: pieceId }
      : { position: state.ball.position, carrierId: state.ball.carrierId };
const moveEvent: ActionEvent = {
  type: 'MOVE',
  pieceId,
  from: piece.position,
  to,
  slot: state.movementSlot,
  timestamp: Date.now(),
  ballAfter: ballAfterMove, // <-- stale if a steal/tackle effect below changes the outcome
};
let newEventLog: readonly ActionEvent[] = [...state.eventLog, moveEvent];
```

## Open Questions

1. **Should the DESIGN-02 fix be a full early-return (skip rendering interactive layers entirely) or a narrower guard (keep rendering pieces/ball/hex-fill but skip highlight-set computation)?**
   - What we know: During REPLAY, pieces and the ball legitimately need to render and move every frame (that's the whole point of replay). Only the _highlight/click-handler_ derivation (validMoveHexSet, zoiRiskSet, kickoff zones, pass-target sets, etc.) and the per-piece `canSelect*`/`isClickable` boolean cascade are unconditionally wasted.
   - What's unclear: Whether the planner wants a single top-of-function early-return that renders a simplified non-interactive SVG tree (larger diff, clearest separation) or a narrower guard wrapping just the highlight-derivation block while still flowing through the existing single big render JSX with all `onClick`s replaced by no-ops when `phase === 'REPLAY'` (smaller diff, less duplication, but more conditionals threaded through the existing 962-hex map body).
   - Recommendation: Prefer the narrower in-place guard (wrap the highlight-set computations in `if (phase !== 'REPLAY') { ... }` and force `onClick = undefined` whenever `phase === 'REPLAY'`) — this avoids duplicating the SVG layout/structure (PitchMarkings, GoalNets, clipPath, BallMarker, PieceOverlay rendering) in two places, which would be a larger and riskier diff for a 962-element list.

2. **Is a new automated replay-correctness regression test required, or is documenting+fixing sufficient for this audit phase?**
   - What we know: `replay.integration.test.ts` currently has zero coverage for (a) a MOVE-then-successful-STEAL_ATTEMPT sequence's frame-by-frame ball position, and (b) HEADED_PASS/GK_PUNT replay visibility.
   - What's unclear: Whether REQUIREMENTS.md's REPLAY-06 success criterion ("UAT Test 6 from v1.1 passes without regression") is satisfied by browser-based manual UAT alone, or whether the planner should also add automated unit/integration coverage to prevent the same regression pattern (new ballAfter-bearing event type, forgotten REPLAY_ELIGIBLE_TYPES entry) from recurring.
   - Recommendation: Given the Validation Architecture section below and this codebase's existing pattern of pairing every REPLAY-0x fix with a dedicated integration test (Phase 14 plans 02/03 each added 1-2 tests), the planner should add at least: (a) a test asserting a contested-steal MOVE's replay frame already reflects the post-steal carrier, and (b) a test asserting a HEADED_PASS/GK_PUNT event produces a visible frame with the correct ball position.
