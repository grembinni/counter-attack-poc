# Phase 18.1 Plan 02: HexGrid REPLAY-Phase Interactivity Guard Summary

**Added a `phase === 'REPLAY'` short-circuit to HexGrid's highlight-set derivation, per-hex onClick cascade, and per-piece isClickable cascade — eliminating the wasted 962-hex/22-piece interactive derivation that ran unconditionally on every post-game replay frame, while pieces/ball/base hex fill continue to render and animate normally.**

- **Completed:** 2026-06-21T17:22:40Z (Task 2 GREEN commit)

## Accomplishments

- `HexGrid.tsx` no longer computes `validMoveHexSet`, `zoiRiskSet`, or `tackleRiskSet` during `phase === 'REPLAY'` — they resolve to empty sets immediately instead of running their `.filter()`/`getZoIDefenders()` work over up to 22 pieces and N valid-move hexes.
- The per-hex `onClick` derivation's entire phase-branch cascade (KICK_OFF_SETUP, FREE_KICK_SETUP, GK_DIVE, shooting/header/pass-target branches, etc.) is skipped outright during REPLAY — `onClick` stays `undefined` for all 962 hexes on every replay frame.
- The per-piece `isClickable` cascade is forced `false` during REPLAY (defense-in-depth; the underlying `canSelect*` booleans were already individually phase-gated).
- Pieces, the ball, and base hex fill (`PitchMarkings`, `GoalNets`, `BallMarker`, `PieceOverlay`) are untouched by the guard and continue to render/animate every replay frame exactly as before.
- 3 new component tests added to `HexGrid.test.tsx` under a `DESIGN-02:` prefixed describe block: a REPLAY-phase no-clickable-cursor assertion (using defender-adjacent-to-carrier geometry with `selectedPieceId`/`validMoveHexes` seeded so the assertion is meaningful), a MOVE-phase control case proving the same geometry IS clickable outside REPLAY, and a REPLAY-phase no-highlight-tint assertion using the same defender-adjacent geometry that would otherwise produce a risk tint.
- Full client suite (225 tests across 12 files) passes with zero new failures; typecheck and lint are clean.

## Decisions Made

- Confirmed at edit time (per `<read_first>` instructions) that `validMoveHexSet`, `zoiRiskSet`, and `tackleRiskSet` were the only highlight-set derivations NOT already behind a play-phase-specific `phase === 'X'` guard; all other sets (`gkDiveTargetSet`, `highPassContestZoneSet`, `gkKickTargetSet`, `quickThrowTargetSet`, `snapDeflectPathSet`, etc.) needed no change since `REPLAY` never equals any of their gating phase values.
- Chose a single `if (phase !== 'REPLAY') { ...existing cascade... }` wrapper for the onClick derivation over threading the condition into each of the ~10 individual `else if` branches — smaller diff, identical runtime effect, and consistent with RESEARCH.md's "prefer the narrower in-place guard" recommendation (Open Question 1).
- Did not modify `selectionState` derivation (`isSpentNow`/`isHeaderContestant`/`selectedPieceId` checks) — traced that `isHeaderContestant` is already gated by `isHeaderPhase = phase === 'HEADER'` and `selectedPieceId` is never set during REPLAY (no REPLAY-phase code path calls `selectPiece`), so `selectionState` already resolves to `'none'`/`'activated'`-only correctly without further guarding; adding a redundant guard here would have been unnecessary diff noise.

Per the analysis-paralysis/fail-fast guidance for TDD RED phases ("if a test passes unexpectedly during RED, investigate before proceeding"), the test was strengthened to seed the same defender-adjacent-to-carrier geometry, `selectedPieceId`, and `validMoveHexes` used by the highlight-tint test, making `isValidMove` true and `onClick = emitMove(...)` reachable pre-fix. Re-run confirmed genuine RED (cursor became `'pointer'` against unmodified code), then GREEN after the Task 2 fix. This resolution happened entirely within Task 1's RED-authoring step, before any commit — no extra commit was needed.
