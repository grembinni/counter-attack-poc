<objective>
Replace the interactive click-to-select-destination clear-out shipped in 38-20/38-21/38-22 with an
automatic straight-line-toward-goal move applied at corner-award time, on the server only.

Purpose: `38-24-SUMMARY.md` bug 1 — "repositioning on corner kick should be automatic and not
prompted … move the player in a straight line toward the goal until they are 3 hexes away". The
shipped `CORNER_KICK_CLEAR_OUT` phase makes the manager walk each in-zone piece one hex per click and
then press Confirm; the verifier rejected that interaction model outright.

`applyAutomaticCornerClearOut` engine helper wired into `triggerOutOfBoundsRestart`'s `CORNER_KICK`
branch, and the complete removal of the interactive clear-out engine functions and socket branches.
The `CORNER_KICK_CLEAR_OUT` `GamePhase` literal and `cornerKickClearOutSlot` field stay in
`packages/shared/src/types.ts` for now — plan 38-28 removes them once the client references are gone.

## Locked assumptions

- **A-AUTO-01 (clear distance).** "3 hexes clear of the corner" is implemented as
  `!isWithinCornerExclusionZone(hex, cornerHex)`, i.e. `hexDistance(hex, cornerHex) > CORNER_EXCLUSION_RADIUS`
  (final distance 4 or more). This is the same predicate the shipped permanent defender-exclusion
  rule already uses, so the two can never drift apart. Never restate the literal `3`.
- **A-AUTO-02 (goal direction).** "toward the goal" is `cornerClearOutGoalHex(bylineOwnerTeam)` where
  `bylineOwnerTeam` is the team OPPOSITE `cornerKickTeam` — the conceding team whose byline the
  corner is taken from. This is the same `goalHex` the deleted `isLegalClearOutStep` used.
- **A-AUTO-03 (population).** BOTH teams' pieces are cleared, matching the shipped two-slot
  (ATTACKER then DEFENDER) interactive behaviour. Goalkeepers are not exempt.

    Add one new exported pure function to `packages/shared/src/outOfBounds.ts`, placed immediately
    after `isLegalClearOutStep` and before `isSpillCornerDirection`:

    `cornerClearOutDestination(from: HexCoord, cornerHex: HexCoord, goalHex: HexCoord, occupied: readonly HexCoord[]): HexCoord`

    Behaviour, in this exact order:

    1. If `!isWithinCornerExclusionZone(from, cornerHex)` return `from` unchanged — a piece already
       clear of the corner is never moved (A-AUTO-01).
    2. Walk `hexLine(from, goalHex)` starting at index 1 (index 0 is `from` itself). Return the FIRST
       hex that satisfies all three of: `isPitchHex(hex)` is true; no entry of `occupied` has the
       same `q` and `r`; `isWithinCornerExclusionZone(hex, cornerHex)` is false. Do NOT abort the
       walk when an intermediate hex fails — skip it and keep scanning, so a blocked hex mid-line
       cannot strand the piece inside the zone.
    3. Fallback when the line yields no candidate: scan `PITCH_HEXES` for every hex that is
       unoccupied AND outside the exclusion zone, and return the one minimising
       `hexDistance(hex, from)`, tie-broken by smaller `hexDistance(hex, goalHex)`, then smaller `q`,
       then smaller `r`. This mirrors `resolveThrowInHex`'s existing deterministic sort shape
       (distance, then q, then r) — keep the same comparator style so the two read alike.
    4. If even the fallback finds nothing (unreachable on a real 37x26 pitch with 22 pieces), return
       `from` unchanged — never return an off-pitch or occupied hex.

    The function is pure: no `GameState`, no piece objects, no I/O. `occupied` is a plain
    `HexCoord[]` supplied by the caller so the engine controls whether the moving piece's own
    current hex is included (it must not be).

    Write the JSDoc in this module's established voice: name the requirement (`CORNER-01`), the
    source (`38-24-SUMMARY.md` bug 1, gap-closure round 3), state that it REPLACES the interactive
