<objective>
Resolve the corner kick itself: extend `applyRoll`'s existing `PASS` case so a corner's Low Pass
option is accuracy-gated the same way High Pass already is (CORNER-04), confirm the High option's
mandatory header falls out of the existing `HIGH_PASS`→`HEADER` transition unchanged (CORNER-05),
and tear the corner context down cleanly on every resolving branch.

Per D-07 the corner context lives in Corner Kick's own `cornerKick*` fields; only the pure
`computeCombinedScore`/`validatePassAccuracy` helpers and the existing HEADER duel are reused.

Purpose: this is the second novel surface in the phase, but smaller than it looks. High corners
are ordinary High Passes with an extended range cap (the range work lives in 38-05). Low corners
are the genuinely new mechanic — `STANDARD_PASS` never rolls for accuracy in this engine today.
The design extends the existing `requiresAccuracyCheck` boolean rather than building a parallel
pass-resolution pipeline.

Output: the accuracy-gate extension, a dedicated `CORNER_KICK_ACCURACY` event with its Undo/Replay
registrations, and a Pitfall-3 audit proving `cornerKickTeam` survives every intermediate return.
</objective>

## Trust Boundaries

| Boundary                        | Description                                                                                                                                                                              |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| client `game:roll` → engine     | The passType and target hex are client-chosen; the die is generated server-side with `crypto.randomInt` by the handler and passed in. `applyRoll` never generates dice itself (ARCH-01). |
