# Phase 46 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase type note:** This is a milestone-closing audit/cleanup phase, not a net-new-surface phase. There is no new screen, no new component library, and no new visual language to introduce. The contract below is deliberately a **"conform to what already exists" contract** — every value is either quoted directly from the project's existing token/doc system (`tokens.css`, `docs/HIGHLIGHT-REFERENCE.md`) or is the specific target value the CLEANUP-0X audit findings (46-RESEARCH.md) must converge two divergent surfaces onto. Do not introduce new colors, new spacing values, or new type sizes anywhere in this phase — every fix is either "use the value the other 3 surfaces already use" or "add one line to an existing constant table."

## Spacing Scale

This project does not enforce a strict 8-point spacing scale; existing components use a denser set of values (4/6/8/10/12/16/20/24px) appropriate to a data-dense scoreboard/roster UI viewed at typical desktop viewport widths. Phase 46 makes no change to the spacing system itself. The declared scale below documents current practice for reference; the binding rule for this phase is narrower and stated after the table.

| Token | Value | Usage |
|-------|-------|-------|
| 3xs | 4px | Icon-to-label gaps, badge padding |
| xs | 6px | Compact row gaps (`.statChip`, `.cardHeader`) |
| sm | 8px | Column gaps in stat grids, panel internal padding |
| sm+ | 10-12px | Card padding, `.cardBody` row gaps |
| md | 16px | Section padding, panel margins |
| lg | 20-24px | Major layout gaps, screen-level padding |

**Binding rule for this phase:** for every CLEANUP-11 alignment fix (PlayerStatsPanel ↔ roster/bench card family), copy the spacing value **from the already-aligned roster/bench pair** (`LineupAssignmentScreen.module.css`'s `.statGrid`/`.cardBody`/`.cardHeader` values) onto the divergent surface (`PlayerStatsPanel.module.css`). Do not average, split the difference, or invent a new intermediate value.

Exceptions: none.

## Typography

This project uses a wider, denser type scale than a typical 3-4-size marketing UI (appropriate to a stat-heavy sports scoreboard: player names, roles, jersey numbers, 6-9 attribute values, and countdown/helper text all coexist in a small card). Phase 46 does not change the type scale. The table documents the sizes actually in use across the surfaces this phase touches, plus the two binding alignment targets.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Stat label (abbreviated, e.g. "PAC") | 9-10px | 700 (bold) | 1 (single line, no wrap) |
| Stat value badge | 11px | 800 (extrabold) | 1 (circular badge, centered) |
| Card meta (role chip, jersey #, flag row) | 12-13px | 700 (bold) | 1.2 |
| Card name (player full name) | 13-14px | 700 (bold) | 1.2 |
| Panel helper text (`.helperLine1`, e.g. "Free Move!") | 14-16px | 700 (bold) | 1.3 |
| Panel helper body (`.helperLine2`) | 12-14px | 400 (regular) | 1.4 |
| Section/screen heading | 20-22px | 700 (bold) | 1.2 |

**Binding rule for CLEANUP-11 (PlayerStatsPanel alignment):** `PlayerStatsPanel.module.css`'s `.playerName`/`.roleChip`/`.jerseyNum` are currently `13px`/`700` — this already matches the roster/bench family's `.cardName`/`.cardRole`/`.cardNum`. The confirmed divergence is **not** font size — it is (a) the `TeamBadge` size prop (`56` in `PlayerStatsPanel.tsx` vs `48` in the roster/bench family) and (b) a stale doc comment in `PlayerStatsPanel.tsx` claiming a "4-column / 7-stat" grid when the actual rendered grid is 3-column / 6-stat, identical to the roster/bench family. Fix: change `TeamBadge` size from `56` to `48` in `PlayerStatsPanel.tsx`; correct the stale comment to match the real 3-column/6-stat shape (do not change the actual grid — it already matches).

## Color

Full color contract lives in two existing canonical files, not restated here as raw hex — **`packages/client/src/styles/tokens.css`** (chrome: backgrounds, borders, text, CTA states, card semantic badges) and **`docs/HIGHLIGHT-REFERENCE.md`** (hex tints, piece/hex rings, standalone overlays — the pitch-board highlight system). Phase 46 does not introduce new colors; every fix below is "reuse an existing token/entry," per `docs/HIGHLIGHT-REFERENCE.md`'s own "Adding a New Highlight" checklist (its section titled that, step 3: add to the existing `Record`/`Set` constant, never invent a new mechanism).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--color-bg-page` (`#121212`) / `--color-bg-pitch` (`#0a0a0a`) | App background, pitch background |
| Secondary (30%) | `--color-bg-surface` (`#1c1c1c`) / `--color-bg-surface-alt` (`#262626`) | Cards, panels, roster/bench surfaces |
| Accent (10%) | `--color-accent-gold` (`#f5c518`) | Reserved for: confirmation/required-action rings (`RING_STYLES.required`/`.confirmed` in `HexCell.tsx`), the header-target contest bullseye, CTA-pending state family. Do not extend gold to any new element in this phase — it is not a general "brand color." |
| Destructive | `--color-danger` (`#ef4444`) | Error text, disabled states, the red offside ring (`isOffside`, `PieceOverlay.tsx` — **the sole app-wide use of red within the highlight/ring system**), red-card badge |

Accent reserved for: confirmation rings and CTA-pending buttons only (per `tokens.css` inline documentation and `HIGHLIGHT-REFERENCE.md` section 2b) — never for a new "highlight this is important" use invented during this phase.
