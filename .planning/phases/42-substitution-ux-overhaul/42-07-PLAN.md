<objective>
Turn `LineupAssignmentScreen.tsx`'s `mode === 'midmatch'` branch from a single interaction model into two coexisting modes on one screen: a default positioning mode with on-field drag-to-swap, and an explicit substitution mode entered through an action button that becomes Cancel.

Purpose: this screen carries shipped, tested Phase 40 substitution logic (3-sub cap, jersey/slot inheritance, red-card and subbed-out exclusions, roster-continuity overlay). Research flags this as the single highest-regression-risk item of the milestone, because the path of least resistance is to thread a `mode` conditional through the existing guards, which silently narrows their applicability. This plan therefore keeps the two modes' drop handlers as two separate functions sharing no guard body, and leaves substitution mode's behavior byte-for-byte as it ships today (42-08 upgrades it afterwards). At the end of this plan both modes are fully reachable and working.

Scope boundary (D-01): every drag interaction this plan adds — both position-swap and substitution — lives entirely inside the mid-match roster panel (`LineupAssignmentScreen`'s `mode === 'midmatch'` branch, opened via `GameBoard.tsx`'s `SubstitutionButton` modal). The live `HexGrid`/pitch view gains no drag affordance in this phase, and `HexGrid.tsx` is deliberately absent from this plan's `files_modified`.

Output: a working default positioning mode, a working mode toggle, a SENT OFF placeholder for red-carded slots, and no change whatsoever to substitution mode's existing guards.
</objective>

## Trust Boundaries

| Boundary                   | Description                                                                                                                         |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| user → roster panel        | Drag gestures are user-driven; the resulting `onReposition`/`onSubstitute` calls become socket events that the server re-validates. |
| client mode state → server | `subMode` exists only in client memory. The server has no notion of it and gates every reposition/substitution independently.       |
