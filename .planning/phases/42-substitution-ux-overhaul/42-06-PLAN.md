Add an exported `applyRosterReposition(state, team, pieceIdA, pieceIdB)` to `gameEngine.ts`, placed immediately after `applySubstitution` and before `applyRosterContinuity`. **Rejection reasons (exact strings):** `'WRONG_PHASE' | 'INVALID_REPOSITION' | 'GK_SLOT_LOCKED' | 'REPOSITION_BALL_CARRIER'`.

**Guard order (validate everything before any mutation):**

1. `if (!isStoppagePhase(state.phase))` → `'WRONG_PHASE'`. Defence in depth; the handler checks too.
2. `if (pieceIdA === pieceIdB)` → `'INVALID_REPOSITION'`.
3. Resolve both pieces from `state.pieces`. If either is undefined, or either `teamId !== team` → `'INVALID_REPOSITION'`.
4. GK-slot lock: reject if either piece has `role === 'GK'`, OR if either piece's slot index (parsed from its id with `/-(\d+)$/`, matching the client's own parse in `LineupAssignmentScreen.tsx`) is `0` → `'GK_SLOT_LOCKED'`. Both conditions, because a prior substitution can change `role` in a slot but never changes the id. Reuse the existing `GK_SLOT_LOCKED` string so the client's already-present rejection message ("Swap rejected — GK cannot be moved.") works with no client change.
5. `if (state.ball.carrierId === pieceIdA || state.ball.carrierId === pieceIdB)` → `'REPOSITION_BALL_CARRIER'`. Rationale to record in a comment: a stoppage can have a designated carrier (goal-kick GK, corner taker, throw-in thrower) whose selection was made under restart-specific rules; swapping the occupant of the carrier's slot would silently hand the restart to a different player without re-running those rules.
6. Do NOT reject a red-carded piece here. D-05 explicitly requires the vacated slot of a sent-off player to remain a real, droppable slot so the manager can reshuffle shape around the numerical disadvantage. Add a comment stating this exception is deliberate and must not be "fixed" by adding `isActivePiece` — this is the one eligibility site in the codebase where a dismissed piece is a legitimate participant.

**Swap semantics (locked — do not substitute your own model):** the swap moves the OCCUPANT between slots; `id`, `position` and `number` stay bound to the slot. Build the two new pieces as:

- `newA = { ...pieceB, id: pieceA.id, position: pieceA.position, number: pieceA.number }`
- `newB = { ...pieceA, id: pieceB.id, position: pieceB.position, number: pieceB.number }`

Everything else travels with the person: `playerId`, `firstName`, `lastName`, `nationality`, `role`, all nine numeric attributes, `yellowCards`, `redCarded`, `onPitch`, `injuryCount`.

Record the three reasons this model is required, in the function's doc comment:

- It is byte-for-byte the SUB-03 inheritance contract (`buildSquadPieces`: id is slot identity; `applySubstitution`: the substitute inherits slot, jersey number and position).
- `applyRosterContinuity` overlays a rebuilt kick-off formation by `id` and takes ONLY `position` from the reset array, keeping identity from the live roster — so a swap expressed as identity-follows-slot survives every goal and half-time reset, while a swap expressed as position-follows-player would be silently undone at the next goal.
- The mid-match roster grid groups cards by the slot index parsed from `piece.id`, so identity-follows-slot is what makes the dragged card visibly move columns.

Note in the same comment that on-pitch observable state is identical either way (the same person ends up standing on the same hex wearing the same slot's number) — the difference is purely which slot id holds whom, which is what resets and grouping depend on.

**State build:** return `{ ok: true, state: { ...state, pieces: newPieces, eventLog: [...state.eventLog, repositionEvent] } }`. Do NOT touch `phase`, `activeTeam`, `movementSlot`, `subsUsed`, `addedTime`, `addedTimeBonus` or `bench` — a reposition is free, uncapped, repeatable, and never advances the FSM or costs added time. Add a comment stating this explicitly, contrasting it with `applySubstitution` which increments three counters.

**Event:** append a `ROSTER_REPOSITION` `ActionEvent` populated with pre-swap values: `pieceId: pieceIdA`, `pieceIdB`, `playerAName: \`${pieceA.firstName} ${pieceA.lastName}\``, `playerBName`likewise from`pieceB`, `jerseyNumberA: pieceA.number`, `jerseyNumberB: pieceB.number`, `team`, `timestamp: Date.now()`.

**Undo registration:** add `evt.type === 'ROSTER_REPOSITION'` to `applyUndo`'s boundary disjunction, directly beside the `SUBSTITUTION` entry, with a comment: a reposition is a committed stoppage-time roster change that lives entirely outside the movement-slot undo model, so Undo must never cross it — identical reasoning to SUBSTITUTION.

**Replay registration:** do NOT add `'ROSTER_REPOSITION'` to `REPLAY_ELIGIBLE_TYPES`. Add an explicit exclusion comment next to the existing SUBSTITUTION exclusion note stating that a reposition carries no `ballAfter` and moves no piece to a new hex (it swaps who occupies a hex), and that `buildReplayFrames` reconstructs from the starting XI where the swap has no meaning — this is a decided exclusion, not an omission.
