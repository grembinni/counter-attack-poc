## Implementation Decisions

### Bug-Bash Items In Scope Here (BUG-06, BUG-07, BUG-10) — original 2026-06-20 session

- **BUG-06:** `offsidePieceIds` must reset to `[]` for ALL players (not just the offending player) when a free-kick restart concludes. D-43 (Phase 17) added a full reset on `GAME_FREE_KICK_READY`'s both-ready transition, and D-47 generalized it to kick-off — read both before fixing; this is reported as a regression/incomplete case of that existing logic, not a net-new feature. Find the actual gap (likely a code path that bypasses the reset, e.g. a kick taken via a different transition than the one D-43/D-47 patched).
- **BUG-07:** After a header duel is won, drop the target-selection sub-phase entirely — deliver the resulting pass directly. Read `gameEngine.ts`'s `GAME_HEADER_TARGET` handler and the `HEADER`→pass-delivery flow (Phase 17.1 D-05, "multi-contestant header... confirmed done"). The post-header pass must be: (a) non-contestable (no interception roll/ZoI — mirrors the existing BUG-01 fix that already suppresses interception for header-derived passes, `lastActionType === 'HEADER'` in `applyPass`), and (b) labeled/logged as `HEADER`, not as a one-touch/first-time-pass action type.
- **BUG-10:** Clicking an already-activated (already-moved, `movedPieceIds.includes(id)`) player piece must still open/select that piece's player card — same click handler path as unmoved pieces, just don't allow it to also re-trigger move-target highlighting.

### Bug-Bash Addendum (BUG-12..18) — gathered 2026-06-22

- **BUG-12 (folded todo, `2026-06-21-add-toggle-to-skip-move-phase-after-first-time-pass.md`):** Add a config/feature-flag toggle (default off, per "I want to skip it for now") that, when disabled, causes the FIRST_TIME_PASS_MOVE transition in `gameEngine.ts` to be bypassed — deliver the ball and proceed directly to the next phase, as if no repositioning window existed — while leaving the FIRST_TIME_PASS_MOVE phase/handler code intact for when the toggle is re-enabled. Do not delete the underlying mechanic.
- **BUG-13 (folded todo, `2026-06-21-bug-double-tackle-attempt-when-attacker-enters-hex-challenge.md`):** When an attacker moves into a hex within Zone of Influence of two defenders, only one `TACKLE_ATTEMPT` currently fires. Fix: after the first tackle resolves with the attacker retaining the ball, sequence in a second `TACKLE_ATTEMPT` against the second contesting defender before the move fully resolves. Needs investigation into the ZoI/tackle-attempt resolution path in `moveValidator.ts`/`gameEngine.ts` to determine where the second attempt sequences in.
- **BUG-14 (Snapshot after pace exhaustion):** `ActionPanel.tsx`'s `canSnapshot` (MOVE phase, ~line 613) requires `!movedPieceIds.includes(carrierId)`, so Snapshot disables the instant the carrier is added to `movedPieceIds`. Root cause: `gameEngine.ts`'s `computeMovedPieceIds` (~line 458-463, plain MOVE) and the FREE_MOVE equivalent (~line 329-331) add the moving piece to `movedPieceIds` immediately when `paceExhausted` becomes true on that piece's own move step — there is no deferral. **Locked fix:** mirror the existing "abandoned piece" deferral pattern that already exists for pieces that stop moving WITHOUT exhausting pace (`abandonedIds`, ~line 453-457: a piece is only locked into `movedPieceIds` once the player selects and moves a _different_ piece, i.e. `isNewActivation` fires for someone else). Apply the same deferral to the `paceExhausted` case: do not add the carrier to `movedPieceIds` purely because their own move step exhausted their pace — only add them via the `abandonedIds` path, when the player next selects and moves a different piece. This keeps Snapshot available for as long as the exhausted-pace carrier remains the actively-selected piece.
- **BUG-15 (goal-log color):** `ActionLog.tsx` renders `SHOT_ATTEMPT`(`outcome === 'GOAL'`)/`GOAL` event content text via `.goalContent` (amber `#e8a020`) instead of the standard `.content` (gray `#e0e0e0`) used by every other event type, driven by the `isGoal` flag set at lines ~386, ~485, ~518 and consumed at the render ternary (~line 785). **Locked fix:** remove the `isGoal` styling distinction entirely — `GOAL`/`SHOT_ATTEMPT`(GOAL outcome) content text renders with the same `.content` class as all other events. No replacement distinct styling (not bold, not a different color) — full removal.
- **BUG-16 (FTP/HP move-log player format):** `ActionLog.tsx`'s `FTP_MOVE` case (~line 661-675) and `HP_MOVE` case (~line 646-660) both render the player via the bare `P` component (`<P pieceId={...} prefix={team} />`), which shows only a role-letter + number (e.g. "D #7") and never resolves to the actual player name — unlike every other event type (`MOVE`, `GOAL`, `SHOT_ATTEMPT`, etc.), which uses `PNamed` to render `#{number} {Full Name}`. This is the same A/D role-letter-prefix defect class that commit `260621-hnd` already swept from `DEFLECT_ATTEMPT`/`STEAL_ATTEMPT`(×2)/uncontested `HEADER` — `FTP_MOVE` and `HP_MOVE` were missed by that sweep. **Locked fix:** replace `<P pieceId={event.pieceId} prefix={team|ftpTeam} />` with `<PNamed pieceId={event.pieceId} />` (no prefix) in both the `FTP_MOVE` and `HP_MOVE` cases. User only flagged the FTP_MOVE log specifically, but the identical code-shape defect in `HP_MOVE` is fixed in the same pass per the established "fix inconsistencies found during the sweep inline" precedent (Phase 18 D-04) — this is a parity fix, not new scope. `GK_KICK`/`GK_KICK_MOVE`'s use of `P` with `"GK"`/`"K"`/`"O"` prefixes is NOT touched — those are legitimate role labels, not the redundant `A`/`D` pattern, and were not flagged.
- **BUG-17 (kickoff-setup replay visibility):** `GAME_KICK_OFF_MOVE` (`gameHandlers.ts` ~line 1650-1714) repositions a piece directly on `room.gameState.pieces` and broadcasts state — it pushes **no `ActionEvent` to `eventLog` at all** (confirmed: no `KICK_OFF_SETUP`-related event type exists in `shared/src/types.ts`'s `ActionEvent` union). Since `buildReplayFrames` (`gameEngine.ts` ~line 4030+) reconstructs replay frames purely by walking `finalState.eventLog`, every KICK_OFF_SETUP repositioning move (including the full-squad reset into kickoff formation after a goal) is invisible to replay — the replay jumps straight from the goal frame to whatever the next eventLog-eligible event is, with no frames showing players moving into formation. This is the same defect _class_ as the GK_KICK/LOOSE_BALL_LAND REPLAY-06 gaps (a movement path that bypasses eventLog/replay-frame capture), but a distinct instance (no event logged at all, vs. an event logged but missing `ballAfter`/excluded from `REPLAY_ELIGIBLE_TYPES`). Needs investigation into whether to add a new lightweight `ActionEvent` type for KICK_OFF_SETUP repositioning (mirroring `MOVE`'s shape) or another mechanism that gives `buildReplayFrames` visibility into these piece positions without disrupting D-23's "no pace/ZoI limits" free-repositioning behavior.
- **BUG-18 (Undo broken/incomplete coverage):** Two distinct problems, both in scope:
  1. **Regression in the already-"supported" MOVE phase:** `ActionPanel.tsx`'s shared `canUndo` (~line 113-132) returns `false` immediately whenever `lastDiceRoll` is truthy (line 114), before even scanning `eventLog`. Root cause confirmed: `gameEngine.ts`'s `applyStartMovement` (~line 224-262, the PASS/KICK_OFF/LOOSE_BALL → MOVE transition — the dominant path into MOVE during normal open play) does **not** reset `lastDiceRoll: null`, unlike the GK_RESTART 'movement' branch (~line 2470) which already does this correctly. Since most possession changes route through a dice-resolved pass/duel before reaching MOVE via `applyStartMovement`, `lastDiceRoll` is almost always still truthy on MOVE entry, permanently disabling Undo for that entire MOVE phase. **Locked fix:** add `lastDiceRoll: null` to `applyStartMovement`'s returned state, mirroring the GK_RESTART branch.
  2. **Coverage gap:** server `validUndoPhases` (`gameHandlers.ts` ~line 1094) only lists `['MOVE', 'HIGH_PASS_MOVE', 'FIRST_TIME_PASS_MOVE']`. Extend Undo to every phase where a piece can move: `GK_KICK_MOVE`, `SNAPSHOT_DEFLECT`, `FREE_MOVE_ATTACK`/`FREE_MOVE_DEFENSE`, `HEADER` contestant repositioning, `FREE_KICK_SETUP` — matching the user's explicit ask for "consistent" Undo "across all move actions." For each newly-covered phase, audit its phase-transition-into-that-phase code for the same missing-`lastDiceRoll`-reset omission found in `applyStartMovement` before assuming Undo "just works" once added to `validUndoPhases`.
  - **Replay interaction (explicitly flagged by user — "consider replay impacts"):** BUG-17 established that some movement paths (`GAME_KICK_OFF_MOVE`) bypass `eventLog` entirely. Before wiring Undo into any phase, confirm that phase's moves actually produce a reversible `eventLog` entry — `applyUndo`'s scan-and-revert approach only works against logged events. Newly-covered Undo phases must not regress replay visibility, and any phase found to share BUG-17's "no eventLog entry" gap should get that fixed as a prerequisite, not worked around.

## Existing Code Insights

### Established Patterns

- `lastActionType` discrimination — already used to suppress header-pass interception (BUG-01 precedent for BUG-07's "non-contestable" requirement)
- `abandonedIds` deferred-activation pattern (`gameEngine.ts`, both plain-MOVE and FREE_MOVE variants) — a piece is only locked into `movedPieceIds` when the player moves on to a _different_ piece, except for the `paceExhausted` case which currently locks immediately; BUG-14 closes that one remaining gap in an otherwise-established pattern
- `PNamed` (full name, optional role prefix) vs. `P` (role-letter + number only, no name resolution) — `PNamed` is the established convention for every event type except the two BUG-16 stragglers
- `lastDiceRoll: null` reset on phase transition — present on 5 of the engine's phase-transition return sites (GK_RESTART movement/throw/kick branches, HALF_TIME, one other) but absent from `applyStartMovement`, the most-traveled entry point into MOVE

### Integration Points

- BUG-14, BUG-17, and BUG-18 all touch `gameEngine.ts`'s movement-phase state machine in adjacent but distinct ways (movedPieceIds timing, eventLog completeness, lastDiceRoll lifecycle) — sequence carefully to avoid edit conflicts if planned as separate plans within the same wave
- BUG-18's coverage-gap fix (extending `validUndoPhases`) is downstream of BUG-17's finding (some movement paths have no eventLog entry) — don't wire Undo into a phase whose moves aren't logged without first confirming (or fixing) that logging gap
