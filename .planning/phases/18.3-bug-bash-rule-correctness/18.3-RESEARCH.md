## Summary

Phase 18.3 is a pure bug-bash phase — no new features, no new dependencies, no external packages. All 13 bugs (BUG-06 through BUG-21, excluding BUG-08, BUG-09, BUG-11 which shipped in Phase 18.2) target existing rule/flow gaps across three layers: the server-side game engine FSM (`gameEngine.ts`, `gameHandlers.ts`), the shared type/validator layer (`moveValidator.ts`, `offside.ts`, `types.ts`), and the React client (`ActionLog.tsx`, `ActionPanel.tsx`, `HexGrid.tsx`, `PieceOverlay.tsx`).

The bugs divide naturally into four risk tiers. **Tier 1 (formatting/visual, low risk):** BUG-15 (remove amber goal styling), BUG-16 (PNamed in FTP/HP log), BUG-19 (jersey number source of truth) — mechanical search-and-replace within client components. **Tier 2 (client interaction, medium risk):** BUG-10 (click-to-card on moved pieces), BUG-12 (FTP-move toggle), BUG-21 (Snapshot goal-line highlight investigation). **Tier 3 (engine state correctness, high care):** BUG-06 (offside reset gap), BUG-07 (header delivery bypass), BUG-14 (movedPieceIds timing), BUG-17 (replay eventLog gap), BUG-18 (Undo regression + coverage extension), BUG-20 (free-move interrupt timing). **Tier 4 (investigation-required):** BUG-13 (double-tackle sequencing), BUG-21 (root cause unknown).

**Primary recommendation:** Sequence fixes by risk tier — Tier 1 first (safe, fast, self-contained), then Tier 2, then Tier 3 in dependency order (BUG-17 before BUG-18; BUG-14 before BUG-20; BUG-06 confirmed-gap before fix). BUG-13 and BUG-21 require investigation steps at their plan's Wave 0.

### BUG-07: Header Pass Delivery Without Target Selection [VERIFIED: codebase read]

**What the code does today:**
`applyResolveHeaderTarget` (line 2960) requires the winning team to explicitly call `GAME_HEADER_TARGET` with a chosen hex. The non-goal-line path (line 3031) transitions to PASS with `lastActionType: 'HEADER'` and emits a `HEADED_PASS` event.

**The bug:** `GAME_HEADER_TARGET` is a separate player action — the winner must select a target hex. BUG-07 wants to skip this entirely and deliver directly after the duel resolves.

**Where the decision lives:**
In `GAME_HEADER_CONTESTANT` handler in `gameHandlers.ts`, after `computeHeaderDuelWinner` runs, the handler currently emits state still in HEADER phase (waiting for `GAME_HEADER_TARGET`). The fix redirects: when a winner is determined, the server immediately calls the equivalent of `applyResolveHeaderTarget` with the ball's current hex as the target, or — per BUG-07 — delivers the ball at the winner's current position directly without the intermediate `HEADER` phase stop.

**Key constraint:** The non-contestable requirement is already handled: `lastActionType === 'HEADER'` already suppresses interception in `applyPass` (BUG-01 precedent). The logging fix is: ensure the `HEADED_PASS` event type (not `FIRST_TIME_PASS`) is used. The quick-task `260621-b8f` already added `HEADED_PASS` to the ActionEvent union and `REPLAY_ELIGIBLE_TYPES`.

**Fix approach:** In the post-duel winner branch of `GAME_HEADER_CONTESTANT` handler, instead of leaving phase as HEADER (awaiting target selection), immediately transition to PASS (or to `GK_DIVE` if the winner's position is goal-line-adjacent). The winner's current position becomes the "target" — no separate `GAME_HEADER_TARGET` event needed.

**Confidence:** HIGH [VERIFIED: codebase read]

### BUG-13: Double Tackle Attempt [VERIFIED: codebase read]

**What the code does today:**
`validateMove` returns at most one `TACKLE_ATTEMPT` effect (the first eligible defender at the destination). `applyMove` resolves exactly that one effect. After a FAIL, the carrier retains the ball and the mover is added to `tackleAttemptedByIds`.

**The gap:** When the attacker (carrier) steps into ZoI of TWO defenders, `validateMove`'s ZoI check returns on the first defender found. The second defender never gets a TACKLE_ATTEMPT.

**Investigation required:** Determine whether the second defender's attempt should be handled:

1. **In the same `applyMove` call:** After the first TACKLE_ATTEMPT FAIL, re-run `validateMove` (or an inline ZoI check) against the updated `tackleAttemptedByIds` state to detect the second defender and sequence another `TACKLE_ATTEMPT` before returning.
2. **Via a separate client action:** The engine transitions to a waiting state and the client triggers a second `GAME_MOVE`-equivalent for the second defender — but this contradicts the "attacker moves into a hex" model.

Option 1 (inline second-attempt loop within `applyMove`) is architecturally consistent with the existing code. The `validateMove` exclusion logic already filters `tackleAttemptedByIds` at line 120, so a second call to `validateMove` with the updated state would naturally return the second defender's `TACKLE_ATTEMPT` effect. The fix loops: after each FAIL, re-check ZoI with updated `tackleAttemptedByIds` before committing the final return.

**Confidence:** MEDIUM — approach identified, but loop termination logic and dice injection for multi-attempt scenarios need care. [ASSUMED: inline loop is correct — confirm by reading full `applyMove` TACKLE branch]

### BUG-14: Snapshot After Pace Exhaustion [VERIFIED: codebase read]

**What the code does today:**
`computeMovedPieceIds` at line 458: `if (paceExhausted || forceIncludeSelf) ids.add(pieceId)` — the carrier is added to `movedPieceIds` the moment their pace is exhausted on their own move step.

`canSnapshot` at line 613: `!movedPieceIds.includes(carrierId)` — Snapshot is blocked the instant the carrier enters `movedPieceIds`.

**The `abandonedIds` pattern (already exists, lines 453–457):**

```typescript
const abandonedIds = isNewActivation
  ? Object.keys(state.paceUsedByPieceId).filter(
      (id) => id !== pieceId && !state.movedPieceIds.includes(id),
    )
  : [];
```

A piece is only locked into `movedPieceIds` when the player starts activating a DIFFERENT piece (`isNewActivation` = true for the new piece, causing the old one to be swept into `abandonedIds`).

**Fix:** Remove `paceExhausted` from the inline `computeMovedPieceIds` condition for the carrier's own piece. Instead, let the carrier only enter `movedPieceIds` via the `abandonedIds` mechanism when a different piece is subsequently activated. Concretely: `computeMovedPieceIds` should add `pieceId` only when `forceIncludeSelf` is true (used on explicit force-lock paths), not when merely `paceExhausted`.

**Mirror in FREE_MOVE path:** `applyFreeMove` at line 331 has the same pattern: `if (paceExhausted) newMovedPieceIds.add(pieceId)`. Apply the same deferral there for consistency (though FREE_MOVE has no `canSnapshot` usage).

**Confidence:** HIGH [VERIFIED: codebase read]

### BUG-20: Free-Move Interrupt Timing [VERIFIED: codebase read]

**What the code does today:**
`broadcastState` (roomStore.ts line 246): `room.gameState = applyFreeMoveZoneCheck(room.gameState)` — fires after EVERY resolved action regardless of current phase. `applyFreeMoveZoneCheck` at line 1022 returns unchanged state when phase is already `FREE_MOVE_ATTACK/DEFENSE` or `HALF_TIME/FULL_TIME`, but fires freely during an active MOVE slot (ATTACKER_4/DEFENDER_5/ATTACKER_2) or during HEADER.

**The bug:** If the ball crosses a zone boundary mid-MOVE-slot (e.g., carrier in DEFENDER_5 runs ball into final third), `applyFreeMoveZoneCheck` immediately overlays `FREE_MOVE_ATTACK/DEFENSE` — snapping the phase away from MOVE before the remaining MOVE slot players have acted.

**Fix approach (guard flag on `applyFreeMoveZoneCheck`):**
Add a parameter or check inside `applyFreeMoveZoneCheck` that detects "we are mid-slot" — specifically, if `state.phase === 'MOVE'` and `state.movementSlot !== null` and `state.movedPieceIds.length < slotQuota`, defer the interrupt. The interrupted phase/activeTeam gets saved to `freeMoveResume` when the interrupt does fire (already exists for the resume mechanism). The slot must complete first.

Similarly for HEADER phase: if `state.phase === 'HEADER'`, defer.

**Alternative (re-check at phase boundary):** Instead of guarding `applyFreeMoveZoneCheck`, call it only at natural phase exit points (end of MOVE slot, end of HEADER resolution) rather than in `broadcastState`. This is cleaner architecturally but touches more code paths.

**The D-33 trigger condition is unchanged:** Ball crossing a final-third boundary is still the trigger — only the timing of acting on it changes.

## Common Pitfalls

### Pitfall 1: Undo Coverage Extended Without lastDiceRoll Audit

**What goes wrong:** Adding a phase to `validUndoPhases` without verifying its transition clears `lastDiceRoll` — Undo appears to be enabled but `canUndo` returns false at line 114 forever.
**Why it happens:** The `lastDiceRoll` regression is specific to `applyStartMovement` (the dominant MOVE entry point) but other phase transitions may have the same omission.
**How to avoid:** For each new phase added to `validUndoPhases`, grep for `phase: '<new-phase>'` in `gameEngine.ts` and confirm each return site sets `lastDiceRoll: null`.

### Pitfall 2: BUG-18 Coverage Before BUG-17

**What goes wrong:** Wiring Undo into phases whose moves bypass `eventLog` (e.g., `KICK_OFF_SETUP`). `applyUndo` works by scanning `eventLog` — if no event was logged, undo has nothing to revert.
**How to avoid:** Confirm every newly-Undo-covered phase produces reversible `eventLog` entries before wiring Undo into it. BUG-17 ships first.

### Pitfall 3: Edit Conflicts from Adjacent Files

**What goes wrong:** BUG-14/BUG-17/BUG-18 all touch `gameEngine.ts` in adjacent but distinct sections. BUG-19 and BUG-16 both touch `ActionLog.tsx`.
**How to avoid:** Sequence plans so that simultaneous modifications to the same file are batched into one plan task or are clearly non-overlapping code regions. The sequencing note from CONTEXT.md is binding: "sequence carefully to avoid edit conflicts if planned as separate plans within the same wave."

### Pitfall 4: movedPieceIds Deferral Breaking ATTACKER_2 Quota

**What goes wrong:** Removing `paceExhausted` from `computeMovedPieceIds` means pieces that exhaust pace are not locked. If a player exhausts their ATTACKER_2 pieces' pace in one step and tries activating a third, the slot quota check in `validateMove` (line 82: `activatedCount >= slotQuota`) blocks them correctly — but the `movedPieceIds` display count used by `ActionPanel.tsx` countdown may show incorrect remaining count.
**How to avoid:** After changing `computeMovedPieceIds`, verify the `movedPieceIds.length` countdown in `ActionPanel.tsx` still reflects actual locked-in pieces correctly, not just pace-exhausted ones.

### Pitfall 5: pieceNum() Fix Breaks PNamed

**What goes wrong:** `PNamed` at line 58 calls `pieceNum(pieceId)` — if `pieceNum()` now does a store lookup and the store's `pieces` array doesn't yet have the piece (e.g., during early replay frames or edge-case timing), the fallback `pieceId` is used instead of the number.
**How to avoid:** Ensure the fallback in the fixed `pieceNum()` is the raw piece ID string (acceptable graceful degradation) and not a crash. Mirror `pieceName()`'s existing null-safe `if (piece === undefined) return fallback` pattern exactly.

### Pitfall 6: Header Delivery Without Target Causes GK_DIVE Routing Issue

**What goes wrong:** BUG-07 eliminates target selection. When delivering the ball "directly," the code must still route to `GK_DIVE` if the winner's position is goal-line-adjacent, or to PASS otherwise. Simply skipping `GAME_HEADER_TARGET` and transitioning directly to PASS at the winner's hex is wrong if that hex is a goal-line hex.
**How to avoid:** Replicate the `isGoalLineTarget` routing check from `applyResolveHeaderTarget` in the new immediate-delivery path.
