    `validatePass(state, piece, from, to, passType)` where `passType: 'STANDARD' | 'FIRST_TIME' | 'HIGH' | 'LONG'`:

    Range rejection (PASS-01..04, D-01):
    - STANDARD: reject with `RANGE_EXCEEDED` if `hexDistance(from, to) > 11`
    - FIRST_TIME: reject with `RANGE_EXCEEDED` if `hexDistance(from, to) > 6`
    - HIGH: reject with `RANGE_EXCEEDED` if `hexDistance(from, to) > 15`
    - LONG: no distance cap (always passes the range check)
    - All types: reject with `RANGE_EXCEEDED` if `hexDistance(from, to) === 0` (cannot pass to own hex)

    Path blocking (PASS-01 only — Standard Pass "cannot pass through an opponent's hex"):
    - For STANDARD only, compute `hexLine(from, to).slice(1, -1)` (skip passer's hex and destination per Pitfall 3) and reject with `PATH_BLOCKED` if any opponent piece occupies any intermediate hex.
    - FIRST_TIME, HIGH, LONG do NOT block on intermediate-hex opponents (the ball travels at height or is otherwise unblockable in flight).

    **PASS-04 landing constraints (LONG only — REQUIRED, not optional):**
    - For LONG only, after the range check, evaluate landing legality against the destination `to`:
      - **Own-piece exclusion:** if ANY piece in `state.pieces` with `teamId === piece.teamId` and `id !== piece.id` has `hexDistance(to, p.position) <= 5`, reject with `{ ok: false, reason: 'LANDING_RESTRICTED' }`. ("cannot land within 5 hexes of own players")
      - **Opponent adjacency exclusion:** if ANY piece in `state.pieces` with `teamId !== piece.teamId` has `hexDistance(to, p.position) <= 1`, reject with `{ ok: false, reason: 'LANDING_RESTRICTED' }`. ("cannot land adjacent to an opponent")
    - The own-piece check excludes the passer's own piece (a passer trivially has hexDistance 0 to their own past position — exclude self via `id !== piece.id`).
    - Both checks are computable from `state.pieces` alone with no pitch-geometry dependency, so they are IN scope for Phase 2.
    - Precedence within LONG: range check (always passes for LONG, but the `=== 0` guard still applies) → landing constraint → interception (skipped: see below).

    Interception list (D-05, applies to STANDARD, FIRST_TIME, HIGH — NOT LONG; LONG cannot be intercepted in flight, only refused at landing):
    - Compute the travel path `hexLine(from, to).slice(1)` (skip passer's own hex; include destination).
    - For each path hex, collect opponents at distance 1 (via `getZoIDefenders`).
    - Deduplicate by piece `id`, return as `interceptors: PlayerPiece[]`.
    - LONG returns `interceptors: []` on success.

    Effects:
    - For FIRST_TIME, the success result includes `effect: { type: 'FIRST_TIME_PLAYER_MOVES' }` so the FSM can prompt the in-flight player move (Specific Ideas).
    - For all other types, no effect is attached on the basic success path.

    `validatePassAccuracy(piece, passType, diceValue, penalties)` where `passType: 'HIGH' | 'LONG_SAME_THIRD' | 'LONG_CROSS_THIRD'`:
    - Threshold: HIGH = 8, LONG_SAME_THIRD = 9, LONG_CROSS_THIRD = 10 (PASS-03, PASS-04)
    - Attribute selection: HIGH → `piece.aerialAbility`; LONG_SAME_THIRD and LONG_CROSS_THIRD → `piece.dribbling`. This is an ASSUMED mapping per RESEARCH.md Open Question 1 (now RESOLVED as assumption A1, flagged for Phase 4 verification before live use); document it explicitly in a JSDoc comment with a TODO citing CONTEXT.md verification before Phase 4 live use.
    - Use `computeCombinedScore(attribute, diceValue, penalties)` so DICE-04 -2 cap is applied centrally.
    - Return `{ accurate: true }` if score ≥ threshold; otherwise `{ accurate: false, triggerLooseBall: true }` (PASS-05).
    - STANDARD and FIRST_TIME pass types do NOT call `validatePassAccuracy` — they have no accuracy check (interception only).
