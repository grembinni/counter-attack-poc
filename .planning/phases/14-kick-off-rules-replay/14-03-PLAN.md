<objective>
Implement REPLAY-04 and REPLAY-05. REPLAY-04: halve the replay frame interval from 1000ms to 500ms (the one-line setInterval delay in startReplayStream). REPLAY-05: restructure buildReplayFrames so that within each Movement Phase, all moved pieces advance simultaneously across K step-frames (K = the maximum number of steps any single piece took in that phase), instead of emitting one frame per individual MOVE event.

Purpose: v1.0 replay is slow and animates pieces one-at-a-time, which misrepresents a Movement Phase where all selected pieces move together. Faster playback plus simultaneous stepping makes the replay both quicker and faithful to how a phase actually resolves.
Output: A 500ms interval and a batched, phase-boundary-aware buildReplayFrames, with integration coverage for both.
</objective>

  <action>
    Replace the flat per-event loop in buildReplayFrames with a movement-phase accumulator. As the loop iterates finalState.eventLog:
    1. Continue skipping SLOT_ADVANCE events (no frame, no board change) — but use SLOT_ADVANCE as a movement-phase boundary marker as well.
    2. When the event is a MOVE, do not push a frame immediately. Instead append the move into a `moveGroup` accumulator keyed by pieceId — a Map<string, HexCoord[]> where each entry is that piece's ordered list of destination hexes (`event.to`) for consecutive MOVEs in the current phase. Also keep the per-piece `from`/starting position so the first step renders correctly; the current reconstructed `pieces` array already holds each piece's pre-phase position, so the accumulator only needs the sequence of `to` hexes.
    3. When a non-MOVE, non-SLOT_ADVANCE event is encountered (or the eventLog ends), FLUSH the accumulated moveGroup before handling that boundary event: let K = the maximum path length across all pieces in moveGroup. For step n = 1..K, build a frame in which every accumulated piece is at its path[min(n, path.length) - 1] hex (i.e. its n-th step, or its final hex if it has fewer than n steps), apply that to a working copy of `current.pieces`, and push a frame using the established REPLAY frame-emit pattern (`{ ...current, phase: 'REPLAY', score: { ...current.score } }` with the stepped pieces). After emitting all K step-frames, commit the final stepped positions into `current.pieces` (the board is now at end-of-phase) and clear the moveGroup.
    4. Then handle the boundary event exactly as the existing code does post-14-02: apply its board mutation (GOAL score increment, KICK_OFF movementSlot, etc.), apply the universal `ballAfter` ball update from 14-02, and if it is in REPLAY_ELIGIBLE_TYPES push a single frame for it.
    5. After the loop, if the moveGroup is non-empty (the log ended on a MOVE), perform a final flush using the same K-step logic.

    Preserve the post-14-02 universal ball update for non-MOVE events. For MOVE-derived step-frames, the ball position is unchanged from `current.ball` unless a MOVE carried a carrierId change in its ballAfter — if a MOVE's ballAfter differs from current.ball, apply it on the step-frame that corresponds to that MOVE's final position (a MOVE that picks up a loose ball updates carrierId at its landing step). Do not regress REPLAY-06: every MOVE's ballAfter must still be honored.

  </action>
