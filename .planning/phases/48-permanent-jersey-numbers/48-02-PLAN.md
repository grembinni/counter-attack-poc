Add one exported function to `packages/server/src/draftSession.ts`, placed immediately after `assignBenchNumbers` (after line 406) so the two sit together:

`export function backfillBenchNumbers(session: DraftSession, side: DraftSide, rng: RandomIntFn): DraftSession`

Behavior, in order:
1. Read the side's fields with the existing module-private `getSide(session, side)` — it yields `benchIds` and `benchNumbers`.
2. Compute `missingIds` = the DISTINCT ids in `benchIds` that have no own-property entry in `benchNumbers`. Deduplicate: 48-RESEARCH.md and the existing `draftSession.integration.test.ts` end-to-end case both confirm `benchIds` can legitimately contain a repeated id (pack generation only guards duplication within a round), so a repeated id must consume exactly one number.
3. If `missingIds.length === 0`, return `session` unchanged by reference — no allocation, no RNG call. This is the load-bearing half of D-05 ("never re-roll once assigned").
4. Otherwise build the candidate range `BENCH_NUMBER_MIN..BENCH_NUMBER_MAX` inclusive, filter out every number already present in `Object.values(benchNumbers)`, shuffle the remainder with the existing module-private `shuffle(range, rng)`, and assign `shuffled[i]` to `missingIds[i]`. Excluding in-use numbers is what keeps D-03's per-team uniqueness true after a backfill; the range (85 values) is always far larger than any possible bench size, so no rejection loop is needed — mirror the reasoning already written in `assignBenchNumbers`'s docstring.
5. Return `withSide(session, side, { benchNumbers: { ...benchNumbers, ...drawn } })`.

Never call `Math.random` — randomness only ever arrives through the injected `rng: RandomIntFn` (the project-wide `crypto.randomInt`-backed convention). Do not change `assignBenchNumbers`, `applyRearrange`, `applyPick`, `advanceSubStep`, `buildDraftView`, `getSide` or `withSide`.

Write a docstring above it citing Phase 48 / D-05 / NUMBER-05, stating that it is idempotent, that it is the only sanctioned way to add bench numbers after the initial `assignBenchNumbers` draw, and that it deliberately never re-rolls an existing entry.

Then add `describe('backfillBenchNumbers (Phase 48, D-05)', ...)` to `packages/server/src/draftSession.test.ts`, placed immediately after the existing `describe('assignBenchNumbers (D-15/D-16)')` block. Build every fixture from the existing `baseSession({...})` factory. Cover exactly these cases:
- an id present in `benchIds` but missing from `benchNumbers` receives a number in `[15, 99]`;
- an id already present in `benchNumbers` keeps its exact prior value across the call (assign `{ x: 42 }`, add a second missing id, assert `x` is still `42`);
- the drawn number never equals an already-in-use number (seed `benchNumbers` with several values, backfill one id, assert the result is not among the seeded values);
- calling `backfillBenchNumbers` twice in a row returns the identical `benchNumbers` object contents the second time (idempotence), and the second call returns the same session reference (`expect(second).toBe(first)`);
- a `benchIds` array containing the same id twice produces exactly one entry for that id;
- the other side's `benchNumbers` is untouched (backfill `'home'`, assert `awayBenchNumbers` is unchanged).

Use the real `randomInt` for range assertions (as the existing `assignBenchNumbers` suite does) and a deterministic `constantRng` where a fixed draw makes an assertion sharper.
